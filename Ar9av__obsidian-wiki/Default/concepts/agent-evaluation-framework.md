# Agent Evaluation Framework

Agent 评测框架回答的核心问题是：如何系统化地度量一个 Agent"到底行不行"。它不是简单地跑几个测试用例，而是一套从用例定义、执行、评分到反馈闭环的完整工程方法论。

## 评测的不是模型，是四层组合

大多数团队说"评测 Agent"时，潜意识里在评测模型。但评测的真正对象是"**模型 + Prompt + 工具 + 工作流**"的组合 ^[extracted]：

| 层 | 作用 | 典型问题 |
|---|------|---------|
| 模型层 | 底层大模型的能力上限 | 推理能力不足、知识过期 |
| Prompt 层 | 把任务翻译成模型能理解的指令 | 指令歧义、边界情况未覆盖 |
| 工具层 | Agent 可调用的外部工具 | 检索不准、参数构造错误、工具缺失 |
| 工作流层 | 多步骤任务的编排逻辑 | 分支判断错误、异常处理缺失 |

**关键洞察**：模型层往往不是瓶颈。一家公司评测其 AI 客服 Agent，准确率 62%。换了更大模型，65%——投入巨大，效果甚微。后来定位到是工具层的问题：知识库检索返回的结果不准确。优化检索策略后，62% → 84%。换模型提升 3%，修检索策略提升 22%。^[extracted]

## 评测七概念链

一次评测的执行过程串联七个核心概念 ^[extracted]：

```
Task → Trial → Transcript → Outcome → Grader → Suite → Harness
```

| 概念 | 定义 | 关键设计 |
|------|------|---------|
| **Task** | 一条明确的测试指令，含输入和成功标准 | 两个领域专家独立判断应得出相同 pass/fail |
| **Trial** | 让 Agent 跑一次 Task | 同一 Task 通常跑多次（非确定性） |
| **Transcript** | 完整过程记录——每步推理、每次工具调用、每个中间结果 | 评测里最重要的诊断工具 |
| **Outcome** | Agent 实际做了什么（而非说了什么） | 数据库里有没有退款记录才算数 |
| **Grader** | 评分器，一个 Task 可挂多个 | 规则型 + LLM 型 + 状态型组合 |
| **Suite** | 多个 Task 围绕同一目标组成的评测套件 | 如"退款""取消订单""升级投诉" |
| **Harness** | 端到端跑评测的基础设施 | 提供工具、并发执行、记录轨迹、评分、聚合 |

评测的其实是 [[concepts/agent-harness|Agent Harness]]（让模型能作为 Agent 运行的脚手架）和模型协同工作的整体。^[extracted]

## Anthropic 评测方法论

Anthropic 的框架核心回答"评测由哪些零件组成，怎么组装"。

### Grader 三件套

| 类型 | 特点 | 适用场景 |
|------|------|---------|
| **代码型** | 快、确定性、可复现、易调试 | 工具调用验证、状态检查、格式约束 |
| **模型型** | 灵活、能捕捉细微差别 | 语义质量、策略合理性、语气妥当性 |
| **人工** | 金标准 | 校准、争议仲裁、高风险场景抽查 |

三种组合策略：加权（多维度加权求和）、全过（安全类评测）、混合（关键项硬过 + 其他加权——最常用）。^[extracted]

### 能力评测 vs 回归评测：攻与守

- **能力评测**：问"这个 Agent 能做什么？"——从低通过率开始，瞄准 Agent 挣扎的 Task，给团队一座要爬的山 ^[extracted]
- **回归评测**：问"这个 Agent 还能做以前能做的事吗？"——接近 100% 通过率，分数下降意味着有什么东西坏了 ^[extracted]

能力评测有自然生命周期：通过率越来越高后"毕业"成为回归评测套件。Claude Code 的评测演进就是这条路：先从狭窄领域（简洁性、文件编辑）开始，逐步扩展到更复杂行为（过度工程），最终形成持续运行的回归套件。^[extracted]

### pass@k 与 pass^k

Agent 行为在不同运行之间有变化。两个指标捕捉这种不确定性 ^[extracted]：

- **pass@k**：k 次尝试中至少一次成功的概率。k=10 时趋近 100%。适合"一次成功就够"的工具（代码助手给出多个方案）
- **pass^k**：k 次尝试全部成功的概率。k=10 时趋近 0%。适合"每次都必须成功"的 Agent（客服、支付、退款）

生产系统更关心 pass^k。版本对比还需要配套统计检验：置信区间、显著性判断、最小可感知变化阈值。^[extracted]

### 四个容易踩的坑

1. **多 Trial**：一次通过可能是运气，十次通过八次才是能力
2. **并发控制**：多 Trial 共享数据库或文件系统时必须事务隔离
3. **环境隔离**：Claude Code 早期模型通过检查 git 历史获得"不公平优势"——评测环境必须隔离，模型只能看到当前 Trial 应该看到的信息 ^[extracted]
4. **可重放**：Transcript 必须完整保存，不能复现的 badcase 等于没有 badcase

## 阿里工程化体系

阿里的框架回答"评测怎么跑"——怎么从一次打分变成持续运转的质量工程。

### 指标分级 P0/P1/P2

| 级别 | 作用 | 说明 |
|------|------|------|
| **P0** | 门禁指标 | 不达标不发布 |
| **P1** | 版本对比指标 | 工程优化的量化依据 |
| **P2** | 长期观察指标 | 体验改善和趋势分析 |

一次发布只要 P0 不过，无论 P1/P2 多漂亮都不能过门禁。^[extracted]

### Scorer 优先级与分层筛查

- **Scorer 优先级**：规则 > LLM > 人工——能写成代码的项由规则主判，LLM 只用在语义/策略维度 ^[extracted]
- **分层筛查**：粗筛（90%）→ 精判（8%）→ 人工复核（2%），工程上唯一可承受的成本结构 ^[extracted]

### 人工评分路由

人工评分不应只由"LLM Judge 分数低于某阈值"触发。以下情况必须走人工 ^[extracted]：

- 自动评分不确定：边界分数、低置信度、reason 含糊、Judge 分歧
- 新模型/Prompt/工具 Schema 上线
- 规则与 LLM Judge 结论冲突

### 5 步根因定位链路

```
证据汇总 → 范围收敛 → 分模块诊断 → 责任判定 → 结构化落盘
```

维护"问题现象 × 功能模块"映射表缩小候选范围，再逐模块读 input/output/Prompt/工具返回。根因标签绑定解决角色——语义理解→算法优化、知识召回→运营配置、工具执行→工程修复、风险防控→规则配置。^[extracted]

### 3 条反馈生产线

| 生产线 | 转化方式 |
|--------|---------|
| **回归用例线** | 失败 case 转化为回归测试用例 |
| **训练数据线** | 正确交互模式转化为 SFT 数据，错误模式转化为 RLHF 负例 |
| **配置/知识库修订线** | 知识缺陷转化为知识库补充，规则缺陷转化为配置变更 |

评测的终点不是报告，是把线上失败变成可复用的研发资产。^[extracted]

## 四层 Evaluator 与硬软分离（工程实践）

来自 Alan 的 AI 客服评测实践：将确定性约束、分类能力、生成质量和多轮流程分层评测，不能只看整体通过率 ^[extracted]。

| 层级 | 评估对象 | 实现方式 | 关键原则 |
|------|----------|----------|----------|
| **L1 确定性业务规则** | 句数、禁用词、格式、承诺、顺序、结束后营销等 | 普通代码 | 用"触发条件 + 语义对象 + 动作"组合，避免单关键词误报 |
| **L2 行为意图识别** | 分类 Accuracy/Precision/Recall/F1、混淆矩阵 | 统计指标 | 关键类别（手机号、结束、负面反馈）优先看 Recall |
| **L3 生成回复质量** | 相关性、事实性、覆盖度、完成度、留资价值、语气、上下文一致性 | 七维 LLM Judge | Judge 失败标记"未评测"，不能填 0 分或改变业务状态 |
| **L4 多轮流程回归** | 咨询→引导→留资、微信转手机号、负面处理、结束等关键路径 | 多轮剧本 | 单轮正确不代表整段对话正确 |

**硬规则与软质量必须分开**：
- 能用字符串、结构化字段、顺序或知识字段确定的要求，用代码判断
- 需要理解语义、自然度、承接关系的要求，使用 LLM Judge
- 事实编造、越界承诺、结束后营销等红线独立否决，不能被高质量分抵消 ^[extracted]

**总分用于趋势，门禁用于决策**：发布决策必须查看是否新增红线失败、关键意图 Recall 是否下降、多轮关键流程是否失败、Judge 可用率是否足够、数据集和参数是否可比 ^[extracted]。

## 五维评测维度

| 维度 | 上线问题 | 关键指标 |
|------|---------|---------|
| **任务完成率** | 用户的问题有没有被解决 | 端到端通过率 |
| **回答质量** | 答案对不对、好不好 | 准确性、相关性、可操作性 |
| **鲁棒性** | 极端场景会不会崩 | 对抗输入通过率、多轮一致性 |
| **响应速度** | 用户等不等得了 | P50/P99 延迟、TTFT（比总延迟更重要） |
| **安全性** | 会不会出大事 | 内容安全、信息安全、行为安全、爆炸半径 |

对话型 Agent 还有额外难点：上下文依赖、目标切换、情绪回应、人工接管、多轮一致性。对话评测要同时看 Turn（单轮）、Session（整段会话）、Trace（执行轨迹）、Outcome（最终结果）四个层次。^[extracted]

## 评测集构建：四类来源

| 来源 | 作用 | 做法 |
|------|------|------|
| **专家设计用例** | 定标准 | 领域专家手写核心业务路径期望行为 |
| **LLM 扩展用例** | 扩覆盖 | 规则定结构骨架 + LLM 生成自然语言变体，一条手写可扩 10-50 条 |
| **线上真实数据** | 反映实际分布 | 从线上会话或工单记录中筛选代表性样本 |
| **Badcase 回流** | 收集典型失败模式 | 线上发现的失败 case 沉淀回评测集 |

**反常识**：评测集不能只靠随机抽样线上数据——线上样本有幸存者偏差，正常流程占大多数，真正会让 Agent 出错的边缘场景占比很低。^[extracted]

推荐路径：先做 50-200 条高质量 golden set，覆盖核心业务路径和高风险边界；成熟后扩展到分类采样集、长尾集、对抗集、线上回流集。Anthropic 的建议更激进：20-50 条简单 Task 就能起步。^[extracted]

### 评测集构建：三要素模型

高质量评测用例包含三个核心要素 ^[extracted]：

| 要素 | 内容 | 关键设计 |
|------|------|---------|
| **任务输入** | 提问/多轮上下文、场景分类标签 | 多轮对话需精确复现对话状态 |
| **运行环境配置** | 状态类型与参数、Mock 服务 | 任何可能影响 Agent 行为的配置必须显式声明 |
| **Ground Truth** | 期望结果、关键证据、必/禁调工具 | 不仅验证"做了什么"，还验证"没做什么" |

维护形式：支持类 Excel 工具（快速录入）和 Git 仓库维护（工程化版本管理）两种模式。Git 仓库标准化结构 ^[extracted]：
```
skill-name/
├── files/          # 评测用的文件
├── tests/          # Code 评估脚本
├── eval.json       # 定义评测任务
└── setup.yaml      # 定义环境配置
```

### 仿真环境：确定性保障

Agent 的副作用（文件修改、API 调用）要求评测环境必须隔离。将外部依赖抽象为三类接口 ^[extracted]：

| 接口类型 | 特征 | 隔离策略 |
|----------|------|---------|
| **静态只读接口** | 文档查询类，数据不变 | 本地镜像/版本化索引 |
| **Mock 服务** | 有状态/时效性工具 API | 录制真实响应，回放固定数据 |
| **沙箱环境** | 可在隔离环境运行工具 | Docker 容器 + OverlayFS + 网络命名空间 |

沙箱核心价值：以文件修改类任务为例，无沙箱时文件被永久修改且多任务互相干扰；有沙箱后所有操作限制在容器内 `/workspace`，支持 100 个任务并行互不干扰。^[extracted]

## 评估器分层策略

评估器按任务特性选择最合适的方法 ^[extracted]：

| 评估器类型 | 评估方法 | 特点 | 适用场景 |
|-----------|---------|------|---------|
| **人工评估** | 专家审查、客户反馈 | 高精度、高成本 | 基准标注、争议仲裁 |
| **Code 评估** | 单元测试、字符串相似性、轮次、Token、必/禁调工具 | 低成本、稳定 | 确定性任务、CI 门禁 |
| **LLM/Agent 评估** | 量表评分、断言评分、参考评分、对比评分 | 灵活、易波动、成本较高 | 开放性任务 |

**LLM 评估的四种方法** ^[extracted]：
- **量表评分**：多维度 1-5 分制，适合细粒度质量分析
- **断言评分**：布尔断言集合，比量表更客观
- **参考评分**：与 Ground Truth 做语义匹配（非字面匹配）
- **对比评分**：Pairwise 比较，消除绝对评分尺度问题

波动性问题解决方案：多次评估投票（N-shot）+ 人工校准 + 迭代优化。^[extracted]

### Agent 轨迹评估：从 Trace 到可评估数据

原始 Trace 信息多、密度低，直接输入 LLM 会超出上下文限制。设计**三阶段加工流水线** ^[extracted]：

1. **轨迹提取**：保留 LLM 决策逻辑和工具调用关系，丢弃耗时、Token 数、框架内部细节等技术噪音
2. **工具返回压缩**：工具返回压缩为 `${response}` 占位，保留调用结构
3. **语义去重**：基于 Embedding 的聚类，将 10000 条 Trace 去重为约 150 个候选样本，使人工审核可行

### Skills 仓库评测实践

评测对象是 **Skill**（技能/工具）级别，采用**多 Agent 协作架构** ^[extracted]：
- 主 Agent：评测 orchestrator，负责任务分发
- Task 子 Agent：执行具体用例任务
- Eval 子 Agent：对输出结果进行评估

这种"用 Agent 评测 Agent"的元设计，实现了评估系统的可扩展性和一致性。

## [[entities/nova-flow|NovaFlow]] 三层评测框架（支付宝）

支付宝在 AIDD 2026 提出的 NovaFlow 框架，将评测与可观测深度融合 ^[extracted]：

| 层 | 核心能力 | 产出 |
|---|---------|------|
| **在线效果可观测** | 实时评测 + 自动归因 = 质量闭环 | 在线流量自动化标准化评估，实时发现 Badcase 并归因 |
| **端到端链路可观测** | 白盒化透视"思考路径" | 统一可观测视图与语义节点建模 |
| **问题处置修复可观测** | 可归因、可进化 | 问题自动归因与定责，数据驱动持续迭代 |

核心组件：**Benchmark**（行业考纲）+ **User Simulator**（行业考题）+ **Judge Model**（行业考官）。

实测数据：分析数据总量 40.44 万条，Badcase 率从 ~20% 降至 2.73%，知识缺失占 Badcase 比 24%，归因更新策略 T+1 自动化。^[extracted]

## 评测成本与不评测的代价

**评测成本**：构建 500 条测试用例 = 2-3 名领域专家 × 2 周 + 自动化框架 = 1 名工程师 × 1-2 周 + 持续监控 = 每周 1-2 小时。^[extracted]

**不评测代价**：Agent 每天处理 10000 次请求，5% 有问题 = 500 个用户体验受损/天，其中 15% 可能流失。每天损失可达数万元。上线前发现的 bug 修 2 天，上线后发现修 2 个月。^[extracted]

## 可立即上手的五步流程

1. **定义评测目标** — Agent 类型决定评测重点（客服重安全质量、代码重完成率准确性、数据分析重可操作性鲁棒性）
2. **构建评测集** — 每个任务至少 10-20 个用例，正常 60% / 边界 25% / 对抗 15%
3. **自动化评测** — 每个维度有可量化评估方法，流程可重复
4. **人工抽检** — 每周抽检 50-100 个评测结果，重点抽检"高置信度通过"的 case
5. **持续监控 + 反馈回路** — 用户纠正自动回流评测集，评测集持续喂养长大
