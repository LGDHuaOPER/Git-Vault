# Agent Timeline：看懂 AI Agent 调试从“看日志”到“看轨迹”的变化

![](附件资源/Agent%20Timeline：看懂%20AI%20Agent%20调试从“看日志”到“看轨迹”的变化/img_1.png)

过去我们调试 AI，常常只看最后一句回答。

回答对不对，语气像不像，事实有没有错，代码能不能跑。

但 Agent 进入真实工作流以后，这种看法越来越不够用。

一个 Agent 出错，可能不是模型“笨”了，而是它在某一步拿错了文档、调错了工具、遇到 API 超时、没有传递权限上下文，或者在重试时把中间状态弄乱了。

Honeycomb 在 2026 年 6 月 29 日发布了一篇面向 Agent Timeline 的 OpenTelemetry 实操指南。它不是单纯发布一个新监控界面，而是把一个更重要的问题摆到台前：

> 当 AI Agent 不再只是回答问题，而是会调用工具、访问数据库、跑测试、改工单、写报告时，我们不能只看“最终回答”，必须能复盘它完成任务的整条轨迹。

这就是今天值得讲清楚的主题：**Agent Timeline，也就是 AI Agent 的任务时间轴。**

![](附件资源/Agent%20Timeline：看懂%20AI%20Agent%20调试从“看日志”到“看轨迹”的变化/img_2.png)

## 一、现实变化：Agent 出错不再只是“答错一句话”

如果 AI 只是聊天机器人，调试相对简单。

用户问一句，模型答一句。我们主要检查：

- 有没有幻觉；
- 有没有答非所问；
- 有没有违反安全规则；
- 语气和格式是否符合预期。

但 Agent 的工作方式完全不同。

一个典型 Agent 任务可能长这样：

- 用户提出一个模糊目标；
- 模型拆解任务；
- Agent 选择工具；
- 工具去查日志、数据库、知识库或外部 API；
- 模型根据工具返回结果继续判断；
- 必要时重试、转人工或降级；
- 最后输出报告、代码补丁、客服回复或业务动作。

这里面任何一步都可能出错。

比如一个代码 Agent 接到任务：

> 登录接口最近偶尔返回 401，帮我看一下。

它最终给了一个补丁。但补丁上线后问题还在。

如果只看最终补丁，你很难判断问题出在哪里：

- 它是不是只看了单元测试，没有看线上日志？
- 它是不是误以为 401 来自密码校验，实际来自 token 刷新？
- 它是不是只修了 Web 入口，漏掉了移动端入口？
- 它是不是为了让测试通过，把异常吞掉了？
- 它是不是没有跑完整回归测试？

这时，“模型回答质量”已经不是唯一问题。

真正的问题变成：**一次 Agent 运行到底走过哪些步骤，每一步输入了什么、调用了什么、返回了什么、失败在哪里。**

## 二、一句话讲清核心概念

> Agent Timeline 是一次 AI Agent 运行的“时间轴病历”：它把用户请求、模型调用、工具调用、数据库访问、错误、重试、人工审批和最终结果，按时间顺序串成一条可复盘轨迹。

![](附件资源/Agent%20Timeline：看懂%20AI%20Agent%20调试从“看日志”到“看轨迹”的变化/img_3.png)

这句话里有三个关键词。

第一是**一次运行**。

它不是统计平均水平，而是回答某一次任务到底发生了什么。

第二是**时间顺序**。

Agent 的错误常常来自顺序：先查了旧文档，再生成了错误回答；先调用了失败工具，再错误地当成成功；先拿到不完整数据，再做了确定结论。

第三是**可复盘轨迹**。

它不是把日志堆在一起，而是让人能沿着一条线看清楚：

- 用户最初问了什么；
- 模型用了哪个版本；
- 工具调用传了哪些参数；
- 工具返回了什么；
- 哪一步耗时异常；
- 哪一步标记失败；
- 哪一步产生最终输出。

## 三、它到底是什么：从日志、指标到 trace

传统系统监控里有三类常见数据：日志、指标和 trace。

日志像流水账，告诉你某个时刻发生了什么。

指标像仪表盘，告诉你一段时间内延迟、错误率、吞吐量、成本等数字。

trace 则像任务链路图，告诉你一次请求从入口到出口经过了哪些服务，每一步耗时多少，哪里失败。

Agent Timeline 本质上是把这套思路带进 AI Agent。

过去我们可能分别看到：

- 应用日志里写着“工具调用超时”；
- 模型平台里显示 token 用量很高；
- 数据库监控里出现慢查询；
- 工单系统里用户评价很差；
- Agent 框架里只有一段最终回答。

这些信息都是真的，但分散在不同地方。

Agent Timeline 想解决的是：**把这些分散信号绑定到同一次 Agent 任务上。**

![](附件资源/Agent%20Timeline：看懂%20AI%20Agent%20调试从“看日志”到“看轨迹”的变化/img_4.png)

Honeycomb 的指南里特别强调了一个细节：不要只记录 LLM 调用。只要某个 span 是 Agent 触发的，包括下游 HTTP 请求、数据库查询、队列任务，也应该带上同一个 conversation id。

换句话说，Agent 的轨迹不应该停在模型边界。

如果 Agent 调了一个“查订单”工具，而这个工具内部又访问了订单库、风控服务和支付接口，这些下游步骤也应该能被串到同一条轨迹里。

否则你只能看到“模型调用了工具”，却看不到工具里面到底哪里坏了。

## 四、为什么现在出现：Agent 的失败位置变多了

Agent Timeline 不是凭空出现的新名词，它背后是 AI 应用形态的变化。

以前的 AI 应用主要有一个失败点：模型输出。

现在的 Agent 系统至少有六类失败点。

![](附件资源/Agent%20Timeline：看懂%20AI%20Agent%20调试从“看日志”到“看轨迹”的变化/img_5.png)

### 1. 输入失败

用户任务本身可能含糊、矛盾或缺少上下文。

比如用户只说“帮我处理这个客户”，但没有说明客户 ID、处理目标、权限边界和历史沟通记录。

如果没有记录原始输入和上下文来源，后面很难判断是 Agent 理解错了，还是任务本身就不完整。

### 2. 模型失败

模型可能误判意图、生成错误计划、忽略系统提示，或者因为模型版本变化导致行为不同。

这也是为什么需要记录  `gen_ai.request.model`  和  `gen_ai.response.model`  这类字段：你请求的是一个模型名，实际返回可能是某个具体版本。

### 3. 工具失败

很多 Agent 故障不是发生在模型里，而是发生在工具调用里。

工具可能返回 500、超时、参数错误、权限不足，也可能返回了格式合法但业务含义错误的数据。

如果工具调用没有自己的 span，你只能看到“Agent 失败”，看不到失败点。

### 4. 数据失败

企业知识库、向量检索、SQL 查询、文件读取都可能出错。

典型问题包括：

- 检索到旧政策；
- 召回了相似但不相关的合同；
- SQL 条件漏了地区或日期；
- 文档解析时丢失表格结构；
- 数据权限过滤不完整。

这些错误会让最终回答看起来很专业，但事实基础已经错了。

### 5. 控制失败

Agent 不只是“会做”，还必须知道什么时候不能做。

比如高金额退款必须转人工，删除数据必须二次确认，外部邮件必须审核后发送。

如果轨迹里没有记录权限拒绝、人工审批、降级路径和重试次数，团队很难判断 Agent 是能力不足，还是控制边界没有设计好。

### 6. 结果失败

最终输出也需要被连接回轨迹。

比如客服满意度、人工审核结果、代码测试结果、工单状态、用户是否追问，都应该能反向帮助团队判断这条轨迹是否成功。

否则你只有“Agent 运行结束”，没有“这次运行到底好不好”。

## 五、解决什么问题：从“它错了”到“错在哪一步”

Agent Timeline 最直接解决的是调试问题。

当一个 Agent 失败时，团队不再停留在“它又胡说了”“模型不稳定”“提示词要改”这种粗粒度判断，而是能定位到具体环节。

### 客服 Agent：用户抱怨不是唯一线索

想象一个客服 Agent 处理退款问题。

用户说：

> 我退款两次都没到账，你们到底怎么回事？

Agent 回复不当，用户投诉。

如果只看对话，可能会以为是模型语气不好。

但看完整轨迹后，可能发现真正的问题是：

- CRM 显示该用户是老合同客户，有特殊退款条款；
- 知识库里新退款政策刚更新，但检索命中了旧文档；
- 订单 API 第一次返回超时，Agent 重试后拿到不完整结果；
- 高金额退款本应转人工，但控制逻辑没有触发。

这四种原因对应的修法完全不同。

![](附件资源/Agent%20Timeline：看懂%20AI%20Agent%20调试从“看日志”到“看轨迹”的变化/img_6.png)

如果是语气问题，可以改提示词。

如果是知识库旧文档，可以改检索和文档治理。

如果是 API 超时，可以改工具重试和降级。

如果是转人工失败，就要改权限和流程。

**没有轨迹时，团队很容易把所有问题都归咎于模型；有轨迹时，团队才知道该修哪里。**

### 代码 Agent：不要只看补丁

代码 Agent 更典型。

它可能读文件、跑测试、修改代码、再运行命令。

最终补丁能不能通过测试，只是结果之一。更重要的是它怎么到达这个结果。

![](附件资源/Agent%20Timeline：看懂%20AI%20Agent%20调试从“看日志”到“看轨迹”的变化/img_7.png)

一个合格的轨迹应该能回答：

- 它读了哪些文件？
- 它看了哪些日志？
- 它是否找到最近相关提交？
- 它运行了哪些测试？
- 哪个测试失败过？
- 它有没有跳过关键验证？
- 它有没有修改与任务无关的模块？

这会改变我们使用 coding agent 的方式。

过去我们可能只问：

> 这个 Agent 会不会写代码？

现在更应该问：

> 这个 Agent 的工作过程能不能被审查？

### 数据分析 Agent：错图表背后可能是错 SQL

数据分析 Agent 也一样。

用户问：

> 上周转化率为什么下降？

Agent 最后生成了图表和解释。图表看起来很漂亮，但结论错了。

原因可能不是模型不会分析，而是 SQL 过滤条件漏了渠道，或者数据清洗时把异常值删错了。

![](附件资源/Agent%20Timeline：看懂%20AI%20Agent%20调试从“看日志”到“看轨迹”的变化/img_8.png)

如果没有轨迹，审核者只能读最终报告。

如果有轨迹，审核者可以看到：

- 它查了哪些表；
- SQL 条件是什么；
- 查询耗时是否异常；
- 中间 DataFrame 行数如何变化；
- 图表来自哪一步代码；
- 最终解释是否引用了真实结果。

这会让数据分析从“看起来像分析”变成“可以追溯的数据工作流”。

## 六、和过去做法有什么区别

Agent Timeline 不是简单地“多存一些日志”。

它和过去做法的区别，可以用一张表概括。

| 维度 | 过去：看回答/看日志 | 现在：看 Agent Timeline |
| --- | --- | --- |
| 关注对象 | 最终输出或单点日志 | 一次任务的完整链路 |
| 常见问题 | 不知道错误发生在哪一步 | 能定位模型、工具、数据、权限、下游系统 |
| 数据组织 | 分散在模型平台、应用日志、数据库监控里 | 用 conversation id / trace id 串起来 |
| 调试方式 | 猜提示词、换模型、人工复现 | 沿时间轴查看 span、错误、重试和返回值 |
| 适用场景 | 简单问答、内容生成 | Agent 自动化、客服、代码、数据分析、企业流程 |
| 风险治理 | 事后看结果 | 事中记录证据，事后可审计 |

这里最关键的变化是：**调试单位从“模型回答”变成“一次任务链路”。**

这个变化和传统软件从日志走向分布式 tracing 很像。

当系统只有一个服务时，看日志还够用。

当系统变成微服务、消息队列、数据库、第三方 API 后，只看单点日志就不够了。

Agent 也是如此。

当 AI 只回答问题时，看回答还够用。

当 AI 开始调用工具、协作多个子 Agent、触发业务系统后，就必须看轨迹。

## 七、为什么 OpenTelemetry 很关键

这次值得关注的不只是 Honeycomb 的产品界面，而是它选择了 OpenTelemetry 的 GenAI 语义约定作为基础。

OpenTelemetry 可以理解为一套开源可观测性标准。它让不同语言、框架和平台能用相对统一的方式描述 trace、metrics 和 logs。

GenAI semantic conventions，也就是生成式 AI 语义约定，试图规定 AI 应用里的关键字段应该怎么命名、怎么记录。

比如：

- 模型请求用什么字段；
- 模型响应用什么字段；
- token 用量怎么记录；
- 工具调用怎么记录；
- Agent 名称怎么记录；
- conversation id 如何贯穿多步任务。

![](附件资源/Agent%20Timeline：看懂%20AI%20Agent%20调试从“看日志”到“看轨迹”的变化/img_9.png)

这件事的实际价值很清楚。

如果每个 Agent 框架、每个模型供应商、每个监控平台都用自己的字段，团队会遇到几个问题：

- 换模型后，历史数据不好对比；
- 换框架后，监控面板要重做；
- 线上问题很难跨系统追踪；
- 成本、延迟、质量无法放在同一张表里分析；
- 合规审计时，很难解释一次自动化决策的证据链。

而统一语义约定的目标，就是让“Agent 做了什么”变成更通用的数据结构。

这不是为了追求术语统一，而是为了让 AI 工程团队能复用已有的可观测性工具链。

## 八、具体怎么落地：先做最小可用轨迹

很多团队听到可观测性，会误以为必须先采购平台、搭大系统。

其实不是。

更务实的做法是先从一个高频 Agent 任务开始，建立最小可用轨迹。

![](附件资源/Agent%20Timeline：看懂%20AI%20Agent%20调试从“看日志”到“看轨迹”的变化/img_10.png)

可以按下面步骤做。

### 第一步：选一个真实任务链路

不要从抽象场景开始。

选择一个每天都会发生、失败后有明显成本的任务，比如：

- 客服退款处理；
- 销售线索总结；
- 企业知识库问答；
- 数据分析报告；
- 代码缺陷修复；
- 合同条款初审。

### 第二步：给每次运行分配 ID

每次 Agent 运行都要有一个稳定 ID。

可以叫 conversation id、task id 或 trace id，名字不重要，关键是它能贯穿整条链路。

没有这个 ID，后面所有日志都会散开。

### 第三步：记录模型和提示词版本

至少记录：

- 模型请求名称；
- 实际响应模型版本；
- prompt 模板版本；
- 输入 token；
- 输出 token；
- 延迟；
- finish reason。

这能帮助团队判断：行为变化是来自模型升级，还是提示词改动，还是输入变长。

### 第四步：记录工具调用

每次工具调用都应该是一个 span。

至少记录：

- 工具名；
- 调用参数；
- 返回结果摘要；
- 错误类型；
- 重试次数；
- 耗时；
- 是否触发降级。

注意，敏感字段要脱敏，不能为了调试把用户隐私、合同全文或密钥直接塞进监控系统。

### 第五步：记录下游系统

如果工具内部访问数据库、HTTP API、队列或文件系统，也要尽量把下游 span 串起来。

否则你只能看到“查订单工具失败”，看不到是订单库慢、支付接口错，还是权限系统拒绝。

### 第六步：把质量反馈接回来

一条轨迹如果只有技术信号，仍然不完整。

最好把结果反馈也接回来：

- 用户是否满意；
- 人工审核是否通过；
- 测试是否通过；
- 工单是否重新打开；
- 代码是否被 reviewer 退回；
- 报告是否被业务方采用。

这样团队才能把成本、延迟和质量放在一起看。

## 九、对个人和企业意味着什么

### 对个人：不要只收藏“好用提示词”

个人使用 AI 时，最常见的改进方式是收藏提示词。

这有用，但不够。

如果你经常用 AI 做内容、代码、研究或数据分析，更应该建立自己的小型复盘习惯。

比如：

- 保存 3 到 5 个真实任务样本；
- 记录 AI 用了哪些资料和工具；
- 要求 AI 输出“不确定点”和“验证步骤”；
- 对重要结论保留来源链接或中间计算；
- 失败时不要只换模型，而是复盘哪一步出错。

这就是个人版 Agent Timeline。

它不一定需要平台，但需要一种意识：**AI 的结果要能被追溯。**

### 对企业：Agent 上线要有证据链

企业场景更严肃。

一旦 Agent 进入客服、销售、财务、法务、研发、数据分析等流程，它的输出就会影响真实业务。

这时企业不能只问：

> 这个 Agent 平均准确率多少？

还要问：

> 当它做错时，我们能不能知道它为什么错？

![](附件资源/Agent%20Timeline：看懂%20AI%20Agent%20调试从“看日志”到“看轨迹”的变化/img_11.png)

企业可以从四件事开始：

- 定义关键链路 trace 字段；
- 建立失败分类：模型、工具、数据、权限、用户输入；
- 把成本、延迟、质量放进同一看板；
- 上线前用真实历史任务做回放测试。

这会直接改变 AI 项目的验收方式。

过去验收可能是“演示能跑”。

以后更合理的验收应该是：

- 出错能定位；
- 成本能归因；
- 数据能脱敏；
- 权限能审计；
- 质量能回流；
- 关键任务能人工接管。

## 十、风险或边界：能观察，不等于自动安全

Agent Timeline 很重要，但不能被神化。

它解决的是“可观察”和“可复盘”，不是自动保证 Agent 正确。

![](附件资源/Agent%20Timeline：看懂%20AI%20Agent%20调试从“看日志”到“看轨迹”的变化/img_12.png)

### 边界一：轨迹里可能有敏感数据

完整记录 prompt、工具参数、工具返回值，确实能提高调试效率。

但这些内容可能包含用户隐私、合同、订单、医疗信息、财务数据或内部机密。

所以生产环境必须考虑：

- 哪些字段不能采集；
- 哪些字段要脱敏；
- 数据保留多久；
- 谁能查看；
- 是否需要按环境区分采样策略。

> 注意：不要为了调试方便，把所有 prompt 和工具返回结果原样记录到长期存储里。Agent 可观测性本身也需要权限和数据治理。

### 边界二：看到轨迹不代表理解业务正确性

Timeline 能告诉你 Agent 调了哪个工具、用了多久、返回了什么。

但它不一定知道业务结论是否正确。

比如 Agent 生成了一份合同审查意见，轨迹显示所有工具调用都成功了。但法律判断是否准确，仍然需要专业评估。

所以 Agent Timeline 要和评测、人工审核、业务指标结合使用。

### 边界三：采样和成本要控制

如果每一次 Agent 运行都完整记录所有输入输出，存储和查询成本可能很高。

更现实的策略是：

- 高风险任务全量记录；
- 普通任务按比例采样；
- 失败任务提高采样；
- 敏感字段只记录摘要；
- 非生产环境保留更详细内容。

### 边界四：标准仍在演进

OpenTelemetry 的 GenAI 语义约定正在持续发展。

这意味着团队落地时要避免把字段设计得过死。

短期可以先采用核心字段：conversation id、agent name、operation name、model、token、tool、error、latency。

长期再跟随标准演进。

## 结论：AI 工程化的下一步，是让 Agent 的过程可见

Agent Timeline 代表的不是一个孤立功能，而是 AI 工程化的一种转向。

过去我们太容易把 AI 系统简化成“模型好不好”。

但真实世界里的 Agent 不是一个模型，它是一条工作流。

它有用户输入，有模型判断，有工具调用，有数据库，有权限，有重试，有人工审批，也有最终业务结果。

只看最后回答，就像只看医生开的药，却不看诊断过程、化验结果和用药记录。

真正可用的 Agent，需要能做事，也需要能解释自己做事的过程。

未来评估一个 Agent，不只看它能不能完成任务，还要看它失败时能不能被复盘、被修复、被治理。

这就是从“看日志”到“看轨迹”的变化。
