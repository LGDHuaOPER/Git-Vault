# 知识编译

> LLM Wiki 的核心范式：在摄入时将知识一次性合成为持久化页面并持续维护，而非在每次查询时从原始资料重新推导。

## 正文

知识编译（Knowledge Compilation）是 [[LLM Wiki]] 的核心范式，代表了与 [[RAG vs Wiki|RAG（检索增强生成）]] 相对的知识处理策略。

### 编译 vs 检索

| 维度 | 知识编译 | RAG / 检索 |
|------|----------|------------|
| 合成时机 | 摄入时 | 查询时 |
| 知识积累 | 每次摄入都有积累 | 每次查询从零开始 |
| 存储形式 | 持久化 Markdown 页面 | 向量嵌入 + 原始块 |
| 维护方式 | Agent 主动更新页面 | 重新索引 / 嵌入 |
| 查询成本 | 便宜（直接读页面） | 贵（每次推导） |
| 适合规模 | 中等（约 100 来源） | 大规模 |

### 为什么编译有效

传统 RAG 有一个结构性缺陷：**没有任何积累**。每个问题都从原始块开始，模型一遍又一遍地重新推导相同的理解。关于代码库的第十个问题并不比第一个更便宜或信息更充分。

知识编译将合成时机反转：让 LLM 在摄入时一次性将知识组装成持久化的页面，然后维护它们。当新资料到达时，模型读取它、更新它触及的实体页面、修改摘要，并就与已有内容的矛盾做出标记。

### 三层架构

知识编译系统通常采用三层架构：

1. **原始资料**（不可变）：只读
2. **Wiki 页面**（LLM 生成并维护）：完全由模型拥有
3. **配置文件**（模式规范）：告诉模型如何组织和工作

### 局限性

- **规模**：在约 100 个来源以下效果最好，超出需要引入搜索
- **保真度**：早期摘要可能丢失源中的细节，后续回答继承该损失
- **过时性**：编译页面只在最后刷新时真实
- **编译成本**：预支 Token 构建可能永不被查询的页面

### Karpathy 的洞见

> "你从不（或很少）自己写 Wiki，LLM 编写并维护全部。Obsidian 是 IDE；LLM 是程序员；Wiki 是代码库。"
