# LLM 可观测 vs 传统可观测：到底有什么不同？

> 一篇 5 分钟科普文。看完你会知道：为什么 Datadog 那一套监不住 LLM，为什么 Langfuse、Braintrust 这些新平台都在做 Prompt 管理、Experiment 这些"以前根本不存在的东西"，以及——我们为什么要做 Observability 3.0。

##

## 一个"成功"的接口

## 先讲个真实的场景。

## 你的客服机器人接口刚刚返回了 200 OK ，延迟 820ms，CPU 没飙，错误率为 0，所有 Grafana 大盘绿油油。

然后用户来投诉：

> "它告诉我退货政策是 30 天，但我们公司明明是 7 天。这答案完全是它自己编的。"

打开 Datadog，没有任何告警。所有指标都说："一切正常。"

这就是 LLM 应用进入生产之后，运维、开发、产品三方一起经历的尴尬时刻：**传统监控告诉你系统是健康的，用户告诉你系统在胡说八道。**

LLM 可观测这门学问，就是从这一刻开始的。

##

## 一句话讲清楚区别

##

|  | 传统系统 | LLM 系统 |
| --- | --- | --- |
| 对错 | ** 确定的 ** | ** 概率的 ** |
| 监控要回答 | "还活着吗？" | "回答得好吗？" |

传统软件的世界里，1+1 永远等于 2，登录成功就是 200，失败就是 401。监控的本质，是确认"系统是否按设计运行"。

LLM 的世界里没有这种确定性。同样的 Prompt，今天答得很漂亮，明天可能跑偏；同样的输入，参数调一格，输出可能从"客观中立"变成"满嘴跑火车"。

监控一个确定性系统，你问的是"还活着吗"；监控一个概率性系统，你必须问"答得对吗、答得准吗、答得贵不贵"。

这是 LLM 可观测和传统可观测最根本的差别——**不是数据多了几条，是问题本身换了。**

##

## 为什么传统可观测平台看不懂 LLM？

##

具体到工程层面，传统 APM 在 LLM 应用面前会失灵在四个地方。

**① 看不见幻觉。** `HTTP 200`  不代表答案是对的。一个完全瞎编的回答和一个完美的回答，从 HTTP 状态码看起来一模一样。传统监控天生不知道"内容质量"是个信号。

**② 看不见质量退化。** 你把 Prompt 改了一行，P99 延迟没变、错误率没变——但是 15% 的回答开始忽略关键事实。这种退化不会让接口"红"，传统告警一条都不会响。

**③ 看不见成本。** Token 成本散落在一次请求里的几十个子调用上，CPU 时间根本反映不了。传统平台没有"按 prompt 版本聚合花了多少钱"的概念。

**④ 看不见路径。** 这是最致命的一点。

传统应用一次请求是一条直线：API → 服务 → 数据库 → 返回。

LLM Agent 一次请求是一棵树：先 Plan、再检索、调几个工具、可能开个子 Agent、可能重试 3 次、循环 3 轮，最后才出答案。中间任何一个节点都可能"成功地走错路"。

##

## 所以 LLM 可观测平台都在做哪些"新东西"？

##

如果你最近看过 Langfuse、Braintrust、Phoenix 这些新平台的官网，你会注意到一堆传统可观测里压根没有的名词：**Prompt、Evaluation、Dataset、Experiment、Score、Playground……**

这些不是市场部凭空发明的功能，而是上面那四个"看不见"逼出来的解药。

**Prompt 管理**——因为 Prompt 是 LLM 应用真正的"源代码"。 PM 改一行 Prompt 不应该等一次发版，工程师回滚一个版本不应该靠翻 Git。Prompt 需要像配置一样能热更新、像代码一样有版本号、像 trace 一样能被关联引用。这是一个新的一等公民对象，传统监控里没有任何概念能映射它。

**Evaluation（评估）**——把"答得对不对"变成可执行的分数。 人不可能每天看上万条对话。所以行业的共识是：再让另一个 LLM（或一段规则代码）去给输出打分——是否忠实、是否相关、是否有幻觉、工具调对了吗。这就是 LLM-as-Judge。**Score 是 LLM 可观测里第四种信号**，和 Metric / Log / Trace 并列。

**Dataset（数据集）**——把"坏例子"沉淀下来。 你今天发现一个 bad case，怎么保证下次改 Prompt 时不会再退化？答案是把它存进 Dataset，作为回归测试集。这其实是把"软件测试"那一套，搬到了 LLM 应用上。

**Experiment（实验）**——改之前先证明它真的更好。 把新 Prompt + 旧 Prompt 在同一个 Dataset 上各跑一遍，比一比谁的 Score 更高。**这是 LLM 时代的"灰度发布"——但灰度的不是流量，而是统计学意义上的质量。**

**Playground**——工程师在多个变体上快速试错的对比台。

一句话总结：**传统可观测平台只做"看见"，LLM 可观测平台必须做"看见 → 改好 → 验证 → 发布"的完整闭环。** 少任何一环，团队就得切到另一个工具，闭环就断了。

##

## 对比：可观测的三代演进

##

如果把这十几年放在一起看，整个行业其实经历了三代。每一代不是抛弃上一代，而是在上一代的底座上回答一个新问题。

![](附件资源/LLM%20可观测%20vs%20传统可观测：到底有什么不同？/img_2.png)

|  | ** Observability 1.0 ** | ** Observability 2.0 ** | ** Observability 3.0 ** |
| --- | --- | --- | --- |
| 时代 | APM 时代 | 云原生 / 分布式 | AI 原生 / 概率系统 |
| 回答的问题 | "还活着吗？" | "哪里慢了 / 错了？" | " ** 为什么答错了？怎么改？ ** " |
| 监控对象 | 单机进程 | 微服务、容器 | LLM 应用、Agent、RAG |
| 核心信号 | CPU / 错误率 | Metric + Log + Trace | 三件套 ** + Prompt + Score + Dataset ** |
| 失败的定义 | 进程挂了 | 请求超时 | 答得不对、答得太贵、Agent 死循环 |
| 闭环动作 | 重启 / 扩容 | 修 bug | ** 改 Prompt / 换模型 / 跑 Experiment ** |
| 谁在用 | SRE | SRE + 开发 | + AI 工程师 + 产品 |
| 代表 | Nagios、早期 New Relic | Datadog、Prometheus、OTel | Langfuse、Braintrust、 ** OpenObserve ** |

##

## 我们的主张：Observability 3.0 不是 LLM 工具，是新一代统一底座

##

行业现在的状态是：你需要 Datadog 看基础设施，需要 Prometheus 看指标，需要 Langfuse 看 LLM 调用，需要 Braintrust 跑 Eval。**四套工具、四份数据、四张账单。**

这不是终点，这只是过渡。

因为真实的 LLM 故障从来都是全栈的——可能是模型本身的问题，可能是 GPU 推理队列堵了，可能是向量库延迟尖刺，可能是上游某个 API 超时，可能是 Prompt 改坏了。**只看 LLM 调用层的"AI 可观测平台"，注定只看见冰山一角。**

OpenObserve 想做的事情很简单：

> 把 Trace、Metric、Log、Prompt、Score、Dataset、Experiment 放在同一个数据底座里 ，让 AI 工程师、SRE、产品经理在同一张图上回答"为什么这次答错了"。

不是再做一个 Langfuse 的副本，也不是在 Datadog 上贴个 LLM 模块。**而是把 3.0 装进同一个底座，让 1.0 和 2.0 的能力天然延续过来。**

这就是 Observability 3.0 的含义：

- 1.0 让你知道"还活着吗"
- 2.0 让你知道"哪里慢了"
- 3.0 让你知道"为什么这次答错了，下次怎么改，改完会不会更好"

LLM 应用正在快速进入生产环境。监控这件事，必须升级到 3.0，OpenObserve正在快速进入3.0时代。
