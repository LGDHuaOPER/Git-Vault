# LLM 可观测性：从 GPU 监控到安全护栏（第五章）

Model Observability — Seeing Through the Black Box

前四章我们解决了"怎么部署、怎么调度、怎么扩缩"的问题——模型跑起来了，集群也稳定了。但**跑起来不等于跑得好**。用户能感知到的首 Token 延迟是多少？模型有没有在悄悄"编故事"？GPU 资源是否被充分利用？这些问题的答案，藏在可观测性体系里。

## 为什么 LLM 监控≠传统应用监控？

在传统微服务中，我们盯 CPU 利用率、QPS、P99 延迟就够了。但 LLM 完全不同——计算主力是 GPU 而非 CPU，而且推理的两个阶段截然不同：

-
- Prefill（预填充） ：计算密集型，一次处理全部输入 Token，速度取决于 GPU 算力
-
- Decode（解码） ：显存密集型，逐 Token 生成，速度取决于显存带宽
-

更棘手的是，你无法预测一个请求会生成多少 Token——同样是"请帮我写一段话"，输出可能 10 个 Token，也可能 2000 个。这使得传统的"请求数"变得几乎没有参考价值。在 LLM 的世界里，**Token 才是真正的计量单位**。

## 可观测性三大支柱：日志 / 指标 / 追踪

Kubernetes 生态的可观测性并非从零开始，我们可以复用成熟的技术栈：

![](附件资源/LLM%20可观测性：从%20GPU%20监控到安全护栏（第五章）/img_1.png)

**日志（Logs）**：vLLM 的启动日志记录了版本、参数、模型加载进度、VRAM 占用（如"model weights take 14.99GiB"）和可用路由。每个请求的接收也会被记录（可通过  `--disable-log-requests`  关闭）。生产环境通常用 Grafana Loki 收集长期存储。

**指标（Metrics）**：容器通过  `/metrics`  端点暴露 OpenMetrics 格式的时序数据，由 Prometheus 周期性拉取。KServe 通过注解自动配置采集：在 ServingRuntime 上声明端口号和路径，在 InferenceService 上启用  `serving.kserve.io/enable-prometheus-scraping: "true"`  即可。

**追踪（Tracing）**：vLLM 内置 OpenTelemetry SDK 支持，只需配置  `--otlp-traces-endpoint`  指向 Jaeger 等收集器，即可追踪单个请求从网关到模型到后端的完整执行链路。与指标的 Pull 模式不同，追踪数据由组件主动 Push。

**Knative 模式注意**：Pod 中同时运行模型服务器、Knative Sidecar 和 Istio Proxy，Prometheus 只能抓取单一端点。KServe 提供了 qpext 指标聚合组件（通过  `serving.kserve.io/enable-metric-aggregation`  启用）来聚合所有容器的指标。

## LLM 关键性能指标：Token 级精密监控

抛弃"请求数"，拥抱 Token 维度的指标：

![](附件资源/LLM%20可观测性：从%20GPU%20监控到安全护栏（第五章）/img_2.png)

**TTFT — 首 Token 时间**（ `vllm:time_to_first_token_seconds` ）：用户发出请求到收到第一个 Token 的等待时间。本质上就是 Prefill 阶段的耗时。对于聊天机器人等实时场景，这是最关键的用户体验指标。离线批处理则不太在意。

**TPOT — 每 Token 耗时**（ `vllm:time_per_output_token_seconds` ）：也称 Inter-Token Latency（ITL），衡量每个后续 Token 的生成速度。人类平均阅读速度约每秒 3 个词，因此至少保证 4~5 tokens/sec 才能让用户感觉不到延迟。这是 Decode 阶段的直接反映。

**Token 吞吐量**：vLLM 分别提供输入 Token 处理速率（ `prompt_tokens_total` ）和输出 Token 生成速率（ `generation_tokens_total` ），以及合计指标（ `tokens_total` ）。注意：一个长请求可能把 GPU 全占满，请求数和 Token 数之间没有简单换算关系。

**请求队列**：当请求超过当前 Batch 容量时，vLLM 会排队。 `num_requests_waiting`  和  `num_requests_running`  是自动伸缩的天然触发信号。

## Prometheus + KServe：指标采集实战

![](附件资源/LLM%20可观测性：从%20GPU%20监控到安全护栏（第五章）/img_3.png)

配置监控只需两步。第一步，在 ServingRuntime 上通过注解声明指标端点：

`annotations:
prometheus.kserve.io/port: '8080'
prometheus.kserve.io/path: "/metrics"`

第二步，在 InferenceService 上启用采集。KServe 控制器会自动将 Prometheus 注解注入到 Pod 中，再配合 ServiceMonitor 实现 15 秒间隔的自动抓取。

在告警层面，可以为关键指标设定阈值。例如 TPOT 超过 0.3 秒持续 5 分钟则触发告警，并关联 Runbook（标准操作手册）指导值班工程师排查请求队列和 GPU 状态。

## GPU 监控：厂商各有工具链

GPU 指标需要专门的采集工具。各厂商的方案思路一致：管理组件采集 GPU 使用数据 → 导出器暴露  `/metrics`  → Prometheus 接入。

-
- NVIDIA ：DCGM（Data Center GPU Manager）+ DCGM-Exporter + GPU Operator，一键 Helm 部署
-
- AMD ：ROCm SMI + AMD Device Metrics Exporter + AMD GPU Operator
-
- Intel ：XPU Manager + Prometheus Metric Exporter
-

这些工具覆盖利用率、显存、温度、功耗、PCIe 带宽等底层指标。虽然各厂商的指标命名尚未统一，但通过 GPU Operator 的自动部署能力，运维负担可以降到最低。

## 模型质量监控：不只是快，还要对

LLM 有一个传统应用没有的风险：**它不会崩溃，但会一本正经地胡说八道**。传统应用遇到异常数据会报错，但 LLM 会"优雅地"返回一个听起来很合理、实际完全错误的结果。

这就是**幻觉（Hallucination）**问题。书中的经典例子：问 ChatGPT"徒步横渡英吉利海峡的世界纪录是什么？"，它煞有介事地编造了一个 2020 年的德国人和 14 小时 51 分钟的成绩——根本不存在。更危险的是，如果企业客服机器人幻觉了不存在的退款政策，后果不堪设想。

幻觉产生有三大原因：训练数据不完整、采样参数（temperature/top_k/top_p）过于"创意"、用户提问过于笼统。其中我们能控制最多的是第三项——优化 Prompt 质量。

## LLM-as-a-Judge：让 AI 审查 AI

部署前的 Benchmark 可以筛选模型，但上线后的持续质量评估怎么办？答案是用一个"裁判模型"来审查"工作模型"的输出——这就是 LLM-as-a-Judge。

实际做法是：从全部推理请求中抽取 1%~10% 的响应，用 GPT-4 或专用裁判模型从相关性、连贯性、事实性、安全性等维度打分。关键是**异步处理**——不能阻塞用户请求，否则既增加延迟又浪费算力。评估结果导出为 Prometheus 指标后，就能和基础设施指标一起做趋势追踪和降级告警。

评估提示词要具体。不要问"这个回答对不对？"，而是问"这个回答的语气是否正式？""是否包含个人隐私信息？"——越聚焦，裁判模型越可靠。

## 安全护栏：输入验证 + 输出过滤

![](附件资源/LLM%20可观测性：从%20GPU%20监控到安全护栏（第五章）/img_4.png)

幻觉之外，还有**越狱攻击**（Jailbreaking，让模型违反服务条款）和**提示注入**（Prompt Injection，如"忽略所有之前的指令"）。防护手段是在输入端和输出端都加 Guardrail：

-
- NeMo Guardrails（NVIDIA） ：用 Colang 领域语言定义对话流和安全约束，支持输入/对话/检索/执行/输出五类 Rails，可部署为 K8s 容器
-
- FMS Guardrails Orchestrator（IBM） ：集成 TrustyAI，编排多个检测器形成安全管道，违规行为自动导出为 Prometheus 指标
-
- Guardrails AI ：Python 库 + Hub 预置检测器，代码级集成，适合嵌入应用层
-
- Llama Stack（Meta） ：Safety API + Shield 机制 + /v1/moderations 端点，预训练分类模型
-

**成本 vs 安全的平衡**：用另一个 LLM（如 7B 的 Llama Guard）做安全检测会增加延迟和资源消耗。关键是在精确度（更小的专用模型）和召回率（更强大的通用模型）之间找到适合你场景的平衡点。

## SLI / SLO / SLA：用 Token 指标定义服务质量

![](附件资源/LLM%20可观测性：从%20GPU%20监控到安全护栏（第五章）/img_5.png)

传统 SRE 的 SLI/SLO/SLA 层次在 LLM 领域同样适用，只是指标需要"换血"：

-
- SLI（服务等级指标） ：实测的 TPOT 值——这就是用户最直接的感受
-
- SLO（服务等级目标） ：承诺 99.999% 的请求 TPOT 低于 0.1 秒
-
- SLA（服务等级协议） ：月度可用性 99.9%，违反则进入合同处罚流程
-

建议把质量指标也纳入 SLI 体系——不仅是基础设施快不快，还要看模型输出对不对、安不安全。建立**质量 SLO**，与延迟 SLO 并列追踪。

## 本章要点回顾

-
- LLM 监控的核心从"请求数"转向"Token 维度"——TTFT 衡量等待感，TPOT 衡量流式体验
-
- KServe + Prometheus 的采集配置与传统应用几乎一致，只需注意 Knative 模式下的 qpext 聚合
-
- GPU 指标需厂商专用工具（NVIDIA DCGM / AMD ROCm SMI / Intel XPU Manager）
-
- 模型质量监控同样是一等公民：LLM-as-a-Judge 异步采样评估 + ROUGE 等离线指标
-
- 安全护栏（NeMo / FMS / Guardrails AI / Llama Stack）应在输入和输出两端双重部署
-
- SLI/SLO/SLA 体系要覆盖基础设施延迟 + 模型质量两个维度
-
