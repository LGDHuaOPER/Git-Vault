# AI 应用上线后怎么监控？7 款评测与可观测性工具，帮你告别“盲人调参”

> Agent 能跑起来，只代表 Demo 完成了；能不能发现问题、解释问题并持续改进，才决定它能否真正上线。

**

![7款AI评测与可观测性工具公众号头图](附件资源/AI%20应用上线后怎么监控？7%20款评测与可观测性工具，帮你告别“盲人调参”/img_1.png)

**

**过去做软件监控，我们关心的是接口有没有报错、服务器有没有宕机。**

到了大模型应用时代，仅仅看到一个  `200 OK`  已经远远不够。接口调用成功，不代表回答正确；延迟没有异常，不代表模型没有胡说；Agent 顺利跑完整个流程，也不代表它调用了正确的工具。

更麻烦的是，大模型应用的故障往往不会直接“崩掉”。它可能只是悄悄变差：一次提示词调整让回答质量下降，一次模型升级让工具调用开始漂移，某类用户的对话突然变得特别贵，或者检索系统不断返回看似相关、实际无用的资料。

这些问题靠传统日志很难看清。于是，一个新的工具类别迅速变得重要： **大模型可观测性与评测平台。**

这篇文章不打算做一份功能清单，而是想回答一个更实际的问题：LangSmith、Langfuse、Phoenix、Datadog、Lunary、TruLens 和 Helicone，到底有什么区别？你的团队应该从哪一个开始？

## 大模型可观测性，到底在“观察”什么？

普通监控主要关注系统是否正常运行，大模型可观测性还要回答： **模型为什么给出这个结果？**

一次看似简单的 Agent 请求，背后可能包含提示词组装、模型推理、知识库检索、工具调用、结果验证和多轮重试。真正有用的可观测性平台，会把这些步骤串成一条完整的执行轨迹，让工程师看到每一步的输入、输出、耗时、成本和评分。

一套基本完整的大模型可观测性能力，通常包括五部分：

- • 执行轨迹： 记录模型调用、检索步骤、工具调用和 Agent 决策过程。
- • 质量评测： 用代码规则、人工标注或大模型裁判判断回答是否准确、相关、可靠。
- • 成本分析： 按模型、用户、会话或功能统计令牌消耗和调用费用。
- • 提示词管理： 保存提示词版本，比较修改前后的质量和成本变化。
- • 线上监控： 发现延迟异常、质量回退、安全风险和成本飙升，并触发告警。

**可观测性解决“发生了什么”，评测解决“做得好不好”。**

现在主流平台正在把这两件事放到一起：先用执行轨迹还原过程，再用评测器为结果打分，最后把线上失败案例沉淀成新的测试集。

## 1. LangSmith：LangChain 和 LangGraph 团队最省心的选择

**如果你的应用已经大量使用 LangChain 或 LangGraph，LangSmith 通常是阻力最小的起点。**

LangSmith 由 LangChain 团队开发，优势不是某一个单点功能特别突出，而是把开发、调试、评测和生产监控连成了一套完整工作流。开启追踪后，你可以看到 Agent 调用了哪些工具、每一步生成了什么内容、哪一步耗时最长，以及最终为什么走到这个结果。

它同时支持两类评测：上线前，可以用固定数据集比较不同模型、提示词和工作流；上线后，可以对真实流量进行抽样评分，监控安全、格式、回答质量和异常变化。线上出现的失败轨迹还可以直接加入数据集，修复后再跑一轮回归测试。

LangSmith 并不只支持 LangChain，但如果你的系统本来就在 LangChain 生态中，它的自动追踪和调试体验会更顺滑。需要注意的是，完整自托管主要面向企业方案，因此数据部署方式和预算要提前确认。

**适合谁：**

使用 LangChain 或 LangGraph，希望在同一个平台完成追踪、数据集管理和评测的团队。

参考：LangSmith 可观测性文档｜LangSmith 评测文档

## 2. Langfuse：开源、自托管和提示词管理的均衡选手

**如果你希望掌握数据和部署方式，又不想自己拼出一整套系统，Langfuse 是非常均衡的选择。**

Langfuse 是开源的大模型工程平台，覆盖执行轨迹、评测、数据集、实验和提示词管理。它基于 OpenTelemetry 构建，能够接入现有的分布式追踪体系，也支持 LangChain、LlamaIndex、CrewAI 和主流模型提供商。

Langfuse 的一个明显特点，是把提示词当作正式的工程资产。团队可以集中保存和发布提示词版本，把每个版本与执行轨迹、质量分数和成本关联起来。这样一来，提示词修改不再是“凭感觉改几句话”，而是可以比较修改前后的真实影响。

它的自托管能力对重视数据主权的团队很有吸引力。不过，自托管并不等于零成本：数据库、升级、备份、权限和监控都需要有人维护。团队在选择时要区分“没有软件许可费”和“没有运维成本”。

**适合谁：**

希望开源自托管、重视数据控制，同时需要追踪、评测和提示词管理的团队。

参考：Langfuse 文档｜提示词管理

## 3. Arize Phoenix：RAG 和评测工作流的强项选手

**如果你的应用高度依赖知识库检索，Phoenix 值得优先试。**

Arize Phoenix 是 Arize AI 推出的开源可观测性与评测平台，底层围绕 OpenTelemetry 和 OpenInference 构建。它可以记录模型调用、检索、工具使用和自定义逻辑，并把这些信息组织成完整轨迹。

Phoenix 对 RAG 应用尤其友好。RAG 出问题时，不能只看最终答案，因为故障可能发生在两个完全不同的位置：检索阶段没有找到正确资料，或者生成阶段拿到了资料却没有正确使用。Phoenix 可以分别检查检索相关性、回答相关性和事实依据，并查看具体返回了哪些文档块。

它还支持代码检查、大模型裁判和人工标注，并能把生产轨迹整理成数据集，用实验比较不同检索策略、模型和提示词。对希望保留开放标准、避免在埋点层被单一平台锁定的团队，这一点很有价值。

**适合谁：**

RAG 比重较高、重视评测实验和数据可移植性的 AI 工程团队。

参考：Phoenix 官方文档｜Phoenix 评测文档

## 4. Datadog Agent Observability：把模型问题和基础设施问题放在一起看

**如果公司已经全面使用 Datadog，没有必要为了大模型再搭一座新的监控孤岛。**

Datadog 已将相关能力扩展为 Agent Observability。它能记录模型调用、工作流和动态 Agent 的完整轨迹，监控延迟、令牌、成本、错误和质量指标，还可以把这些数据与应用性能、日志、数据库和基础设施指标关联起来。

这对大型企业尤其重要。一次 Agent 延迟升高，原因未必是模型变慢，也可能是数据库阻塞、检索服务异常或资源不足。Datadog 的价值在于，团队可以在同一个监控体系里继续向下追查，而不必在多个平台之间来回切换。

它还提供异常检测、质量评测以及隐私和提示词注入风险检查。代价是平台相对偏重，对尚未建立 Datadog 体系的小团队来说，可能不是最轻量的起点。

**适合谁：**

已经使用 Datadog 管理基础设施、APM 和日志，希望统一监控 Agent 与底层系统的企业。

参考：Datadog Agent Observability 文档

## 5. Lunary：小团队快速看到用户、会话和成本

**如果现阶段最关心的是“谁在用、用了多少、花了多少钱”，Lunary 的上手成本相对较低。**

Lunary 是一款开源的大模型可观测性平台，提供执行轨迹、用户会话、成本统计、提示词管理和评测。它强调轻量接入，适合还没有专门平台团队、但已经需要看清线上使用情况的早期产品。

和单纯记录模型请求相比，Lunary 更重视用户和会话维度。你可以追踪某位用户经历了哪些对话、某类功能消耗了多少成本，并把最终用户的点赞、点踩或其他反馈接入评测流程。

它的覆盖面比较全面，但生态规模和企业级集成能力与头部平台仍有差距。对于小团队，这未必是缺点；功能简单、部署轻，反而意味着能更快开始使用。

**适合谁：**

希望用较少工程投入获得会话追踪、成本分析和用户反馈的初创团队。

参考：Lunary 官方文档｜Lunary GitHub

## 6. TruLens：不是先做监控，而是先把 RAG 评明白

**如果你的核心问题是“如何严谨评价 RAG”，TruLens 比通用监控平台更聚焦。**

TruLens 是一套以评测为中心的开源框架。它最有代表性的概念是 RAG Triad，也就是从三个维度检查 RAG：检索到的上下文是否与问题相关，回答是否与问题相关，回答是否真正建立在上下文证据之上。

这三个指标看似简单，却对应了 RAG 最常见的三类故障：找错资料、答非所问，以及拿着正确资料继续胡编。TruLens 还支持大模型裁判、自定义反馈函数、运行结果比较和本地记录，适合在研发阶段系统比较不同检索配置。

它更像一套专用评测框架，而不是覆盖所有生产监控需求的一站式平台。如果团队还需要完整告警、用户分析和基础设施关联，通常要与其他可观测性工具搭配使用。

**适合谁：**

以 RAG 质量评测为核心任务，希望深入比较检索和生成效果的研发团队。

参考：TruLens 官方文档｜RAG Triad

## 7. Helicone：改一个接口地址，先把请求和成本看起来

**如果你不想先做复杂埋点，只想尽快看见模型请求，Helicone 的代理模式很直接。**

Helicone 与多数平台的接入方式不同。它可以作为模型 API 前面的网关：应用不再直接请求模型提供商，而是把请求发给 Helicone，再由它转发并记录。很多场景只需要修改 API 基础地址，就能开始查看请求、令牌、成本、用户和会话数据。

代理层还可以承担缓存、限流和用量控制。对于重复请求较多或采用多租户计费的产品，这些能力能够直接影响成本。但代理模式也意味着它位于请求链路中，团队必须认真评估数据流向、可用性、延迟和故障处理方案。

**适合谁：**

需要快速接入请求日志和成本监控，或需要网关、缓存与用户用量控制的产品团队。

参考：Helicone 官方文档｜Helicone GitHub

## 七款工具放在一起，应该怎么选？

这些平台不是简单的“谁功能最多谁最好”。 **真正的选择标准，是你现在最急着解决哪一个问题。**

| 你的团队情况 | 优先考虑 | 核心理由 |
| --- | --- | --- |
| 已经使用 LangChain 或 LangGraph | LangSmith | 原生追踪体验最好，开发与评测闭环完整 |
| 需要开源、自托管和数据主权 | Langfuse | 功能均衡，提示词管理成熟，部署自主 |
| RAG 很重，希望深入分析检索质量 | Arize Phoenix | RAG 轨迹和评测工作流完整，基于开放标准 |
| 企业已经全面使用 Datadog | Datadog Agent Observability | 能把 Agent、应用和基础设施问题统一关联 |
| 小团队想快速看用户、会话和成本 | Lunary | 轻量，用户分析和成本维度直观 |
| 当前最重要的是严谨评测 RAG | TruLens | 评测优先，RAG Triad 清晰、聚焦 |
| 想用最少代码先记录请求和费用 | Helicone | 代理接入快，还能提供缓存、限流和用量控制 |

如果仍然不知道该选哪一个，可以用下面这套简单判断：

- • 先看现有技术栈。 已经深度绑定 LangGraph，就先试 LangSmith；已经全面使用 Datadog，就优先复用现有平台。
- • 再看数据要求。 需要数据留在自己的环境里，就重点比较 Langfuse、Phoenix、Lunary、TruLens 和 Helicone 的自托管方案。
- • 最后看当前痛点。 想调试 Agent 看执行轨迹，想改善 RAG 看检索评测，想控制账单看用户和成本，目标不同，答案也不同。

## 不要一上来就追求“大而全”

**可观测性平台不是装上 SDK 就自动产生价值。**

如果没有定义关键任务、成功标准和需要监控的指标，再漂亮的仪表盘也只是堆积日志。团队更适合从一个最小闭环开始：

- 1. 选择 10 到 20 个最重要或最容易出错的真实任务。
- 2. 为这些任务记录完整执行轨迹，包括模型、检索和工具调用。
- 3. 先检查任务结果、错误率、延迟和成本，再增加少量质量评分。
- 4. 把线上失败案例加入评测数据集，修复后运行回归测试。
- 5. 只有当现有流程真的不够用时，再引入更复杂的告警、实验和自动评测。

这样做的好处，是每一项指标都对应具体问题，每一次评测都能够推动产品改进，而不是为了“有可观测性”而建设可观测性。

## 写在最后

**大模型应用最危险的状态，不是明确报错，而是看起来正常、实际上正在悄悄变差。**

可观测性工具的意义，就是把这种模糊变成证据：哪一步出了问题、影响了哪些用户、质量下降了多少、成本为什么增加，以及一次改动究竟让产品变好还是变坏。

LangSmith、Langfuse、Phoenix、Datadog、Lunary、TruLens 和 Helicone 没有绝对排名。选型时与其比较几十项功能，不如先问三个问题：我们需要看见什么？数据必须留在哪里？哪个问题最值得先解决？

**最好的工具，不是功能最全的那一个，而是能让团队最快建立“发现问题—定位原因—验证修复”闭环的那一个。**
