_**01**_

Agent 产品为什么需要技术建模

传统产品需求往往可以用“输入—处理—输出”描述：用户提交信息，系统完成处理，再返回结果。但 Agent 产品通常不是一次同步调用，而是一段可能持续较长时间的工作过程。它可能需要读取多个数据源、调用多个工具、等待用户确认、处理外部系统失败，并在中间生成可复用的结果。

因此，Agent 产品需求不能只描述“用户输入什么、模型回答什么”。它至少要解释任务如何拆分、步骤之间是否存在硬依赖、可调用的工具是否会改动外部系统、何处需要用户确认，以及发生超时、拒绝或服务异常时任务应当停止、降级还是恢复。最终交付也不能只是一段回复，而要明确是结构化数据、可下载产物，还是一个已写入业务系统的资源。

如果一份 Agent 需求只能描述输入和输出，它通常还没有进入工程设计阶段。产品经理设计的不只是交互页面，还包括一套能够被执行、被观察和被验收的任务模型。

本文所说的 **Agent Harness**，不是某个特定框架的名称，而是承接任务定义、步骤调度、工具调用、权限执行、结果校验和运行观测的控制层。业务工作流决定“要完成什么”，工具实现决定“如何访问外部能力”，Harness 则把两者组织成一段可约束、可追溯的运行。本文关注的正是产品经理需要参与定义的这部分系统契约，而不讨论某一种模型或编排框架的具体实现。

_**02**_

从用户目标到 Agent Workflow

产品经理首先需要把用户目标转换成可执行的工作流，而不是直接把目标写成一个 Prompt。

例如，“根据用户反馈生成改进建议，并在确认后提交到目标工作系统”可以拆解为：

读取反馈数据

```shell
-> 清洗和去重
-> 按问题类型聚类
-> 统计影响范围
-> 查询历史记录
-> 生成候选建议
-> 检查建议冲突
-> 输出评估报告
-> 用户确认并提
```

每一个步骤都需要具备明确的工程属性：

| ** 字段 ** | ** 示例 ** |
| --- | --- |
| 步骤名称 | 用户反馈聚类 |
| 输入 | 反馈记录 |
| 输出 | 问题分类结果 |
| 使用工具 | 数据查询、文本分析 |
| 是否可并行 | 是 |
| 是否需要审批 | 否 |
| 失败处理 | 重试或跳过 |
| 产出类型 | 结构化数据 |
| 验收标准 | 每条反馈必须有分类 |

产品经理不一定需要实现聚类算法，但需要判断工作流是否完整：哪些步骤必须串行，哪些步骤可以并行，哪些结果可以被后续步骤消费，哪些环节需要产品经理介入。

**为步骤定义执行语义**

工作流不能只有顺序，还要定义调度语义。通常可把步骤分成四类：

| ** 步骤类型 ** | ** 典型场景 ** | ** 技术要求 ** |
| --- | --- | --- |
| serial | 先完成数据清洗，再做聚类 | 前序输出校验通过后才可启动 |
| parallel | 同时查询历史记录与统计影响范围 | 独立输入、并发上限、聚合策略 |
| fan-out/fan-in | 按问题类别分别分析，再汇总建议 | 分片键、子任务失败容忍度、聚合条件 |
| human-gate | 向目标系统提交记录前等待确认 | 暂停条件、审批 payload、过期处理 |

例如，问题聚类和历史记录匹配可以并行，但建议生成是否必须等待两者完成，取决于历史记录在这项业务中是硬依赖还是增强信息。前者应阻塞后续生成；后者可以记录“历史匹配缺失”并降级继续。两种行为都要由任务定义决定，不能让执行器在运行时猜测。

建议把这种语义写进 Workflow DSL 或 JSON 配置，而不要散落在 Prompt 中。下面的配置将历史匹配视为硬依赖，因此任一步失败都会阻塞建议生成：

```bash
  "id": "generate\_recommendation",
  "dependsOn": \["cluster\_feedback", "analyze\_impact", "match\_history"\],
  "mode": "serial",
  "input": {
    "clusters": "$steps.cluster\_feedback.output",
    "impact": "$steps.analyze\_impact.output",
    "history": "$steps.match\_history.output"
  },
  "onFailure": "block",
  "timeoutSeconds": 90
}
```

这里的 dependsOn 定义依赖图，input 明确数据绑定，onFailure 定义失败传播。示例把影响范围统计也列为前置依赖，避免建议生成在缺少影响信息时继续执行。产品需求写清这些字段后，研发才能稳定实现调度、重试和可视化进度。

_**03**_

任务模型：不要只设计一轮对话

Agent 产品需要明确任务对象，而不是只围绕会话设计。建议将用户目标、输入、执行过程和结果组织在一个任务模型中：

```nginx
Task
├── taskId
├── userGoal
├── inputRefs
├── workflowVersion
├── owner
└── runRefs
```

```nginx
Run
├── runId
├── taskId
├── currentStep
├── status
├── outputs
├── approvals
└── errors
```

产品经理需要区分以下对象：

| ** 对象 ** | ** 完整定义 ** | ** 典型作用 ** |
| --- | --- | --- |
| Conversation | 用户与 Agent 之间按时间组织的消息和上下文记录。 | 提供交互入口与沟通历史。 |
| Task | 围绕一个明确业务目标组织的任务定义，包含输入、工作流和完成标准。 | 承载需要被完成和验收的业务工作。 |
| Run | 某个任务在特定配置、输入版本和时间点下的一次执行实例。 | 支持失败重试、运行对比和过程追踪。 |
| Artifact | 任务执行后生成的、可被访问、下载或继续消费的结果对象。 | 承载报告、结构化结果或外部系统记录。 |

一个任务可以包含多轮对话、多次运行和多个产物。对话是交互载体，任务是业务目标，运行是一次执行实例，产物是可继续使用的交付结果。如果把这些对象混成一个聊天线程，后续很难支持重试、对比、恢复和结果归属。这里的 Task.owner 表示业务归属或责任主体，不等同于发起会话的用户；Run.approvals 保存本次执行实际使用的审批记录引用，而不是把审批内容复制进每条消息。

**任务对象需要版本和引用语义**

任务对象在工程上至少要支持两个能力：**输入可复现与结构可演进**。前者要求任务保存输入的稳定引用，不是只保存提示词中的长文本；后者要求对象允许字段逐步增加，同时保持历史任务可读。

```perl
{
  "taskId": "task\_01J...",
  "schemaVersion": 2,
  "goal": "基于用户反馈生成需求建议",
  "inputRefs": \[
    {"type": "feedback\_sheet", "id": "file\_123", "version": "v7"}
  \],
  "workflowVersion": "feedback-analysis@1.3.0",
  "runs": \["run\_a1", "run\_a2"\],
  "artifactRefs": \["artifact\_report\_01"\]
}
```

schemaVersion 解决对象结构演进，workflowVersion 解决同一任务在不同编排版本下的行为差异，inputRefs.version 则避免数据源更新后无法解释历史结论。产品经理至少需要提出“历史任务是否必须复现”“规则更新后旧任务如何展示”这两个问题；它们会直接影响存储模型与审计成本。

_**04**_

工具设计：产品经理要定义工具契约

Agent 是否可靠，很大程度取决于工具是否设计清晰。产品经理不一定编写工具实现，但需要参与定义工具契约：

```bash
Tool:
  name
  description
  inputSchema
  outputSchema
  permission
  sideEffect
  timeout
  retryPolicy
```

以“提交建议到目标工作系统”工具为例：

```makefile
submitRecommendation:
  input:
    title
    description
    priority
    targetScope
    idempotencyKey

  output:
    recordId
    url
    status

  permission:
    write\_target\_system

  sideEffect:
    create\_external\_record
```

产品经理需要确认：

- 工具什么时候可以被调用；
- 参数是否足够完整；
- 返回结果是否足够支持下一步；
- 工具是否修改外部系统；
- 是否需要审批；
- 调用失败后是否可以重试；
- 是否允许重复调用；
- 是否需要幂等键。

此处注意工具不是“给模型调用的接口列表”，工具是 Agent 工作流中的业务动作协议。一个工具的输入、输出、权限和副作用如果没有明确约定，模型的自由度越高，系统的不确定性也越高。

**4.1 输入校验、输出校验和错误码必须分层**

工具调用至少需要三层校验：

- 调用前校验： 使用 JSON Schema、字段枚举和权限策略拒绝非法参数，例如优先级不在允许范围、项目不属于当前授权范围。
- 执行后校验： 对工具返回值做 Schema 校验，避免模型把错误响应误当成成功结果继续推理。
- 业务结果校验： 验证业务不变量，例如提交成功后必须获得可查询的 recordId

建议让工具返回稳定的结果，不要把异常拼成自然语言：

```json
{
  "ok": false,
  "requestId": "req\_8f2c",
  "error": {
    "code": "DUPLICATE\_RECORD",
    "retryable": false,
    "message": "同一业务动作已提交记录",
    "details": {"recordId": "record\_1024"}
  }
}
```

其中 retryable 决定执行器是否自动重试，requestId 用于日志关联，details 让后续步骤可以选择跳转已有记录而不是重复提交。这里的 DUPLICATE_RECORD 适用于“业务上不允许重复”的场景；若调用方携带的是同一幂等键，服务端更稳妥的做法是返回首次成功的资源，并在响应中标明 idempotentReplay: true。产品经理在定义工具输出时，应要求区分“未执行”“执行失败”“已执行但结果不满足业务条件”和“幂等重放返回已有结果”。

**4.2 工具描述是约束接口**

模型看到的工具描述会影响调用决策，但它不能替代机器可校验的 Schema。推荐把人类可读说明、机器可读 Schema 和策略约束分离：

```javascript
Tool description -> 告诉模型何时使用、何时禁止使用
JSON Schema       -> 约束参数类型、枚举、必填项
Policy           -> 约束主体、资源范围、风险等级
Executor         -> 负责超时、重试、幂等与审计
```

这能避免把“禁止修改其他项目”“标题最长 80 字”之类的硬约束仅写在 Prompt 中。Prompt 可以被误解，Schema 和 Policy 必须能够在执行前强制生效。

_**05**_

权限与副作用：用风险等级设计审批

不同工具对系统的影响不同，权限策略不能只采用“允许”或“禁止”两种状态。可以按照副作用和风险将工具分级：

| ** 等级 ** | ** 类型 ** | ** 示例 ** | ** 默认策略 ** |
| --- | --- | --- | --- |
| L0 | 只读计算 | 文本分类、格式转换 | 自动执行 |
| L1 | 读取业务数据 | 查询历史记录、查询知识库 | 权限校验 |
| L2 | 生成内部产物 | 生成方案草稿、报告、测试用例 | 自动执行并记录来源 |
| L3 | 修改业务数据 | 向目标系统提交记录、更新任务字段 | 明确授权，必要时审批 |
| L4 | 高风险外部动作 | 删除数据、发送消息、对外发布 | 强制审批和审计 |

策略可以进一步表达为结构化配置：

```javascript
Policy:
  tool: submitRecommendation
  riskLevel: L3
  requireApproval: true
  allowedScopes: \[...\]
  allowedFields: \[...\]
  idempotencyRequired: true
```

产品经理需要把“需要确认”转化为可执行规则：哪些工具必须确认，哪些参数变化会触发重新确认，确认的有效范围是什么，拒绝之后如何处理，是否允许预授权，以及审批过程如何记录。

**授权应绑定主体、资源和动作**

审批不仅仅是一个布尔值。有效授权至少应绑定三类上下文：

- Subject：谁在授权，例如当前用户或代理服务身份
- Resource：可访问或修改什么，例如 scopeId、documentId、tenantId
- Action：允许做什么，例如 read、create、update、publish

例如“允许提交建议”并不等于“允许向所有目标空间写入记录”。更可执行的授权记录是：

```javascript
{
  "subject": "user\_12345",
  "action": "recommendation.submit",
  "resource": {"scopeId": "workspace\_1001"},
  "constraints": {"priorityIn": \["P1", "P2"\], "expiresAt": "2026-08-22T12:00:00Z"},
  "approvalId": "approval\_01"
}
```

当工具参数越过资源范围、修改了受约束字段或审批过期时，执行器必须重新请求授权。这样可以避免一次确认被错误扩展为无限范围的通行证。

_**06**_

结果协议：从文本回答到结构化交付

Agent 的结果不应只有一段 Markdown 文本。不同任务需要定义不同的结果协议，例如：

```makefile
Result:
  summary
  evidence
  decisions
  risks
  pendingQuestions
  artifactRefs
  nextActions
```

用户反馈分析可以输出：

```css
{
  "summary": "...",
  "clusters": \[\],
  "priorityRecommendations": \[\],
  "matchedRequirements": \[\],
  "evidenceRefs": \[\],
  "uncertainties": \[\],
  "nextActions": \[\]
}
```

产品经理需要区分四类结果，因为它们对应不同的存储、展示和后续消费方式：

| ** 结果类型 ** | ** 完整说明 ** | ** 适用场景 ** |
| --- | --- | --- |
| 自然语言说明 | 面向用户阅读的结论、解释和执行过程摘要。 | 在会话中说明判断依据与下一步建议。 |
| 结构化业务结果 | 满足固定字段约束、可被程序继续读取和校验的数据对象。 | 将分析结果传给后续 Agent、页面组件或规则引擎。 |
| 可下载产物 | 具备文件格式、版本和访问地址的独立交付物。 | 输出报告、表格、文档或图片等可留存材料。 |
| 外部系统记录 | 在目标工作系统中创建或更新的稳定资源。 | 形成可继续跟进的事项、任务或数据记录。 |

结构化结果可以被前端展示，也可以被后续 Agent 消费；产物可以导出为报告；外部系统记录则需要返回稳定的 ID 和访问地址。重要结论还应带有证据引用和不确定性说明，避免把推测包装成事实。

**6.1 将证据与结论建成可追溯关系**

结果协议中的 evidenceRefs 不应只是 URL 列表，需要能表达“哪条结论依据了哪些来源”。推荐使用可定位引用：

```javascript
{
  "recommendationId": "rec\_01",
  "statement": "登录失败提示需要覆盖网络异常场景",
  "confidence": 0.82,
  "evidence": \[
    {"sourceId": "feedback\_328", "locator": "row:328", "role": "user\_feedback"},
    {"sourceId": "metric\_login", "locator": "2026-08-01..2026-08-15", "role": "metric"}
  \],
  "assumptions": \["反馈样本已完成去重"\]
}
```

confidence 不能替代证据，但可以帮助界面进行排序和提示；assumptions 则把模型推理依赖的前提显式化。对于需要进入外部系统的结果，建议增加 resultVersion、generatedAt、generatorVersion，以便后续比较不同版本的分析差异。

**6.2 结果发布前增加确定性校验**

LLM 输出具有非确定性，结构化输出也可能字段齐全但业务不正确。因此，发布前应增加确定性校验器，例如：

```diff
- 每条建议至少绑定一条 evidence
- priority 必须属于 P0/P1/P2/P3
- sourceRef 必须属于本次 Task 的可访问输入
- externalRecordId 只能在写工具成功后出现
- 风险等级为高时必须有 nextAction
```

这些规则更适合由普通代码或规则引擎执行，而不是再次交给模型判断。模型负责生成候选结论，校验器负责守住协议边界。

_**07**_

失败处理：重试、恢复与幂等性设计

Agent 任务的失败不能只显示“执行失败，请重试”。至少需要区分：

```nginx
InputError
PermissionError
ToolError
TimeoutError
ModelError
ValidationError
ExternalSystemError
```

不同错误类型应采用不同策略：

| ** 错误类型 ** | ** 处理方式 ** |
| --- | --- |
| 输入错误 | 引导用户补充信息 |
| 权限错误 | 请求授权或更换数据源 |
| 工具错误 | 重试或切换工具 |
| 超时 | 继续后台执行或拆分任务 |
| 模型错误 | 降级模型或重新规划 |
| 校验失败 | 返回 Agent 修正 |
| 外部系统错误 | 保留任务并支持恢复 |

需要特别关注具有副作用的步骤。如果向目标系统提交记录的接口已经成功，但响应在网络传输过程中丢失，简单重试可能造成重复写入。因此，写操作应使用任务 ID、步骤 ID或业务幂等键标识同一业务动作：

同一个 taskId + stepId 不应重复创建相同业务数据

产品经理需要在需求阶段明确：哪些失败可以自动重试，哪些失败必须通知用户，哪些步骤支持从中间位置继续，以及失败时已经产生的产物如何处理。

**7.1 重试策略必须区分读、写与模型生成**

“最多重试三次”不是通用策略。不同类别的操作需要不同的执行规则：

| ** 操作类型 ** | ** 典型失败 ** | ** 推荐策略 ** |
| --- | --- | --- |
| 只读查询 | 网络抖动、限流 | 指数退避重试，可加入抖动 |
| 写外部系统 | 响应丢失、网关超时 | 先按幂等键查询，再决定是否重试 |
| 模型生成 | 格式不合法、内容不完整 | 修复提示词或基于校验错误再生成 |
| 长任务 | 执行超时 | 拆分、异步化或延长租约，不应盲目重复执行 |

指数退避可以表达为 delay = base * 2^attempt + jitter。jitter 的作用是避免大量任务在同一时刻重试造成二次拥塞。对于 L3/L4 写操作，重试前必须优先检查是否已经落库；这是比“请求是否超时”更可靠的判断。

**7.2 幂等键应表达业务动作**

一个可用的幂等键通常由业务主键组成：

```ini
idempotencyKey = hash(taskId + stepId + targetProjectId + normalizedPayload)
```

其中 normalizedPayload 应排除时间戳、展示文案等不影响业务语义的字段。服务端收到相同键时，应返回首次创建的资源，而不是再次执行。这样即使执行器重启、网络响应丢失或用户重复点击，也能把同一业务动作折叠为一次结果。

_**08**_

可观测性与验收：监控不能替代验证

Agent 上线后，最容易出现两种误判：一是任务“跑完了”就被视为成功；二是平均耗时下降就被视为体验变好。前者掩盖了结论无依据、写操作重复执行等问题，后者又可能以牺牲结果质量为代价。对 Agent 而言，观测数据的价值不在于堆出一张大盘，而在于帮助团队定位一次失败究竟发生在任务设计、模型决策、工具接口，还是用户确认环节。

以“根据反馈提交改进建议”为例，如果完成率突然下降，先看任务是否停在输入校验或授权环节；如果完成率没有变化、人工返工却明显增加，再回看引用是否缺失、聚类规则是否漂移、工作流版本是否变化。工具超时率只有和具体的步骤、数据源及重试次数放在一起，才有诊断意义。单独统计“工具成功率”通常解决不了问题。

实践中可以把观测字段压缩为一条可关联的执行记录：

```
traceId, taskId, runId, stepId, toolName,
workflowVersion, promptVersion, inputRef, outputRef,
latencyMs, retryCount, errorCode, approvalId
```

taskId 服务于业务检索，traceId 用于跨服务追踪，workflowVersion 和 promptVersion 用来解释“为什么同一类输入这周开始产生不同结果”。如果一条需求建议被用户退回，团队应该可以沿着这条记录还原它使用了哪个输入版本、走过哪些步骤、调用了什么工具、何处发生重试，以及最终依据来自哪里。

验收也不应停留在“看几条回答是否顺眼”。更实用的做法是保留少量高价值样本：空反馈、历史记录服务不可用、重复提交、目标空间越权、用户拒绝审批等。每个样本都写清不可触碰的边界，而不是罗列一长串泛泛指标。下面的用例同时约束工具选择、结果结构和副作用上限：

```ruby
case: feedback-duplicate-submit
inputRef: fixture://feedback/duplicate.csv
expect:
  requiredTools: \[readFeedback, clusterFeedback, submitRecommendation\]
  forbiddenTools: \[publishAnnouncement\]
  resultSchema: AnalysisResult@v1
  assertions:
    - path: $.recommendations\[\*\].evidenceRefs.length
      operator: greaterThan
      value: 0
    - path: $.artifactRefs\[?(@.type == 'target\_system\_record')\].externalId
      operator: exists
  sideEffects:
    maxSubmittedRecords: 1
```

这类用例更接近契约测试：它不承诺模型必须写出哪一句话，却明确要求不能绕过证据、不能调用无关工具、不能因为重试创建两条需求。把它放进 CI 或灰度回归，比让测试同学反复手工体验更能发现工程回归。

_**09**_

案例：反馈分析 Agent 的技术设计

**9.1 业务目标**

根据用户反馈，自动生成改进建议，并在用户确认后提交到目标工作系统。

**9.2 任务流程**

先导入用户反馈并完成格式检查，然后执行数据清洗、问题聚类和影响范围分析，再匹配历史记录并生成候选方案，经过结果校验和用户确认后，才调用提交建议的写入工具。

该流程中的前半段只读取和分析数据，后半段则从“生成建议”转入“改变业务系统”。这条边界决定了提交动作必须放在用户确认之后，并使用可追踪的幂等键执行。

**9.3 工具列表**

| ** 工具 ** | ** 完整职责 ** | ** 输入和输出边界 ** |
| --- | --- | --- |
| readFeedback | 读取并标准化用户反馈文件，识别空行、非法字段和版本信息。 | 输入为文件引用，输出为可分析的反馈记录集。 |
| queryHistorical-Records | 查询与问题类别、关键词或业务域相关的历史记录。 | 输入为查询条件，输出为带来源标识的候选记录集合。 |
| clusterFeedback | 对反馈记录进行分类、聚类和去重，形成问题主题。 | 输入为标准化记录，输出为带成员列表的聚类结果。 |
| generateRecom-mendation | 根据聚类、影响范围和历史匹配生成候选改进建议。 | 输入为分析结果，输出为附带证据的建议对象。 |
| validateRecom-mendation | 用确定性业务规则验证建议的字段、来源和冲突情况。 | 输入为候选建议，输出为通过项、阻塞项和修复建议。 |
| submitRecom-mendation | 在用户授权的目标空间中提交正式记录。 | 输入为已确认的建议与幂等键，输出为记录 ID、链接和提交状态。 |

**9.4 权限、结果与校验如何落到一条链路上**

这六个工具并不处在同一个风险等级。readFeedback 和 queryHistoricalRecords 会读取业务资料，应在数据源授权范围内以 L1 执行；clusterFeedback 和 validateRecommendation 只处理已获授权的输入，属于 L0；generate-

Recommendation 产生内部分析材料，可按 L2 管理并保留生成版本；submitRecommendation 会向目标工作系统写入记录，必须按 L3 执行，绑定目标空间、用户确认和幂等键。

最终输出的 AnalysisResult 不应只是一段摘要。它至少要包含 clusters、affectedUsers、priority-

Suggestions、matchedRecords、recommen-

dations、risks 和 evidenceRefs。其中每条 recommendations 都应携带证据引用，便于追问“这条 P1 建议对应哪几类反馈”。提交成功后得到的资源不宜混入分析结果，而应作为独立的 SubmitRecommendationResult，或以 artifact-

Refs 中的外部记录引用返回；这样分析输出和写操作结果的生命周期不会混在一起。

提交记录前，校验器要连续确认几件具体的事：标题不能为空；每条建议必须能回指到反馈或历史记录；目标空间必须在当前用户的授权范围内；优先级只能取系统允许的值；相同 taskId + stepId + targetScope 不能已经提交过资源；并且用户必须已经对这一次写操作确认。任何一项不满足，都应该停在提交前，而不是让模型自己补一个默认值继续执行。

验收时建议直接围绕故障场景做判断。空反馈应回到补充输入，而不是生成泛泛的结论；历史记录服务不可用时，可以提示“缺少历史匹配”但不能伪造引用；没有证据的方案不能进入提交步骤；用户拒绝后不得发起写请求；网络超时后必须先按幂等键查询已有结果；成功返回则必须包含记录 ID 和可访问链接。这样的验收描述同时覆盖用户体验和服务端行为，比“任务成功率达到多少”更接近真实风险。

这个案例中，产品经理通过定义任务、工具、权限、结果和验收标准，参与了 Agent 的技术方案设计，而不是只描述一个聊天页面。

_**10**_

产品经理的交付物：需要围绕关键业务动作

Agent 需求经常失败在一个很朴素的地方：文档里写了用户要什么，却没有写清系统在不确定条件下该怎么做。研发只能把判断塞进 Prompt，测试也只能凭感觉点几轮。更有效的交付不是六张独立的清单，而是一张围绕关键业务动作展开的任务卡。

以“提交建议到目标工作系统”这个动作为例，任务应把以下内容写在同一个上下文中：任务要解决哪类用户问题，哪些输入是可信来源，必须经过哪些前置步骤，读取和写入分别可以访问哪些系统，什么情况下暂停等待人确认，外部接口超时后如何避免重复提交，最终要返回什么资源标识，以及哪些反例必须在测试中覆盖。这样研发看到的是一个可实现的闭环，不是一组被拆散的名词。

可以用下面的模板审查一张任务卡是否足够完整：

| ** 审查项 ** | ** 需要回答的问题 ** |
| --- | --- |
| 业务完成条件 | 任务产生什么可验证结果，什么状态下算真正完成？ |
| 输入和来源 | 输入来自哪里，是否有版本号、权限限制和失效处理？ |
| 工作流边界 | 哪些步骤是硬依赖，哪些可降级，哪里必须等待人工决策？ |
| 工具和副作用 | 工具能读写哪些资源，超时与重复调用时会发生什么？ |
| 结果与证据 | 哪些字段必须结构化返回，结论如何回指到来源？ |
| 异常和恢复 | 缺输入、无权限、服务超时和写入不确定时分别怎么处理？ |
| 验收反例 | 哪些越权、重复写入、无证据结论或错误降级必须被拦住？ |

产品经理越早补齐这些问题，研发越容易选择合适的执行模型、工具协议和存储方式，测试也越容易建立稳定的回归样本。这里的目标不是让产品经理承担实现细节，而是避免关键业务判断在实现后期才以补丁形式出现。

_**11**_

总结：从功能需求到 Agent 系统契约

Agent 产品的技术设计，不能停留在 Prompt、模型和聊天界面。真正需要被设计的是一条业务动作链：任务的输入和完成条件先被固定下来，再拆成带依赖关系的步骤；每个步骤只能通过有 Schema、权限和副作用约束的工具执行；结果以可追溯的结构化协议交付；异常、重试和验证则保证这条链在不确定环境下仍然可控。

这不意味着产品经理要替研发决定存储引擎或调度框架。产品经理要负责的是把那些不能靠模型自由发挥的判断提前说清楚：一条需求建议何时算完成，哪些来源可以作为证据，什么范围内允许写入业务系统，用户拒绝或接口超时后应当发生什么，以及哪些反例必须被测试拦住。研发据此选择实现方式，测试据此建立回归样本，双方都不必在上线前再通过补规则修正业务边界。

最终，Agent 产品的竞争力不只是模型回答得是否自然，还要能把复杂工作稳定地转化为可执行、可追溯、可验证的业务结果。好的 Agent 需求，是先把不能出错的业务边界写进任务、工具和验证规则。
