# 智能体全链路可观测技术实现方案（甲方视角）

# 一、项目背景与建设目标

## 1.1建设驱动因素

随着生成式 AI 与智能体(Agent)技术在加速落地，机构正面临前所未有的可观测性挑战。智能体系统的复杂性远超传统应用——它涉及多轮 LLM 调用、工具编排、知识库检索、记忆管理、人工介入等多环节，任何一个环节的黑盒化都可能导致：

安全风险不可见：提示注入(Prompt Injection)、越权指令、数据外发、PII 泄露、幻觉误导等攻击面难以实时感知；

质量风险难度量：回答准确性、事实一致性、合规性缺乏量化评估手段；

成本与性能失控：Token 消耗、API 延迟、并发容量等指标分散在各组件中无法聚合；

监管合规压力：金发〔2026〕8 号《生成式人工智能服务管理办法》要求对 AI 服务全生命周期进行记录、审计与追溯；ISO/IEC 38507:2022 要求组织建立 AI 使用治理框架，其中"可审计性"(Auditability)是核心要求；

运营效率低下：故障排查依赖人工逐层定位，平均修复时间(MTTR)居高不下。

## 1.2建设目标（SMART 原则）

以甲方视角，本方案设定以下四维建设目标，每项均可量化验证：

| ** 目标维度 ****** | ** 具体目标描述 ****** | ** 验收标准 ****** | ** 时间节点 ****** |
| --- | --- | --- | --- |
| 全链路可追踪 | 从用户输入到最终输出的完整调用链可视化，支持回放与根因分析 | 覆盖 ≥95% 的智能体场景，单次查询端到端延迟  | MTTD ≤5 分钟，MTTR ≤30 分钟，误报率 ≤10% | M7 |
| 合规可审计 | 满足监管要求的完整留痕与报表能力，支持数据分类分级 | 审计日志留存 ≥180 天，支持一键导出监管报表 | M12 |

## 1.3设计原则（甲方视角）

标准优先：严格遵循 OpenTelemetry GenAI Semantic Conventions，确保采集数据标准化、互操作性强；同时对接 ISO/IEC 系列标准与国内监管要求。

自主可控：核心平台能力自建或基于开源可控组件，避免单一供应商锁定；关键数据不出域。

分阶段渐进：采用 MVP → 试点 → 推广 → 优化的渐进式路径，每阶段设置明确里程碑与验收条件。

可落地可验证：每个功能点均定义清晰的接口规范、数据格式和验收用例，避免"概念化建设"。

安全内建(Security by Design)：安全可观测不是事后补丁，而是贯穿采集→处理→存储→展示的全流程。

数据最小必要：遵循最小权限与数据最小化原则，采集字段按业务必要性分级审批。

# 二、可观测对象与信号体系扩展

## 2.1智能体系统可观测对象清单

| ** 对象类型 ** | ** 说明 ** | ** 典型组件示例 ** | ** 关键观测点 ** |
| --- | --- | --- | --- |
| 多智能体编排 | 多个 Agent 协作完成任务的路由与调度 | LangGraph / CrewAI / AutoGen | 路由决策、Agent间通信、任务拆解结果 |
| LLM 调用 | 大语言模型的推理过程 | OpenAI / 文心一言 / 通义千问 / 私有部署 | prompt/completion/tokens/model/temperature/top-p/思考链 |
| 工具调用 | Agent 执行外部动作 | API 调用 / SQL 查询 / 文件操作 / 浏览器 | 工具名/参数/返回值/耗时/状态码/错误信息 |
| RAG / 知识库 | 检索增强生成的检索与引用过程 | 向量数据库 / ES / 知识图谱 | query/检索结果/相似度得分/来源文档/引用片段 |
| 记忆与会话 | 上下文管理与会话历史 | 短期工作记忆 / 长期向量记忆 | 记忆读写操作/会话状态变更/上下文窗口使用量 |
| 人工介入(HITL) | 需要人工审核或确认的节点 | 工单系统 / 审批流 | 介入原因/处理人/耗时/决策结果/备注 |

## 2.2信号体系扩展：传统三大信号 + 两项新增

传统可观测性的三大信号（Trace/Metric/Log）不足以覆盖智能体场景的独特需求。本方案在此基础上扩展为五大信号维度：

**【Trace — 调用链】      **

保留 OpenTelemetry Trace 核心能力，但 Span 语义需针对 Agent 场景扩展：LLM Span（含 prompt/token/模型参数）、Tool Span（含输入/输出/错误）、RAG Span（含 query/命中/相似度）、Guardrail Span（含过滤规则/拦截结果）。Span 之间的父子关系反映 Agent 的执行拓扑。

**【Metric — 指标】       **

在常规性能指标（QPS/Latency/Error Rate）基础上增加 Agent 特有指标：

• Token 维度：总 Token 消耗、Prompt/Completion 占比、成本换算

• 质量维度：幻觉检出率、相关性评分分布、合规违规计数

• 安全维度：注入尝试次数、泄露事件数、拦截成功率

• 工具维度：各工具调用频次、失败率、平均耗时

**【Log — 日志】**

结构化日志覆盖 Agent 的推理过程输出（如 CoT 思考链）、异常堆栈、护栏(Guardrail) 决策日志、审计事件日志。日志级别按数据敏感度分级。

**【Evaluation — 评估】★ 新增   **

这是 Agent 可观测区别于传统应用的关键增量信号。通过内置或旁路的评估模型，对每次交互进行自动打分：

• 事实性(Factuality)：回答是否包含虚假信息

• 相关性(Relevance)：回答是否切题

• 合规性(Compliance)：是否违反内部策略或法规

• 有用性(Helpfulness)：对用户的实际帮助程度

• 安全性(Safety)：是否包含有害内容

**【Security — 安全信号】★ 新增 **

专门用于安全运营的信号通道，包括：

• 攻击特征：注入模式指纹、探测行为基线偏离

• 泄露特征：PII 匹配命中、敏感数据外传

• 行为异常：非工作时间访问、批量数据拉取、权限提升尝试

# 三、总体架构设计

## 3.1架构概述

本方案采用"五层 + 横向治理"的分层架构，自下而上依次为接入层、采集层、处理层、存储层和应用层（平台），横向贯穿治理与合规能力。每一层职责清晰、接口标准化，便于分阶段独立建设与替换升级。

架构设计的核心理念是：将可观测性作为基础设施而非附加功能——就像网络监控之于数据中心，可观测性应当成为智能体平台的默认能力。          详细架构见下图：

## 3.2各层职责详述

**【接入层 — 智能体应用】**

这是被观测的对象层。所有运行中的智能体应用——无论是 LangChain 编排的多 Agent 系统，还是基于 AutoGen 的协作框架，或是自主开发的 Agent 引擎——都属于此层。

关键要点：此层不承担任何可观测逻辑，只负责正常业务运行。可观测能力的引入通过下一层的采集探针无侵入地完成。

**【采集层 — 多模式统一采集】**

提供三种互补的采集方式，适应不同技术栈与运维环境：

①SDK 埋点（推荐主力）：在 Agent 应用进程内嵌入 OpenTelemetry SDK，通过框架级 Instrumentation 实现自动埋点，辅以手动埋点补充业务上下文。

②网关/代理（流量侧）：对于无法修改代码的场景（SaaS 服务、第三方 Agent），在 API Gateway 或 Sidecar 层解析流量协议提取信号。

③日志/事件采集（兜底）：订阅应用的日志流与事件总线，通过结构化解析提取可观测数据。

三种方式的输出统一为 OTLP(OpenTelemetry Protocol) 格式，汇聚至 Collector。

**【处理层 — 流式管道】**

接收 OTLP 数据后，经过以下处理流水线：

清洗标准化：去敏（脱敏 PII）、格式归一、字段校验

上下文富化：关联租户标识、用户画像、策略配置、资产元数据

质量评估：调用评估模型对 LLM 输出进行自动评分

安全评估：运行安全检测引擎识别注入、泄露、越权等风险

聚合索引：根据信号类型分流写入不同存储引擎

处理层采用流式架构（Flink/Kafka Streams），保证低延迟（P99 <500ms）。

**【存储层 — 分库分治】**

不同类型的可观测数据具有不同的访问模式，因此采用专用存储引擎：

链路库(Trace Store)：OLAP 列存（ClickHouse/Doris），适合按 trace_id/span_id 的复杂查询与聚合

指标库(Metric TSDB)：时序数据库（Prometheus/VictoriaMetrics），适合降采样、趋势分析与告警

日志库(Log Store)：全文检索引擎(Elasticsearch/OpenSearch)，适合自由文本搜索与关联分析

评估库(Eval Store)：关系型 + 向量混合（PostgreSQL + pgvector），保存结构化评分与语义 embedding 用于聚类

元数据库(Meta DB)：关系型数据库，保存资产目录、策略配置、字典映射等元数据

**【应用层 — 可观测平台】**

面向不同角色的前端平台，详见第七节"平台功能设计"。主要包括：全链路追踪界面、指标仪表盘、质量评估台、安全运营中心、智能告警中心、审计报表模块。

**【治理与合规层（横向贯穿）】**

跨所有层的横切关注点：

标准规范：确保全链路符合 OpenTelemetry GenAI Semantic Conventions 及 ISO/IEC 标准

多租户与权限：RBAC 模型控制数据访问边界，租户间数据隔离

审计留痕：所有平台操作的审计日志，满足监管要求

数据分类分级：采集、传输、存储全程按敏感度分级管控

# 四、全链路追踪数据模型与语义约定

## 4.1Trace 与 Span 层次结构

一次完整的用户交互（一个 Session）对应一条 Trace。Trace 由一棵 Span 树构成，Span 之间的父子关系精确反映了 Agent 的执行时序与调用层次：

![](附件资源/智能体全链路可观测技术实现方案（甲方视角）/img_2.png)

每个 Span 必须携带以下核心属性：

• trace_id：全局唯一，贯穿整条链路

• span_id：当前 Span 唯一标识

• parent_id：父 Span ID（根 Span 为空）

• span_name：Span 名称（如 "agent.llm.chat-completion"）

• start_time / end_time / duration

• status_code：OK / ERROR

• attributes：领域特定属性（见 4.2 语义约定）

## 4.2语义约定扩展（基于 OpenTelemetry GenAI）

本方案的语义约定在 OpenTelemetry 官方 GenAI Semantic Conventions 基础上，结合行业需求进行了扩展。以下是关键属性的分类摘要：

| ** 类别 ** | ** OTel GenAI 原始属性 ** | ** 本方案扩展属性 ** |
| --- | --- | --- |
| LLM 调用 | gen_ai.system / request.model / prompt / completion / usage.prompt_tokens / usage.completion_tokens | gen_ai.request.temperature / top_p / max_tokens / safety_settings / reasoning_content |
| 工具调用 | gen_ai.tool.name / input / output | tool.category(api/search/db/file) / tool.privacy_level / tool.audit_required(bool) |
| RAG 检索 | gen_ai.retrieval.documents / similarity_score | rag.source_db / rag.knowledge_base_id / rag.retention_policy / rag.citation_format |
| 护栏/Guardrail | —（OTel 无） | guardrail.type(input/output) / guardrail.rules_matched / guardrail.action(block/allow/warn) / guardrail.reason |
| 评估 | —（OTel 无） | eval.factuality_score / relevance_score / compliance_score / eval.method(rule_based/model_based)  |
| 安全 | —（OTel 无） | sec.injection_detected / sec.pii_leakage / sec.unauthorized_access / sec.threat_type |
| 上下文传播 | trace_id / span_id / parent_id / baggage | baggage.tenant_id / user_id / session_id / policy_set_id / channel / data_sensitivity_level |

## 4.3上下文传播机制

为保证跨服务、跨模型、跨工具调用的链路串联，必须建立可靠的上下文传播(Context Propagation)机制：

传播载体：W3C Trace Context HTTP Headers（traceparent / tracestate）+ OpenTelemetry Baggage

传播路径：用户请求 → API Gateway → Agent 编排器 → LLM Service → Tool Service → RAG Service → 回传

Baggage 携带内容：tenant_id（租户）、user_id（用户）、session_id（会话）、policy_set_id（策略集）、channel（渠道）、data_sensitivity_level（数据分级）

关键工程要求：所有参与方（自研系统及第三方集成）必须透传上述 Header，不得丢弃。对于不支持 HTTP Header 透传的场景（如消息队列），需要在消息体中显式携带 context 字段。

# 六、数据处理与存储管道

## 6.1处理流水线详解

![](附件资源/智能体全链路可观测技术实现方案（甲方视角）/img_5.png)

图 6-1数据处理与存储管道处理管道采用"微批+流式"混合架构，各阶段职责如下：

**阶段 1 — 采集接入**

Collector 组件（OpenTelemetry Collector 或自研网关）接收 OTLP gRPC/HTTP 请求，支持批量接收与背压控制。数据暂存于 Kafka 缓冲队列，保证削峰填谷。

** 阶段 2 — 清洗标准化 **

• 字段校验：检查必填字段完整性，缺失字段标记警告

• 格式归一：时间戳统一 UTC、字符串编码 UTF-8、枚举值标准化

• 敏感数据处理：按数据分类分级策略执行脱敏（手机号掩码、身份证号哈希、卡号部分遮蔽）

**阶段 3 — 上下文富化**

通过 Join 外部数据源丰富可观测数据的业务含义：

• 关联租户表 → 补充组织层级、部门归属

• 关联用户表 → 补充用户角色、权限范围

• 关联策略配置 → 补充该场景适用的护栏规则集

• 关联资产目录 → 补充模型版本、知识库版本、工具版本

**阶段 4 — 质量评估（异步旁路） **

调用评估模型对 LLM 输出进行自动打分。评估方式分两种：

• 规则型评估：关键词匹配、格式校验、长度阈值等快速判断

• 模型型评估：调用轻量级 LLM-as-Judge 对事实性/相关性/合规性打分

评估结果写入 Eval Span 作为原 Trace 的子 Span，不影响主链路延迟。

** 阶段 5 — 安全评估（同步/近实时）**

安全检测引擎并行运行两类检测：

• 规则引擎：正则匹配已知注入模板、PII 模式、违禁词列表

• ML 模型：注入意图分类器（BERT/小模型）、DLP 分类器、行为异常检测，检测结果产生 Security Event，高置信度事件触发即时告警。

**阶段 6 — 聚合与索引 **

按信号类型分发至对应存储引擎，同时在内存中维护近期窗口的聚合指标（用于实时仪表盘）。

# 八、安全可观测专项设计

## 8.1安全信号全景

![](附件资源/智能体全链路可观测技术实现方案（甲方视角）/img_7.png)

图 8-1安全可观测专项：信号 → 检测 → 处置 → 闭环安全可观测聚焦智能体系统特有的安全风险面，分为三个观测截面：         ** 【输入侧安全信号】**

• 提示注入(Prompt Injection)：检测越狱指令、角色扮演劫持、指令覆盖攻击

• 越权指令：非授权用户试图让 Agent 执行超出其权限的操作（如查询他人账户）

• 探测行为：试探 Agent 能力边界（如询问系统 Prompt、测试过滤规则）

**【处理侧安全信号】**

• 工具滥用：高频调用敏感工具、构造恶意 SQL/API 参数

• 数据外发：Agent 将内部数据发送至不受信的外部地址

• 越权调用：Agent 以高于当前用户权限的身份调用后端服务

**【输出侧安全信号】**

• PII 泄露：输出中包含未脱敏的个人隐私信息（手机号、身份证、银行卡号）

• 违规内容：违反金融营销规定、不当承诺收益、歧视性表述

• 幻觉误导：编造不存在的产品条款、利率、政策信息（可能导致法律风险）

## 8.2检测引擎架构

安全检测采用"规则 + 模型双轨"架构，兼顾速度与准确性：

规则引擎（<10ms 响应）：

• 正则表达式匹配：已知注入模式（如"忽略以上指令"、"你现在扮演..."）、PII 模板（手机号/身份证/银行卡号正则）

• 关键词黑名单：违禁词表（金融行业特有：保本收益、稳赚不赔等）、敏感操作词

• 结构化约束检查：输出长度限制、JSON Schema 校验、允许的工具白名单

ML 模型（50-200ms，异步）：

• 注入意图分类器：基于 BERT/RoBERTa 微调的二分类模型，识别注入意图

• DLP 分类器：多标签分类，识别 PII 类型（姓名/电话/证件/账号/地址）

• 行为异常检测：基于用户历史行为基线的 Isolation Forest / LSTM 异常评分

两种检测的结果融合后输出综合风险分数（0-100），超过阈值的触发告警或阻断。

## 8.3闭环优化机制

安全可观测的价值不仅在于"看见"，更在于"持续变好"。闭环优化包含三条反馈回路：

回路 1 — 实时反馈至 Guardrail          检测到的攻击样本（含 payload 和判定结果）实时回流至输入/输出护栏的策略规则库，使同类攻击下次更快被拦截。

回路 2 — 周期性模型再训练          每周将新产生的标注样本（含误报/漏报的人工修正）加入训练集，重新训练注入分类器和 DLP 模型，发布新版本。

回路 3 — 策略中心迭代          安全运营团队基于月度安全报告，审视规则覆盖度与模型效果，调整检测策略（如新增规则、调整阈值、扩充训练数据）。所有策略变更有完整审计轨迹。

# 九、智能告警与闭环处置

## 9.1告警全生命周期

![](附件资源/智能体全链路可观测技术实现方案（甲方视角）/img_8.png)

图 9-1智能告警与闭环处置流程告警闭环涵盖七个阶段，形成 PDCA 循环：

①事件接入：来自采集层（异常 Span）、评估层（低分样本）、安全层（检测事件）、以及外部系统（监控系统、工单系统）的事件统一接入告警引擎。

② 实时检测与分级：基于预定义规则与动态基线进行实时检测，产出告警事件。告警分为四级：

• P0 致命：业务中断、数据泄露确认发生、重大安全事件 → 电话 + IM 立即通知 + 大屏闪烁

• P1 严重：安全事件疑似发生、核心功能不可用、质量严重劣化 → IM + 工单 + 15 分钟内响应

• P2 重要：质量轻微下降、非核心功能异常、趋势预警 → 工单 + 当日内响应

• P3 提示：容量接近上限、成本超预算、趋势值得关注 → 邮件日报 + 每周回顾

③ 通知路由：按告警等级 + 影响范围 + 值班表确定通知渠道与接收人。支持升级(Escalation)策略（如 P0 未确认 5 分钟自动升级至主管）。

④ 研判定位：值班人员利用 Trace Explorer 回放完整链路，结合 Metrics Dashboard 定位异常根因。安全事件还需在 SecOps Console 中查看攻击详情。

⑤ 处置执行：支持自动与手动两种方式。自动处置（如自动阻断可疑 IP、自动熔断超时接口）需提前审批预案；手动处置由值班人员操作并记录。

⑥ 复盘根因(RCA)：P0/P1 事件必须在 48 小时内完成 RCA 报告，分析根因、影响范围、改进措施。

⑦ 策略优化：RCA 结论转化为具体的规则调整、模型更新、流程改进，反馈至相应系统，关闭循环。

## 9.2闭环度量指标

| ** 指标 ** | ** 定义 ** | ** 目标值 ** | ** 计算方法 ** |
| --- | --- | --- | --- |
| MTTD 平均发现时间 | 从异常发生到告警触发的时间 | ≤ 5 分钟 | 告警时间戳 - 异常开始时间 |
| MTTR 平均修复时间 | 从告警触发的到恢复的时间 | ≤ 30 分钟 | 恢复确认时间 - 告警时间 |
| 误报率 | 误报数量 / 总告警数量 | ≤ 10% | 人工确认为误报的告警 / 总告警 |
| 自动处置率 | 自动处置告警 / 总告警 | ≥ 60%（P2/P3） | 自动执行完成的告警 / 总告警 |
| 复盘闭环率 | 完成 RCA 的 P0/P1 告警比例 | 100% | 已完成 RCA 的 P0+P1 / 总 P0+P1 |

| 业务 Owner | 各业务条线 | 业务场景定义、需求优先级、试点配合 | 各条线 0.2-0.5 FTE |
| 数据治理员 | 数据管理部 | 数据分类分级、隐私合规审核 | 1 人（兼职） |

## 12.2运营 SOP 要点

日常运营（Daily）：

值班人员查看告警面板，处理 P0/P1 告警（SLA: P0 5 分钟响应）

检查采集健康度（数据量是否异常下降、Collector 是否正常）

查看前一日 TOP 异常 Trace，快速研判

周度运营（Weekly）：

• 周例会：通报本周告警统计、处理情况、待跟进事项

• 质量报告审阅：本周评估分数趋势、低分案例分析

• 安全周报：攻击事件汇总、规则效果评估

月度运营（Monthly）：

• 月度运营报告（KPI 达标情况）

• 评估模型效果 review（准确率/召回率/F1）

• 成本报告（Token 消耗、API 费用、存储费用）

• 跨部门协调会（PMO 牵头）：进度同步、阻塞解决、下月计划

季度运营（Quarterly）：

• 季度汇报至 AI 治理委员会

• 策略与规则全面 Review

• 供应商/合作伙伴绩效评估

• 下季度规划与预算调整

# 十三、度量指标体系（KPI）

| 质量 | 评估覆盖率 | 经过自动评估的交互数 / 总交互数 | ≥80% | 周度 |

| 合规 | 审计日志留存达标率 | 留存 ≥180 天的审计日志占比 | 100% | 季度 |

## 13.2KPI 仪表盘设计

建议在平台首页构建 KPI Scorecard，采用红黄绿三色灯机制：

🟢 绿色：达标（≥ 目标值的 90%）

🟡 黄色：预警（目标的 70%-90%）

🔴 红色：不达标（< 目标值的 70%）

连续两个周期红灯的指标自动升级至 AI 治理委员会审议.
