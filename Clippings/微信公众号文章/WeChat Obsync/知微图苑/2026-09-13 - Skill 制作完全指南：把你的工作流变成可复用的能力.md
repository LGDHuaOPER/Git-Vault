# Skill 制作完全指南：把你的工作流变成可复用的能力

— 从0到1 · 实战手册 —

Skill 制作完全指南

把你的工作流变成可复用的能力

结构拆解 + 设计原则 + 完整示例 + 避坑指南 · 建议收藏

如果你已经用了一段时间的 AI 助手，大概会有这种感觉：有些事情每次做都要重新说一遍规则、重新给示例、重新确认格式——明明是同一件事，为什么不能「教一次，以后都这么干」？

Skill 就是干这个用的。

简单说，**Skill 是一套可复用的工作流指令包**。你把某一类任务的完整方法论、操作步骤、模板规范都写进去，以后再遇到同类任务，AI 自动加载这套方法，不用你每次重新讲。

这篇文章从最基础的「什么是 Skill」一直讲到「怎么设计一个高质量的 Skill」，附完整示例和常见坑。读完你就能自己动手做。

01

先搞懂：Skill 到底是什么

一个比喻

如果把 AI 助手比作一个新来的实习生，那 Skill 就是你给她的**岗位 SOP**。

没有 SOP 的实习生：每次做事情你都要从头教，做得时好时坏，全看你当天讲得清不清楚。

有 SOP 的实习生：拿到任务自动按流程来，质量稳定，你只需要在关键节点把关。

Skill 就是这个 SOP。它把「怎么做这件事」的全部知识沉淀下来，以后每次执行都调用同一套方法。

Skill 和 Prompt 的区别

很多人会问：Skill 不就是一个长一点的 System Prompt 吗？还真不是。

**核心区别：**

· **Prompt** 是「一次性指令」——这次对话用，下次就没了。你每次都得重新说。

· **Skill** 是「可注册的能力」——它有名字、有描述、有完整方法论，系统可以根据用户的请求自动判断「这件事该调用哪个 Skill」。

打个比方：Prompt 像你口头交代的任务，Skill 像公司里正式的岗位职责说明书。

Skill 的三个核心特征

**1. 可触发**——Skill 有明确的触发条件（写在 description 里）。系统会根据用户的请求，自动判断要不要调用、调用哪个。

**2. 可复用**——一次编写，反复使用。只要是同类任务，都可以用同一个 Skill 来保证输出质量的稳定性。

**3. 可积累**——Skill 是你个人/团队的知识沉淀。你踩过的坑、总结的方法、形成的规范，都可以写进 Skill 里，越用越好用。

02

Skill 的结构拆解

一个 Skill 其实非常简单，就一个文件：**SKILL.md**。

它的完整目录结构长这样：

.trae/skills/<skill-name>/
└── SKILL.md    ← Skill 的全部内容都在这里

就这一个文件。但里面的内容结构是有讲究的。

SKILL.md 的三段式结构

一个完整的 SKILL.md 由三部分组成：

**1. Frontmatter（头部元数据）**——name 和 description，是 Skill 的「身份证」
**2. 标题 + 一句话总纲**——Skill 是干什么的、核心方法论是什么
**3. 详细内容**——方法论、操作步骤、示例、注意事项等完整指南

第一部分：Frontmatter（最重要）

Frontmatter 是 SKILL.md 最顶部用 --- 包裹的部分，包含两个字段：**name** 和 **description**。

---
name: "wechat-mp-article"
description: "微信公众号推文创作。把一句话选题写成可直接粘进公众号后台的图文成稿——含内容方法论（10 类品类打法、去 AI 味、图文穿插）与粘贴兼容的行内样式排版，产出 HTML 预览稿。触发词：公众号 / 微信推文 / mp 图文 / 公众号排版 / 公众号发文 / 写推送 / 微信文章。"
---

这两个字段里，**description 是灵魂中的灵魂**。

为什么？因为系统判断「用户这个请求该不该调用这个 Skill」，主要靠的就是 description。它不仅要说明「这个 Skill 能干什么」，更要说明「**什么时候该用它**」。

**description 的黄金公式：**

**description = 功能描述 + 触发场景 + 触发关键词**

· 功能描述：这个 Skill 做什么事、产出什么
· 触发场景：在什么情况下应该调用它
· 触发关键词：用户可能说哪些词的时候触发

❌ 反面例子：「写公众号文章的 Skill」——太模糊，系统不知道什么时候该用

✅ 正面例子：「微信公众号推文创作。把一句话选题写成可直接粘进公众号后台的图文成稿。触发词：公众号 / 微信推文 / 公众号排版 / 写推送」

description 的长度控制在 200 字以内最好。太长了信息密度不够，太短了说不清楚触发条件。

第二部分：标题和总纲

Frontmatter 之后是正文。正文的第一部分应该是**一句话总纲**——用一句话说清楚这个 Skill 的核心方法论和最大价值。

比如公众号推文 Skill 的总纲是：「把一句话选题写成可直接粘进公众号后台的图文成稿——含内容方法论与粘贴兼容的行内样式排版。」

总纲的作用是「定调」。让 AI 在执行具体操作之前，先对这个 Skill 的定位和目标有一个整体认知。

第三部分：详细内容

这是 Skill 的主体，怎么写都行，但有几个建议：

**1. 分章节、有结构**——别写成一大段。用 ## 、 ### 分级标题，让 AI 能快速定位到相关章节。

**2. 有方法论也有示例**——光说原则不够，一定要给具体的例子。AI 对示例的理解能力远强于抽象描述。

**3. 明确边界**——不仅要说「该怎么做」，还要说「什么不能做」「什么时候不适用」。边界越清楚，AI 用得越准。

**4. 可以引用参考文件**——如果 Skill 内容很多，可以在 references/ 目录下放参考文档，在 SKILL.md 里索引引用。

03

怎么判断该不该做 Skill

不是每件事都值得做成 Skill。做一个好 Skill 要花时间，得先判断值不值得。

值得做 Skill 的三个信号

**信号一：重复度高**——这件事你已经做过三次以上了，每次做的流程都差不多。比如写周报、整理会议纪要、生成固定格式的报告。

**信号二：质量不稳定**——有时候做得好有时候做不好，全看当天 prompt 写得到不到位。这种情况最适合用 Skill 把最佳实践固化下来。

**信号三：有明确的方法论**——你对这件事已经有了自己的一套打法、步骤、判断标准。把这些沉淀成 Skill，比每次从零开始想效率高得多。

不值得做 Skill 的情况

**1. 一次性任务**——这件事只做一次，以后不会再做了。没必要花时间做 Skill。

**2. 每次都完全不一样**——没有固定流程、没有固定格式，每次都是全新的挑战。Skill 很难覆盖这种高变异性的任务。

**3. 太简单的事**——一两句话就能说清楚的 prompt，没必要做成 Skill。Skill 的 overhead 在那里，太简单的任务不值得。

**判断公式：**

**是否值得做 Skill = 重复频率 × 质量要求 × 复杂度**

三个都高，强烈建议做；两个高，可以做；只有一个高，算了吧。

04

实战：从零做一个 Skill

讲了这么多理论，我们来真刀真枪做一个。

目标：做一个**「周报生成器」** Skill——输入一周的工作记录，自动生成格式规范、重点突出的周报。

第一步：定义 Skill 的定位

动手写之前，先想清楚三件事：

1. **它解决什么问题？**——每次写周报都要花时间整理，格式不统一，重点不突出
2. **用户会怎么触发它？**——用户说「帮我写周报」「整理一下这周的工作」「生成周报」
3. **输出标准是什么？**——结构清晰、重点突出、数据量化、格式统一

第二步：写 Frontmatter

---
name: "weekly-report-generator"
description: "自动生成格式规范、重点突出的工作周报。输入一周工作记录，输出结构化周报（本周完成、下周计划、问题与风险）。触发词：周报 / 写周报 / 工作周报 / 周报生成 / 整理工作记录。"
---

检查一下：功能说了（生成周报）、触发场景说了（输入工作记录输出周报）、关键词也列了（周报/写周报/工作周报...）。合格。

第三步：写总纲和方法论

# 周报生成器

> **结构化输入 → 量化提炼 → 标准化输出 = 高质量周报。**

本 Skill 用于将零散的工作记录整理成格式规范、重点突出的工作周报。核心原则是：用数据说话、突出成果、明确计划、暴露风险。

第四步：写详细操作指南

这部分是 Skill 的核心，要写得越具体越好。下面是一个完整的示例：

## 1. 输入处理

当用户提供工作记录时，先做以下处理：

- 识别每条记录对应的工作类型（项目推进、日常事务、会议沟通、学习成长、其他）
- 提取关键数据（完成数量、耗时、进度百分比、涉及人员）
- 标注成果类事项和事务类事项

## 2. 输出结构

周报固定包含以下四个部分，顺序不可变：

### 2.1 本周完成
- 按项目/主题分组，每组下列具体事项
- 每条事项格式：「【成果/进展】具体描述 + （量化数据）」
- 重要成果放前面，日常事务放后面
- 不超过8条，超过的合并或降级

### 2.2 关键数据
- 用3-5个核心数据量化本周工作
- 数据包括但不限于：完成任务数、处理时长、参与项目数、产出文档数
- 每个数据配一句简短说明

### 2.3 下周计划
- 列出3-5项重点工作
- 每项说明预期产出和时间节点
- 按优先级排序

### 2.4 问题与风险
- 列出当前遇到的障碍、风险或需要协助的事项
- 每条说明：问题描述 + 影响范围 + 建议解决方案
- 没有就写「暂无」，不要编造

## 3. 写作原则

- 成果导向：多写「完成了什么」，少写「做了什么」
- 数据说话：能用数字的地方都用数字
- 简洁明了：每条不超过两行，能用短句不用长句
- 真实准确：只基于用户提供的信息，不编造、不夸大

## 4. 边界说明

- 如果用户提供的信息太少（少于3条记录），先请用户补充
- 如果信息中有不确定的地方，标注「待确认」而不是猜测
- 不替用户做计划，下周计划基于用户提到的待办事项整理
- 只处理工作相关内容，不涉及个人生活

第五步：加上完整示例

光有规则还不够，一定要给一个完整的「输入 → 输出」示例。AI 看例子学习的能力比看规则强得多。

## 5. 完整示例

【输入】
- 周一开始做用户调研问卷，设计了20个问题
- 周二和产品开了需求评审会，确定了V2.0的功能范围
- 周三周四写了数据分析报告，大概8000字，分析了用户行为数据
- 周五跟运营对齐了下个月的活动方案
- 学了一下新的数据可视化工具
- 服务器出了一次故障，花了半天排查

【输出】

# 第37周工作周报

## 一、本周完成

【项目产出】完成用户行为数据分析报告，覆盖5个核心指标，全文约8000字
【项目产出】完成用户调研问卷设计，共20个问题，覆盖使用习惯和满意度两大维度
【项目推进】参与V2.0需求评审，与产品团队确认功能范围和优先级
【协作沟通】与运营团队对齐下月活动方案，明确了活动目标和关键节点
【技术保障】排查服务器故障1次，耗时约4小时，已恢复正常
【学习成长】学习新型数据可视化工具的基础操作

## 二、关键数据

· 产出文档：2份（调研报告 + 数据分析报告）
· 参与会议：3场（需求评审、运营对齐、故障复盘）
· 处理故障：1次，恢复时长4小时
· 学习投入：约4小时

## 三、下周计划

1. 【高】发放用户调研问卷，目标回收200份以上
2. 【高】数据分析报告评审与修订
3. 【中】数据可视化工具实操练习，产出1个Demo
4. 【中】V2.0项目排期确认与任务拆解

## 四、问题与风险

· 服务器故障原因待深入排查，存在再次发生的风险，建议安排全面巡检

这样一个完整的 Skill 就做好了。虽然只是一个简单的例子，但该有的元素它都有：定位清晰、结构明确、有原则、有边界、有完整示例。

05

进阶：高质量 Skill 的七个设计原则

做好一个 Skill 不难，但做好一个**好用的** Skill，有一些设计原则。

原则一：单一职责

一个 Skill 只做一件事。不要试图做一个「万能写作 Skill」，什么都能写——这样的 Skill 什么都写不好。

正确的做法是拆分：公众号推文是一个 Skill，周报是一个 Skill，产品文档又是一个 Skill。每个 Skill 在自己的领域做到极致。

原则二：先定标准，再给方法

先说清楚「好的输出长什么样」（标准），再说「怎么达到这个标准」（方法）。

很多人写 Skill 一上来就讲步骤，但 AI 可能根本不知道你要的「好」是什么。先给靶心，再教射箭。

原则三：示例 > 规则

十句规则不如一个示例。能用示例说明的，就不要只用规则描述。

示例要完整、要具体、要覆盖典型场景。最好有正面示例也有反面示例，AI 对比着学，效果最好。

原则四：明确边界

好的 Skill 不仅要说「能做什么」，更要说「**不能做什么**」「什么时候不该用」「遇到什么情况应该停下来问人」。

边界越清晰，AI 越不会乱发挥。尤其是涉及事实准确性、用户隐私、重要决策的场景，边界条件是安全底线。

原则五：分层结构

内容分层次：核心原则 → 详细方法 → 操作示例 → 进阶技巧 → 常见问题。

AI 阅读 Skill 的时候，是根据需要来的。简单任务可能只看前几节就够了，复杂任务才会翻到进阶部分。分层结构让 Skill 既能快速上手，又有足够的深度。

原则六：可验证

Skill 的输出质量要能验证。最好有明确的检查清单：输出包含哪几个部分？每个部分有什么要求？格式对不对？

有了检查清单，不仅 AI 可以自查，你也可以快速判断输出是否合格。

原则七：持续迭代

Skill 不是一劳永逸的。用的过程中发现问题、积累经验，要及时更新到 Skill 里。

一个好 Skill 的成长路径：v1.0 能用 → v1.1 修了几个 bug → v2.0 加了新场景 → v3.0 形成完整方法论。每用一次，都是在给 Skill 积累素材。

06

常见坑点与避坑指南

坑一：description 写得太模糊

最常见的坑。description 只写了「这个 Skill 做什么」，没写「什么时候触发」。结果就是系统不知道什么时候该调用它，你的 Skill 形同虚设。

**避坑方法：**
description 里必须有触发关键词。格式参考：「做什么事。触发词：XXX / YYY / ZZZ。」

关键词要列全——用户可能用什么词表达这个需求，都列进去。宁可多列，不要漏列。

坑二：Skill 太泛，什么都想做

「写作大师 Skill」「效率工具 Skill」「全能助手 Skill」——这种大而全的 Skill，往往什么都做不好。

**避坑方法：**
宁可做深，不要做全。一个 Skill 解决一个具体问题。如果你有很多不同场景的需求，就做多个 Skill，每个在自己的领域做到极致。

判断标准：如果 Skill 的名字里有「全能」「综合」「大师」这类词，大概率是太泛了。

坑三：只有规则，没有示例

写了一大堆规则、原则、注意事项，但 AI 看了还是不知道具体怎么输出。因为规则是抽象的，AI 对抽象概念的理解能力远不如对具体示例的模仿能力。

**避坑方法：**
每个核心模块都配一个完整示例。复杂的场景配 2-3 个不同角度的示例。

示例要完整，不要只给片段。从输入到输出的全过程都展示出来，AI 才能完整理解你的要求。

坑四：没有边界，AI 乱发挥

只说了「该怎么做」，没说「什么不能做」。遇到输入信息不足、用户要求超出范围、涉及敏感内容的情况，AI 就会自己瞎编。

**避坑方法：**
在 Skill 里专门加一个「边界说明」章节，明确写出：
· 什么情况下不适用
· 信息不足时该怎么办（是请用户补充还是标注不确定）
· 涉及敏感/风险内容时的处理方式
· 绝对不能做的事情

坑五：一版定型，从不更新

Skill 写好就扔那了，用的时候发现各种问题也不改。用了半年还是 v1.0，问题越来越多，最后干脆不用了。

**避坑方法：**
把 Skill 当成一个活的文档，每次用完发现问题就记下来，定期更新。

建议的节奏：前一个月每周更新一次，稳定后每月 review 一次。每次更新都记一下改了什么、为什么改。这就是你自己的「Skill 版本日志」。

坑六：塞太多一次性内容

把某次具体任务的细节、临时数据、个人信息都写进 Skill 里。结果 Skill 变得又长又乱，AI 读取效率低，还可能泄露敏感信息。

**避坑方法：**
Skill 里只放**可复用的方法论**，不放具体任务数据。

· 不要放真实的人名、手机号、邮箱、内部链接
· 不要放某次任务的原始数据、输出结果、实验结论
· 示例用脱敏的、通用的内容，不要用真实案例的原文

记住：Skill 是「方法」，不是「数据」。

07

最后说几句

Skill 这个东西，说简单也简单——就一个 Markdown 文件而已。说难也难——要做好一个真正好用的 Skill，需要你对这件事本身有足够深的理解。

从这个角度说，**做 Skill 的过程，其实是把你自己的工作方法系统化的过程。**

你得想清楚：这件事的标准是什么？步骤是什么？常见坑点有哪些？什么情况下该怎么处理？——这些问题你想明白了，不仅 Skill 写好了，你自己对这件事的理解也上了一个台阶。

所以不要把做 Skill 当成「给 AI 写说明书」，把它当成「给自己的工作方法做一次系统化整理」。

想通了这一层，你做出来的 Skill，质量不会差。

**认知**：Skill = 可复用的工作流 SOP
**结构**：Frontmatter + 总纲 + 详细内容
**关键**：description 要写清触发条件和关键词
**设计**：单一职责 · 示例优先 · 明确边界 · 持续迭代
**避坑**：别太泛 · 别空泛 · 别不更 · 别塞敏感数据
