# 别再把可观测当监控了：AI时代，它正在成为软件工程的数据底座

不测商业报

BUSINESS INSIGHT DAILY

AI × 软件工程 × 可观测

**AI 时代的软件工程**

# 别再把 可观测 当监控了

AI Coding 和 Agent 正在让软件生产越来越快，但整个过程也越来越复杂、越来越难解释。可观测正在从 CPU、日志、Trace，扩展到需求、代码、测试、发布、业务和 AI 全过程。真正重要的，不是拥有更多 Dashboard，而是让整个软件生产系统始终**可看见、可理解、可度量、可追溯、可改进**。

你们公司可能已经有不少“可观测能力”了。

Prometheus、Grafana、ELK、APM、链路追踪、告警平台……Dashboard 越来越多，指标越来越全，告警也越来越及时。

但遇到一次真正复杂的线上问题，场面是不是依然很熟悉：**运维翻日志，开发查代码，测试找用例，产品确认业务影响，最后临时拉一个群，把相关的人全部叫进来。**

**大家手里都有数据，但没有人拥有完整答案。**

更值得关注的是，AI Coding 和 Agent 正在快速进入软件生产过程。代码产生得更快了，自动化程度更高了，但整个过程也可能变得更难解释。

当软件越来越自动地被生产出来，我们还能不能真正看懂它？

这可能才是今天重新讨论“可观测”的真正起点。

01

## 别再把可观测当监控了

先纠正一个最基本的认知：**可观测不等于监控。**

这里最常见的误判，是把可观测理解成“更高级的监控”。监控解决了真实问题，但它没有覆盖理解复杂系统所需的全部上下文。

监控更像是：**我已经知道应该关注什么，所以持续盯住它。** CPU 超过 90%，告警；磁盘空间不足，告警；接口响应超过 3 秒，告警；数据库连接数异常，告警。

这些当然重要，但它们主要回答的是：**What，发生了什么？**

可观测还要继续回答：为什么发生？从哪里开始？和哪一次变更有关？影响到了哪些业务和用户？为什么测试没有提前发现？以后怎样避免？

面对一个越来越复杂的软件系统，我们是否仍然拥有理解它的能力。

而且今天所谓的“系统”，已经不能只理解成生产环境。需求、设计、代码、Review、测试、构建、发布、运行、业务、用户，再加上 AI 和 Agent，共同组成了一个更庞大的**软件生产系统**。

02

## AI 越强，为什么反而越需要可观测？

AI Coding 最直观的变化，是代码生产速度提高了。过去几个小时完成的编码、测试、脚本工作，现在可能几十分钟就能完成。

但值得关注的不只是“快”，而是**软件生产方式本身正在变化。**

**过去：**需求 → 人编码 → 人 Review → 测试 → 发布

**现在：**人的意图 → AI 理解 → AI 生成 → Agent 调用工具 → 自动测试 → 自动修改 → Pipeline → 发布

人的角色开始从大量亲手执行，转向提出目标、定义约束、监督结果和处理例外。效率提高的同时，另一个问题正在被放大：**黑盒。**

当 AI 只是帮开发人员补几行代码时，这个问题并不明显。但当一个 Agent 可以连续执行几十个步骤，修改多个文件、调用多个工具、执行测试，甚至触发后续流程时，我们就必须回答：它做了什么？为什么这样做？使用了哪些上下文？结果是否符合原始需求？出了问题从哪里开始追？

AI 越自主，可观测越重要。

自动化解决的是“机器能不能做”。可观测解决的是“机器做完以后，我们是否仍然知道发生了什么”。

![图2 AI 解决生产速度，可观测守住理解控制与追溯](附件资源/别再把可观测当监控了：AI时代，它正在成为软件工程的数据底座/img_2.png)

图2｜AI 解决生产速度，可观测守住理解、控制与追溯还有一个变化容易被忽视。AI 正在让 Coding 越来越便宜、越来越快。当 Coding 不再是最大的瓶颈，Review、测试、验证、质量控制和风险识别会变得更重要。

这一节只记住一句话AI 负责扩大生产能力，可观测负责让这种能力始终可理解、可控制、可追溯。

03

## 可观测，到底应该观测什么？

如果可观测不再只是生产监控，它的边界就必须重新定义。过去，我们主要观察 Infrastructure、Application 和 Service。今天还要继续向软件生产链路两端延伸。

**需求：**为什么产生、发生过多少次变化、最终是否兑现价值。

**Coding：**修改了什么、风险在哪里、哪些代码由 AI 生成、产生多少返工。

**Review：**高风险变更是否被识别，Review 真正拦截了什么。

**Test：**哪些风险被验证，哪些缺陷被提前发现，哪些问题逃逸到线上。

**Build / Deploy：**构建为什么慢、为什么失败、哪个版本何时发布、包含哪些变更。

**Runtime：**Metrics、Logs、Traces、Events、APM。

**Business / User：**核心交易是否成功、多少用户受影响、真实体验怎样。

**AI / Agent：**Prompt、Model、Context、Tool Call、Token、Eval、Cost、Risk。

![图3 观测对象扩展到软件生产运行和使用全过程](附件资源/别再把可观测当监控了：AI时代，它正在成为软件工程的数据底座/img_3.png)

图3｜观测对象从运行中的软件，扩展到软件生产、运行和使用的全过程回头再看 CPU、内存、日志和 Trace，会发现它们依然重要，但只是整个软件生产系统中的一部分。

记住一句话未来要观测的，不只是运行中的软件，而是软件被生产、运行和使用的全过程。

04

## 为什么工具这么多，出了问题还是要拉群？

需求系统有数据，Git 有数据，CI/CD 有数据，测试平台、APM、日志平台、监控平台和业务系统也都有数据。看起来什么都不缺。

但一次复杂故障发生以后，大家仍然在拉群、截图、发日志、问版本、找负责人。原因往往很简单：**我们缺的不是数据，而是数据之间的关系。**

假设某天用户反馈支付失败。运维查到 Payment Service 响应超时；继续追查，发现两小时前刚发布 Version 3.2.1；这个版本包含 Commit #827，来自 MR #456；MR 修改了一段支付逻辑，其中部分代码由 AI Coding 生成；自动化测试虽然通过，却没有覆盖这个特殊支付场景；继续向前追，最终对应到 Requirement #126 的一次支付流程修改。

Requirement → Code → Review → Test → Deploy → Runtime → Business → User

一个孤立的“用户支付失败”，因此变成了一条完整链路。你不只知道哪里坏了，还能继续追问为什么坏、从哪里开始、为什么没有提前发现、最终影响到了谁。

![图4 完整上下文让人和AI理解问题](附件资源/别再把可观测当监控了：AI时代，它正在成为软件工程的数据底座/img_4.png)

图4｜完整上下文让人和 AI 都有机会真正理解问题Metrics、Logs、Traces 很重要，但 Requirement、Commit、MR、Test、Deployment、Incident 和 Business 之间的关系，可能更重要。

### 你的可观测真的成熟吗？

拿“支付失败”这个最普通的问题，问自己 5 个问题：

- 用户反馈“支付失败”后，5 分钟内能不能定位到具体服务？
- 能不能继续定位到具体 Deployment 和 Commit？
- 能不能知道这次修改对应哪个 MR 和需求？
- 能不能解释为什么 Review 和 Test 没有提前拦住？
- 能不能知道最终影响了多少用户、交易和业务？

如果回答这 5 个问题，需要 5 个团队、10 个平台和 1 个临时群，你们可能已经拥有很多监控工具，但距离一套真正完整的可观测体系，还有一段距离。

记住一句话数据数量不是壁垒，数据之间的关系才是。

05

## 看见以后，怎么判断到底“好不好”？

有数据，不代表能管理。比如 Pipeline 平均 30 分钟。30 分钟到底好不好？单看这个数字，没有答案。

你还需要知道过去是多少、目标是多少、最近是在改善还是恶化、慢在哪里、有没有影响最终交付。

Object → Signal → Metric → Baseline → Target / SLO → Trend → Improvement

先明确要衡量什么，再找到能够代表它的信号，把信号转成可计算的指标，建立当前基线，定义目标，持续观察趋势，最终形成改进。

![图5 看见不等于衡量](附件资源/别再把可观测当监控了：AI时代，它正在成为软件工程的数据底座/img_5.png)

图5｜看见不等于衡量，衡量要能推动下一步动作研发效能回答快不快，质量工程回答好不好，稳定性回答稳不稳，业务体验回答有没有产生价值，AI 工程回答 AI 到底行不行。

但这里很容易进入另一个误区：指标越来越多，Dashboard 越来越多，最后真正每天有人看的，也许只有几个。

这个指标发生变化以后，我们知道应该做什么吗？

如果答案是不知道，这个指标很可能只是报表。真正有价值的指标应该完成：**发现差距、触发行动、验证改善。**

记住一句话不能驱动行动的指标，大概率只是报表。

06

## 可观测，到底是谁的事情？

如果可观测只被运维使用，它的价值其实只发挥了一部分。

**研发**哪里慢、哪里堵，AI Coding 到底提高了效率，还是把时间转移到了 Review 和返工？

**质量**缺陷从哪里产生，为什么没有被提前拦住，哪些模块长期是缺陷热点？

**SRE / 运维**哪个变更导致了故障，影响范围多大，怎样更快恢复？

**产品 / 业务**一个技术问题到底影响了多少用户和交易？

**AI 团队**AI 提高了多少生产力，任务成功率和成本怎样，有没有新的安全风险？

**管理者**研发、质量、稳定性和 AI 的投入，最终有没有产生真实改善？

当这些数据真正串起来以后，AIOps 和 Agent 才有可能进一步做到自动发现异常、自动关联证据、辅助诊断、生成处置方案，甚至执行部分低风险操作。

![图6 可观测从部门工具走向共同基础能力](附件资源/别再把可观测当监控了：AI时代，它正在成为软件工程的数据底座/img_6.png)

图6｜从一个部门的工具，走向软件工程体系的共同基础能力研发、质量、运维、业务和 AI 共同使用的软件工程数据底座。

记住一句话可观测不是某一个部门的工具，而是整个软件工程体系的共同基础能力。

07

## Dashboard 越多，可观测能力就越强吗？

不一定。如果企业已经有几十块大屏、上万个指标和非常丰富的监控平台，但事故发生以后，处理方式依然是“告警 → 看 Dashboard → 翻日志 → 找开发 → 拉群 → 人工判断 → 人工处理”，我们只是把“看见”做得越来越强，并没有改变解决问题的方式。

AI 时代更值得期待的是另一条路径：

Observe → Diagnose → Decide → Act → Verify → Learn

完整获取状态和上下文，关联需求、代码、测试、发布、运行和业务数据，形成方案，在人的确认或明确安全边界内执行，再用技术与业务指标验证是否真正恢复，最后把事件、原因、方案和结果沉淀下来。

![图7 从看见走向自治](附件资源/别再把可观测当监控了：AI时代，它正在成为软件工程的数据底座/img_7.png)

图7｜可观测要进入行动和学习，才算形成真正的闭环AI 自治的第一步，可能不是 Agent，而是 Observability。

AI 如果没有可靠的“眼睛”，就没有可靠的上下文；没有可靠的上下文，就很难可靠诊断；不能可靠诊断，也就更谈不上把执行权交给 Agent。

**Monitoring** 主要解决 What，发生了什么；**Observability** 进一步解决 Why，为什么发生；**AI + Agent** 才有机会继续解决 How & Better，怎么处理，以及怎样让下一次不再发生。

记住一句话可观测的终点不是 Dashboard，而是闭环。

08

## 如果现在就开始做，第一步是什么？

讲到这里，很容易走向另一个极端：既然可观测这么重要，那就规划一个“统一智能可观测平台”，然后定架构、选平台、建指标体系、做大屏、做数据湖，最后项目越来越大。

不要先从“大平台”开始。
从一个真实问题开始。

选一条最重要的业务链路，比如支付。先把生产侧打通：

User → Business → Service → DB → Infrastructure

让用户出了问题时，可以一路看到业务和技术。

再继续向研发侧追：

Runtime → Deploy → Test → Code → Requirement

让线上问题继续追到哪个版本、哪次提交、哪次测试、哪个需求。

然后只选择一组真正关键的指标，例如业务成功率、P95 响应时间、Error Rate、Change Failure Rate、MTTR、缺陷逃逸率。不要贪多。

接下来，不要做 Demo，直接拿最近一次真实事故验证：**能不能从用户问题一路追到根因？**如果不能，补关联；如果能，再让 AI 读取这些上下文，开始辅助关联、总结、诊断和推荐。最后，才逐渐把低风险、高频、高确定性、可回滚的动作交给 Agent。

企业真正可以照着做的路径

一条链路 → 一组指标 → 一次事故 → 一个闭环 → 再复制

先把第一条链路真正做透，再复制到第二条、第三条。
**先看见 → 再串联 → 再衡量 → 再诊断 → 再自动化 → 最后自治。**

记住一句话不要先做大平台，先用一条链路跑通一个闭环。

## AI 越会写代码，“理解软件”可能越值钱

过去的软件工程，一个很大的瓶颈是代码写得不够快。AI 正在快速改变这件事。Coding 变得越来越便宜、越来越快，甚至越来越自动化。

但当代码可以以过去几倍、十几倍的速度产生以后，一个新的问题会越来越突出：**我们还能不能理解这些快速生产出来的软件？**谁改了它？为什么改？AI 参与了什么？有没有被验证？什么时候上线？影响了什么？为什么出了问题？下一次如何避免？

让一个越来越复杂、越来越自动化的软件系统，始终保持可理解、可验证、可控制的能力。

这也是为什么，今天有必要重新理解一次可观测。它正在从运维监控工具走向软件工程数据底座。再向前一步，它甚至可能成为 AI 理解整个软件系统最重要的感知层。

**看不见，就无法理解。无法理解，就很难可靠判断。无法可靠判断，就不应该轻易执行。**

真正值得期待的，不是未来拥有更多 Dashboard，而是整个软件生产系统逐渐拥有观察自己、理解自己、修正自己、持续学习的能力。

先看见。再理解。再行动。最后形成闭环。

**这可能才是 AI 时代，可观测真正值得重新被定义的原因。**
