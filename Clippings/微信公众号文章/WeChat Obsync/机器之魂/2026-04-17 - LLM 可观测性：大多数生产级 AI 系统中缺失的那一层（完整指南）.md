# LLM 可观测性：大多数生产级 AI 系统中缺失的那一层（完整指南）

> 字数 5075，阅读大约需 23 分钟

#

## ![](附件资源/LLM%20可观测性：大多数生产级%20AI%20系统中缺失的那一层（完整指南）/img_1.jpg)

你上线了自己的 LLM 应用。测试阶段运行正常。用户开始使用了。

两周后，有人提交了一个 bug。应用返回了错误答案。

你去检查发生了什么。没有日志，没有发送的 prompt 记录，没有模型收到的内容记录，没有检索器从知识库中拉取的相关片段记录。

**你在盲目调试。**

这并不是边缘场景。这是大多数在没有可观测性的情况下部署 LLM 应用的团队所面临的默认状态。传统软件日志只能告诉你某个事件发生了。

**LLM 可观测性告诉你模型看到了什么、收到了什么、以及为什么会以这种方式响应。**

没有它，你自己的应用对你来说就是一个黑箱。

### 为什么 LLM 需要不同类型的监控

![](附件资源/LLM%20可观测性：大多数生产级%20AI%20系统中缺失的那一层（完整指南）/img_2.jpg)

**标准应用监控覆盖三个方面的内容：**

- • 指标、日志和错误
- • 对于 LLM 来说，这三者遗漏了最重要的故障模式

普通的 Web 服务器要么返回 200，要么不返回。LLM 调用返回 200，但仍可能完全错误。

**模型用流畅、自信但错误的文本进行了响应。你的错误率显示为零。你的状态页面显示为绿色。**

但你的用户得到了一个糟糕的答案。

**LLM 可观测性增加了传统监控所跳过的内容：对请求内部的可见性。**

**这意味着需要追踪：**

- • 发送的 prompt 是什么，包括系统消息和注入的上下文
- • 检索器获取了哪些文档，以及它们与查询的相似度如何
- • 模型返回了什么
- • 每次调用的 token 数量和成本
- • 每个步骤的延迟，而不仅仅是端到端的延迟
- • 输出是否达到质量标准，通过自动化评估器或人工审核

**没有这些信息，你无法调试质量问题。没有基准分数进行比较，你无法知道 prompt 的更改是改善还是损害了效果。你无法在账单出现之前就发现成本飙升。**

### 术语表：可观测性系统实际追踪什么

这里的术语在 LangSmith、Langfuse 和 Arize Phoenix 中保持一致。学一次就够了。

![](附件资源/LLM%20可观测性：大多数生产级%20AI%20系统中缺失的那一层（完整指南）/img_3.jpg)

### Run（运行）

**一次 _run_ 是一个独立的工作单元。一次 LLM 调用就是一次运行。**

- • 一次检索步骤就是一次运行
- • 一次格式化 prompt 的函数调用就是一次运行

如果你使用过 OpenTelemetry 或 Jaeger 等工具中的分布式追踪，run 就相当于 span。

**每次运行都会捕获：** 输入、输出、开始时间、结束时间以及你附加的任何元数据。

LangSmith 和 Langfuse 都支持 OTLP（OpenTelemetry 协议）导出，因此如果你的基础设施已经运行 OpenTelemetry，你可以将 LLM 追踪数据传送到 Datadog、Grafana 或你现有的可观测性堆栈中，而无需添加单独的仪表板。

### Trace（追踪）

**一条 _trace_ 是一条完整用户请求的记录。**

它是由共享 trace ID 关联的多次运行的集合。在 RAG 应用中，单条追踪包含检索运行、prompt 构建步骤和 LLM 调用，按顺序排列。

可以把 trace 想象成收据。一个请求中发生的所有事情，都按顺序记录在上面。

### Thread（会话线程）

**一个 _thread_ 将多轮对话的追踪分组。**

每一轮都会产生自己的追踪，但它们通过共享标识符关联。LangSmith 通过运行元数据中的特殊键来识别： `session_id、`  `thread_id`  或  `conversation_id` 。

对于聊天机器人，线程让你能够看到完整的对话，而不是孤立的单轮交互。

### Project（项目）

**一个 _project_ 是追踪的容器，通常每个应用或环境一个。** 为  `rag-production、`  `rag-staging`  和  `rag-dev`  设置独立的项目可以保持监控的整洁，并让你能够比较不同环境之间的质量。

### Feedback（反馈）

**Feedback 是附加到某次运行的分数。** 它可以来自用户（连接到 API 调用的点赞或点踩按钮）、自动化 LLM-as-judge 评估器，或通过标注队列工作的人工审核员。每个反馈条目都有一个键（如  `user-score`  或  `groundedness` ）以及一个数值或分类值。

反馈将追踪从被动日志记录转变为质量测量系统。

### 元数据和标签

**元数据是在调用时附加到运行的键值对：**

```
{"llm": "gpt-4o-mini", "user_id": "abc123", "app_version": "2.4", "variant": "B"}
```

标签是用于过滤的扁平字符串标签。两者都让你可以在之后切片你的追踪历史：显示版本 2.4 的所有追踪，或显示用户为 abc123 的所有追踪。

记录元数据的成本为零。

**不记录它意味着当出现问题时，你无法分组、比较或诊断。**

### 没有可观测性时 LLM 应用会在哪里出问题

![](附件资源/LLM%20可观测性：大多数生产级%20AI%20系统中缺失的那一层（完整指南）/img_4.jpg)

本节是关注上述所有概念的原因。这些是只有追踪级可见性才能捕获的特定故障模式。

**Prompt 漂移。** 你在六周前修改了一个 prompt。从那以后，一类查询一直在返回质量较低的答案。如果没有逐条追踪的 prompt 日志记录，你无法知道在质量开始下降时哪个版本的 prompt 是线上的。你只能看到输出，却看不到产生这些输出的输入。

**静默检索失败。** 向量搜索可能在不抛出任何错误的情况下返回错误结果。检索器获取了与查询共享词汇但并未回答查询的片段。模型读取这些片段并产生一个听起来合理但错误的响应。没有异常触发。你的错误率保持为零。

以下是实际表现。用户问："LangSmith 评估是如何工作的？"

检索器获取的内容：

```
Chunk 1: LangChain 智能体概述
Chunk 2: 嵌入介绍
Chunk 3: 通用 LLM 评估指标
```

这些都没有解释 LangSmith 实际的评估 API。模型仍然读取并回答了。请求返回 HTTP 200。没有警报触发。

有了追踪，你可以看到确切的片段、它们的相似度分数、发送的 prompt 和输出。你在三十秒内就知道问题出在检索器而非模型。没有追踪，你只能猜测。

- • 隐性成本增长。 Token 数量因 prompt 长度、检索上下文大小和输出长度而异。一次 prompt 更改每请求增加 200 个 token 听起来很小。在每天 10,000 次查询和 GPT-4o 定价的情况下，这大约是每天 10 到 20 美元，即每月额外增加 300 到 600 美元，仅来自一次修改。如果没有逐请求的 token 日志记录，你只能在账单上发现这个问题。
- • 仅影响特定查询类型的延迟。 所有查询的平均延迟可能看起来没问题。但有一类查询总是需要 8 秒。如果没有追踪中的步骤级延迟，你无法判断瓶颈是来自检索器、prompt 构建还是模型调用。每一项都有不同的解决方法。
- • 智能体循环。 在智能体系统中，如果退出条件没有正确触发，智能体可以无限循环调用工具。请求最终会超时。你的日志只显示一个超时错误。它们不会显示在此之前运行的 11 次工具调用、每次返回的内容，或哪个步骤触发了循环。

### 设置可观测性：从零到生产

需要实现两个层面：追踪（发生了什么）和评估（质量如何）。

### 环境设置

```
pip install langsmith openai
export LANGSMITH_TRACING=true
export LANGSMITH_API_KEY="your-langsmith-api-key"
export OPENAI_API_KEY="your-openai-api-key"
```

在 smith.langchain.com/settings 获取你的 LangSmith API key。追踪会发送到名为  `default`  的项目，除非你将  `LANGSMITH_PROJECT`  设置为特定名称。

### 步骤 1：包装 LLM 客户端

一个导入，一行代码更改。这是最低可行起点。

```
from openai import OpenAI
from langsmith.wrappers import wrap_openai
client = wrap_openai(OpenAI())
# 每次 client.chat.completions.create() 调用现在都会自动被追踪
```

这会记录每次 LLM 调用：发送给模型的完整消息列表、响应、模型名称、token 数量和延迟。目前还不需要在其他地方添加装饰器。

### 步骤 2：追踪完整管道

包装客户端只能捕获 LLM 调用，而不能捕获检索步骤或 prompt 构建。使用  `@traceable`  来包装整个管道函数。

```
from openai import OpenAI
from langsmith.wrappers import wrap_openai
from langsmith import traceable

client = wrap_openai(OpenAI())
@traceable
def rag(question: str) -> dict:
docs = retriever(question)
system_message = (
"仅使用以下信息回答：\n" + "\n".join(docs)
)
resp = client.chat.completions.create(
model="gpt-4.1-mini",
messages=[
{"role": "system", "content": system_message},
{"role": "user", "content": question},
],
)
return {"answer": resp.choices[0].message.content, "documents": docs}
```

**现在一条追踪显示：** 收到的输入问题、检索器获取的文档、构建的完整 prompt，以及模型返回的内容。

**返回文档以及答案。** 如果你之后想运行 groundedness 评估，这是必需的。如果你的函数只返回一个字符串，你就无法检查答案是否实际被检索到的上下文所支持。

### 步骤 3：记录元数据和运行 ID

```
from langsmith import traceable, Client
from langsmith import uuid7

ls_client = Client()
@traceable(metadata={"llm": "gpt-4.1-mini", "app_version": "2.4"})
def rag(question: str, user_id: str) -> dict:
...
```

对于动态元数据（如在装饰时未知的用户 ID），使用  `langsmith_extra`  在调用时传递：

```
run_id = str(uuid7())
result = rag(
question,
langsmith_extra={
"run_id": run_id,
"metadata": {"user_id": user_id}
}
)
```

存储这个  `run_id` 。你需要它来将用户反馈附加到特定的运行。

### 步骤 4：捕获用户反馈

```
ls_client.create_feedback(
run_id,
key="user-score",
score=1.0,   # 1.0 = 点赞, 0.0 = 点踩
)
```

将其连接到你的应用使用的任何 UI 反馈机制。即使是一个简单的点赞或点踩也能告诉你用户认为哪些查询有用、哪些没有。一旦有足够的量，这个信号就很有价值。

### 步骤 5：将检索器作为独立运行分离出来

用  `run_type="retriever"`  标记检索器，这样 LangSmith 就知道将其作为独立的追踪组件处理，使追踪结构更容易检查。

```
@traceable(run_type="retriever")
def retriever(query: str) -> list[str]:
# 你的向量搜索逻辑在这里
return results
```

现在追踪将检索步骤和 LLM 步骤显示为顶级  `rag`  追踪下的兄弟运行。你可以看到检索器的输入、输出和延迟，独立于模型调用。

### 层面 2：评估

追踪告诉你发生了什么。评估告诉你质量如何。

**离线评估** 在部署前运行。建立包含 20 到 50 个代表性查询及其参考答案的数据集，对你的管道进行评分，并记录这些基准数字。之后对 prompt、模型或检索策略的每次更改都会在与该基准进行比较后再发布。

**在线评估** 自动对真实生产流量样本进行评分。对每个请求运行评估器成本很高。10% 的随机样本足以捕捉质量趋势。对于大多数团队，即使在大规模下使用 5% 也足够了。

**RAG 应用值得追踪的四个指标：**

| 指标 | 测量内容 | 需要参考答案？ |
| --- | --- | --- |
| 正确性 | 答案在事实层面是否正确？ | 是 |
| 依据性 | 答案是否被检索到的文档所支持？ | 否 |
| 答案相关性 | 答案是否回答了所提的问题？ | 否 |
| 检索相关性 | 检索器是否返回了有用的片段？ | 否 |

依据性和检索相关性不需要精心策划的参考答案。在每个生产请求上运行它们，而无需数据集。

### 生产环境中真正重要的是什么

一旦有了流量，几个特定实践会将保持质量领先的团队与被动应对用户投诉的团队区分开来。

**采样评估，不要对所有内容运行。** LLM-as-judge 评估器消耗 token。10% 的随机样本让你以一小部分成本获得统计信号。对于非常高吞吐量的端点，1% 通常足以捕捉趋势。

**在每次调用上设置  `max_tokens` 。** 无上限的输出长度直接增加成本和延迟。如果你的应用通常需要 300 个 token，将上限设为 400 或 500。截断响应的成本低于在大规模时失控输出峰值带来的成本。

**使用元数据进行 A/B 测试。** 测试两个 prompt 版本？在元数据中用  `{"variant": "A"}`  或  `{"variant": "B"}`  标记运行。LangSmith 的监控选项卡允许你按任何元数据键对图表进行分组，并在真实流量上比较变体之间的质量分数、延迟和 token 使用量。

**将检索质量和生成质量作为独立信号追踪。** 答案质量下降可能来自检索器或 LLM。如果你只测量最终答案质量，你就无法判断是哪一层出了问题。将检索相关性和依据性作为独立指标可以让你立即知道该往哪里看。

**在上线前配置这四个警报：**

- • 依据性分数跌破你的离线基准
- • p95 延迟超过你的响应时间目标
- • 日 token 成本超过你的预算阈值
- • 任何端点的错误率上升超过 2%

**在上线前构建你的评估数据集。** 几乎没人这么做。一旦上线，时间更少，压力更大。在上线前留出一天时间来策划 20 到 50 个带有预期答案的查询。获得基准分数。每次未来部署都与这些数字竞争。

**LangSmith 在其 SaaS 层保留追踪 400 天。** 对于缓慢退化的问题（如 prompt 漂移或检索新鲜度衰减），你需要足够的历史数据来观察趋势。如果某条追踪包含重要内容，在其过期之前将其添加到数据集中。LangSmith 中的数据集永久保留。

### 决策矩阵：每个阶段应设置什么

![](附件资源/LLM%20可观测性：大多数生产级%20AI%20系统中缺失的那一层（完整指南）/img_5.png)

**最低可行设置是：** 包装 LLM 客户端、追踪完整管道、从管道函数返回结构化输出、记录每次请求的运行 ID，并连接用户反馈。这不到一天的工作量，却能给你足够的可见性来调试任何问题。

### 选择工具

四个主要选项并非可互换的。

**LangSmith** 覆盖完整技术栈：追踪、评估、数据集管理、prompt 版本控制和生产监控，全部在一处。免费版可用。适用于任何 LLM 提供商，不仅限于 LangChain。如果你想用一个工具处理完整的可观测性生命周期，这对大多数团队来说是实用的默认选择。

**Langfuse** 是开源的，可以完全自托管。如果你的数据必须留在你的基础设施内，这是正确的选择。追踪和评估的功能覆盖与 LangSmith 接近。自己运行需要更多设置，但可以完全控制数据存储位置。

**Arize Phoenix** 为大规模的生产监控和质量漂移检测而构建。更适合对大量追踪数据进行持续统计分析而非逐请求调试的团队。开源。

**Helicone** 作为代理位于你的 LLM API 调用前面。只需最少的代码更改。适合那些在深度可观测性投资之前首要任务是成本可见性和基本调用日志记录的团队。

选一个。LangSmith 或 Langfuse 是大多数构建 RAG 或智能体应用的团队的正确起点。

### 从哪里开始

如果你今天什么都没有，按照这个顺序很重要。

- 1. 包装 LLM 客户端。十分钟的工作。让你立即了解每次模型调用。
- 2. 将 @traceable 添加到你的主管道函数。再花十分钟。让你获得完整请求追踪。
- 3. 从管道返回结构化输出。这是 groundedness 评估所必需的。
- 4. 记录每次请求的运行 ID 并将用户反馈连接到 create_feedback 。这是质量追踪所必需的。
- 5. 构建你的评估数据集。在下次部署之前做这个，而不是之后。

每个步骤都建立在前一个之上。你不需要一次完成所有五个，但每一个都比前一个显著更好。

原型和生产级 LLM 系统之间的区别不是你选择的模型。而是你能否在系统失败时看到它在做什么。

### 总结

**LLM 系统引入了一种新型故障：** 系统看起来健康，却产生了错误的答案。

你的仪表板显示零错误。你的 API 返回 200。模型生成流畅的文本。一切看起来都很好，直到用户指出答案是错误的。

系统健康和答案质量之间的差距就是大多数 LLM 应用挣扎的地方。

可观测性弥合了那个差距。追踪揭示了模型看到了什么上下文、prompt 是如何构建的、哪些文档被检索到、以及响应是如何生成的。评估增加了缺失的信号：输出实际上是好是坏。

一旦你有了这种可见性，调试就不再是猜测了。

构建可靠 LLM 产品的团队不是那些实验最多模型的团队。他们是能够准确解释每个请求期间发生了什么的人。
