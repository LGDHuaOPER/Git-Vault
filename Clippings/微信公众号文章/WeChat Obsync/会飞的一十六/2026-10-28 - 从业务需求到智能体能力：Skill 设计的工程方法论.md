# 从业务需求到智能体能力：Skill 设计的工程方法论

![](附件资源/从业务需求到智能体能力：Skill%20设计的工程方法论/img_1.png)

## 引言

在智能体（Agent）工程实践中，一个常见的误区是把 Skill 当作"功能模块"来开发——定义接口、编写逻辑、调通测试，流程看似与开发一个 API 无异。然而，当 Skill 真正被智能体调用时，问题往往集中爆发：触发时机不对、决策逻辑混乱、输出格式不可控、改一处动全身。

根本原因在于：**Skill 不是"做"出来的，是从业务需求里"长"出来的。** 先想清楚业务要解决什么问题，Skill 的形态才会自然浮现。

本文从工程视角出发，系统阐述如何把一个模糊的业务需求，转化为一套可运行、可复用、可迭代的 Skill 体系。

## 一、Skill 的本质定义

### 1.1 什么是 Skill

Skill 是智能体的一项**可被自主调度的能力单元**。用户提出任务后，智能体判断该调用哪个 Skill、何时调用、如何组合调用，最终将结果返回用户。

它与普通功能的核心区别在于**调度主体不同**：

| 维度 | 普通功能 | Skill |
| --- | --- | --- |
| 触发方式 | 用户主动点击/调用 | 智能体自主判断 |
| 调用时机 | 确定性 | 上下文依赖 |
| 组合方式 | 用户手动编排 | 智能体动态编排 |
| 容错要求 | 用户可见错误提示 | 需内置降级与兜底逻辑 |

### 1.2 通用 Skill 与业务 Skill

并非所有 Skill 的设计难度相同。需要明确区分两类：

![](附件资源/从业务需求到智能体能力：Skill%20设计的工程方法论/img_2.png)

**通用 Skill**（如查天气、做翻译）：

- 能力单一，输入输出明确
- 不依赖具体业务上下文
- 一次开发，跨场景复用
- 容错标准："差不多就行"

**业务 Skill**（如通话录音分析、合同风险审查）：

- 是一套完整的 决策流程 ，而非单点能力
- 深度耦合业务规则与领域知识
- 每个判断必须回答"依据是什么"
- 容错标准："证据不足宁可留空，不能硬填"

> 真正的设计难点，集中在业务 Skill。以下方法论均围绕业务 Skill 展开。

## 二、业务 Skill 的三大设计约束

在动手设计之前，必须理解业务 Skill 区别于通用 Skill 的三个本质约束。这三个约束决定了后续所有架构决策。

### 约束一：它是决策流程，不是单点能力

业务 Skill 内部往往包含多步判断，且判断之间存在**依赖、互斥、前置**关系。

例如，在通话录音分析场景中：

- 客户说"我想了解一下"→ 需判断是咨询、比价还是真实意向
- 客户说"我考虑一下"→ 需判断是同意回访还是委婉拒绝

这些判断不能靠"调一个接口"解决，必须设计明确的**决策树**：先判断什么、再判断什么、什么条件下中止、什么条件下追问。

### 约束二：它提供框架，不提供答案

业务数据是动态的。今天有效的价格，下个月可能变动；A 客户和 B 客户的商品体系完全不同。

设计原则：**Skill 负责"怎么查"，业务方负责"查什么"。**

![](附件资源/从业务需求到智能体能力：Skill%20设计的工程方法论/img_3.png)

```
这样做的好处：数据变了改数据层，Skill 不用动；Skill 升级不影响业务数据维护。
```

### 约束三：每个结论必须有证据链

通用 Skill 的输出可以是一个简单结果（如"今天 25°C"）。业务 Skill 的输出，每一个判断都必须附带**可追溯的证据**。

![](附件资源/从业务需求到智能体能力：Skill%20设计的工程方法论/img_4.png)

**设计规则**：

- 坐席自己的介绍，不能作为客户意向的证据
- 同一事实不能重复计分
- 证据不足时，对应字段留空，禁止推断填充
- 输出中必须包含  `evidence`  字段，标注判断来源

## 三、六步设计方法论

将一个业务需求转化为可落地的 Skill，建议遵循以下六步。每一步都有明确的输入、动作和产出物。

![](附件资源/从业务需求到智能体能力：Skill%20设计的工程方法论/img_5.png)

### Step 1：定义问题域

**目标**：在写任何代码之前，产出"领域蓝图"。

**必须回答的问题清单**：

| 问题 | 说明 |
| --- | --- |
| 谁在用？ | 用户角色（坐席、主管、质检员） |
| 什么场景？ | 实时辅助、事后分析、批量质检 |
| 帮用户做什么决定？ | 判断意向？推荐话术？标记风险？ |
| 最终交付什么？ | 结构化 JSON？Excel 报表？实时提示？ |
| 什么算成功？ | 准确率指标？覆盖率？响应时间？ |
| 什么绝对不能做？ | 红线行为（如泄露客户隐私、虚假承诺） |

**产出物**：《领域蓝图》文档，包含场景描述、决策目标、约束边界、验收标准。

### Step 2：知识分层拆解

**目标**：将业务知识按**变化频率**和**职责边界**拆成独立层。

以通话分析场景为例，知识可拆为七层：

```apache
Layer 1: 合规规则（极低频变化）
Layer 2: 意图分类体系（低频变化）
Layer 3: 话术策略库（中频变化）
Layer 4: 业务产品数据（高频变化）
Layer 5: 录音案例库（持续新增）
Layer 6: 评分与质检规则（中频变化）
Layer 7: 构建与校验规则（随版本迭代）
```

**拆分原则**：

- 变化频率不同的知识， 必须 分层存放
- 每一层有独立的维护责任方
- 层与层之间通过编码引用，而非内容耦合

### Step 3：关键对象编码

**目标**：建立统一的"语言系统"，让人、模型、数据库、下游系统对齐。

**实践要求**：

- 每个意图有唯一编号（如  `INT-001`  ~  `INT-030`  ）
- 每张话术卡有唯一编号（如  `SCRIPT-001`  ~  `SCRIPT-030`  ）
- 每条合规规则有唯一编号（如  `COMP-001`  ~  `COMP-009`  ）
- 编码一旦发布， 不可复用、不可变更含义

编码的价值：当"识别→推荐→质检→评测→追溯"全链路共用同一套编码时，任何环节的结论都可以被其他环节直接引用和校验。

### Step 4：将业务优先级编码为决策顺序

**目标**：Skill 的执行顺序 = 业务优先级，而非知识出现顺序。

以通话分析 Skill 为例，执行顺序设计如下：

```nginx
Step 1: 合规前置检查
        ├── 勿扰/拒绝/愤怒/投诉 → 命中则中止，标记合规事件
        └── 未命中 → 继续
Step 2: 高风险检测
        ├── 敏感凭证泄露、虚假承诺 → 命中则标记，降权后续推荐
        └── 未命中 → 继续
Step 3: 回访许可核实
        └── 必须有明确口头许可证据，否则不触发回访推荐
Step 4: 意图识别
        ├── 主意图 + 次意图
        └── 每个意图必须绑定证据片段
Step 5: 信息补全判断
        └── 信息不足 → 生成最少必要问题，而非猜测
Step 6: 策略与话术推荐
        └── 基于已确认意图 + 合规状态，匹配话术卡
Step 7: 产品信息注入
        └── 仅在有有效业务数据时输出具体产品/价格
Step 8: 下一动作建议
        └── 明确、可执行的单条建议
```

**关键设计决策**：合规是**前置拦截**，不是"分析完再补一段风险提示"。这直接影响架构——合规检查模块必须在意图识别之前执行。

### Step 5：用真实失败驱动迭代

**目标**：每次迭代只解决一个明确问题，精准定位问题层级。

**迭代流程**：

```
真实调用失败
    │
    ▼
定位问题层级
    ├── 触发层：Skill 没被正确调用？→ 修改路由/触发条件
    ├── 知识层：缺少必要的判断依据？→ 补充知识库
    ├── 决策层：判断顺序/逻辑有误？→ 调整决策树
    ├── 输出层：格式/字段不符合契约？→ 修改输出模板
    └── 约束层：模型自由发挥过度？→ 增加硬约束
    │
    ▼
修改对应层（不要全部塞进 Prompt）
    │
    ▼
回归测试 → 上线
```

**典型迭代案例**：

| 发现的问题 | 定位层级 | 修复方式 |
| --- | --- | --- |
| 用户只说"分析"，模型跳过完整流程 | 触发层 | 增加最简调用约束，强制走完整链路 |
| 模型自造不存在的意图编号 | 知识层 | 增加编码完整性校验，输出前比对编码表 |
| 模型把"考虑一下"判为同意回访 | 决策层 | 增加回访许可证据约束：必须有明确"可以/好的/行"等肯定词 |
| 模型过度推断客户未表达的意图 | 约束层 | 增加"不可过度推断"硬规则 |

### Step 6：交付物即契约

**目标**：Skill 的输出不是"大概正确"，而是"下游系统能直接使用"。

**契约设计示例**（以 Excel 交付为例）：

```cs
字段契约：
  - 总列数：固定 12 列，不可增减
  - 列顺序：固定，不可调整
  - 数据类型：意图编码为 string，置信度为 float(0-1)，时间为 ISO 8601
  - 空值规则：证据不足时填 "N/A"，不可填空字符串
  - 编码引用：必须使用标准编码，禁止使用自然语言描述
  - 文件编码：UTF-8 with BOM
```

当交付物复杂时，可将"分析"和"交付"拆成两个独立 Skill：

- Skill A （分析）：负责判断对不对，输出结构化分析结果
- Skill B （交付）：负责格式行不行，将分析结果映射为特定交付格式

## 四、架构设计：让 Skill 可复用

### 4.1 源知识库与运行快照分离

![](附件资源/从业务需求到智能体能力：Skill%20设计的工程方法论/img_6.png)

**好处**：

- 业务方改知识 → 不影响 Skill 运行（改的是源库，需重新编译快照才生效）
- Skill 升级 → 不影响业务方维护（Skill 只读快照，不直接操作源库）
- 两侧独立演进，通过"编译"动作解耦

### 4.2 能力分层与组合

![](附件资源/从业务需求到智能体能力：Skill%20设计的工程方法论/img_7.png)

上层复用下层能力，但增加自己的业务规则。这样，当基础分析逻辑升级时，所有上层场景自动受益。

## 五、Skill 在智能体系统中的协同

Skill 不是孤立组件。在一个完整的智能体系统中，三者各司其职：

![](附件资源/从业务需求到智能体能力：Skill%20设计的工程方法论/img_8.png)

- Prompt 让智能体"会思考、会表达"
- 工作流 让智能体"会编排、会流转"
- Skill 让智能体"有活干、能落地"

三者缺一不可。缺少 Prompt，Skill 不知道何时该被调用；缺少工作流，多个 Skill 无法协同；缺少 Skill，智能体只能"说"不能"做"。

## 六、工程实践清单

在落地过程中，以下检查清单可以帮助避免常见陷阱：

**设计阶段**：

```
是否产出了《领域蓝图》，而非直接写 Prompt？
知识是否按变化频率分层，而非混在一起？
关键对象是否全部有唯一编码？
决策顺序是否反映了业务优先级（而非知识罗列顺序）？
合规/安全规则是否设计为前置拦截？
```

**开发阶段**：

```nginx
Skill 是否只负责"怎么做"，不硬编码"做什么"的答案？
每个判断是否都有对应的证据字段？
输出格式是否有严格的契约定义？
是否区分了"基础能力"和"场景交付"？
```

**迭代阶段**：

```swift
每次失败是否定位到了具体层级（触发/知识/决策/输出/约束）？
修复是否只改了对应层，而非全部塞进 Prompt？
编码体系是否保持稳定，未随意变更含义？
```

**运维阶段**：

-

```
源知识库与运行快照是否独立管理？
业务方是否能独立维护数据层，无需开发介入？
快照是否有版本管理，支持回滚？
```

## 七、结语

Skill 设计的本质，不是"给智能体加一个功能"，而是"给智能体长出一项能力"。

功能是写死的、被动的、给用户触发用的。能力是活的、可调度的、给智能体自主使用的。

![](附件资源/从业务需求到智能体能力：Skill%20设计的工程方法论/img_9.png)

从业务需求到 Skill，中间隔着的不是代码量，而是**对业务的理解深度**：这个业务到底要解决什么问题？什么行为绝对不能做？决策的优先级是什么？证据的标准是什么？

想清楚了这些，Skill 的设计就是自然而然的事。想不清楚就动手，做出来的东西一定推倒重来。

**先思考，再行动。想清楚，再做对。**
