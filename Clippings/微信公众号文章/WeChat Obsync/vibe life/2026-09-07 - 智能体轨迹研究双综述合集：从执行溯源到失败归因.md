# 智能体轨迹研究双综述合集：从执行溯源到失败归因

## TLDR

**篇一《从智能体轨迹到信任：LLM 智能体中的证据追踪与执行溯源综述》**

- **要解决的问题**：LLM 智能体的评估几乎只看最终答案，无法回答"输出是怎么产生的、每个论断有什么证据、工具调用是否合理、失败发生在哪一步"。

- **核心思路**：把智能体执行建模为完整的类型化溯源图（执行单元、证据单元与它们之间的关系），证据追踪是该图在"证据—支持"关系上的投影，由此为智能体提供过程级问责层。

- **分类体系**：沿六个维度组织研究——轨迹来源、证据与执行单元、溯源关系、追踪粒度与时机、表示形式、信任功能。

- **研究脉络**：综述归入七条主线——溯源表示、证据归因、工具使用溯源、运行时护栏、携带溯源信息的记忆、可观测性与失败诊断（另将基准与指标映射到溯源能力）。

- **评估视角**：讨论评估如何从"答案正确性"走向"过程级问责"，并梳理开放挑战。

**篇二《LLM 智能体轨迹分析综述：从失败归因到系统增强》**

- **要解决的问题**：智能体的失败埋藏在冗长的、以自然语言为主的执行轨迹中，传统软件调试手段难以定位根因。

- **文献范围**：系统收集 2025 年初至 2026 年 4 月间发表的 55 篇论文，横跨软件工程、人工智能与人机交互。

- **组织框架**：沿五个维度梳理文献——失败分类体系、失败归因、系统增强与优化、轨迹监测与分析工具、数据集与基准。

- **主要发现**：识别出四类互补的失败分类视角、四种归因方法范式（从简单 LLM 提示发展到因果推断、微调的追踪模型与动态干预）、三类增强策略。

- **现状瓶颈**：步骤级归因准确率仍然有限、基准多样性不足；近期趋势是完全可观测性与不可恢复失败的标注。

## 篇一 · 从智能体轨迹到信任：LLM 智能体中的证据追踪与执行溯源综述

_From Agent Traces to Trust: A Survey of Evidence Tracing and Execution Provenance in LLM Agents_

**作者**：Yiqi Wang, Jiaqi Zhang, Zhangkai Wu, Taotao Cai, Zirui Liu, Qingqiang Sun, Zequn Sun, Manqing Dong, Mingkai Zheng, Xuefei Yin, Yanming Zhu（格里菲斯大学、江苏大学、南昆士兰大学、北京大学、大湾区大学、南京大学、悉尼大学、南方科技大学）

### # 摘要

基于大语言模型（LLM）的智能体正迅速从被动的文本生成器，演化为具备规划、工具使用、检索、记忆访问、环境交互与多智能体协作能力的自主系统。这些能力扩展了智能体的自主性，同时也使智能体行为越来越难以验证、调试和审计。困难在于：对智能体的评估几乎完全依赖最终答案，而一个正确的答案并不能说明输出是如何产生的、每个论断有哪些证据支持、工具调用是否合理、记忆如何影响了后续决策、执行失败又源于何处。为了回答这些问题，我们将目光从输出转向执行过程本身，并通过**证据追踪**（evidence tracing）与**执行溯源**（execution provenance）对其加以组织。溯源通过建模检索到的证据、工具输出、记忆条目、观察、中间论断、动作与最终答案之间的联系，为可信的 LLM 智能体提供了一个过程级的问责层（accountability layer）。在本综述中，我们把执行溯源视为智能体执行的完整类型化图（typed graph），把证据追踪视为该图在“证据—支持”关系上的投影，由此给出一个统一框架，覆盖从检索依据到审计与恢复的全过程。我们提出了一个沿六个维度刻画智能体系统的分类体系（taxonomy）：轨迹来源、证据与执行单元、溯源关系、追踪粒度与时机、表示形式，以及信任功能。随后我们综述现有方法，并将其归入七条主要研究脉络：溯源表示、证据归因、工具使用溯源、运行时护栏、携带溯源信息的记忆、可观测性与失败诊断。最后，我们将现有基准测试、数据集与指标同溯源相关能力对应起来，讨论评估如何从最终答案正确性走向过程级问责，并概述开放挑战：统一的轨迹模式（schema）、语义溯源、感知溯源的安全、真实的执行轨迹基准、面向恢复的评估，以及隐私感知的审计基础设施。相关资源收录于配套的 GitHub 仓库并持续更新。

**关键词**　LLM 智能体、智能体轨迹、证据追踪、执行溯源、溯源图、工具使用安全、记忆溯源、智能体可观测性、运行时护栏、可信 AI

### # 2 证据追踪与执行溯源的分类体系

在定义了智能体轨迹、证据追踪与执行溯源之后，本节给出贯穿全文的分类体系。目标并非逐一详评每个系统，而是提供一套紧凑的术语，用于比较面向溯源的智能体研究。我们沿六个维度组织这一空间：轨迹来源、证据与执行单元、溯源关系、追踪粒度与时机、表示形式，以及信任功能。图 2 给出直观总览，表 1 给出完整摘要，作为全文的骨架。

这一分类体系借鉴了两条已有传统。以 W3C PROV-DM 为代表的溯源模型，描述实体（entity）、活动（activity）与代理（agent）如何通过使用（usage）、生成（generation）、派生（derivation）、修订（revision）与失效（invalidation）等关系参与产物的生产 [World Wide Web Consortium, 2013]。以 OpenTelemetry 为代表的分布式可观测性框架，把执行建模为 trace 与 span，便于描述多步骤的智能体运行 [OpenTelemetry, 2026]。然而，LLM 智能体引入了这些传统未能完全覆盖的语义与过程性对象：检索到的段落、生成的论断、工具调用的理由、记忆条目、自然语言观察、外部状态变更与智能体间消息。AgentOps、AgentTrace 等面向智能体的可观测性系统进一步表明，有必要对执行产物与上下文同时进行结构化记录 [Dong et al., 2024; AlSayyad et al., 2026]。因此，我们把经典溯源与可观测性视为基础，并将其特化到 LLM 智能体的执行结构上。

#### 2.1 分类体系维度

**轨迹来源**。轨迹来源是产生溯源相关产物的组件。在 LLM 智能体中，这些来源超出了模型输出，还包括推理、检索、工具使用、记忆、环境交互与多智能体通信。推理轨迹可以解释计划或动作选择；检索轨迹提供证据候选；工具轨迹记录调用、参数、输出、权限与错误；记忆轨迹揭示跨会话的影响；环境轨迹记录观察与改变状态的动作；多智能体轨迹捕捉委托、批评与责任传播 [Yao et al., 2023; Shinn et al., 2023; Qin et al., 2024; Zhou et al., 2024; Yao et al., 2025; Wu et al., 2024a; Li et al., 2023]。后续章节将深入讨论工具与记忆两类来源，这里仅用它们界定分类体系的边界。

**证据与执行单元**。轨迹来源产生两大类单元。证据单元是能够支持、反驳、失效化或为论断与动作提供语境的语义对象，如文档、段落、观察、工具输出、记忆条目、策略与中间论断。执行单元是描述智能体做了什么的程序性对象，包括推理步骤、检索调用、工具调用、生成的参数、记忆读写、环境动作、智能体间消息与最终输出。这一区分有用但并不绝对：一个工具输出既是某执行步骤的结果，也可能是后续论断的证据。因此，面向溯源的智能体需要把语义支持与过程执行连接起来，而不能只记录轨迹的一侧 [Gao et al., 2023; Min et al., 2023; Thorne et al., 2018; Ru et al., 2024; Dong et al., 2024; AlSayyad et al., 2026]。

**溯源关系**。关系把原始轨迹单元转化为溯源。我们保留了与 PROV 兼容的基础关系，如 USE（使用）、GENERATE（生成）与 DERIVE（派生），并添加 LLM 执行所需的智能体特定关系：SUPPORT（支持）、DEPEND-ON（依赖）、CONTRADICT（矛盾）、INVALIDATE（失效）、TRIGGER（触发）与 UPDATE（更新）。这些关系把语义依据与过程依赖区分开来。例如，一个段落可以 SUPPORT 一个论断；一个工具调用可以 DEPEND-ON 生成的参数；一个新的观察可以 INVALIDATE 一个计划；一个失败的动作可以 TRIGGER 恢复。这一紧凑的关系集刻意保持最小；第 3 节将讨论日志、图与运行时结构在实践中如何编码这类依赖。

**追踪粒度与时机**。粒度指定轨迹的精细程度。运行级（run-level）轨迹支持粗粒度审计；步骤级（step-level）轨迹支持调试；工具调用级与参数级轨迹支持安全执行；论断级（claim-level）轨迹支持事实归因；token 级或 span 级轨迹提供最精细但也最昂贵的视图。时机指定轨迹何时被收集或使用：执行前（pre-execution）检查可以阻断未授权动作；运行时（runtime）追踪支持策略执行与信息流控制；事后（post-hoc）追踪支持审计与诊断；持续（continuous）追踪支持持久记忆与长程工作流 [Min et al., 2023; Wu et al., 2024b; Costa et al., 2025; Cai et al., 2026; Wang et al., 2025a; Sequeira et al., 2026; Deshpande et al., 2025]。合适的选择取决于工作流的风险与持久性：低风险 RAG 可能只需论断级的事后归因，而高影响的工具使用可能需要运行时的参数级溯源。

**表示形式**。表示形式决定轨迹如何编码。结构化日志保留按时间排列的事件与元数据，但往往让支持、矛盾与影响关系保持隐式。执行图显式表达过程依赖；证据图与论断—支持图强调语义依据；溯源图通过类型化边组合证据单元与执行单元；运行时状态表示支持在线检查与执行约束。此维度在此从简，因为第 3 节将详细评述表示选择。

**信任功能**。追踪的目的不是存储更多日志，而是支持信任功能。验证（verification）追问论断或动作是否有证据支持；归因（attribution）识别哪些证据、工具输出、记忆条目或消息对某个论断或动作有贡献；调试（debugging）在执行中定位失败；安全执行（safety enforcement）阻止不可信或未授权的影响到达敏感动作；审计（audit）为审查与问责重建执行；恢复（recovery）利用溯源来重试、补偿、回滚或修复受影响的状态 [Gao et al., 2023; Es et al., 2024; Deshpande et al., 2025; Rorseth et al., 2025; Debenedetti et al., 2025; Costa et al., 2025; Sequeira et al., 2026]。这些功能解释了分类体系为何同时包含证据支持链接与执行依赖链接。

#### 2.2 设计中的矛盾与取舍（Design Tensions）

这套分类体系揭示出四组设计上的矛盾与取舍，它们将引导后文的综述。第一，按时间顺序记录日志并不等于语义溯源：日志能记下发生过什么，却未必能说明证据是否支持了某个论断、记忆是否影响了某次工具调用。第二，组件级追踪并不能保证端到端的问责，因为失败可能在检索、工具、记忆、环境状态与其他智能体之间传播。第三，静态模式有助于把轨迹对象与关系标准化，但运行时安全还要求在线的来源跟踪、策略检查，以及能够顾及依赖关系的强制执行。第四，轨迹的完整性需要与可部署性相权衡：细粒度溯源有利于验证、调试、审计与恢复，但也会增加存储成本、隐私暴露、标注负担与系统复杂度。第 3–6 节在评述表示方法、工具使用溯源、记忆溯源与评估时，还会回到这些矛盾。

在后文中，这套分类体系将作为一套简洁的比较词汇贯穿使用。第 3 节通过一个具体的溯源图示例对这套词汇加以实例化；附录 B 把代表性系统映射到分类体系的各个维度。

### # 3 溯源表示与证据归因

上一节回答了“应追踪什么”；本节追问“轨迹应如何表示”。我们把溯源表示组织为三层。结构化日志记录类型化的执行事件。执行图通过依赖关系连接指令、检索、工具调用、记忆操作、观察、论断与动作。证据图与论断—支持图进一步说明证据单元对生成的论断是支持、矛盾还是不支持。这一分层视图是全文的核心：日志使执行可重建，图使依赖可检视，论断—支持链接使依据与问责可度量。图 3 提供了一个贯穿本节的示例，展示如何把证据获取、论断构建、工具执行、记忆更新与恢复表示为类型化溯源图，而不是扁平的按时间排列的对话记录。

#### 3.1 从日志到执行图

自然的起点是结构化执行日志。日志不再只存储自由格式的对话记录，而是记录类型化事件，如用户请求、模型输出、检索调用、工具调用、工具输出、记忆读写、环境观察、智能体间消息与最终响应。W3C PROV-DM 提供了实体、活动、代理与派生关系的通用词汇 [World Wide Web Consortium, 2013]。PROV-AGENT 将该词汇适配到智能体工作流，对提示、响应、决策、工具交互与工作流上下文建模 [Souza et al., 2025]。AgentOps 强调智能体生命周期中各产物之间的关系 [Dong et al., 2024]；AgentTrace 则把执行记录组织为运行、认知与上下文三类日志 [AlSayyad et al., 2026]。

日志提供了按时序的可观测性，但依赖分析需要图结构。日志能显示发生了一次检索、一次工具调用与一次记忆写入，却未必能显示哪个检索段落支持了某个论断、哪个工具输出改变了计划、哪个记忆条目影响了某个动作。执行图弥补这一缺口：把执行产物表示为节点，把它们之间的影响关系表示为类型化边。TRAIL 展示了带标注的轨迹如何把失败定位到特定步骤、组件或交互 [Deshpande et al., 2025]。AgenTracer 进一步使用反事实重放与故障注入，把失败归因到责任智能体与步骤 [Zhang et al., 2025a]；Aegis 则使用正—负轨迹对来识别出错智能体与错误模式 [Kong et al., 2025]。因此，日志回答“发生了什么”；执行图回答“什么依赖于什么”。

#### 3.2 证据与论断—支持归因

证据归因在执行依赖之上添加了一个语义层。关键问题是：生成的论断是否真的得到它所引用或依赖的证据的支持。现有工作在不同粒度上论证了这一区分：基于引用（citation）的评估把生成的答案与来源关联 [Gao et al., 2023]；原子事实评估检查细粒度的事实支持 [Min et al., 2023]；来源检查工作表明，被引用的来源可能相关、却不支持特定论断 [Wu et al., 2024b]；论断—证据映射则明确区分被支持的论断、未被支持的论断与被遗漏的证据 [Martin-Boyle et al., 2026]。

**表 2**　LLM 智能体的主要溯源表示形式。

| 形式 | 捕获内容 | 主要作用 |
| --- | --- | --- |
| 结构化日志 | 类型化执行事件，如请求、检索调用、工具调用、记忆操作、观察与输出。 | 执行可观测性与重建。 |
| 执行图 | 指令、证据、工具调用、记忆条目、论断与动作之间的依赖。 | 面向调试、审计与恢复的影响分析。 |
| 证据图 | 证据单元、引用、原子论断与生成答案之间的链接。 | 区分引用存在性、相关性、支持、矛盾与遗漏。 |
| 静态模式 | 对象类型、关系类型、信任标签与必填溯源字段。 | 用于轨迹表示与比较的可复用词汇。 |
| 运行时溯源 | 执行期间具体的“来源—汇点”（source-to-sink）、工具、记忆与动作依赖。 | 运行时监视、执行、恢复与信息流分析。 |

对溯源表示而言，这些区分对应不同的边类型，而非单一的“引用”关系。一个来源可能被 CITED（引用）却不 SUPPORT（支持）某个论断；一个相关段落可能存在、却被 OMITTED（遗漏）于答案之外；一个工具输出可能与某个记忆条目 CONTRADICT（矛盾）；新证据可能使早先的信念 INVALIDATE（失效）。因此，证据图把“证据是否可得”与“证据是否被使用”区分开来。在 LLM 智能体中，携带证据的单元不仅包括检索到的文档，还包括工具输出、记忆条目、环境观察、策略与智能体间消息。

#### 3.3 表示的权衡

静态模式与运行时溯源构成溯源表示的两个互补层。静态模式定义对象类型、关系类型、信任标签与必填字段，包括证据单元、工具调用、记忆条目、论断、动作，以及 SUPPORT、DEPEND-ON、CONTRADICT、UPDATE、INVALIDATE 等关系。运行时溯源在具体执行中实例化该模式，记录来源、工具调用、记忆操作、论断与动作之间的实际依赖。可观测性系统强调运行时轨迹的捕获与检视 [Dong et al., 2024; AlSayyad et al., 2026]；面向安全的系统还把运行时溯源用于执行约束 [Sequeira et al., 2026]、信息流控制 [Costa et al., 2025] 与“来源—汇点”影响分析 [Cai et al., 2026]。

核心的权衡在于粒度。细粒度溯源支持论断验证、失败定位、回滚、审计与策略执行，但会增加存储成本、日志复杂度、隐私暴露与标注负担。粗粒度溯源更易收集，却可能错过支持某个论断的证据、导致出错的记忆条目，或越过信任边界的工具参数。因此，合适的粒度取决于信任功能：低风险 RAG 或许论断级链接即可；使用工具的智能体需要参数级溯源；长期个性化智能体则需要记忆谱系、失效与恢复支持。表 2 总结了本节讨论的主要表示形式。

### # 4 工具使用智能体中的执行溯源

工具使用是智能体溯源面向外部世界的一端：LLM 智能体正是在这里从生成文本转向与 API、数据库、代码解释器、浏览器、文件系统、企业系统及其他外部环境交互。一次工具调用可能读取私有数据、修改外部状态、发送消息、执行代码或触发不可逆动作。因此，可信的工具使用要求追踪：为何选择某个工具、参数来自哪里、输出是否可靠、结果如何影响后续决策。本节评述五个对溯源至关重要的问题：工具执行中应追踪什么；外部内容如何污染工具使用；不安全的影响如何被约束；动作边界如何被强制执行；轨迹如何支持验证与恢复。

#### 4.1 工具调用、参数与输出溯源

工具调用溯源记录从工具选择到下游影响的路径：选择了哪个工具、传入了哪些参数、返回了什么输出、该输出如何影响后续推理或动作。Toolformer [Schick et al., 2023] 与 ToolLLM [Qin et al., 2024] 表明，外部工具可以通过 API 调用、计算、搜索等操作扩展 LLM 的能力。在“是否执行成功”之外，溯源进一步追问：调用是否正当、参数是否来自可信或经授权的来源、输出是否被恰当地使用。

一次工具调用包含若干对溯源关键的对象：被选中的工具、模式（schema）、参数取值、执行结果与下游消费者。**参数溯源**尤为重要，因为合法的工具在其参数来自不可信或错误生成的取值时，也会变得不安全。Agent-Sentry 追踪流入敏感工具参数的取值来源，说明为什么在工具级权限检查之外还需要参数级谱系 [Sequeira et al., 2026]。工具输出同样是携带溯源的单元：它们可能支持论断、更新记忆、触发更多工具、修改外部状态，或与其他证据冲突。WebArena 凸显了在真实 Web 环境中正确解读观察并执行状态变更动作的重要性 [Zhou et al., 2024]；τ-bench 则在领域特定策略下评估工具—智能体—用户交互 [Yao et al., 2025]。因此，工具使用溯源应把来源、参数、输出与下游消费者连接成一条完整的依赖链。

#### 4.2 间接提示注入与工具使用污染

使用工具的智能体容易受到**间接提示注入**（indirect prompt injection）攻击，因为它们消费的外部内容可能包含对抗性指令。与把恶意指令放进用户提示的直接提示注入不同，间接注入把指令嵌入网页、文档、邮件、数据库条目、工具输出或第三方 API 响应。这种攻击利用的是边界失效：不可信数据可能被当作可执行的指令，而不是被动的证据 [Greshake et al., 2023; Liu et al., 2023]。

InjecAgent 在工具集成智能体场景中对间接提示注入进行基准测试 [Zhan et al., 2024]；AgentDojo 在真实任务环境中评估攻击与防御 [Debenedetti et al., 2024]。相关基准进一步拓宽了工具风险面：ToolEmu 在仿真沙箱中评估有风险的工具执行 [Ruan et al., 2024]；OpenAgentSafety 覆盖浏览器、代码执行、文件系统、shell 与消息平台等真实工具 [Vijayvargiya et al., 2026]；MCP-SafetyBench 面向真实 MCP 服务器与多服务器工作流 [Zong et al., 2025]。这些基准共同表明：被污染的工具上下文可能导致未授权的工具使用、隐私泄露、无视用户意图与意外的状态变更。

从溯源的角度看，间接提示注入是一个信息流与影响追踪问题。关键问题是：恶意内容是否影响了后续的工具调用、参数取值、记忆更新或外部动作。扁平的日志可能显示“检索了一个网页、随后调用了邮件工具”，却无法显示收件人、主题或正文来自网页、用户指令还是模型推理。DERIVE、DEPEND-ON、TRIGGER、USE 等关系可以把这种影响显式化。因此，工具使用溯源应当区分可信意图与不可信内容，并支持对流入特权执行通道的不安全信息流施加约束。

#### 4.3 信息流、污点追踪（Taint Tracking）与溯源执行

近期的防御工作日益把工具使用安全视为**信息流**（information flow）问题。它们不再仅依赖提示工程或输出过滤，而是追踪信息从哪里来、如何传播、是否被允许影响敏感动作。这一观点延续了经典的信息流控制（information-flow control）：安全策略调节主体、客体与安全等级之间的流动 [Denning, 1976; Sabelfeld and Myers, 2003]。对 LLM 智能体而言，对应目标是阻止低完整性或不可信的数据，对特权工具调用、记忆更新或状态变更动作施加未授权的影响。

防御工作在不同层面落实这一原则。Instruction Hierarchy 在指令来源之间建立优先级 [Wallace et al., 2024]；StruQ 通过结构化通道把指令与不可信数据分离 [Chen et al., 2025]；CaMeL 在执行时显式实现这种分离，把控制流与数据流隔离开，并限制外部数据影响智能体行为的方式 [Debenedetti et al., 2025]；FIDES 通过在执行期间强制实施的机密性与完整性标签，形式化了智能体级的信息流控制 [Costa et al., 2025]。在更细的粒度上，NeuroTaint 采用污点追踪（taint tracking）思路：把来自不可信来源的数据打上“污点”标记，并跟随这些标记在神经与符号组件之间的传播，从而还原不可信数据的影响路径 [Cai et al., 2026]；Agent-Sentry 则追踪敏感工具参数是否受到不可信来源的影响 [Sequeira et al., 2026]。

关键的教训是：不安全的行为可能源于“影响”，而不仅是“内容”。一个网页用于摘要可能是安全的；但若其中嵌入的指令决定了邮件收件人、数据库参数或授权信号，它就是不安全的。运行时溯源通过连接来源、变换与汇点，把这一区分显式化，使执行策略既考虑取值的内容，也考虑其来源与用途。

#### 4.4 访问控制与执行边界

信息流追踪必须与访问控制及执行边界配合。即使智能体能够调用许多工具，也不应允许它在任何上下文中调用任何工具。**最小权限**（least privilege）与**完全仲裁**（complete mediation）等经典原则要求：敏感动作被显式授权、访问决策在使用点被检查 [Saltzer and Schroeder, 1975]。在使用工具的智能体中，这些原则转化为工具权限、参数约束、用户确认、沙箱与策略中介的执行。

近期系统在不同层面落实这些原则。AgentSpec 对智能体动作与工具使用强制执行用户定义的运行时约束 [Wang et al., 2025a]。AgentBound 为 MCP 服务器提供能力受限的访问控制，限制每个服务器可用的资源 [Bühler et al., 2025]。Agent-Sentry 则使用执行溯源（包括逐参数的数据流），依据学习到的行为与用户意图对工具调用设界 [Sequeira et al., 2026]。这些系统共同表明：工具使用安全要求控制“在什么上下文中、以什么参数、带着什么外部影响，可以访问哪些工具与资源”。

溯源使这些控制具备上下文敏感性。例如，Agent-Sentry 使用逐参数的数据流与用户意图对齐程度来评估拟议的工具调用 [Sequeira et al., 2026]。只读的搜索工具或许可以消费不可信的网页内容；而邮件、数据库更新或代码执行工具则可能要求参数来自经授权的用户意图、经过验证的工具输出或显式批准。因此，访问控制与溯源是互补的：能力策略划定智能体可用的工具与资源 [Bühler et al., 2025]；溯源与运行时规则决定某个具体动作应当放行、限制、要求确认还是阻断 [Wang et al., 2025a; Sequeira et al., 2026]。

#### 4.5 运行时护栏与执行前/后验证

运行时护栏在执行之前、之中或之后检查智能体行为。执行前护栏决定拟议的工具调用是否放行；运行时监视器跟踪信息流与状态变更；执行后验证检视轨迹、输出与副作用，用于调试、审计与恢复。通用护栏系统说明了安全机制如何围绕 LLM 应用布置：NeMo Guardrails 提供可编程的对话护栏 [Rebedea et al., 2023]；Llama Guard 提供基于模型的输入/输出安全分类 [Inan et al., 2023]。但使用工具的智能体需要对执行状态、工具参数与下游影响的检查，而不仅是输入—输出文本。

对高影响工具而言，执行前验证至关重要。感知溯源的护栏可以检查：工具是否被授权、用户意图是否存在、参数是否格式良好、敏感字段是否来自可信来源、动作是否违反策略。AgentSpec 形式化了智能体动作上的运行时约束 [Wang et al., 2025a]；Agent-Sentry 使用执行溯源验证敏感工具参数是否受不可信来源影响 [Sequeira et al., 2026]；ToolEmu 则在仿真沙箱中评估有风险的工具执行，作为对这些防御的补充 [Ruan et al., 2024]。

执行后验证支持失败定位与修复。当智能体给出错误答案或执行了不安全动作时，轨迹可以帮助识别失败源于证据、工具使用、记忆还是下游推理。AgentOps 记录智能体产物及其生命周期关系 [Dong et al., 2024]；AgentTrace 把执行记录组织为运行、认知与上下文轨迹 [AlSayyad et al., 2026]；TRAIL 使用带标注的轨迹定位失败 [Deshpande et al., 2025]；LADYBUG 使用基于轨迹的调试支持失败定位与修复 [Rorseth et al., 2025]。

因此，有效的护栏同时需要语义溯源与过程溯源：语义溯源把论断链接到支持或反驳它的证据；过程溯源把动作链接到经授权的路径与可信的输入。两者结合，有助于发现无依据的论断、被污染的参数、未授权的工具调用与无效的状态更新。

#### 4.6 小结

使用工具的智能体使执行溯源成为必需，因为工具调用可能消费不可信信息、暴露私有数据、修改外部状态并触发下游后果。核心问题是：工具参数从哪里来、工具输出是否可信、外部内容如何影响动作、执行是否停留在授权边界之内。近期的提示注入基准、信息流控制、污点追踪、执行设界、运行时护栏、可观测性与基于轨迹的调试等工作，标志着从“只看输出的安全”向“感知溯源的执行控制”的转变。

综合：从工具日志到影响控制。工具使用溯源正从“记录事件”走向“治理影响”。工具级轨迹能显示调用了哪个 API，却不能显示调用是否必要、正当、与用户目标一致。参数谱系能检测敏感参数中的不可信取值，却可能漏掉对工具输出的错误解读。基于信息流与污点的方法能约束不安全的影响，但在摘要、改写、记忆整合与多步推理面前仍然困难。下一步是把工具调用谱系、语义证据支持、来源信任、状态变更、策略合规与恢复依赖，在完整的智能体工作流上统一起来。

### # 5 记忆作为携带溯源信息的证据

如果说工具使用是智能体溯源面向外部世界的一端，记忆就是面向内部的一端：证据不再产生即时的外部动作，而是被保留、变换、检索，并在轮次、任务、会与环境之间复用。这使记忆成为溯源链的持久部分：一个记忆条目之后可能支持某个论断、塑造某个计划、填入某个工具参数、更新另一条记忆，或为某个最终答案提供论证。因此，记忆进一步凸显了前文所述关于轨迹完整性的矛盾：智能体受益于紧凑、持久、自适应的记忆，而问责要求来源谱系、检索上下文、时间有效性、冲突状态与下游影响。

本节并不综述一般意义上的记忆架构。已有工作回顾了 LLM 智能体的记忆机制与评估协议 [Zhang et al., 2025b; Du, 2026]，以及基于图的记忆系统 [Yang et al., 2026]。我们把记忆条目视为**携带证据的对象**。在这一视角下，记忆不仅是被存储与检索的东西，而是具有来源、变换、修订、有效性条件与后续影响的产物。缺少这些链接，长期记忆就会退化为不透明的证据来源，而不再是智能体执行中可审计的组件。

图 4 总结了这一生命周期。与以存储为中心的记忆观不同，它把记忆条目视为携带溯源的证据对象，其来源、更新、检索、有效性与下游影响都应保持可检视。

#### 5.1 记忆写入、来源归因与谱系

记忆溯源始于记忆条目被写入之时。一次记忆写入可能来自用户输入、检索到的文档、环境观察、工具输出、反馈、反思或其他智能体的消息。现有记忆系统展示了不同的写入路径：Generative Agents 存储观察以供后续反思与规划 [Park et al., 2023]；Reflexion 在失败后将言语反馈写入情景记忆 [Shinn et al., 2023]；MemoryBank 通过交互更新长期用户记忆 [Zhong et al., 2024]；MemGPT 通过显式读写操作管理跨记忆层级的移动 [Packer et al., 2023]；A-MEM 把新记忆链接进不断演化的记忆结构 [Xu et al., 2026]。

![alt](附件资源/智能体轨迹研究双综述合集：从执行溯源到失败归因/img_4.jpg)

_**图 4** 跨智能体会话中作为溯源载体的记忆。记忆条目由来源证据写入，经由更新与整合维护，被检索进入后续智能体执行，用于影响论断与动作，并接受针对冲突、过期、投毒与失效的审计。_

从溯源的角度看，重要的单元不是记忆记录本身，而是记录与产生它的证据之间的关系。每次记忆写入都应携带来源与谱系元数据，包括来源类型、时间戳、写入智能体、支持证据、变换操作、置信度与更新历史。这遵循更广泛的溯源原则：生成的产物应与其生产实体、活动与代理相关联 [World Wide Web Consortium, 2013; Souza et al., 2025]，也与记录执行产物及运行上下文的追踪框架相一致 [AlSayyad et al., 2026; Sequeira et al., 2026]。这种谱系至关重要，因为记忆写入往往伴随着信息变换：文档被摘要、观察被合并、偏好被推断、失败被抽象为反思。因此，携带溯源的记忆应当区分原始观察、抽取的事实、推断的记忆与修订后的记忆。

综合。记忆的可问责性从写入时开始。如果一条记忆在存储时不带来源与变换元数据，后续验证就只能检视其表面内容，而无法检视其证据基础。

#### 5.2 记忆检索、时间有效性与下游影响

检索决定哪些存储的信息重新进入当前执行。被检索的记忆可能影响任务分解、答案生成、工具选择、参数构造、用户建模与未来的记忆更新。现有记忆系统支撑了这一以检索为中心的视角：MemoryBank 与 Mem0 强调个性化与跨会话连续性 [Zhong et al., 2024; Chhikara et al., 2025]；MemGPT 与 LongMem 管理超出当前上下文窗口的信息 [Packer et al., 2023; Wang et al., 2023]；A-MEM 通过动态记忆链接改进检索 [Xu et al., 2026]。

溯源风险在于：被检索的记忆可能只部分相关、已经过期、过度泛化、来自幻觉内容、被对抗性交互投毒，或在当前上下文中无效。**记忆投毒**（memory poisoning）与**记忆注入**（memory injection）攻击表明，持久记忆可以跨会话操纵后续的响应与动作 [Chen et al., 2024; Dong et al., 2025; Tian et al., 2026; Pulipaka et al., 2026]。因此，**时间有效性**（temporal validity）居于核心：一条记忆应记录它何时被创建或更新、当时有哪些证据支持、这些证据现在是否仍然有效、后续观察是否已取代它。

感知溯源的检索轨迹应记录：触发检索的查询或上下文、被检索的记忆条目、原始来源、相关性信号、有效性状态，以及通往论断、工具调用、动作、最终答案或后续记忆更新的下游链接。这样，系统就能识别最终输出是否受到某条特定记忆的影响、这种影响是否正当。它还支持**选择性失效**：当某条记忆过期、无依据、涉私或被污染时，可以定位受影响的论断、动作与派生记忆，而不再把执行历史视为不透明的整体 [Wang et al., 2025b; Wei et al., 2025; Sequeira et al., 2026]。

综合。检索不仅是一个相关性问题，还是一个影响问题：一旦记忆进入上下文，溯源就必须追踪它塑造了什么、这种影响是否仍然站得住脚。

#### 5.3 冲突、矛盾与被投毒的记忆

持久记忆可能积累不相容、已失效或被污染的信息。一条存储的记忆可能与新证据冲突、编码对抗性指令，或把一个薄弱的推断当作稳定事实保存。近期的攻击使这一风险变得具体。AgentPoison 表明，被投毒的长期记忆或 RAG 知识库可以充当智能体的后门（backdoor）基础 [Chen et al., 2024]；记忆注入攻击表明，恶意记录可以通过普通交互被引入 [Dong et al., 2025]；环境注入与休眠记忆投毒研究进一步表明，不可信的网页、文档或代码仓库可以进入记忆、静默存续，并在之后操纵行为 [Zou et al., 2026; Pulipaka et al., 2026]。

这将记忆溯源与工具安全及信息流控制联系起来。FIDES 追踪机密性与完整性标签以限制不安全的信息流 [Costa et al., 2025]；NeuroTaint 强调，不安全的影响可以在语义变换与记忆复用中存续，而不表现为精确的文本复用 [Cai et al., 2026]；InjecAgent 与 AgentDojo 等间接提示注入基准，展示了不可信外部内容如何操纵使用工具的智能体 [Zhan et al., 2024; Debenedetti et al., 2024]。当这类内容被写入记忆时，一次单轮攻击就演变为长程的溯源失败。

综合。记忆质量不能只以召回、个性化或一致性来度量；它还取决于来源信任、写入路径的正当性、冲突状态、污染风险，以及记忆是否会在后果重大的决策中被激活。

#### 5.4 基于记忆的验证与长期审计

基于记忆的验证把证据追踪从检索文档与当前工具输出，扩展到持久记忆。当一个论断或工具动作依赖记忆时，系统应把该记忆条目与创建它的观察、文档、工具调用、用户陈述或反思联系起来，并与后续修订、冲突、失效及下游使用联系起来。PaperTrail 等论断—证据接口通过把答案与来源分解为离散的论断与证据单元，论证了这一粒度的必要性 [Martin-Boyle et al., 2026]。AgentOps 与 AgentTrace 为结构化执行日志与检视提供了基础 [Dong et al., 2024; AlSayyad et al., 2026]；Agent-Sentry 展示了溯源图如何支持面向来源的工具调用参数执行约束 [Sequeira et al., 2026]。长期记忆需要跨会话的同类结构。

尽管 MemGPT、A-MEM、Mem0 等系统不断进步 [Packer et al., 2023; Xu et al., 2026; Chhikara et al., 2025]，大多数记忆系统仍以召回、个性化、效率或一致性为优化目标，对来源追踪、时间有效性、冲突、污染、隐私暴露与下游影响的支持有限。这一缺口至关重要，因为记忆本身可能成为攻击面：被投毒、被注入、过期或涉私的记忆，可能在不表现为外部证据的情况下塑造论断与动作 [Chen et al., 2024; Tian et al., 2026; Pulipaka et al., 2026; Wang et al., 2025b]。A-MemGuard 等防御工作提示，记忆应支持检查与纠正，而不只是写入时过滤 [Wei et al., 2025]。

### # 6 基准测试、数据集与指标

评估是证据追踪与执行溯源变得可度量的环节。在最终答案正确性之外，感知溯源的评估还应追问：论断是否得到证据支持、工具调用是否正当、记忆是否有效、不安全的影响是否被阻断、失败能否被定位与修复。现有基准为 RAG 归因、引用质量、工具使用、记忆、多智能体行为与智能体安全提供了有用信号，但它们大多评估孤立组件。因此，本节聚焦覆盖缺口而非逐一罗列数据集；数据集级目录见附录 C。

#### 6.1 现有基准覆盖了什么

RAG 与归因基准为证据追踪提供了最坚实的基础，因为它们评估生成输出是否立足于被检索或被引用的证据。代表性工作评估引用支持、忠实性（faithfulness）、幻觉、来源支持度与原子事实支持 [Gao et al., 2023; Min et al., 2023; Niu et al., 2024; Ru et al., 2024; Wu et al., 2024b]。其局限是结构性的：它们通常把最终答案或论断连接到来源，却很少评估工具调用、记忆操作、环境观察、中间决策或智能体间消息如何塑造这些论断。因此，它们是强证据归因基准，却是不完整的执行溯源基准。

智能体与工具使用基准把评估从静态答案扩展到交互执行。它们暴露轨迹、工具调用、环境状态、策略约束与最终外部状态，把评估从“答案是否正确”转向“智能体是否正确且安全地执行了任务” [Liu et al., 2024; Zhou et al., 2024; Qin et al., 2024; Yao et al., 2025]。工具使用安全基准进一步引入间接提示注入、有风险的工具上下文、真实工具与 MCP 风格的工作流 [Ruan et al., 2024; Zhan et al., 2024; Debenedetti et al., 2024; Vijayvargiya et al., 2026; Zong et al., 2025]。这些场景与溯源高度相关，因为不安全行为往往取决于不可信内容对工具参数、执行边界或状态变更动作的隐蔽影响。

轨迹调试、记忆与多智能体基准覆盖了额外的溯源维度，但仍显碎片化。面向轨迹的工作评估失败能否被定位到步骤、组件、智能体或错误模式 [Deshpande et al., 2025; AlSayyad et al., 2026; Zhang et al., 2025a; Kong et al., 2025]；记忆基准评估召回、个性化、一致性或多会话任务成功 [Maharana et al., 2024; Kim et al., 2026]；多智能体基准评估协作或失败归因 [Cemri et al., 2026; Zhang et al., 2025a; Kong et al., 2025]。这些基准为溯源提供了有用的代理指标，却很少标注记忆谱系、时间有效性、跨智能体证据传播或关系级依赖。

#### 6.2 溯源评估的核心缺口

**第一个缺口是跨组件溯源**。当前基准通常一次评估一个组件：证据依据、工具使用、记忆、多智能体协作或安全。然而，真实的智能体失败往往跨越组件：一段检索段落支持某个中间论断，该论断决定某个工具参数，工具输出更新记忆，而该记忆条目随后影响最终动作。很少有基准评估这条从证据与工具输出，到记忆更新、中间论断、最终答案、外部状态变更与恢复动作的完整链条。

**第二个缺口是关系标注**。许多基准暴露轨迹，但很少标注类型化溯源关系。全栈溯源基准应能判别：一个证据单元是 SUPPORT 还是 CONTRADICT 某个论断、一次工具调用是否 DEPEND-ON 不可信来源、新证据是否使某条记忆 INVALIDATE、一个观察是否 TRIGGER 修复。没有这类标签，评估往往只能间接度量正确性、忠实性或攻击成功率，而不能直接度量轨迹完整性、溯源准确性、依赖覆盖、记忆有效性或跨智能体责任。

**第三个缺口是面向恢复的评估**。现有基准通常判定智能体是成功、失败、产生幻觉、违反策略，还是执行了不安全动作。它们很少评估溯源能否帮助系统修复执行：使过期记忆失效、隔离被污染的证据、重试工具调用、请求人工批准、回滚不安全的状态变更，或对不可逆动作进行补偿。这很重要，因为溯源不应只在事后解释失败，还应支持安全的恢复与治理。

#### 6.3 证据追踪与执行溯源的指标

表 5 围绕溯源功能而非基准族，重组了基准指标。证据归因与安全指标相对成熟，因为它们已在 RAG、引用、幻觉、工具使用安全与提示注入场景中使用。相比之下，执行溯源指标——轨迹完整性、溯源准确性、依赖覆盖与时间一致性——大多仍处于“提出中”阶段：它们是自然的期望目标，但该领域尚无公认定义或被广泛采用的数据集。

这一指标视角强化了图 5 的主要结论。证据归因追问论断是否有依据；执行溯源追问过程是否可追踪；安全与鲁棒性追问不安全影响是否被检测或阻断；调试与恢复追问轨迹是否支持定位与修复。因此，感知溯源的基准应同时评估最终结果与产生该结果的轨迹结构。

#### 6.4 走向全栈溯源基准

全栈溯源基准应包含完整的执行轨迹，而不仅是最终答案或最终状态。它至少应记录：用户请求、检索到的证据、工具调用与输出、记忆读写、智能体间消息、中间论断、最终响应、外部状态变更，以及策略或权限上下文。它还应标注 SUPPORT、CONTRADICT、DEPEND-ON、UPDATE、INVALIDATE、TRIGGER 等类型化关系，使溯源质量可以被直接度量，而不是从任务成功中推断。

这类基准还应包含对抗性、时间性与面向恢复的条件。对抗性条件测试不可信内容能否影响工具参数、记忆或特权动作；时间性条件测试智能体能否区分当前证据与过期记忆、处理更新并在长程工作流中保持谱系；恢复任务则要求智能体或监视器利用溯源进行修复，包括重试、回滚、隔离、人工批准或补偿。

要点在于：基准设计必须从组件级评估走向过程级问责。现有基准有价值，因为它们评估了智能体技术栈的重要部件；但证据追踪与执行溯源要求为“这些部件如何交互”提供标签与指标。构建能够联合覆盖证据、工具、记忆、通信、安全、类型化关系与恢复的基准，仍是可信 LLM 智能体的核心开放问题。

### # 7 开放问题与未来方向

尽管 RAG 归因、智能体可观测性、工具使用安全、记忆系统、基于图的表示、调试与多智能体评估不断取得进展，LLM 智能体的证据追踪与执行溯源仍然碎片化。现有系统越来越多地记录执行产物，却很少解释证据、工具、记忆、观察、消息与动作如何共同塑造智能体的最终答案或外部行为。本节概述走向感知溯源智能体的开放问题——这类智能体应支持验证、审计、归因、运行时安全、恢复与治理。

#### 7.1 统一且可互操作的轨迹模式

一个核心开放问题是缺乏面向 LLM 智能体的统一轨迹模式（trace schema）。现有框架与基准记录不同的产物，包括提示、模型响应、工具调用、检索文档、记忆操作、环境观察、执行元数据与错误事件 [Dong et al., 2024; AlSayyad et al., 2026; Souza et al., 2025; Deshpande et al., 2025; Cemri et al., 2026]。然而，很少有模式能同时表示推理步骤、检索、工具调用与输出、记忆读写、智能体间消息、中间论断、最终响应与外部状态变更。

现有标准提供了有用的构件，却没有完全解决智能体溯源问题。W3C PROV-DM 为实体、活动、代理与派生关系提供通用词汇 [World Wide Web Consortium, 2013]；OpenTelemetry 与 OpenLineage 为分布式追踪与数据工作流谱系提供抽象 [OpenTelemetry, 2026; OpenLineage Contributors, 2026]；PROV-AGENT 把溯源建模适配到智能体工作流 [Souza et al., 2025]。未来的模式应把这些运行性轨迹结构与语义证据关系连接起来：表示论断、证据单元、工具观察、记忆条目、环境状态与智能体消息，以及 SUPPORT、CONTRADICT、DEPEND-ON、UPDATE、INVALIDATE 等关系。这样的模式将使智能体轨迹更易于跨框架比较、重放、标注、审计与交换。

#### 7.2 论断级与语义溯源

当前归因方法往往在粗粒度上操作，如答案级引用、上下文级忠实性或步骤级日志 [Gao et al., 2023; Ru et al., 2024; Wu et al., 2024b; Schreieder et al., 2025]。然而，智能体输出常常包含多个论断、中间假设与面向动作的推断。一个最终响应可能部分正确：某个论断有检索证据支持，另一个超出来源进行了推断，还有一个被工具输出或记忆条目反驳。这推动了**论断级溯源**（claim-level provenance），并可依托 ALCE、FActScore、RAGTruth、RAGChecker、SourceCheckup 等细粒度事实性与归因工作 [Gao et al., 2023; Min et al., 2023; Niu et al., 2024; Ru et al., 2024; Wu et al., 2024b]。

对智能体而言，更困难的问题是**跨变换的语义溯源**。证据可能在影响某个论断或动作之前，先被改写、摘要、聚合、压缩进记忆、经工具传递，或被另一个智能体复用。因此，字符串级匹配与“引用是否存在”是不够的。未来工作应追踪跨检索、工具输出、记忆更新、反思与智能体间通信的语义依赖，包括证据被间接使用或跨多步变换的情形。语义污点追踪（semantic taint tracking）与因果影响方面的工作指明了方向，但面向长智能体执行的鲁棒论断级溯源仍是开放问题 [Cai et al., 2026]。

#### 7.3 记忆与多智能体溯源

记忆溯源仍不成熟。长期记忆系统允许智能体跨会话存储、检索、更新与复用信息，但对“记忆条目来自哪里、是否仍然有效、是否与新证据冲突、如何影响后续论断或动作”的支持有限。现有记忆与图记忆综述覆盖了架构、评估方法与关系型记忆结构 [Zhang et al., 2025b; Du, 2026; Yang et al., 2026]，但“作为携带溯源证据的记忆”仍是一个独立的开放问题。

未来的记忆系统应为记忆条目附加溯源元数据，包括来源归因、写入时间、更新历史、检索上下文、下游使用、冲突状态与失效事件。记忆不应被当作一个不加区分的上下文仓库（context reservoir）：一条派生自用户输入、检索证据、工具输出、环境观察、反思或他人消息的记忆，应携带不同的信任含义。当记忆影响工具调用、个性化或长期决策时尤其如此。记忆投毒与记忆注入攻击进一步表明，被攻破的记忆可以在不修改模型权重的情况下影响未来行为 [Chen et al., 2024; Dong et al., 2025]。

多智能体溯源引入了额外的**责任**（responsibility）问题。智能体之间会通信、委托任务、相互验证输出，并共同产生最终决策。AutoGen 与 CAMEL 等框架展示了分布式智能体工作流 [Wu et al., 2024a; Li et al., 2023]；MAST、AgenTracer 与 Aegis 表明，失败可能需要归因到责任智能体、步骤或错误模式 [Cemri et al., 2026; Zhang et al., 2025a; Kong et al., 2025]。未来的溯源模型应追踪论断、证据、消息与错误如何跨智能体传播，并把责任归因与论断级证据支持、记忆谱系及恢复动作集成起来。

#### 7.4 运行时安全、执行约束与恢复

LLM 智能体的运行时安全需要的不只是输出过滤。在使用工具的智能体中，危险行为可能出现在：不可信内容影响工具参数、私有信息流入公开输出、过期记忆影响特权动作，或智能体在预期边界之外调用工具。只检视最终答案或当前工具调用的护栏，可能错过这些“来源—汇点”依赖。感知溯源的护栏应对影响拟议动作的证据、记忆条目、工具输出、观察与外部内容进行推理 [Zhan et al., 2024; Debenedetti et al., 2024, 2025; Costa et al., 2025; Sequeira et al., 2026; Bühler et al., 2025]。

近期的提示注入基准、控制/数据流分离、信息流控制、语义污点追踪、运行时约束、执行溯源图与访问边界等工作，指向了感知溯源的执行 [Ruan et al., 2024; Zhan et al., 2024; Debenedetti et al., 2024, 2025; Costa et al., 2025; Cai et al., 2026; Wang et al., 2025a; Sequeira et al., 2026; Bühler et al., 2025]。剩下的挑战是**恢复**。大多数系统聚焦于检测或阻断不安全行为，但可信智能体还需要修复无依据或不安全的执行。未来系统应利用溯源：使过期记忆失效、隔离被污染的证据、以更正后的参数重试工具调用、请求人工批准、回滚不安全的状态变更，或从安全检查点重放执行。这要求溯源表示支持干预与恢复，而不仅是解释。

#### 7.5 现实基准、隐私与治理

当前基准仍缺乏真实的完整执行轨迹。RAG 基准提供证据标签但通常缺少工具与记忆；工具使用安全基准提供攻击与工具调用但往往缺少论断级证据标签；记忆基准评估召回或个性化但很少评估谱系、冲突处理或下游影响；多智能体基准分析失败但往往缺少完整溯源标注。AgentBench、WebArena、τ-bench、TRAIL、MAST、LOCOMO、MemoryArena 等基准提供了重要基础 [Liu et al., 2024; Zhou et al., 2024; Yao et al., 2025; Deshpande et al., 2025; Cemri et al., 2026; Maharana et al., 2024; Kim et al., 2026]，但没有一个基准族能完整评估跨检索、工具使用、记忆、多智能体通信、安全攻击与恢复的证据追踪与执行溯源。

未来基准应从孤立的答案级、任务级或攻击级评估，走向轨迹级评估。它们应捕获跨检索、工具、执行边界、记忆、环境交互、智能体间通信与状态变更的完整执行记录，并标注支持、矛盾、依赖、触发、更新、失效、不安全影响、责任智能体与恢复干预等溯源关系 [World Wide Web Consortium, 2013; Dong et al., 2024; AlSayyad et al., 2026; Souza et al., 2025; Deshpande et al., 2025; Cemri et al., 2026; Zhang et al., 2025a; Kong et al., 2025; Vijayvargiya et al., 2026; Zong et al., 2025]。与此同时，溯源轨迹可能包含敏感用户数据、机密文档、凭据、工具输出、API 参数、内部推理产物与长期记忆条目。因此，未来系统必须支持轨迹最小化、访问控制、匿名化、保留策略、加密与选择性披露。没有感知隐私的治理，溯源基础设施本身可能成为合规与安全风险的来源 [Dong et al., 2024; AlSayyad et al., 2026; Costa et al., 2025]。

总体而言，感知溯源的智能体需要的不仅是更丰富的日志。它们需要可互操作的模式、语义的论断级归因、记忆与多智能体谱系、带恢复能力的运行时执行约束，以及把可追踪性、可审计性、安全、隐私与可恢复性作为一等能力加以评估的基准。

### # 8 结论

LLM 智能体正在超越孤立的文本生成，走向检索证据、规划中间步骤、调用工具、更新记忆、与环境交互并与其他智能体协作的系统。这一转变使最终答案正确性不足以支撑可信性：可靠的智能体系统还必须揭示答案来自哪里、哪些证据支持它们、工具与中间动作如何做出贡献、失败或不安全的影响从何处进入执行过程。本综述把证据追踪与执行溯源定位为在智能体生命周期中研究这些问题的统一视角。我们评述了关键的溯源表示——结构化日志、执行图、证据图、工具依赖图、记忆溯源与多智能体通信轨迹——并讨论了它们在归因、调试、验证、安全执行、评估与恢复中的作用。

我们的综述表明，该领域已取得重要进展，但仍碎片化。现有系统常常记录来源或工具调用，却很少提供细粒度的论断级支持、语义影响追踪、记忆谱系、跨智能体溯源传播，或对抗条件下的鲁棒追踪。展望未来，证据追踪与执行溯源应成为可靠智能体系统的一等基础设施层。我们希望本综述有助于巩固这一新兴研究方向，并推动可追踪、可审计、可恢复的 LLM 智能体的发展。

### # 附录 D 开放问题的附加细节

本附录扩展第 7 节讨论的开放问题。正文给出研究议程；本附录提供更详细的设计需求、代表性基础与评估维度。

#### D.1 轨迹模式需求

统一的 LLM 智能体溯源模式，应把运行性执行记录与语义证据关系结合起来。表 9 总结了主要的模式需求。

现有标准与框架提供了部分基础。W3C PROV-DM 定义了实体、活动、代理、生成、使用、派生与失效等通用溯源概念 [World Wide Web Consortium, 2013]；OpenTelemetry 提供分布式追踪抽象；OpenLineage 提供数据工作流谱系 [OpenTelemetry, 2026; OpenLineage Contributors, 2026]；AgentOps 与 AgentTrace 通过记录结构化智能体产物与执行上下文，更接近 LLM 智能体可观测性 [Dong et al., 2024; AlSayyad et al., 2026]；PROV-AGENT 把溯源建模适配到智能体工作流 [Souza et al., 2025]。然而，LLM 智能体溯源还需要额外的语义单元与关系，尤其是生成的论断、证据支持、矛盾、记忆失效、工具参数影响与智能体间责任。

**表 9**　统一 LLM 智能体溯源模式的设计需求。

| 需求 | 应表示的内容 | 为何重要 |
| --- | --- | --- |
| 轨迹来源 | 用户指令、模型输出、检索调用、工具调用、记忆操作、环境观察、智能体间消息与最终响应。 | 支持智能体执行的端到端重建。 |
| 证据单元 | 文档、段落、工具输出、观察、记忆条目、策略、中间论断与最终论断。 | 支持论断级验证与归因。 |
| 执行单元 | 推理步骤、检索操作、工具调用、参数生成步骤、记忆读写、环境动作与消息交换。 | 支持调试、安全执行与审计。 |
| 类型化关系 | SUPPORT、CONTRADICT、DEPEND-ON、DERIVE、TRIGGER、UPDATE、INVALIDATE、USE 与 GENERATE。 | 把原始日志转化为暴露影响与责任的溯源图。 |

| 重放与恢复字段 | 检查点、回滚目标、失效事件、修复步骤、人工批准与状态变更记录。 | 支持干预与恢复，而不仅是事后解释。 |

#### D.2 语义与论断级溯源的详细议程

论断级溯源至少应区分当前系统中常被混为一谈的五种关系：引用存在性、来源相关性、论断支持、矛盾与证据遗漏。ALCE、FActScore、RAGTruth、RAGChecker、SourceCheckup 及相关归因综述为这一方向提供了基础 [Gao et al., 2023; Min et al., 2023; Niu et al., 2024; Ru et al., 2024; Wu et al., 2024b; Schreieder et al., 2025]。然而，智能体场景带来额外挑战：证据可能在影响最终答案或动作之前，已经过推理、检索、工具、记忆、反思或智能体间通信的变换。

因此，未来工作不仅应评估最终论断是否被支持，还应评估支持性信息如何流经执行。重要情形包括：派生自多个检索段落的论断；与记忆条目矛盾的工具输出；从前次对话摘要而来的记忆条目；论证或阻断动作的策略约束；传播无依据假设的智能体间消息。NeuroTaint 等语义污点与因果影响方法，提示了追踪变换影响的一条路径，但鲁棒的语义溯源仍是开放问题 [Cai et al., 2026]。

#### D.3 记忆与多智能体溯源清单

表 10 列出了未来记忆与多智能体系统应暴露的溯源字段。

记忆系统不应把长期记忆当作通用的上下文仓库。记忆条目应携带谱系、有效性、信任与下游使用元数据，尤其是在它们影响工具调用、个性化或长程决策时。记忆投毒与记忆注入攻击凸显了追踪“被攻破的记忆如何影响后续执行”的必要性 [Chen et al., 2024; Dong et al., 2025]。多智能体系统需要平行的消息级溯源。在由委托、批评、验证与角色分工构成的工作流中，溯源不仅应识别哪个最终答案出错，还应识别哪个智能体引入了无依据论断、哪个智能体未能验证它、哪条消息传播了它 [Wu et al., 2024a; Li et al., 2023; Cemri et al., 2026; Zhang et al., 2025a; Kong et al., 2025]。

**表 10**　记忆与多智能体溯源清单。

| 场景 | 溯源字段 | 开放问题 |
| --- | --- | --- |
| 记忆写入 | 来源、时间戳、写入者、证据基础、置信度与策略上下文。 | 记忆是来自可信证据，还是来自无依据/被注入的内容？ |
| 记忆更新 | 前一版本、更新来源、更新原因、冲突状态与失效标记。 | 更新是对早先记忆的修订、矛盾还是失效？ |
| 记忆检索 | 检索查询、被检索的记忆条目、排序分数、复用上下文与下游消费者。 | 为何复用该记忆？它如何影响当前执行？ |
| 记忆删除或失效 | 删除触发器、失效证据、受影响的下游论断/动作与恢复步骤。 | 能否在不破坏可审计性的前提下移除过期或被投毒的记忆？ |
| 智能体间通信 | 发送者、接收者、角色、消息内容、引用证据、委托任务与验证状态。 | 哪个智能体引入、验证、复用或放大了某个论断？ |
| 多智能体失败 | 责任智能体、责任步骤、错误模式、传播消息与反事实轨迹。 | 失败源于何处？如何跨智能体传播？ |

#### D.4 运行时安全与恢复需求

运行时溯源应同时支持执行约束与修复。表 11 总结了这一区分。

当前大多数系统聚焦于检测、阻断或策略执行。更强的感知溯源运行时应支持干预。例如，若某个工具参数派生自不可信网页内容，系统不仅应阻断该动作，还应识别被污染的来源、移除派生参数、请求确认，并防止同样的污染被写入记忆。若某条记忆随后被新证据反驳，系统应使其失效，并识别依赖它的下游论断或动作。这些恢复操作要求溯源图保留证据、工具、记忆、状态变更与动作之间的依赖。

**表 11**　感知溯源智能体的运行时安全与恢复需求。

| 能力 | 溯源需求 | 代表性基础 |
| --- | --- | --- |
| 提示注入检测 | 识别不可信外部内容是否影响特权指令、工具调用或记忆更新。 | InjecAgent、AgentDojo、ToolEmu [Zhan et al., 2024; Debenedetti et al., 2024; Ruan et al., 2024] |
| 信息流控制 | 跨输入、工具、记忆与输出追踪机密性与完整性标签。 | CaMeL、FIDES [Debenedetti et al., 2025; Costa et al., 2025] |
| 语义污点追踪 | 追踪跨摘要、改写、推理与记忆整合的影响。 | NeuroTaint [Cai et al., 2026] |
| 参数验证 | 检查敏感工具参数是否派生自可信来源或显式用户意图。 | Agent-Sentry [Sequeira et al., 2026] |
| 执行设界 | 在运行时强制执行工具权限、访问边界与策略约束。 | AgentSpec、AgentBound [Wang et al., 2025a; Bühler et al., 2025] |
| 恢复 | 使过期记忆失效、隔离被污染证据、重试工具调用、请求批准、回滚状态变更，或从安全检查点重放。 | 开放问题，建立在溯源执行与轨迹调试之上。 |

#### D.5 基准与治理需求

未来基准应把溯源作为一等对象评估，而不是任务成功的隐式副产品。表 12 总结了主要的基准与治理需求。

现有基准族提供了部分基础。RAG 与归因基准支持证据依据；工具使用与安全基准暴露工具调用、不安全动作与提示注入风险；记忆基准评估召回与个性化；多智能体基准评估协作与失败模式；轨迹调试基准支持失败定位 [Gao et al., 2023; Ru et al., 2024; Wu et al., 2024b; Liu et al., 2024; Zhou et al., 2024; Ruan et al., 2024; Debenedetti et al., 2024; Yao et al., 2025; Vijayvargiya et al., 2026; Zong et al., 2025; Maharana et al., 2024; Kim et al., 2026; Deshpande et al., 2025; Cemri et al., 2026; Zhang et al., 2025a; Kong et al., 2025]。剩余的缺口是对溯源链的端到端评估——把证据与工具输出连接到记忆更新、中间论断、最终答案、外部状态变更与恢复动作。

隐私与治理应与溯源质量一同评估。溯源轨迹可能包含敏感用户信息、机密文档、凭据、API 参数、内部推理产物与长期记忆条目。AgentOps 与 AgentTrace 等可观测性系统为轨迹收集提供了基础 [Dong et al., 2024; AlSayyad et al., 2026]；FIDES 则强调机密性与完整性约束 [Costa et al., 2025]。未来系统还应支持轨迹最小化、访问控制、匿名化、保留策略、加密与选择性披露，使溯源基础设施本身不会成为隐私或合规风险。

**表 12**　现实溯源基准与治理的需求。

| 需求 | 当前局限 | 未来基准目标 |
| --- | --- | --- |
| 完整执行轨迹 | 现有基准常常只捕获答案、工具调用、攻击、记忆检索或失败标签。 | 捕获检索、工具、记忆、环境状态、智能体间消息、论断、动作与状态变更。 |
| 关系标注 | 溯源关系很少被直接标注。 | 标注 SUPPORT、CONTRADICT、DEPEND-ON、TRIGGER、UPDATE、INVALIDATE、不安全影响与恢复干预。 |
| 跨组件覆盖 | RAG、工具使用、记忆与多智能体基准通常评估孤立能力。 | 评估证据、工具、记忆、消息与状态变更如何共同影响最终输出与动作。 |
| 恢复评估 | 基准通常测试成功、失败、幻觉或不安全动作。 | 测试智能体能否通过使记忆失效、隔离证据、重试工具、请求批准或回滚不安全动作来修复轨迹。 |

| 审计与治理 | 仅收集轨迹并不保证问责。 | 评估轨迹是否可检视、符合策略、可比较并可用于审计。 |

## 篇二 · LLM 智能体轨迹分析综述：从失败归因到系统增强

_A Survey for LLM Agent Trajectory Analysis: From Failure Attribution to Enhancement_

**作者**：Junjie Wang, Yawen Wang, Mengzhuo Chen, Xiaofei Xie, Chunyang Chen, Fangwen Mu, Zhe Liu, Qing Wang（中国科学院软件研究所智能博弈重点实验室 / 中国科学院大学 / Singapore Management University / Technical University of Munich）

摘要——大语言模型(LLM)智能体(Agent)已成为一种变革性的软件范式:它通过自然语言推理、多智能体协作与工具集成,实现自主任务执行。然而,其非确定性的决策过程与复杂的交互模式,给失败诊断与系统改进带来了前所未有的挑战。与传统软件中失败往往表现为代码缺陷不同,智能体的失败埋藏在冗长、以自然语言为主的执行轨迹(Trajectory)之中——这些轨迹包含自然语言推理,掩盖了根因,使修复变得困难。本综述系统梳理了 LLM 智能体轨迹分析这一快速兴起的领域,覆盖失败归因(Failure Attribution)与系统增强(System Enhancement)两大主题。我们收集了 2025 年初至 2026 年 4 月间发表的 55 篇论文,横跨软件工程、人工智能与人机交互。我们从五个关键维度组织文献:失败分类体系、失败归因、系统增强与优化、轨迹监测与分析工具,以及数据集与基准。分析表明,尽管该领域已从简单的 LLM 提示,迅速发展到因果推断、微调的追踪模型与动态干预,但步骤级归因准确率仍然有限,基准的多样性仍是瓶颈。我们识别出四类互补的分类视角、四种归因方法范式与三类增强策略,并批判性地评估了现有基准,指出近期向完全可观测性与不可恢复失败标注的转变。本综述既是当前研究的结构化概览,也为构建鲁棒、高效、可持续自我改进的智能体生态系统提供战略指南。我们同时呼吁软件工程界更深入地参与这类新兴软件的研究,把缺陷定位、程序修复与实证方法的专业积累,用于应对 LLM 智能体带来的独特挑战。

#### 4.1失败分类体系

如前所述,作为一种新兴的软件形态,LLM 智能体所表现出的失败,其形式与特征与传统软件存在实质差异。因此,多位研究者着手分析这些系统为何以及如何失败:他们检查这些系统产生的轨迹以诊断失败根因,并超越单个失败实例,建立对失败为何发生、如何发生的结构化理解。这些努力催生了针对此类系统的众多失败分类体系。

##### 4.1.1分类体系梳理

研究者提出了多种分类体系来结构化地理解 LLM 智能体的失败。这些工作虽在具体划分上各不相同,但可以通过它们分析系统失败的视角加以综合。为提供更精炼的比较视角,我们围绕四个引导性问题组织现有工作:(1)失败发生在任务流水线的哪个阶段(WHERE)?(2)智能体的哪项核心能力失效(WHAT)?(3)谁(哪个智能体或系统组件)负有责任(WHO)?(4)在给定环境上下文下,失败为何会发生(WHY)?

**(1)按任务执行阶段组织的分类体系(WHERE)。**这一视角沿任务天然的顺序流水线剖析智能体失败,提出根本性的调试问题:"任务流水线的哪个环节出了错?"该视角对开发者非常直观,并与运维监测相吻合,因为它将失败直接映射到任务轨迹中可观测的阶段。

例如,Lu 等 [22] 与 Guo 等 [23] 都采用这种基于阶段的视角对失败分类。Lu 等建立了三层失败原因分类体系,突出规划错误、任务执行问题与错误的响应生成。具体而言,任务规划相关失败包括不当的任务分解、导致无限循环的失败自我修正,以及超出智能体能力的不切实际的规划;任务执行失败包括未能利用外部工具、生成有缺陷的代码与环境配置不当;响应生成阶段则易出现格式问题、上下文窗口限制导致的信息丢失,以及超出最大交互轮数。

**(2)按智能体能力模块组织的分类体系(WHAT)。**从外部工作流转向内部认知,这一视角聚焦智能体的核心功能组件,追问:"智能体的哪项核心认知功能失效了?"AgentErrorTaxonomy [24] 与 TRAIL [25] 等分类体系采用这一视角,围绕记忆、反思、规划、行动与系统执行等模块组织失败。该视角对于旨在增强智能体特定能力、理解智能体智能组合本质的研究至关重要。

例如,Zhu 等 [24] 提出 AgentErrorTaxonomy——一种横跨记忆、反思、规划、行动与系统级操作的模块化失败模式分类。记忆失败指回忆或检索信息时的错误(错误回忆、遗漏、检索失败),它们会扭曲后续推理;反思失败是监控进度或解读结果时的失误(进度误判、结果误读),阻碍路线修正;规划失败包括逻辑不成立或不可行的策略(不可能的动作、忽视约束、子目标不一致),它们会级联引发后续失误;行动失败是执行操作中的错误(格式错误的输出、参数错误、遗漏参数),这些错误显眼,但往往掩盖上游错误;系统级失败是推理之外的错误,如工具崩溃、API 不匹配或超出步数限制,凸显系统鲁棒性问题。

**(3)按系统与交互组织的分类体系(WHO)。**这一视角将分析提升到智能体系统及其生态的层面,针对由交互引发的失败,追问:"谁该负责——智能体、协调机制,还是平台?"MAST [28]、AgentFail [27] 与 AgentRx [26] 等框架采用这一视角,顶层类别包括规格说明问题、智能体间失配与平台级失败。这一视角对诊断多智能体协作中复杂的、往往非确定性的失败至关重要——问题不在任何单个节点的推理,而在于支配其集体行为的通信、共享理解或基础设施。

例如,Cemri 等 [28] 提出 MAST(多智能体系统失败分类体系),识别出 14 种独特的失败模式,组织为 3 个类别:规格说明问题、智能体间失配与任务验证。具体而言,规格说明失败源于系统设计决策,以及拙劣或含糊的提示词规格;智能体间失配失败源于执行过程中智能体间交互与协调的崩坏;任务验证失败涉及未能检测或纠正错误的、不充分的验证过程,或任务过早终止。

**(4)按环境上下文组织的分类体系(WHY)。**这一视角聚焦由智能体运行环境条件塑造的失败模式,追问:"在特定环境上下文下,失败为何发生?"当周围环境的性质——如有限的可观测性、有状态的导航、轮次或 token 预算限制——强烈影响智能体行为与失败模式时,这类分类体系尤为有用。

Aegis-Song [29] 中的分类体系是这一视角的代表。它刻画智能体与环境交互时如何失败,包括探索失败、利用失败与资源耗尽。例如,探索失败指智能体无法从环境中收集所需的关键上下文;利用失败指智能体已获得相关信息,却未能在环境约束下正确使用;资源耗尽则涵盖由有限的轮次或 token 预算引发的失败。

##### 4.1.2最普遍的失败

表 2 列出了各失败分类体系中排名前三的失败。我们将在各种研究中最频繁出现的失败类型汇总如下。

**指令与格式保真:**这一类型表现为格式错误(TRAIL)、响应内容偏差(AgentFail)、指令遵循(AgentRx)与指令不合规(TRAIL、Aegis-Song),位居榜首。它凸显了在可靠遵循输出规范与复杂指令方面的持续困境——这也是更广泛的 LLM 研究中一贯确认的基础性局限 [76], [77]。

**任务规划与分解:**不当任务分解(Lu 等)、低效规划(AgentErrorTaxonomy)与目标偏离(TRAIL)等失败,指向在逻辑上构建并贯彻长时程任务方面的不足。

**交互、状态与协调:**在多智能体场景中,步骤重复与推理-行动失配(MAST)颇为常见,暴露了维持一致状态与协作的困难。

**知识与推理局限:**知识或推理受限(AgentFail)与幻觉(许多体系中隐含)仍是底层 LLM 的根本约束。

#### 4.2失败归因

失败归因是诊断与改进 LLM 智能体的基石。它旨在系统地判定:哪个智能体出了错、关键错误发生在哪一步,以及为什么。核心挑战在于,从复杂、异构的交互数据(涵盖 LLM 推理、工具调用与环境反馈)中观察到的失败出发反向推理,推断内部逻辑的断裂处并锁定根因。这项任务尤其困难,因为失败被观测到的位置往往不是其源头:规划、知识或协调中的初始错误,可能经过多步智能体推理与工具执行的传播与变形,掩盖其原始来源。这种传播在症状与根因之间造成了显著鸿沟,需要更精细的、基于推断的归因技术。

当前针对 LLM 智能体的失败归因研究大致可分为四类,反映出分析深度与干预强度的递进。我们从基于模式分析的方法开始(第 4.2.1 节),它被动地从执行轨迹中挖掘统计规律以定位故障;在观测数据的基础上,基于 LLM 推理的方法(第 4.2.2 节)利用基础模型天生的分析能力,模拟人类式的诊断推理;为克服通用 LLM 的局限,基于模型微调的技术(第 4.2.3 节)在精选的失败数据集上训练专门的追踪模型,以求更高的效率与准确率;最后,基于动态运行时的方法(第 4.2.4 节)采取干预主义范式,通过运行时编辑与仿真主动检验因果假设。以下小节逐一详细介绍。

##### 4.2.1基于模式分析的归因

作为归因技术中最"偏观测"的一类,基于模式分析的方法通过在大量执行轨迹之间挖掘重复出现的信号来定位故障,完全依赖数据驱动的统计分析,不做运行时干预。这一族技术经历了三个递进阶段:从粗粒度的可疑度评分,到阶段级责任追踪,最终到具有因果意识的结构化错误表示。

最早的工作将传统软件工程中的经典缺陷定位思想迁移到智能体场景。FAMAS [30] 开创了这条技术路线,它改造了基于频谱的缺陷定位:系统性地重放轨迹,根据每个智能体动作在失败与成功运行中出现的频度计算"可疑度"分数,并用一个定制公式同时整合智能体级与动作级的激活模式。Barrak 等 [31] 通过 Planner → Executor → Critic 流水线实现同一目标,责任沿流水线向前传播,直到锁定最早的未修复错误。

后续工作将重心转向知识复用与效率。CORRECT [32] 将反复出现的失败蒸馏为紧凑的错误模式,供实时识别复用,从而将诊断与昂贵的轨迹重放解耦。SDBL [33] 应对可扩展性挑战:在细粒度定位之前先收窄搜索空间,借鉴代码缺陷的表现模式来圈定潜在故障区域。

最新的工作则以结构化错误建模充实基于模式的归因。AgentEval [23] 构建有向无环图(DAG),显式追踪根因如何向后继步骤传播,从点式定位迈向对错误级联的捕捉。PROMAS [34] 引入因果增量表示与向量马尔可夫熵模型,精确定位轨迹偏离成功行为的时刻——将模式匹配与因果变化检测有效结合。

##### 4.2.2基于 LLM 推理的归因

基于 LLM 推理的方法从挖掘相关性转向模拟人类式诊断推理。这类方法利用基础模型的分析能力,通过精细的提示与结构化推理过程,从完整任务轨迹推断根因。这一类别内部的演进轨迹清晰:从朴素提示,到带共识机制的结构化推理流水线,再到显式因果建模,最后到以外部验证或记忆增强 LLM 推理的混合方法。

这一范式最早的实例是对完整轨迹的直白提示。开创性的 Who&When 基准 [11] 确立了该范式,评估了三种基本策略——一次性给出(All-at-once)、逐步进行(Step-by-step)与二分查找(Binary search)——既证明了用 LLM 处理这一复杂任务的可行性,也暴露了其有限的准确率。

为提升可靠性,后续工作引入了更结构化的推理过程。ECHO(通过上下文层次与目标共识分析进行错误归因)[35] 为整条交互轨迹构建层次化上下文表示,在各上下文上提供独立的目标分析,并通过共识投票交叉验证结论。RAFFLES [36] 采用迭代式多组件流水线:中央"裁判"(Judge)系统性地调查故障,而专门的"评估器"(Evaluator)不仅评估系统组件,还评估裁判自身推理的质量,形成自我修正的诊断回路。

除了结构与因果层面的增强,一些方法还引入外部机制来为 LLM 推理提供依据。CodeTracer [40] 将执行日志组织为带嵌套作用域的层次化"轨迹树",使 LLM 能在合适的抽象层级上推理。AgentRx [26] 将约束合成与基于 LLM 的判断相结合,生成关于约束违反的、可审计的验证日志,再由 LLM 加以定位。ERRORPROBE [41] 用情景记忆增强推理,以检索增强的验证缓解诊断过程本身的幻觉。

##### 4.2.3基于模型微调的归因

与基于提示的方法不同,这一范式专注于训练专职失败归因的专门模型。由此得到的专用追踪模型学会高效解析复杂的智能体交互、识别错误传播模式,并以相比通用 LLM 更高的准确率与推理效率定位故障。

AgenTracer [42] 奠定了这一方向的基础流水线。它首先通过反事实重放与程序化故障注入标注失败的智能体轨迹,产出精选数据集 TracerTraj;依托这一资源,训练出以多粒度强化学习训练的轻量级失败追踪器 AgenTracer-8B,能够高效诊断冗长多智能体交互中的错误。

GraphTracer [43] 从顺序式轨迹分析迈向结构化图表示。它构建信息依赖图(IDG),显式刻画智能体如何引用并在先前输出之上构建,从而能沿依赖边而非时间步追踪故障传播。其训练数据由图感知的故障注入生成,失败追踪器的训练也以图结构奖励为引导。

随后,Aegis-Kong [44] 将这一范式规模化、系统化。它构建了迄今最大的合成归因数据集之一,并开展了全面的实证研究,直接比较三种不同的学习策略——监督微调、强化学习与对比学习——在训练鲁棒失败归因模型上的效果。结果显示,强化学习与对比学习优于标准监督微调,表明归因任务能够从"下一词元预测"之外的目标中获益。

##### 4.2.4基于动态运行时的归因

超越被动的日志分析,这一组技术采取主动的、干预主义的归因方式。其关键设计原则是:先形成关于根因的假设,再通过有针对性的干预加以检验——即系统性地测试"若修改假设的根因,失败是否就不会发生"。

DoVer [45] 是一个干预驱动的调试框架,通过有针对性的干预(如编辑消息、修改计划)为假设生成补充主动验证。AgentDebug [24] 应用了类似思想:为每一步、每个模块赋予细粒度错误类型,再依据诊断出的错误类型引导有针对性的重新执行(re-rollout)。

该范式进一步演进为将 LLM 推理与动态验证紧密集成。TraceElephant [46] 与 AgentFail [27] 是典型代表:先用基于 LLM 的候选定位,再做反事实验证。

#### 4.3系统增强与优化

诊断失败的最终目的在于实现改进。一旦失败的根因被归因,下一个关键步骤就是利用这一洞察来增强系统的能力、可靠性与效率。本节聚焦利用轨迹分析驱动增强与优化的方法。这可以通过重塑智能体运行所处的外部结构与环境实现(第 4.3.1 节),通过革新智能体自身的内部驱动与机制实现(第 4.3.2 节),或通过在运行时附加轻量级的过程管理或监督层实现(第 4.3.3 节)。

##### 4.3.1结构与工作流优化

这一范式从外部重新设计多智能体系统的协作架构与交互环境,以提升整体性能与鲁棒性。现有工作可按其干预深度组织,目标逐层深入系统栈。

环境级优化是干预最浅的形式,只修改智能体运行的条件,不触及核心逻辑。Song 等 [29] 设计了 Aegis:增强环境可观测性、卸载常见计算,并对智能体动作进行推测执行。

工作流级优化将目标内移到协作图结构及其相关配置。Wang 等 [47] 提出 Maestro,一个框架无关的优化器,在显式的 rollout 与 token 预算下联合搜索图拓扑与智能体配置,由执行轨迹的反思性文本反馈引导。CE-Graph [48] 采用诊断驱动的变体:先从反例估计失败分布,将失败密集区域识别为重复出现的模式,再施加有针对性的、受算子约束的图编辑。ILWS [49] 更进一步,把系统级指令当作带版本、可编辑的"伪参数",由每次会话后的反思引擎进化。与优化图拓扑的 Maestro 和 CE-Graph 不同,ILWS 精炼的是支配所有智能体行为的共享指导原则,从而在不修改底层模型的情况下实现事后自我改进。

##### 4.3.2智能体内部优化

与修改外部框架不同,这一路线聚焦优化智能体内部的决策逻辑以提升性能。方法可按修改的粒度组织:从高层提示词,到模型机制,再到可复用技能。

提示词级优化侵入性最小。SCOPE [50] 将提示词进化形式化为在线学习问题,在战术性错误解决与战略性原则精炼之间取得平衡。Fang 等 [69] 采取互补的归因驱动方法:先识别哪些决策或推理步骤导致了失败,再生成上下文相关的指导来引导未来行为。

策略/指令级优化修改智能体的内部策略或系统指令,例如"避免未经验证的工具调用"。AgentDevel [51] 将自我进化形式化为一条发布工程流水线:LLM 评审者刻画失败,脚本化诊断产出工程规格说明,以"翻转为中心"的准入机制优先处理回归修复。ReCreate [52] 利用交互轨迹作为信号,自动创建并增强领域智能体,把单次任务的成败转化为智能体行为规则的持久更新。

模型级优化直接调整底层 LLM。SEAlign [53] 用树搜索对关键动作进行细粒度偏好优化,直接调整模型的决策偏好,而非表面提示词。

技能级优化构建可复用能力。Trace2Skill [55] 从多条轨迹并行提出补丁,并经无冲突合并将其融合,把单次修复转化为可组合的技能。

##### 4.3.3运行时与监督优化

第三种范式转而通过优化执行过程的数据流,或附加轻量级的外部监督层,来提升效率与鲁棒性。

输入空间优化减少智能体上下文中的噪声。AgentDiet [56] 从轨迹中移除无用、冗余或过期的信息,在不改变决策逻辑的前提下削减 token 成本。

行为空间优化在执行过程中注入外部引导信号。SUPERVISORAGENT [57] 用无需 LLM 的自适应过滤器检测关键节点并主动纠正错误。Wink [58] 优先考虑低开销,周期性地把智能体从不当行为中"轻推"出来,适合持续的后台监控。Liu 等 [54] 基于以过程为中心的度量(如进度率、动作熵)触发干预,实现自适应的、目标驱动的引导。

#### 4.4轨迹监测与分析工具

智能体系统的可观测性——即能够捕获并理解其内部状态与交互——对失败诊断与系统改进至关重要。本节评述通过使执行轨迹可解释来增强可观测性的方法,它们同时支持自动分析与人在回路的检查。

该领域的工作可按主要侧重粗略分为两组:面向底层、非侵入式系统监测与被动诊断的工具(第 4.4.1 节),以及面向高层、交互式分析与主动调试的工具(第 4.4.2 节)。

##### 4.4.1系统级监测与被动诊断工具

这一类别致力于从智能体系统中被动、透明且全面地采集执行数据。

第一组工具聚焦外部、非侵入式的插桩,在不修改应用代码的前提下观测智能体行为。AgentSight [59] 是一个可观测性框架,在稳定的系统接口处从应用代码外部监测智能体,用于识别浪费资源的推理循环,揭示隐蔽的协调瓶颈。

在被动数据采集的基础上,另一条工作线将结构化诊断分析直接嵌入监测流水线。Moshkovich 等 [60] 提出 AgentOps 自动化流水线,涵盖行为观测、指标收集、问题检测、根因分析、优化建议与运行时自动化六个阶段。

第三个方向优先考虑人类可读性,构建让轨迹对开发者直观可见的交互式可视化。AgentDiagnose [61] 提供定量可视化与诊断框架:(i)评估模块量化五项核心智能体能力——回溯与探索、任务分解、观察读取、自我验证与目标质量;(ii)可视化模块通过 t-SNE 动作嵌入、交互式词云与状态转移时间线凸显轨迹语义。类似地,Agent Trajectory Explorer [62] 提供直观界面,支持对智能体执行轨迹的可视化检查与人工标注。

##### 4.4.2交互式分析与主动调试工具

超越数据采集,这一类别聚焦构建让开发者能够探索并干预智能体轨迹的交互式工具。

AGDebugger [63] 是交互式调试工具,允许用户重置到先前状态并修改过去的智能体消息,从而支持迭代的、假设驱动的调试。XAgen [64] 连接自动判断与人在回路反馈:它能把执行轨迹转成可交互的流程图用于轨迹可视化,也允许用户对输出做标注,作为失败归因与迭代改进的反馈。DiLLS [65] 旨在揭示并结构化多智能体系统的行为,将执行信息组织为三层:总体规划与执行、动作安排与结果、具体操作日志。

##### 4.4.3面向从业者的可观测性平台

除文献中的研究原型外,更广泛的生态还包括广泛使用的、面向从业者的 LLM 智能体轨迹可观测性平台。代表性的开源例子包括 Langfuse、Weave 与 Arize Phoenix,支持轨迹检查、提示词/工具调用监测、评估与工作流调试。也有商业或托管平台,如 LangSmith5、HoneyHive6 与 Braintrust7,为多步 LLM 应用与智能体系统提供面向生产的追踪、评估与监测能力。尽管这些工具并非通过存档的研究论文引入,因而不在本综述的主体语料之内,它们在实际 AgentOps 中扮演着重要角色,可作为真实部署中轨迹监测与诊断的宝贵基础设施。

#### 4.5数据集与基准

基准与数据集为该领域的研究提供基础支撑:它们既是衡量与比较不同归因技术性能的客观、统一的评估标准,也是为数据驱动诊断模型提供高质量训练数据的来源。现有研究大致可分为两类:从真实失败收集的、以评估为中心的基准,以及同时面向训练与评估的、经错误注入构造的合成数据集。

##### 4.5.1从真实失败收集的基准

这类数据集从实际部署的智能体中收集自然发生的失败,因而贴近真实应用场景。

Zhang 等 [11] 提出 Who&When 基准——该领域的开创性基准,几乎被所有失败归因研究使用。每条失败轨迹都标注了失败责任智能体与对应失败步骤,部分还以自然语言标注了失败原因。AgentRx [26] 聚焦首个不可恢复的失败步骤,认为可恢复的步骤对归因的意义较小。Chen 等 [46] 指出既有基准依赖部分可观测性(仅智能体输出),因此提出具有完整执行轨迹与可复现环境的 TraceElephant。这与真实开发者场景一致:可用于诊断的是完整轨迹,而非仅输出。

其他基准提供更细粒度或多视角的标注。TRAIL [25] 与 AgentErrorBench [24] 提供更细粒度的根因,以促进对失败的更好理解。MPBench [66] 引入多视角归因:在失败步骤与失败原因之外还标注理想动作,提供更丰富的诊断信号。

若干基准面向特定智能体类型而非通用 LLM 智能体。AgentFail [27] 聚焦平台编排的智能体工作流,提供覆盖完整生命周期的细粒度标注(精确位置、根因与修复策略),支持超越简单错误检测、深入分析整个失败过程。CodeTraceBench [40] 聚焦软件工程智能体(SWEAgent、OpenHands 等)。

##### 4.5.2经错误注入的合成数据集

这类数据集通过向成功轨迹中主动注入错误来构造,因而具有精确的错误定位与标注。除评估外,它们也适用于模型训练。

Kong 等 [44] 构造了 Aegis——一个包含 9,533 条轨迹、标注了责任智能体与错误模式的大型数据集。构造方式是使用一个基于 LLM 的操纵器,向成功的执行轨迹自适应地注入上下文相关的错误。Yu 等 [32] 构造了 CORRECT-Error——一个超过 2,000 条多智能体轨迹的合集,带细粒度的步骤级错误标注;它由真实世界失败分布引导的错误注入流水线构建,产出的轨迹在可控覆盖与自然多智能体失败的真实性之间取得平衡。

### # 5讨论

#### 5.1从归因到增强的鸿沟

图 9 以可视化方式汇总了各失败归因技术的输出,以及各增强技术的输入。

![alt](附件资源/智能体轨迹研究双综述合集：从执行溯源到失败归因/img_15.jpg)

_图 9失败归因技术的输出与增强技术的输入之间关系的桑基图。_

可以观察到,失败归因技术的输出以三类信息为主:责任智能体、失败步骤与根因,其中责任智能体最为常见。而在增强一侧,几乎所有方法都以原始轨迹为主要输入,只有少数接受失败步骤或根因。

一个明显的鸿沟由此浮现:被大量产出的"责任智能体"信息,从未被任何增强方法消费。原因可能在于,这类粗粒度信息(即"哪个智能体负责")对"智能体究竟错在哪里、如何修复"缺乏足够的细节,因而对后续修复几乎没有可操作的指导。即便是失败步骤与根因,从归因流向增强的路径也很稀疏,只有 CE-Graph [48]、Fang 等 [69] 等少数技术加以利用。

失败步骤使用有限的原因在于:失败步骤只标明执行轨迹中的一个位置,并不直接指出应修改智能体的哪个部分,因而无法为增强技术提供针对性指导。相比之下,根因被更多技术采用,因为许多增强技术依赖失败的原因或描述来推断合适的修改策略。尽管如此,并非所有技术都利用失败分析信息——有些技术仅依据最终任务得分、成功率或其他聚合数据进行优化,不做任何失败原因分析。

总体而言,从失败归因到系统增强的管线是断裂的:归因聚焦于识别责任智能体,但增强技术并非为消费这些信息而设计,它们仍然依赖原始轨迹,而非归因的结构化输出。

#### 5.2方法选择指引

前几节沿多个维度组织了现有技术,而希望在实际场景中应用这些方法的从业者,还面临更高层的决策,例如目标环境是生产还是科研、预算约束(token 消耗、训练开销等)如何。本小节综合现有证据,尝试给出可操作的指引。

**生产环境与科研环境。**若干方法源自工业研究实验室(如来自 Amazon Web Services 的 ECHO [35]、来自 Microsoft Research 的 AgentRx [26])。然而,它们的评估几乎全部在 Who&When 等学术基准上进行,所用智能体(如 CaptainAgent、MagneticOne)未必能完全代表真实的生产部署。

尽管如此,我们确认了至少两种已在生产环境成功部署并报告了具体运营收益的方法:Wink（Meta）在在线 A/B 测试中解决了 90% 的单次干预不当行为;AgentDiet（字节跳动）在真实编码智能体环境 Trae Agent 中,在保持性能的同时将 token 成本降低 40%–60%。

**预算约束。**基于原始论文报告的数据 [39],我们分析不同归因技术的资源消耗模式:1)基于 LLM 推理的方法(如 CHIEF [39]、ECHO [35])产生中等的 token 开销,通常为单次提示的 2–3 倍;2)典型的基于模式的方法 FAMAS [30] 涉及反复重放,token 消耗显著更高(例如比基于推理的方法高 6–8 倍);3)基于微调的方法(如 AgenTracer [42]、GraphTracer [42])一旦部署,单条轨迹的推理成本可以更低,但模型训练需要大量投入;4)基于动态运行时的方法(如 DoVer [45])的单次诊断成本通常最高,因为它们主动重执行或干预智能体,且要求在线访问执行环境;不过,它们往往取得最好的归因准确率(如图 8 所示),因为主动的假设检验比被动分析更能消解根因的歧义。

总体而言,没有单一方法在所有维度上占优。从业者应基于其准确率需求、预算(一次性成本与单条轨迹成本)以及在线干预是否可行来选择。

#### 5.3与成熟软件工程技术的联系

LLM 智能体的轨迹分析与软件工程若干成熟领域密切相关。我们将本综述的若干主要维度映射到代表性的传统软件工程技术,如表 7 所示。

### # 6挑战与机遇

基于上述对轨迹相关研究的分析,我们总结未来研究的挑战与机遇。

#### 6.1通过更强的因果理解提升归因准确率

由于 LLM 智能体固有的非确定性推理与复杂交互,精确的失败归因仍是重大挑战,既有基准上的步骤级准确率仍然有限(如图 8 所示)。困难在于超越表面层次的轨迹检查,走向对智能体内部决策逻辑的结构化理解。迄今性能最高的 CHIEF [39] 开始应对这一问题:它把扁平的执行日志转换为层次因果图,显式建模数据流转与错误传播。这表明,将轨迹中潜藏的逻辑与因果关系形式化,是提升归因的一条可行路径。

这是该研究方向上有价值的第一步。未来探索可以发展更全面的模型,既捕捉智能体架构的确定性成分(如工作流结构、工具调用协议),也捕捉其基于 LLM 推理的概率性本质。此外,正如传统软件通常受益于静态分析与动态运行的结合 [84], [85],突破范式界限的混合技术可能是另一个有前景的方向。

#### 6.2重新思考 LLM 智能体失败分析的评估

失败归因技术的评估必须与其在调试和修复中的实际用途对齐。我们识别出当前做法不足的三个关键维度。

##### 6.2.1从准确率到实用性:修复驱动的度量

如第 5.1 节所示,失败归因技术的输出以责任智能体、失败步骤或根因为主,但增强方法很少消费这些结构化结果,仍依赖原始轨迹。这一脱节表明,当前以步骤级或智能体级准确率为中心的评估,未必能反映一项技术在支持系统修复中的实际效用。

因此,我们倡导修复驱动的度量:评估归因输出(如根因描述)能被增强方法直接使用的程度,或能为调试节省多少工作量。这类度量将激励归因技术产出真正可操作的信息,从而帮助弥合从归因到增强的鸿沟。

##### 6.2.2超越部分可观测:全面基准的需求

在过去相当长一段时间里,Who&When [11] 几乎是唯一专为 LLM 智能体失败归因设计的基准。它提供部分可观测的执行轨迹——仅包含智能体输出,不含原始任务指令、提示词或上下文消息等对应输入。这种受限设置适合评估某些黑盒场景下的归因方法,即内部输入或中间状态不可得时(例如调试部署在外部平台上的智能体)。然而,在许多面向开发者的实际调试场景中,开发者通常能获得丰富得多的执行信息,包括任务指令、提示词、中间消息、工具调用与环境状态。

近期 TraceElephant [46] 等基准的引入填补了这一空缺——它们提供完整执行轨迹与可复现环境——代表了必要的一步。未来的机会包括从真实部署构建更多样、更大规模的基准,在现实条件下稳健地评估归因与增强两类方法。

##### 6.2.3从二元结果到能力评估:在开放场景中评估

现有大多数失败诊断方法只提供粗粒度输出(如二元失败标签),并严重依赖特定任务的判定标准(oracle,如测试用例)来判定成败。然而,LLM 智能体日益部署于缺乏明确判定标准的开放场景(如创意任务),评估正从简单的通过/失败判断,转向在开放场景中评估智能体的能力。

AgentDiagnose [61] 展示了这一方向的初步尝试:用"LLM 作为评判者"(LLM-as-a-judge)的方式,从五个能力维度评估智能体。一个关键机遇在于发展基于轨迹的分析,对智能体能力(如规划保真度、工具使用、状态追踪)给出细粒度、多维度的评估。这类详细诊断不仅帮助开发者定位薄弱环节,还可作为改进智能体训练的中间监督信号。

#### 6.3走向系统化的 AgentOps:从零散工具到集成治理

尽管归因、增强与监测均有所进展,这些能力仍然是零散的——尚无一个集成框架来治理 LLM 智能体从离线评估到生产运行的完整过程。AgentOps SDK [86]、IBM Telemetry [87] 等新兴工业举措表明了对一门系统学科的需求,但学术研究相对滞后。正如近期一篇综述 [88] 所指出的,AgentOps 通常包含四个关键阶段:监测、异常检测、根因分析与解决,共同促成可问责、可观测的智能体。

为此,我们需要开放的可观测性标准、可在线运行的归因方法、反映真实条件的基准,以及保持人在回路的治理框架。单点进展已有,但集成化、系统级的方案仍然缺席。我们认为,若要从脆弱的原型走向可靠的生产系统,AgentOps 应当成为一等的研究议题,而非工具层面的补遗。

#### 6.4拓展视野:真实世界中的轨迹分析

除受控环境外,以下三个方向可将轨迹分析与真实世界的失败诊断连接起来。

##### 6.4.1从生产部署中学习

当前基准与数据集主要构建自受控环境或合成错误注入。它们虽有助于建立基线,却可能无法覆盖真实部署智能体所遇失败的全部多样性与不可预测性。生产环境带来受控设置无法复制的复杂性:含糊的用户请求、持续演变的外部 API、波动的延迟,以及意想不到的边界情况 [89]。此外,部署中的失败常与实验室评估中不存在的系统级问题(如资源约束、网络不稳定)交织在一起。

这一差距为实证软件工程研究带来了机会,例如开展大规模、纵向的研究,从生产环境收集轨迹数据,不仅记录失败,也记录成功的恢复、适应模式与系统更新的长期效应。这类实证基础将支持对归因与修复技术更真实的评估,并启发面向在线诊断实际约束的方法。

##### 6.4.2领域特定的失败诊断

不同应用领域有独特要求,并引入通用轨迹分析方法可能忽视的独特失败模式。以编码智能体(如 SWE-agent [90]、AutoCodeRover [91])为例,它们在大型代码库中导航、生成补丁并与版本控制系统交互,其轨迹包含丰富的结构化代码片段、依赖图与测试输出——通用自然语言方法无法利用这些信息。类似地,GUI 智能体 [92] 与动态视觉界面交互,解读屏幕布局、处理 UI 事件并适应应用状态变化;其失败往往源于误读视觉元素、错误的动作序列,或无法处理意外的界面跳转。

其他领域,如网页导航智能体与机器人领域的具身智能体,也各有特征性的失败模式。开发融合领域知识(如代码结构、屏幕布局、对话行为)的专门诊断工具,可显著提升归因方法的准确率与可操作性。此外,跨领域迁移学习可能揭示智能体失败的可泛化规律,为设计更鲁棒的诊断技术提供依据。

##### 6.4.3超越任务完成:约束满足、对齐与安全

现有大多数失败归因与增强技术,仅以任务完成与否来定义成功与失败,即智能体是否达成了既定目标。然而在真实部署中,智能体可能在达成任务的同时违反重要约束、危及安全或背离人类价值观。例如,智能体可能为释放磁盘空间而删除备份数据,或为提升执行速度而移除加密——满足眼前目标,却制造了不可接受的风险。此类行为很难被当前基准捕捉。

弥补这一缺口打开了若干有前景的研究方向。未来基准可以超越二元任务结果,纳入多维标注;归因技术也可以被改造为不仅识别失败发生的位置,还识别发生了何种行为违规、该违规是否可恢复。通过将"失败"的内涵扩展到任务成功之外,社区可以构建不仅有效、而且可信并与人类期望对齐的智能体。

### # 7相关工作

#### 7.1面向软件工程任务的 LLM 智能体

软件工程社区已迅速采用基于 LLM 的智能体来自动化多种开发活动。ChatDev [93] 与 MetaGPT [94] 等多智能体框架模拟协作的软件团队,从高层规格出发编写代码、进行代码评审并管理项目。SWE-agent [90]、AutoCodeRover [91] 与 ExpeRepair [95] 等专门智能体,通过导航仓库、复现缺陷并生成补丁来处理真实 GitHub issue,在 SWE-bench 等基准上取得最先进的结果。编码之外,智能体还被用于单元测试生成 [96]、缺陷定位 [97] 与自动化软件测试 [98],展现出重塑软件工程工作流的潜力。

然而,正如第 1 节所示,这些智能体的采用也带来了新的可靠性挑战。Bouzenia 与 Pradel [12] 完成了首个针对软件工程智能体"思考-行动-结果"(thought-action-result)轨迹的实证研究,揭示了反复出现的失败模式——如重复相同动作而无后续跟进——以及调试反模式,如生成修复却不加测试。他们的工作凸显了对系统化、自动化技术的迫切需求:诊断智能体为何失败、如何修复其行为。本综述直接回应这一需求。

#### 7.2LLM 智能体的自动构建与自我进化

与软件工程社区聚焦于把智能体用于开发任务并行,人工智能社区深入探索了如何从零开始或从最小种子出发,自动构建、优化与进化 LLM 智能体。

早期工作将智能体定制框架化为提示调优或上下文学习,而近期进展把整个智能体——其指令、策略、工具使用模式乃至协作工作流——都视为可优化的参数。例如,SCOPE [50] 将提示词进化形式化为在线学习问题,通过双流机制与视角驱动的探索,在战术性错误解决与战略性原则精炼之间取得平衡。另一条研究线聚焦于通过系统化探索设计空间来优化多智能体协作结构,由从轨迹中提取的诊断信号驱动;例如,Maestro [47] 在 token 或 rollout 预算下联合搜索图拓扑与智能体配置,由轨迹的反思性文本反馈引导。

尽管形式多样,所有这些自动构建技术都关键地依赖于理解智能体为何成功或失败——而这正是本综述的焦点。

#### 7.3AgentOps:LLM 智能体的可观测性与运营管理

与本文综述的失败归因与系统增强技术进展并行,一门互补学科已在软件工程、DevOps 与 AI 基础设施的交汇处出现:AgentOps。本文更多关注如何分析轨迹以诊断与修复失败,而 AgentOps 面向更广泛的问题——如何在智能体整个生产生命周期中观测、监测与管理它们,如 AgentOps SDK [86]、使用 watsonx Orchestrate 的 IBM Telemetry [87]。

Dong 等 [67] 提出 AgentOps 的系统分类法,识别智能体生产生命周期中可追踪的产出物,并强调可观测性是可靠性的前提。Moshkovich 与 Zeltyn [60] 阐述了显式集成根因分析与优化建议的六阶段 AgentOps 自动化流水线。Wang 等 [88] 的综述详细定义并解释了 AgentOps 的四个关键阶段:监测、异常检测、根因分析与解决。可以看到,它们都包含与本综述核心的失败归因与系统增强维度相对应的阶段。

现有 AgentOps 文献主要是工业白皮书、平台文档与早期学术分类法,聚焦可观测性基础设施、平台架构与运营最佳实践,而非归因方法或增强策略的分析。本综述补充了这一新兴学科,为其可(且日益)落地实施的诊断技术提供了首张结构化路线图。

### # 8结论

轨迹分析已迅速成为理解、诊断与改进 LLM 智能体的核心视角。本综述系统概述了面向失败归因与系统增强的 LLM 智能体轨迹分析这一新兴领域。通过收集并综合 2025 年初至 2026 年 4 月间发表的 55 篇相关论文,我们沿五个关键维度绘制了研究版图:失败分类体系、失败归因、系统增强与优化、轨迹可视化与分析工具,以及数据集与基准。

我们的分析揭示了一个快速成形中的领域,其驱动力在于人们认识到:传统软件诊断技术不适合智能体失败的非确定性、语言密集与交互内蕴的本性。通过同时呈现成果与持续存在的缺口,我们希望引导研究者与从业者迈向下一代鲁棒、可问责、能自我改进的智能体生态系统。从今天的脆弱原型到可靠、可部署的智能体系统,这段旅程将在很大程度上取决于我们分析、归因并利用每条智能体轨迹中丰富信息的能力。我们希望这项工作能加速这一旅程。
