# Knowledge OS：打造可自进化的 企业知识中枢—— Wiki-RAG + GraphRAG 融合的活态认知架构设计

![](附件资源/Knowledge%20OS：打造可自进化的%20企业知识中枢——%20Wiki-RAG%20+%20GraphRAG%20融合的活态认知架构设计/img_1.png)

Knowledge OS · 技术架构

Knowledge OS：打造可自进化的企业知识中枢

—— Wiki-RAG + GraphRAG 融合的活态认知架构设计

传统 RAG 只是"文档问答"，而 Knowledge OS 追求的是检索即更新，问答即沉淀——知识在使用中持续进化。**本文从架构设计、核心模块、技术选型到落地路径，完整拆解一套可自进化的企业知识中枢**是如何构建的。

01

项目定位：不只是文档问答

Wiki-RAG 不是传统的"文档问答"，而是一个**可自进化的企业知识中枢**。 它的核心理念来自 Karpathy 提出的 **LLM Wiki** 模式——不是每次问答都从头检索，而是让系统像人一样**持续编译知识、积累理解**。

**输入 → 处理 → 输出****输入**：Wiki 文档（飞书/Confluence/Markdown）、结构化数据、对话沉淀**处理**：语义切片 + 实体抽取 + 关系构建 + 向量化**输出**：精准检索 + 知识图谱推理 + 生成式问答 + 知识缺口发现**核心差异**：**检索即更新，问答即沉淀**，知识在使用中持续进化

与传统 RAG 相比，Knowledge OS 解决了一个根本性痛点：**RAG 不积累知识，也不会真正形成对知识的连续理解**。 每次提问都从头检索，每次问答都是一次性的——这是传统方案的致命缺陷。 而 Knowledge OS 让每一次问答都成为知识进化的燃料。

02

整体架构：五层分层设计

![](附件资源/Knowledge%20OS：打造可自进化的%20企业知识中枢——%20Wiki-RAG%20+%20GraphRAG%20融合的活态认知架构设计/img_2.png)

系统采用经典的五层分层架构，从上到下分别是应用层、编排层、能力层、数据层和基础设施层。 每一层职责清晰、解耦独立，既方便团队协作，也支持渐进式演进。

**应用层（Vue3）**：问答界面、知识图谱可视化、文档管理、评估后台、开放 API**编排层（Eino Graph）**：Query 理解 → 检索规划 → 混合检索 → 上下文组装 → 生成 → 校验**能力层**：RAG 引擎 + GraphRAG + 记忆模块 + Tool 工具集**数据层**：Qdrant（向量）+ PostgreSQL（关系+全文）+ Redis（缓存）+ MinIO（对象存储）**基础设施层**：LLM Gateway + Tracing（OpenTelemetry）+ 任务队列（Asynq）+ 文档解析管道

**编排层选型：Eino Graph**Eino 是字节跳动 CloudWeGo 团队开源的 Go 语言 LLM 应用框架，截至 2026 年 GitHub 星标已突破 11,500+。 它不是 LangChain 的 Go 移植版，而是严格遵循 Go 的设计哲学——接口抽象、组合优于继承、显式错误处理。 在字节内部，Eino 已支撑豆包、抖音等核心业务，是经过大规模生产验证的 Agent 编排框架。

03

核心模块一：文档摄入管道

![](附件资源/Knowledge%20OS：打造可自进化的%20企业知识中枢——%20Wiki-RAG%20+%20GraphRAG%20融合的活态认知架构设计/img_3.png)

文档摄入管道（Ingestion Pipeline）是知识中枢的"入口"，负责将各种格式的原始文档转化为可检索、可推理的知识单元。

完整链路：源文档 → 格式解析 → 语义切片 → 元数据抽取 → 实体/关系抽取 → 向量化 → 入库

**关键技术：父子块切片（Parent-Child Chunking）****这是 2026 年生产级 RAG 系统的标配方案。核心思路是：检索时用放大镜，返回时用全景图**。

**存储两份**：细粒度子块（200-512 Token）专用于向量检索；大块父块（1000+ Token）通过 ID 关联**检索时**：用子块在语义空间精准定位命中点**返回时**：根据关联 ID 取出父块，将完整上下文交给 LLM**效果**：兼顾检索精度和上下文完整性，解决传统切片"上下文断裂"问题

**补充知识点**：2025 年微软发布的 **LazyGraphRAG** 带来了新的思路——把图谱摘要延迟到查询时再计算， 索引成本降至完整 GraphRAG 的 0.1%，代价是每个查询多 2-8 秒。对于文档规模大但查询频率不高的场景，这是一个极具性价比的选择。

04

核心模块二：混合检索引擎

![](附件资源/Knowledge%20OS：打造可自进化的%20企业知识中枢——%20Wiki-RAG%20+%20GraphRAG%20融合的活态认知架构设计/img_4.png)

单一检索方式都有盲区。混合检索 + 重排序是提升 RAG 效果最稳定的组合，没有之一。

**三路召回**：**向量检索**（语义相似）：适合"怎么做X""X的原理是什么"等语义匹配问题**全文检索**（BM25 关键词）：精确术语、代码、人名、错误信息、产品型号**图谱检索**（实体/关系）：关系型问题，"X项目的负责人是谁""A系统依赖哪些模块"

**融合排序：RRF（Reciprocal Rank Fusion）****向量检索的余弦相似度在 0~1 之间，BM25 得分没有固定上限——直接加权相加是不公平的。 RRF 的巧妙之处在于：完全不看原始分数，只看排名**。

**RRF 公式**：RRF 得分 = 1 / (排名 + k)，k 通常取 60（Google 与滑铁卢大学 2009 年 SIGIR 论文确立的标准值）**核心优势**：天然奖励多路共识——文档在多路都排前面，综合分就越高**工程要点**：BM25 索引和向量索引必须同源，chunk 列表下标一一对应**进阶**：RRF 融合后再过一遍 Cross-Encoder 精排，是目前最稳的组合

**GraphRAG 增强****2024 年微软研究院提出 GraphRAG，通过 LLM 从非结构化文本中抽取实体、关系和事件，构建知识图谱， 并利用社区聚类生成多层知识摘要。相比传统 RAG，GraphRAG 在回答全局性、总结性问题**时优势显著， 在全面性、多样性及复杂推理任务中表现更优。

**GraphRAG 工作流程**：1. Query 先做实体链接，识别问题中的核心实体
2. 从图谱中取实体的 1-2 跳邻居子图
3. 子图结构 + 节点描述作为补充上下文
4. 社区摘要提供全局视角，适合多文档综合、关系推理

双层检索机制：Local Search（局部深挖）+ Global Search（全局总结），互补传统向量检索的盲区

05

核心模块三：问答编排

问答编排是整个系统的"大脑中枢"，负责协调检索、生成、校验等多个环节。我们使用 Eino Graph 实现有向无环图（DAG）编排。

**核心 Graph 节点**：**Query Rewrite**：把模糊问题改写为检索友好的查询，支持多 Query 扩展、HyDE 假设文档嵌入**Retrieval Planner**：判断问题类型（事实型/关系型/推理型），选择检索组合策略**Hybrid Retrieval**：执行混合检索，并行调用向量、全文、图谱三路召回**Context Assembler**：按相关性排序，控制 Token 预算，标注来源**Generator**：LLM 生成回答，强制引用溯源**Fact Checker**：验证回答中的每个事实点是否有来源支撑，无来源则标注或剔除

**关键设计：幻觉控制****幻觉是 RAG 系统最大的信任危机。我们的应对策略是三层防线**：

**第一层**：强制引用溯源——每个事实点必须标注来源 chunk**第二层**：Fact Checker 节点——自动校验回答与来源的一致性**第三层**：无来源不回答——宁可说"知识库中未找到相关信息"，也不编造答案

06

核心模块四：知识自进化

![](附件资源/Knowledge%20OS：打造可自进化的%20企业知识中枢——%20Wiki-RAG%20+%20GraphRAG%20融合的活态认知架构设计/img_5.png)

知识自进化是 Knowledge OS 与传统 RAG 的核心差异点，也是系统"越用越聪明"的秘密武器。 这个理念与 Karpathy 提出的 **LLM Wiki** 模式高度一致——知识库不是静态索引，而是一个**有状态的、持续编译的知识体**。

**自进化闭环**：用户问答 → 收集反馈 → 识别知识缺口 → 生成待补充条目 → 人工审核 → 回写 Wiki

四大进化机制：

**1. 知识缺口发现**：当检索结果不足或用户点踩时，自动记录问题，形成待补充清单**2. 答案沉淀**：高质量的问答对（经人工确认）自动转化为 Wiki 条目或 FAQ**3. 图谱补全**：从问答中抽取新的实体和关系，补充知识图谱**4. 热度学习**：高频查询的文档块提升检索权重，冷门内容自动降权

**补充：EvoRAG 思路**学术界提出的 EvoRAG 框架进一步拓展了自进化的维度——不仅知识库可以进化， 检索模块、查询理解模块、答案生成模块都可以根据反馈反向传播进行优化。 当某种类型的反馈积累到阈值时，系统自动触发对应模块的迭代升级。

07

技术选型亮点

技术选型遵循三个原则：Go 原生优先（与团队技术栈一致）、**开源可控**（私有化部署）、**生产验证**（社区活跃、有大规模落地案例）。

**Embedding 选型：BGE-M3**北京智源研究院开源，569M 参数，1024 维向量，支持 100+ 语言
三合一能力：同时支持稠密检索 + 稀疏检索 + 多向量检索（ColBERT），一个模型覆盖三种检索模式**多粒度**：最大输入 8192 Token，从短句子到长文档全覆盖**MTEB 榜单**：中文 MTEB 榜单第一梯队，多语言跨语言检索能力突出

**向量数据库：Qdrant**Rust 实现，高性能，支持过滤和 payload 索引
原生支持混合检索（稠密 + 稀疏），与 BGE-M3 完美配合
对比 Milvus：Qdrant 更轻量、部署简单；Milvus 功能更全、适合超大规模场景

**编排框架：Eino Graph**字节跳动 CloudWeGo 开源，Go 原生 LLM 应用框架
内置 ReAct Agent、流式响应、中断恢复等企业级特性
在字节内部支撑豆包、抖音等核心业务，经过大规模生产验证

08

落地路径：四阶段渐进

采用渐进式落地策略，每个阶段都有明确的交付目标和验收标准，避免"大而全"的一次性交付风险。

**Phase 1：基础 RAG（4 周）**文档摄入管道（Markdown + 飞书 Docx）→ 父子块切片 + 向量化 → 基础向量检索 + 生成问答 → 简单问答界面
目标：能回答"文档里有答案"的问题

**Phase 2：混合检索 + 图谱（6 周）**BM25 全文检索 → 实体/关系抽取管道 → 知识图谱存储和查询 → GraphRAG 检索融合 → 图谱可视化
目标：能回答需要跨文档、关系推理的问题

**Phase 3：自进化 + 评估（4 周）**问答反馈收集 → 知识缺口识别 → 评估体系搭建（黄金测试集 + 自动评估）→ 答案沉淀回写
目标：系统越用越聪明，质量可量化

**Phase 4：Agent 化（持续）**接入 Tool 调用（查数据库、发通知、创建任务）→ 多步推理 Agent → 多 Agent 协作
目标：从"知识问答"升级为"知识工作者"

09

关键技术难点与应对

飞书 Docx 解析质量：基于飞书开放 API 获取结构化内容，保留块级格式；表格单独处理**切片粒度优化**：父子块结构 + 按语义边界切分 + 可配置粒度，避免"切太碎丢语义、切太大引噪声"**检索精度**：混合检索 + RRF 融合 + Cross-Encoder 重排 + 查询改写，四层优化检索命中率**幻觉控制**：强制引用溯源 + Fact Checker 节点 + 无来源不回答**图谱构建质量**：LLM 抽取 + 规则校验 + 实体归一化 + 人工审核闭环**成本控制**：缓存高频查询 + 小模型做检索规划 + 大模型只做最终生成

结语：知识在使用中进化

Knowledge OS 的核心信念：**知识不是静态的存储，而是动态的流动。****检索即更新，问答即沉淀。**
每一次问答，都是知识进化的契机；
每一次反馈，都是系统成长的养分。
让企业的知识不再是沉睡的文档，
而是一个活着的、持续进化的认知生命体。
