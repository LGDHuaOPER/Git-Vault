# AI 智能体应用时代，可观测性怎么做？

#

团队把 AI 助手、RAG 工作流、业务 Agent 推到线上后，先遇到的往往不是 500，也不是服务雪崩，而是另一类问题：请求成功、链路没断，用户仍觉得不好用。

比如，用户问报销制度，系统却去调天气工具；检索返回正常，却注入了过期政策；模型输出不差，但 Agent loop 从 3 步涨到 8 步，单次成本翻倍。放到传统监控面板里，这些问题通常不够红、不够响。

这正是 AI 智能体应用和传统应用的关键差异：过去主要观测系统有没有坏，现在还要观测它为什么这么判断、为什么这么行动，以及这套行动是否还值得继续上线。

![可观测性的不同](附件资源/AI%20智能体应用时代，可观测性怎么做？/img_1.png)

可观测性的不同本文要讲的是：AI 智能体可观测性的新增量，不是“多打一层日志”，而是把 trace、evaluation、dataset / experiment 接成一个能持续修行为的闭环。这套方法不是大厂专属，多数团队都能从最小路径起步，在一两周内搭出第一版。

## 传统可观测性，为什么解释不了 AI 智能体

先看差异。传统应用主要观测代码路径、服务依赖、数据库、缓存、消息队列和资源状态。请求经过哪些服务、哪一跳超时、哪台机器 CPU 飙高，基本都能在 APM 和日志体系里找到答案。

但 AI 智能体应用多了一层运行时决策。它会带着什么 prompt 进入模型，会拼接哪些上下文，会不会发起检索，会调用哪个工具，会不会继续下一轮 loop，这些都不是开发者提前写死的固定路径。很多关键动作，是在运行中由模型和编排策略共同决定的。

故障形态也随之变化。传统应用常见的是报错、超时、依赖不可用；AI 智能体更常见的是“不报错，但结果不对”。工具调用成功却调错工具；检索成功却召回偏了；模型返回却答非所问；接口一直是 200，单位任务成本却悄悄上涨。

判断标准也变了。错误率、延迟、吞吐和资源消耗依然重要，但不够。还得看任务成功率、答案质量、工具成功率、检索命中质量、人工接管率、token 消耗、单位任务成本。一个 AI 系统可能技术指标健康，却在业务结果上持续失分。

所以，传统可观测性主要回答“系统有没有坏”，AI 智能体可观测性还要回答“系统为什么这样行动，以及这种行动是否值得继续上线”。

## 真正要观测的，不是更多日志，而是三组关键对象

如果对象列得太散，很容易写成名词表。更实用的方式是压成三组问题。

第一组问题，是它看到了什么、怎么做决定。

这一组最关键的不是“最终 prompt 长什么样”，而是进入模型前的完整上下文：system instruction、模板变量、历史消息、RAG 注入片段、工具定义、模型参数、被裁剪内容。很多线上问题不是模型不行，而是模型在错误上下文里做了看上去合理的判断。

第二组问题，是它实际做了什么。

也就是每一步 agent action：发起了哪次检索、调了哪个工具、工具参数是什么、结果是什么、是否重试、是否进入下一轮 loop、停止条件是什么、是否触发人工接管。AI 应用真正难查的问题，往往不是某个 RPC 调用失败，而是“它为什么会走到这一步”。

第三组问题，是它做得值不值。

这组至少要同时看三类信息：结果质量、耗时与 token 成本、任务成功率与人工接管率。很多系统不是不能跑，而是靠高成本、低稳定性和人工兜底勉强跑着。

把这三组对象串起来，才是一条有用的 AI trace。它不只是“请求经过了哪些服务”，而是“一个用户请求如何变成决策、行动和结果”。

## AI 可观测性的关键，不是 trace 本身，而是 trace + evaluation + dataset

不少团队把 trace 接出来后就停下了。trace 只能回答“发生了什么”，回答不了另外两个问题：结果好不好，改完后是否真的更好。

因此，AI 可观测性一定要把 trace、evaluation、dataset 连起来。

![AI可观测性闭环](附件资源/AI%20智能体应用时代，可观测性怎么做？/img_3.png)

AI可观测性闭环trace 负责还原现场。它告诉你：模型看到了什么，检索到了什么，为什么选了这个工具，一共跑了多少步，花了多少 token。

evaluation 负责判断结果。它把“这次输出好不好”变成结构化信号。可以是规则校验、人工标注，也可以是模型评审。形式不重要，关键是结果能被聚合、筛选和比较。

dataset 负责沉淀样本。线上问题如果只停留在群聊和印象里，团队每次都像在重复发现同一类故障。更稳妥的做法是把失败样本、边界样本、高成本样本沉淀下来，形成可复验的数据集。

当这三者接起来，实验才有意义：你改了 prompt、换了模型、收紧了工具描述、调整了检索策略之后，不是“上线看看”，而是拿同一批样本去比较质量、延迟、成本和人工接管率是否真的改善了。

所以 AI 智能体可观测性的新增量，不是更花哨的 tracing，而是让团队第一次具备持续修系统行为的能力。

## 从 0 到 1，先跑一条最小可行的建设路径

很多团队一听“AI 可观测”，就会想到很重的平台工程：全链路埋点、统一评估平台、离线实验系统、全量回放集群。这样容易把事情做大，迟迟不落地。

更可行的办法是先跑通一条最关键的线上任务。对大多数已上线 AI 功能的团队来说，第一版不必追求平台化，先把下面 5 步做完整，就足够把排障和迭代拉回工程节奏。

### 第一步：先定义一个最小任务单元

不要一上来追求“全量可观测”，先选一个最核心、投诉最多、价值最清晰的任务。

比如“问制度库并回答”“根据工单信息生成处理建议”“根据客户对话判断是否需要转人工”。先把任务单元定义清楚：什么叫成功，什么叫失败，什么叫高成本但勉强成功，什么场景必须转人工。没有任务单元，后面的 trace 和 evaluation 都会失焦。

这一阶段只做一件事：给这类任务统一一个  `trace_id`  或  `session_id` ，把用户输入、检索、模型调用、工具调用、最终结果挂到同一条链路下。先保证一条任务能被完整还原，比一开始铺开多个场景更重要。

### 第二步：先把第一批必须埋的字段、事件、指标埋全

AI 可观测性最怕“看起来埋了很多，真正排障时关键信息还是断的”。第一版不要贪多，先把最影响排障效率的字段埋齐。

必须埋的字段，至少包括这几类：

- • 请求标识： trace_id 、 session_id 、 user_id 、 task_type 、 app_version
- • 输入信息：用户原始问题、输入渠道、语言、是否命中敏感场景
- • 模型调用： model_name 、 temperature 、 max_tokens 、prompt 版本、system prompt 版本、输入 token、输出 token、模型延迟、模型费用
- • 检索信息：retrieval query、召回文档 ID、文档版本、知识库来源、top_k、重排分数、最终注入片段
- • 工具调用： tool_name 、调用原因、输入参数、输出摘要、耗时、是否成功、错误码、重试次数
- • Agent 过程：loop 次数、每步 action、停止原因、是否回退、是否触发人工接管
- • 结果信息：最终回答、结构化结论、是否完成任务、失败原因分类、人工反馈、用户反馈
- • 评估信息：准确性分、完整性分、是否违规、是否命中业务规则、评估器版本

必须埋的事件，第一批至少要有：

- • session_started
- • retrieval_started / retrieval_completed
- • llm_call_started / llm_call_completed
- • tool_call_started / tool_call_completed
- • agent_step_completed
- • human_handoff_triggered
- • session_completed
- • evaluation_completed

必须盯的指标，也不要铺太开，先盯最关键的一组：

- • 任务成功率
- • 人工接管率
- • 平均 loop 次数与 P95 loop 次数
- • 工具调用成功率、误调用率
- • 检索命中率或“答案引用有效知识”的比例
- • 平均输入 / 输出 token
- • 单任务平均成本与 P95 成本
- • 平均延迟与 P95 延迟
- • 评估通过率

这一步做完，你还没有“AI 可观测平台”，但已经有了一套能排障、能对齐认知、也能积累样本的底座。

### 第三步：给线上结果加一层轻量 evaluation

很多团队卡在这一步，是因为把 evaluation 想得太重。第一版不需要先做一套复杂评分体系。

更现实的做法是三层并行，能上什么先上什么。

第一层是规则评估。比如回答里是否引用了知识库版本号，是否调用了不该调用的工具，是否在应当拒答的场景给出了确定性结论。这层最稳定，适合先做，也最容易和业务规则对齐。

第二层是人工反馈。给运营、客服、业务专家一个最简标注入口，不求精细打分，先能标“答对 / 答错 / 不完整 / 成本过高 / 应转人工未转”就已经很有价值。

第三层是模型评审。让另一个模型辅助判断答案是否命中问题、是否遗漏关键信息、是否存在明显幻觉。它不必当最终裁判，但很适合做筛查器，把值得人工复核的样本先挑出来。

这一步的关键不是评分有多准，而是把“线上结果是否可接受”落成结构化数据，并且能和 trace 一一对应。

### 第四步：把坏样本沉淀成 dataset，而不是只在群里复盘

只要线上出现下面几类样本，就应该自动或半自动进数据集：

- • 用户明确投诉的样本
- • evaluation 不通过的样本
- • 成本异常高的样本
- • loop 异常长的样本
- • 工具误调用样本
- • 检索命中但答案错误的样本

数据集里不要只留问题和答案，至少还要带上对应 trace 链接、知识片段、工具调用记录、评估结果、故障标签。否则过几天再看，团队还是得重新翻日志。

第一版数据集不用大，50 到 100 条高质量失败样本，通常就够支持第一轮回归和改版验证。

### 第五步：把改动放进实验，而不是直接赌线上

当你开始改 prompt、改工具描述、改知识召回、改停止条件时，不要直接凭感觉发版。先在失败数据集上做对照实验。

最简单的对比方式就是盯住四个维度：

- • 质量有没有提升
- • 成本有没有失控
- • 延迟有没有恶化
- • 人工接管率有没有下降

只要你的实验结果能回写到同一批样本上，团队就能避免一种很常见的错觉：局部修好了，但整体反而变差了。

## 两个具体排障例子：怎么用 trace + evaluation + dataset 找问题

### 例子一：工具都成功了，答案还是错的

用户问：“外地出差住宿超标后怎么报销？”

线上系统给出的答案却在讲“差旅申请如何提交”，而且中途调用了一次天气工具。传统日志里，这次请求几乎没有异常：HTTP 200，工具调用成功，模型也正常返回。

看 AI trace，问题很快就会露出来。

先看输入上下文，发现 system prompt 里有“优先使用工具补充上下文”的泛化指令，但没有明确限定“工具选择必须与用户问题语义相关”。再看 agent step，第一步模型把“外地出差”错误联想成“出行信息”，触发了天气工具。天气工具结果返回后，第二步模型继续围绕这段无关信息推理，最终偏离了真正问题。

再看 evaluation，业务规则评估命中了两条：一是“未回答超标报销规则”，二是“调用了与任务无关的工具”。这就不是“答案偶然答偏”，而是可稳定归类的问题：工具选择约束不足。

接下来把这批样本沉淀进 dataset，标签打成  `tool_misfire`  或  `irrelevant_tool_invocation` 。然后做两组实验：

一组改 system prompt，明确工具调用前必须先判断是否能缩小答案不确定性；另一组不只改 prompt，还给工具描述补上适用边界，并加一条规则评估，凡是政策问答场景调用天气、日历、地图等无关工具，一律降分。

实验结果通常很清楚：误调用率下降，loop 次数下降，成本也一起下来。这样修的不是一条偶发 case，而是一类可复现的行为偏差。

### 例子二：检索命中了知识库，答案还是用了旧政策

另一个更隐蔽的例子是“检索没坏，但知识还是错了”。

用户问的是 2026 年最新报销标准。trace 里能看到检索服务成功返回了 5 条文档，重排分数也正常，最终答案却引用了 2024 年旧制度。

这类问题如果只看“检索成功率”，完全看不出来。继续往下看 trace，会发现召回集合里同时存在新旧两个版本，而最终注入上下文时，旧文档排在了前面；再看知识字段，旧文档的  `doc_version`  缺失，新文档虽然更新，但标题写法不统一，导致重排器没有稳定把新版本顶上去。

再看 evaluation，准确性评估未通过，同时规则校验触发了“引用了过期版本知识”。这说明问题不在模型生成，而在知识注入策略。

接下来沉淀 dataset，把所有“命中多版本文档但答案引用旧版”的样本单独成组。然后做三件事：

第一，补知识侧元数据，强制要求文档带  `doc_version` 、 `effective_date` 、 `is_current` 。

第二，调整检索后处理，在注入前先做版本去重与有效期过滤，而不是把排序权完全交给模型。

第三，增加一条离线评估：凡是问题涉及制度、价格、条款、生效时间，答案必须优先引用  `is_current=true`  的知识。

这类问题一旦修复，提升的不只是准确率，往往还有用户信任。因为用户最不能接受的，不是系统说“我不知道”，而是系统一本正经地引用过期规则。

## 当前主流开源方案，应该怎么分层看

如果只按产品名看智能体可观测性，很容易越看越乱。更实用的办法是先按层次拆：哪些定义标准，哪些补语义和采集，哪些负责把 trace、评估、数据集放到工作台里，哪些更偏网关、请求治理和成本控制。

这样看，很多争论会自然消失。OpenTelemetry 不是 Phoenix 的替代品，Langfuse 也不是 OpenInference 的上位版本，它们解决的是不同层的问题。真正要做的不是选一个“全能平台”，而是先明确自己缺哪一层。

![](附件资源/AI%20智能体应用时代，可观测性怎么做？/img_4.png)

### 第一层：标准层，用来统一上下文和链路表达

这一层的核心代表是 OpenTelemetry。

它解决的问题很直接：把一次 AI 请求放回团队熟悉的 trace、span、metric、log 体系里。对已经在用 Jaeger、Tempo、Grafana、Datadog、Elastic 或自建 tracing 管道的团队，这一点尤其重要。你不希望 AI 系统变成一块只能单独登录查看的黑盒。

OpenTelemetry 适合的团队，通常有两类。一类是已经有成熟 observability 栈，希望 AI 应用继续沿用现有采集、传输、存储和告警路径；另一类是平台工程能力较强，希望埋点模型、工具、检索链路时，不被某个单一上层产品绑死。

它的边界也很清楚。OpenTelemetry 擅长定义链路和上下文传递，但并不理解“这一步是检索”“这一段文本是 prompt 模板”“这次失败属于工具误调用”。它能把轨迹记下来，但默认不提供 AI 语义。

所以如果团队只停在这一层，通常会得到一条结构完整但业务解释力有限的 trace：知道 span 顺序，不一定知道为什么这次智能体行为是坏的。

### 第二层：采集 / 语义层，用来把 AI 运行时变成可解释数据

这一层接近 OpenInference 这类开放语义约定。

它解决的不是“有没有 trace”，而是“AI trace 里该有什么字段和语义”。比如一次 LLM 调用，除了耗时和状态码，还应带上模型名、token 使用量、prompt、completion、tool call、retrieval metadata、评估结果、会话或任务标识。没有这一层，团队很容易把 AI 观测做成一堆普通 RPC span，再靠人工猜测哪一段是模型、哪一段是工具、哪一段是知识注入。

OpenInference 的价值，在于它给这类字段提供了一套相对开放、可互通的表达方式。它和 OpenTelemetry 不是对立关系，更像是在后者之上补了一层 AI 语义：底下还是 trace，往上才有 prompt、document、tool、eval 这些对象。

这一层适合两类团队。第一类是有编排框架、Agent runtime 或中间层，希望把语义埋点掌握在自己手里；第二类是准备同时接多种上层工具，不想一开始就锁死在某一家专有 SDK 里。

它的边界同样明显。语义约定不是工作台。你可以用 OpenInference 把数据采出来，但它不会自动给你一套样本筛选、人工标注、实验对比和回归看板。它更像“把现场拍清楚”的那一层，而不是“拿这些现场持续做优化”的那一层。

### 第三层：观测 / 评估工作台层，用来真正支撑排障、评测和迭代

到了这一层，代表性方案更接近 Phoenix 和 Langfuse。

它们解决的问题，是把前面采到的 trace、prompt、检索片段、工具调用、评分结果、数据集、实验对比放到一个能日常使用的工作台里。团队不只看请求有没有成功，还能筛高成本样本、对比 prompt 版本、回看工具误调用、把失败样本沉淀成评测集。

如果按使用侧重点区分，Phoenix 更偏“面向评估与调试”的研究台气质，尤其适合把 trace、eval、dataset 放在一起看，做问题归因和实验比较；Langfuse 更偏“面向生产协作”的产品化工作台，在 tracing、prompt 管理、会话查看、标注与反馈闭环上更容易直接落地。两者都能承接开放埋点，也都常被拿来做 AI 应用的一线排障面板。

这一层适合的团队很明确：已经不满足于看基础 trace，而是进入“每周复盘失败样本、持续改 prompt / 检索 / 工具策略”的阶段。通常是有线上流量、开始遇到质量与成本双重压力的小中型团队，或者要给多个 AI 场景提供统一工作台的平台团队。

它们的边界在于：工作台不是底层标准，也不是万能治理层。你仍然需要回答数据从哪里来、要不要接入现有 tracing 栈、原始敏感数据怎么脱敏、线上入口流量由谁控制。单靠工作台本身，解决不了所有埋点规范和网关治理问题。

这里顺带澄清两个常被一起提到的名字。

LangSmith 在开发调试和评测工作流上很强，很多团队上手也快，但它并不是纯开源方案，更多是围绕 LangChain / LangGraph 生态和托管工作流展开；如果团队目标是优先拥抱开放标准和自托管，它更像一个功能强、但路线不同的参考项。Helicone 更偏请求代理、日志记录、成本与使用量分析，和 Phoenix、Langfuse 不是同一重心，它更接近后面要说的网关 / 成本层。

### 第四层：网关 / 成本层，用来控入口、记账和做统一治理

这一层的关注点不是“模型为什么答错”，而是“所有请求从哪里进、花了多少钱、能不能统一控流和审计”。像 Helicone 这样的方案更偏这一层。

它解决的是生产入口治理问题：多模型路由、API 代理、请求日志、token 计费、成本分摊、缓存、限流、Key 管理，外加一部分基础 tracing。对于同时接多个模型供应商、多个团队共享同一套模型预算、或者需要先把调用入口收拢起来的团队，这一层非常实用。

它适合的平台化团队诉求很明确：统一接入 OpenAI、Anthropic、Azure OpenAI、各类开源推理服务；知道哪个业务线最烧钱；做预算告警和配额控制；或先通过代理层降低 SDK 接入复杂度。

它的边界也不能搞混。网关和成本层能回答“钱花到哪了、流量怎么走、哪些请求异常”，但通常不擅长回答“这次回答为什么业务上不合格”。它更强在入口治理和成本可见性，不是完整的智能体评估工作台。

### 选型时，不要问谁最强，先问自己现在缺哪一层

如果是初始阶段，最常见的问题不是标准不统一，而是没有一块能回看 trace、筛失败样本、顺手做点评估的地方。这时优先补工作台层最划算，通常从 Langfuse 或 Phoenix 这一类开始，再视情况接上 OpenTelemetry / OpenInference。先把排障和复盘跑起来，比一开始追求完美分层更重要。

如果已经有一定基础，且有多个 AI 场景同时上线，建议分两步走：底层用 OpenTelemetry + OpenInference 统一埋点和语义，上层选 Phoenix 或 Langfuse 作为工作台。这样既保留开放性，也让不同业务线共用一套 trace 语义和评估方法。

如果已经有成熟 observability 栈（日志、APM、trace、告警平台），优先级通常不是再造一套底层，而是在现有栈上补 AI 语义和工作台能力。也就是继续用 OpenTelemetry 承接基础链路，再引入 OpenInference 这类语义约定和一层面向 AI 排障与评测的工作台。这样改动最小，也最容易进入现有运维体系。

智能体可观测性的开源生态，不是“一家替代所有家”，而是分层组合。标准层负责不锁死，语义层负责说人话，工作台层负责让团队真能排障和迭代，网关层负责把入口、成本和治理收回来。把这几层的职责想清楚，选型反而不难。

## 生产落地时，最容易踩的几个坑

AI 可观测性最难的地方，不是概念，而是落地时会不自觉走偏。下面这些坑，几乎每个团队都会踩。

第一个坑，是只采模型调用，不采业务语义。

你知道某次模型耗时 2.3 秒、用了 4000 token，却不知道它在完成什么任务、结果有没有业务价值。这种数据很难支持真正的业务排障。解决办法很简单：从第一天起就把  `task_type` 、成功定义、失败分类带上。

第二个坑，是 trace 很细，但没有版本信息。

没有 prompt 版本、工具 schema 版本、知识版本、评估器版本，团队就很难知道一次波动到底是模型漂了，还是你昨天改了配置。版本号不是锦上添花，而是排障起点。

第三个坑，是把 evaluation 当成一次性项目。

很多团队前期认真做了十几条规则，后面就不维护了。结果业务变了、知识变了、流程变了，评估标准却还是旧的。evaluation 不是验收文档，它本身也是生产系统的一部分。

第四个坑，是坏样本积累了，但没有统一标签。

今天说“答偏了”，明天说“工具乱调”，后天说“知识有问题”，最后大家都在描述现象，没有形成可统计、可回归的故障分类。建议第一版就统一一套粗标签，比如： `retrieval_miss` 、 `stale_knowledge` 、 `tool_misfire` 、 `loop_runaway` 、 `unsafe_answer` 、 `should_handoff_but_not` 。先粗分，再慢慢细化。

第五个坑，是只盯质量，不盯成本。

AI 系统很容易陷入一种假性优化：准确率升了一点，但 loop 次数、token 和工具调用数一起飙升，最后无法规模化上线。任何改动都要同时过质量和成本两道门。

第六个坑，是敏感数据直接全量落库。

为了排障，把用户原文、身份证号、合同内容、内部文档全量扔进 tracing 系统，看起来省事，后面一定会出合规问题。更稳妥的做法是分级存储、字段脱敏、敏感内容打标、原文按权限回看，不要把“可观测”做成“无边界留痕”。

## 如果要落地实施，应该先做什么

第一，挑一个线上最重要的 AI 任务，不要贪多。最好是已经有用户量、已经有投诉、已经有人在手工兜底的那个场景。

第二，补齐一条最小 trace。至少把用户输入、最终 prompt、检索结果、工具调用、最终输出、token、成本、人工接管串到同一个  `trace_id`  下。

第三，拉出第一批失败样本。哪怕只有 30 条，也足够开始发现共性。不要追求“大而全”，先追求“真问题”。

第四，加一层最轻的 evaluation。先有规则评估和人工标注，不要等完美评估体系。

第五，每周固定做一次样本复盘。不是看 dashboard 漂不漂亮，而是一起回答三个问题：这周最常见的失败类型是什么；哪些问题是检索、工具、提示词还是停止条件导致的；下一个版本优先修哪两类问题。

这五件事做完，团队就能从“AI 功能上线了但靠感觉维护”，进入“AI 功能按工程方式迭代”。

## 开源方案对照小表

| 方案 | 分层定位 | 适合解决的问题 | 更适合的团队 | 主要边界 |
| --- | --- | --- | --- | --- |
| OpenTelemetry | 标准层 / 基础遥测层 | 统一 trace、span、metric、log 表达；接入现有 observability 栈 | 已有监控体系、希望保持开放标准的团队 | 能记链路，但不天然理解 prompt、tool、retrieval、eval 等 AI 语义 |
| OpenInference | 采集 / 语义层 | 给 LLM、Agent、Tool、Retriever、Evaluator 等对象补充统一语义 | 有自研 Agent runtime、希望跨工具复用语义埋点的团队 | 不是工作台；负责把现场描述清楚，不负责直接做样本管理和实验面板 |
| Phoenix | 观测 / 评估工作台层 | 结合 trace、eval、dataset、experiment 做调试、归因、回放与比较 | 已有线上流量，开始频繁做问题归因和评测迭代的团队 | 更偏评估与调试，不是底层标准，也不是统一流量入口 |
| Langfuse | 观测 / 评估工作台层 | tracing、prompt 管理、会话查看、反馈闭环、数据集与实验协作 | 需要较快落地生产协作工作台的小中型团队 | 仍需搭配底层埋点和现有 observability / 治理体系 |
| Helicone | 网关 / 成本层 | 请求代理、成本核算、多模型路由、配额与入口治理 | 需要统一模型入口、控预算、做路由治理的平台型团队 | 更强在治理和记账，不是完整的评估 / 数据集工作台 |
| LangSmith | 开发调试 / 评测工作流层 | tracing、评测、调试、实验对比，适合 LangChain / LangGraph 生态 | 已深度使用 LangChain 生态、接受其路线的团队 | 不是纯开源路线，更多是平台化工作流而非开放标准层 |

如果只想记一句： `OpenTelemetry`  管底座， `OpenInference`  管 AI 语义， `Phoenix / Langfuse`  管工作台， `Helicone`  管入口和成本；选型时先看自己缺哪一层，不要一上来找“一家全包”。

## 结尾：AI 时代的可观测性，最终不是为了看，而是为了改

传统可观测性并没有过时。服务健康、资源状态、依赖关系、错误率和延迟，依然是生产系统的底座。

但 AI 智能体应用把问题往前推了一步。系统即便不报错，也可能在错误地理解、检索、调用和消耗预算。这时，光知道它活着没有用，关键是知道它为什么这么做，以及这种做法是否还值得继续上线。

AI 智能体可观测性的真正新增量，不是把日志打得更细，也不是把 tracing 画得更花，而是把行为轨迹、结果评估、失败样本和回归实验接成闭环。
