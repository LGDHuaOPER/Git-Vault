# 轨迹与可观测性：如何知道 Agent 为什么成功或失败

凌晨一点，一项自动化任务显示“工具执行失败”。屏幕上只有这一行结论：不知道模型是否给出了错误参数，不知道权限策略是否拒绝了动作，也不知道工具是否已经启动、超时或把部分结果写回了环境。

![](附件资源/轨迹与可观测性：如何知道%20Agent%20为什么成功或失败/img_1.png)

面向已经理解 Tool、Permission、Hook、Subagent 与并行调度、需要定位 Agent 运行问题的开发者和技术负责人。重点是把最终文本、日志、结构化事件和 Trace 分开，建立最小的事件关联与脱敏边界；

一次任务最终成功，不等于过程没有越权、重试、超时或局部失败；一次任务最终失败，也不等于最后抛错的组件就是根因。要让工程团队能够复盘，Harness 需要保留受控的执行证据，而不是在控制台多打印几行文本。

## 只有最终答案，为什么无法排障

最终答案只回答“任务最后输出了什么”。它无法说明这个结果经过了哪些请求、权限判断和环境动作。

例如，下面三种信息的作用完全不同：

| **信息形态** | **擅长回答什么** | **单独无法回答什么** |
| --- | --- | --- |
| 最终文本或最终状态 | 任务最后得到什么结果 | 哪一步导致结果、经历过哪些动作 |
| 普通日志 | 某个组件曾输出什么文本 | 多组件事件是否属于同一次任务、前后关系是否稳定 |
| 结构化事件 | 某类动作、状态和属性是什么 | 所有事实是否已收集、业务目标是否正确 |
| Trace | 同一次任务内事件如何关联 | 根因、权限正确性和外部副作用是否可自动判定 |

![](附件资源/轨迹与可观测性：如何知道%20Agent%20为什么成功或失败/img_2.png)

一条“请求超时”日志，可能来自模型调用、MCP 服务、文件系统、网络代理或工具本身。若没有稳定的任务标识、事件标识和关联关系，排障很容易退化成翻找分散日志：像拿着“包裹未送达”四个字去反查整条物流链路。

可观测性的起点不是收集一切，而是先明确要保留哪些可验证事实：某次任务何时开始、请求了哪个受限工具、策略允许还是拒绝、工具以什么结果结束、任务为何收束。无法解释的空白，应保留为空白，而不是由系统补写一个听起来合理的根因。

## Trace、Span、Event 与 Attribute 分别做什么

OpenTelemetry 的追踪语义为跨组件操作提供了一组通用概念。把它们拆开理解，比把所有记录都叫“日志”更有用：

- Trace ：一次端到端操作的关联范围。一次 Agent 任务可作为一条 Trace；
- Span ：有起点和终点的操作区间，例如一次模型请求、一次工具执行或一个子任务；
- Event ：发生在某个时间点的事实，例如权限拒绝、开始重试或终止原因；
- Attribute ：描述操作或事件的结构化字段，例如工具名、结果码、重试次数或脱敏后的调用标识。

![](附件资源/轨迹与可观测性：如何知道%20Agent%20为什么成功或失败/img_3.png)

这些概念是观察模型，不是要求每个小型 Harness 都实现完整追踪协议。一个教学快照如果只需要解释“模型请求—权限判断—工具结果—任务结束”，把每个可见节点记录为结构化事件即可。没有必要为了使用 Trace 这个词就提前引入 Collector、Exporter、采样器、上下文传播器或仪表盘。

教学快照中的 TraceEvent 是自定义领域事件：它借用 Trace、Span、Event 与 Attribute 的观察视角，但不等同于 OpenTelemetry Span，也不是附着在 Span 上的 OpenTelemetry Span Event。trace_id、parent_event_id 与 correlation_id 只用于本地关联，不构成 OpenTelemetry SpanContext。只有完成目标版本的字段映射，并验证 SDK、Exporter 与上下文传播后，才可以讨论与 OpenTelemetry 的互操作性。

OpenTelemetry 的 GenAI 语义约定正在演进，公开资料中包含 invoke_agent、chat、execute_tool 等操作语义，以及工具调用 ID、参数和结果等关联字段。字段名称、稳定性和实现支持会随版本变化；发布时应以目标版本规范为准，不应把某个字段写成永久不变的产品契约。

## 一条 Agent 轨迹至少要保存哪些事实

最小可用的事件集合不需要很大：

-
-
-
-
-
-
-
-

```
RUN_STARTEDMODEL_REQUESTEDMODEL_RESPONDEDTOOL_REQUESTEDPERMISSION_DECIDEDTOOL_STARTEDTOOL_FINISHEDRUN_FINISHED
```

每个事件只保留关联和诊断所需的字段：

-
-
-
-
-
-
-
-
-

```
trace_id event_id sequence occurred_at event_type status parent_event_id correlation_id attributes
```

trace_id 把同一次任务中的事件放在一起；event_id 标识一条事实；sequence 让单进程教学模型能以确定顺序展示记录；parent_event_id 表示有限的直接上游关系；correlation_id 可把同一工具调用的请求、权限判断、启动和结束事件串联起来。

status 表示当前事件的已记录状态：权限决策可以是允许或拒绝，工具结束可以是成功或失败；工具事件失败只说明该局部动作失败。只有 RUN_FINISHED.status 表示整项任务的终态；摘要中的 terminal_status 只是从结束事件提取出的任务级结论，不能由任意工具事件的状态替代。

![](附件资源/轨迹与可观测性：如何知道%20Agent%20为什么成功或失败/img_4.png)

这些关联字段不等于完整因果证明。时间先后不必然等于因果，单进程的序号也不能解决分布式系统的时钟偏差。它们的价值是缩小排查范围：能知道某个失败工具结果与哪次调用、哪次权限决策和哪条任务轨迹相关，而不是自动宣布“模型就是根因”。

任务结束尤其需要显式记录。RUN_FINISHED.status 至少应区分成功和失败；这与其他事件的局部 status 分属两个判断层级。生产系统还可能需要超限、中断、等待人工确认或部分完成等业务终态；若要表达这些终态，应扩展终态模型，而不要把某个工具的成功、失败或权限拒绝直接升级为任务结论。没有终止事实的 Trace 只能说明记录暂时停在某处，不能武断地归类为失败。

## 事件链必须穿过模型、权限与工具边界

工具调用不是模型输出一段 JSON 后就自然完成的动作。它通常经历一条受约束的链路：

-
-
-
-
-
-
-
-

```
模型请求工具→ 参数校验→ Permission 决策→ TOOL_PRE Gate→ 工具开始→ 工具成功或失败→ 结果回到运行状态→ 任务结束
```

![](附件资源/轨迹与可观测性：如何知道%20Agent%20为什么成功或失败/img_5.png)

在这条链路上，记录动作和执行动作是两件不同的事：

- TOOL_REQUESTED 只说明模型或上层流程请求了一项工具能力；
- PERMISSION_DECIDED 记录策略的允许或拒绝，不等于工具已运行；
- TOOL_STARTED 才说明执行层开始处理；
- TOOL_FINISHED 记录该次执行的局部结果；
- RUN_FINISHED 说明整个任务的终态，不应由单个工具结果替代；局部失败不自动推出任务失败，任务终态也不抹去已记录的局部失败。

Hook 可以产生额外的门禁或观察事件，但事件记录本身不应放宽 Permission，也不应绕过更早的拒绝。Trace 是证据链，不是授权链；把“已记录”误认为“已批准”，等同于把监控摄像头当成门禁卡。

多个 Agent 运行时，主任务与子任务可通过父 ID 或外部关联 ID 建立关系。不同 Worker 的完整上下文、敏感材料和原始工具结果不应因为“为了观测”就无差别复制到主流程。可关联不等于全量可见。

## 受控事件、写入前脱敏、确定性摘要

领域对象保持不可变，事件类型、状态和属性在构造时完成基本校验：

-
-
-
-
-
-
-
-
-
-
-
-
-
-
-
-
-
-
-

```
class TraceEventType(str, Enum): RUN_STARTED = ”run_started” MODEL_REQUESTED = ”model_requested” TOOL_REQUESTED = ”tool_requested” PERMISSION_DECIDED = ”permission_decided” TOOL_FINISHED = ”tool_finished” RUN_FINISHED = ”run_finished” @dataclass(frozen=True)class TraceEvent: trace_id: str event_id: str sequence: int occurred_at: datetime event_type: TraceEventType status: TraceStatus parent_event_id: str | None = None correlation_id: str | None = None attributes: tuple[TraceAttribute, ...] = ()
```

InMemoryTraceRecorder 在写入事件时做四类收窄：

- 固定一条trace_id，拒绝其他任务混入；
- 事件 ID 不可重复，序号必须从 1 开始连续递增；
- 非根事件只能引用已记录且非自身的父事件；
- 先按RedactionPolicy脱敏，再将副本保存进内存快照。

![](附件资源/轨迹与可观测性：如何知道%20Agent%20为什么成功或失败/img_6.png)

核心脱敏逻辑只针对显式配置的属性键，以不区分大小写的方式识别：

-
-
-
-
-
-
-
-
-
-

```
def redact_event(event: TraceEvent, policy: RedactionPolicy) -> TraceEvent: sensitive_keys = {key.lower() for key in policy.sensitive_keys} attributes = tuple( TraceAttribute( attribute.key, policy.replacement if attribute.key.lower() in sensitive_keys else attribute.value, ) for attribute in event.attributes ) return replace(event, attributes=attributes)
```

例如，api_key、authorization、token、password 会在进入内存快照前替换为 [REDACTED]。这不是通用秘密发现器：它不会递归解析嵌套 JSON、自由文本、编码内容或模型输出，也不能证明所有敏感数据都已保护。能做到的只有一个明确承诺：已建模的显式属性键不会以原值进入这个教学模型保存的事件。

摘要同样只陈述已记录的事实：事件总数、每类事件数量、失败事件 ID、最后的任务终态和是否已经结束。错误码可以帮助定位，但摘要不应把 failure_code=timeout 擅自翻译成“网络一定故障”或“模型一定生成错误”。

## 可观测性首先是数据边界问题

记录不足会让排障失明；记录过量会把可观测系统变成新的泄露面。默认应该把内容与元数据分开。

| **类别** | **可考虑记录** | **应收紧或避免默认记录** |
| --- | --- | --- |
| 任务关联 | Trace ID、事件 ID、父事件 ID、事件类型 | 用户身份原文、完整对话内容 |
| 工具执行 | 工具名、调用 ID、结果码、耗时、重试次数 | 完整参数、完整结果、文件内容 |
| 权限判断 | 策略结果、规则标识、拒绝类别 | 授权头、令牌、宿主机敏感路径 |
| 错误信息 | 受限错误类别、脱敏后的错误码 | 密钥、密码、堆栈中的私密文本 |
| 模型交互 | 请求大小、模型标识、结构化结果类别 | 隐藏推理链、未经授权的输入全文 |

![](附件资源/轨迹与可观测性：如何知道%20Agent%20为什么成功或失败/img_7.png)

默认不记录完整参数、完整结果和输入全文，不等于任何情况下都绝不采集原始内容。排查特定事故、处理授权争议或满足明确审计义务时，可能需要受控采集少量原始输入、工具参数、工具结果或错误片段。这类采集应默认关闭，只针对已定义字段和最短必要时间，经数据分类与授权审批后进入隔离存储，并限制访问、导出和二次使用；到期后应按既定流程删除。隐藏推理链不属于此类采集例外，这些生产治理能力也不属于纯内存教学快照的实现范围。

脱敏发生在存储前，比“先完整写入、之后再清理”更可靠，但仍不是全部治理。生产环境还需要定义采样规则、保留期限、访问控制、导出对象、数据地域、删除流程和审计责任。不同数据分类、法规和组织授权要求并不相同，不能由一个字符串替换函数代替。

同样要区分 Trace 与事实源。Trace 可以告诉系统“某个工具报告成功”，却不必然证明数据库最终状态正确、远端部署已经生效或业务规则满足。外部副作用仍应由结果校验、幂等、补偿、人工确认和业务审计共同处理。

## 公开资料如何对照，而不把概念混成产品承诺

OpenTelemetry、Langfuse 和 Claude Code 讨论的层级不同：

| **对象** | **可对照的公开方向** | **不应由此推出的结论** |
| --- | --- | --- |
| OpenTelemetry | Trace、Span、事件、属性及 GenAI 语义约定 | 任意教学事件类天然兼容标准或已覆盖分布式追踪 |
| Langfuse | Agent、Tool、Generation 等观察类型及嵌套实践 | 所有应用都必须采用相同数据模型或存储后端 |
| Claude Code | claude -p 的 --output-format json、--output-format stream-json 与 --verbose 等公开 CLI 输出能力；Monitoring 文档列出的 OpenTelemetry 指标、事件与可选数据采集控制 | 教学 TraceEvent 已映射为 Claude Code 事件、内部 Trace 结构、隐藏推理、未启用时的采集行为、遥测实现或所有运行行为 |

OpenTelemetry 的规范提供通用词汇；Langfuse 的文档展示工程平台如何组织不同观察类型；Claude Code 的对照范围应限于公开且可在发布时复核的接口：CLI 参考中的 claude -p 输出格式与 verbose 行为，以及 Monitoring 文档列出的 OpenTelemetry 指标、事件和可选数据采集控制。CLI 的 JSON 或 stream-JSON 输出、Monitoring 导出与教学内存事件不是同一协议；它们不能反推内部 Trace 数据模型、隐藏推理、未公开遥测实现或任意配置下的完整运行过程。目标安装版本、OS 与运行环境、权限和配置来源、启用项、数据采集范围、存储与导出边界及稳定性标记，都应在发布日按官方资料逐项复核。

## 测试能证明局部契约，不能伪称生产可观测性

在项目根目录运行：

-

```
python -B -m unittest discover -s ”articles/agent-harness全景/code/21-observability” -p ”test_observability.py” -v
```

测试模块定义 6 个 unittest 测试方法，分别验证：

- 值对象拒绝空 ID、非法序号、无时区时间、空或重复属性键，以及不合理的事件与状态组合；
- recorder 拒绝跨 Trace、重复事件 ID、跳号、倒序号和未知父事件；
- 正常的任务、模型、工具、权限和结束事件保留确定顺序、父事件和调用关联；
- api_key、authorization、token、password 等显式键在写入前被替换，普通属性保持不变；
- 成功、失败和未结束的轨迹生成不同的确定性摘要，不把错误码伪装成根因；
- AST 检查拒绝生产模块引入网络、Shell、并发 Runtime、动态执行和文件持久化能力。

![](附件资源/轨迹与可观测性：如何知道%20Agent%20为什么成功或失败/img_8.png)

这些测试不能证明分布式上下文传播、时钟同步、采样策略、持久化摄取、访问控制、保留期限、数据合规、真实模型行为、工具副作用、完整秘密识别或生产隐私保护。它们只能证明：调用方提供确定的 ID 与时间时，这个本地教学模型会按契约关联事件、在存储前替换已配置的属性键，并从已保存事件生成有限摘要。

## 小结

Agent 可观测性不等于堆积日志，也不等于记录所有内容。更可靠的做法是让每层留下最少必要、可关联、可保护的事实：

-
-
-
-
-
-
-
-
-
-
-
-
-
-

```
同一次任务属于哪条 Trace？→ trace_id 这条记录是什么、发生在何时？→ event_id、event_type、sequence、occurred_at 它与哪次调用或上游动作相关？→ parent_event_id、correlation_id 能安全保留哪些诊断信息？→ 受限 attributes 与写入前脱敏 任务如何结束、哪里出现失败？→ status、failed_event_ids、terminal_status
```

Trace ID 不能代替权限，脱敏函数不能代替数据治理，工具成功事件不能代替业务验收。把这些边界说清楚，团队才有机会从“任务失败了”走到“哪一条证据支持下一步排查”。
