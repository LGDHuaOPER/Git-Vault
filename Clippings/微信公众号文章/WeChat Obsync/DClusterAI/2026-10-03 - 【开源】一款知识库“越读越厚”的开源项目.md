# 【开源】一款知识库“越读越厚”的开源项目

> 同一份 PDF 问第三次，RAG 还是从零检索、从零拼接—— **知识没有沉淀，每次提问都在重新推导**。Karpathy 在方法论里写下的解法是：让 LLM 增量构建并维护一个持久 Wiki，"知识只编译一次并持续更新"。本文基于源码，拆开这个把方法论写成 13 万行源码的桌面应用：两步思维链摄入、SHA256 增量缓存、Rust 里的混合检索、四信号知识图谱，以及一条刻意"不回流"的深度研究链路。

**规模**:474 个文件;TS/TSX 362 个 / 9.46 万行(其中测试 151 个文件 / 3.52 万行),Rust 41 个 / 3.51 万行,Chrome 扩展 4346 行
**热度**:⭐ 20.1k Star · 2.3k Fork · 创建于 2026-04-08 · 889 次提交 · 最近发布 v0.6.12
**交付**:Tauri v2 跨平台桌面应用(macOS / Windows / Linux)+ 本地 HTTP API(19828)+ MCP Server(12 工具)+ Chrome 剪藏扩展(19827)
**栈**:React 19 + Vite + Tailwind v4 + Zustand + Milkdown · Rust 后端 + LanceDB(可选向量)· **纯本地,可不配任何云服务跑通**

## 一、RAG 的病根:知识不沉淀

Karpathy 那篇 75 行的 https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f 开头就把话说透了:

> "the LLM is rediscovering knowledge from scratch on every question. There's no accumulation."
> ——每次提问,LLM 都在从零重新发现知识。没有积累。

他的解法不是更好的检索,而是换一层中间物:**LLM 增量构建并维护一个持久的 Wiki**,放在你和原始资料之间。新资料进来时 LLM 不是"索引一下等着被检索",而是读它、抽取信息、合入既有 Wiki——更新实体页、修订主题摘要、标出新旧矛盾。原文的三个关键词是:

> **"the wiki is a persistent, compounding artifact."** ——Wiki 是一个持久的、复利增长的产物。

架构只有三层、操作只有三个,本项目**原封不动地保留**了这套骨架:

![问题定位:RAG 与 Wiki 的分水岭](附件资源/【开源】一款知识库“越读越厚”的开源项目/img_1.png)

|  |  |  |
| --- | --- | --- |
| 层 | 谁拥有 | 规则 |
| ** Raw sources ** | 你 | 不可变,LLM 只读 |
| ** Wiki ** | LLM | 全权创建、更新、交叉引用 |
| ** Schema ** | 你和 LLM 共同演化 | 告诉 LLM 结构约定与工作流 |

三个操作:**Ingest**(摄入)、**Query**(查询)、**Lint**(健康检查)。配套两个特殊文件: `index.md` (内容目录,LLM 查询先读它再下钻,原文说这"在 ~100 个源、几百页的规模上出奇地好用,可以省掉 embedding 基础设施")和  `log.md` (追加式日志,固定前缀  `## [2026-04-02] ingest | 标题` , `grep "^## \[" log.md | tail -5`  就能解析)。

还有一句被反复引用的话,解释了这件事为什么过去做不成:

> "Humans abandon wikis because the maintenance burden grows faster than the value. LLMs don't get bored, don't forget to update a cross-reference, and can touch 15 files in one pass."

**人放弃知识库,是因为维护负担长得比价值快。** LLM 不会烦,一次能改 15 个文件。所以原文的角色分工是:**人负责选料、定向、提问;LLM 负责其余一切。**

llm_wiki 就是把这 75 行抽象设计实例化成产品的工程——而真正值得拆的,是它在"忠实"和"增强"之间做的每一次取舍。

## 三、整体设计思路:忠实保留,以及五处被论证过的增强

看这种"复刻方法论"的项目,最容易犯的毛病是数功能。真正值得学的是:**原始设计里没有的东西,它加了什么、为什么加、以及加的时候踩了什么坑。**

![忠实保留与五处增强](附件资源/【开源】一款知识库“越读越厚”的开源项目/img_3.png)

**增强一: `purpose.md`  —— schema 管"怎么运作",purpose 管"为什么存在"。**
Karpathy 只定义了 Schema(结构规则),没定义这个 Wiki 的**方向意图**。本项目新增  `purpose.md` :目标、关键问题、研究范围、演进中的论点,LLM 在每次摄入和查询时都读它拿上下文( `buildGenerationPrompt`  的可选区块)。项目创建时由 Rust 写入( `src-tauri/src/commands/project.rs:121` )。

**增强二:index 与 overview 归应用所有,不再让 LLM 重写。**
生成 prompt 里有一行非常直白( `src/lib/ingest.ts:2436` ):

```
Donotgeneratewiki/index.mdorwiki/overview.md.Theapplicationmaintainsaggregatenavigationseparatelysolargewikisareneverrewrittenthroughmodeloutput.
```

—— **大 Wiki 的聚合导航绝不经过模型输出**。摄入完成后由  `updateWikiIndexDeterministically` ( `ingest.ts:1703` )确定性追加新页条目,只维护一个  `## Recently Updated`  段、上限 200 条;另有  `rebuild_wiki_index_inner` ( `project_maintenance.rs:294` )从 frontmatter 全量重建。这一步修掉的是 Karpathy 原设计里一个随规模恶化的隐患:index 会越来越大,让 LLM 每次全量重写它,既烧 token 又会丢条目。

**增强三:两步摄入,替代"读一遍同时写"。**
原始设计是单步:LLM 阅读的同时就写入。本项目拆成**两次顺序调用**——先分析、再生成(第四节展开)。

**增强四:内容页合并,而不是覆盖。**
同一个实体被第二份资料再次触及时,不能把旧内容冲掉。 `ingest.ts:2159`  起的注释写清了三层合并:frontmatter 数组字段(sources/tags/related)由应用层做并集;正文不同则**再调一次 LLM 生成融合后的正文**; `type/title/created`  强制锁回旧值,只盖  `updated` 。LLM 合并失败就回退到"新正文 + 数组并集"。

**增强五:异步审核,替代全程人机协作。**
原始设计建议摄入时人全程在场。本项目让 LLM 在摄入中**标记**需要人工判断的项,人**异步**处理——且操作类型被枚举锁死( `ingest.ts:2244` ): `contradiction`  /  `duplicate`  /  `missing-page`  /  `suggestion`  四种,每项附  `OPTIONS: Create Page | Skip`  和预生成的 2-3 条搜索查询。**约束操作类型是防幻觉手段**:LLM 想凭空发明一个操作,格式解析这一关就过不去。

把取舍放进一张表:

|  |  |  |  |
| --- | --- | --- | --- |
| 设计问题 | Karpathy 原设计 | 它的选择 | 换来了什么 |
| Wiki 为何存在 | 未定义 | 新增  `purpose.md`  | 摄入/查询有方向感,不是泛泛总结 |
| 聚合导航谁来写 | LLM 每次摄入更新 index | 应用确定性重建 | 大 Wiki 不再被模型输出重写 |
| 摄入节奏 | 单步读写 | 两步:先分析后生成 | 质量提升,且分析可独立校验 |
| 已有页面被再次触碰 | 更新既有页 | 三层合并(并集+LLM 融合+锁字段) | 多来源贡献都保留 |
| 人何时介入 | 摄入全程 | 异步审核队列 + 枚举操作 | 不阻塞流水线,LLM 不能发明动作 |

**方法论是抽象的,工程全在细节里。** 下面三节拆它最重的三块:摄入、检索、图谱。

## 四、两步思维链摄入:先讨论,再动笔

这是全仓最值得抄的部分。两次调用分工明确( `src/lib/ingest.ts` ):

![两步思维链摄入](附件资源/【开源】一款知识库“越读越厚”的开源项目/img_4.png)

**第一步·分析**( `buildAnalysisPrompt` , `ingest.ts:2328` )。docstring 自述:_"This is the 'discussion' step — the AI reasons about the source before writing wiki pages."_ 让 LLM 输出六块结构化分析:Key Entities / Key Concepts / Main Arguments & Findings / Connections to Existing Wiki / Contradictions & Tensions / Recommendations。实体逐个打  `Page-worthy: yes/no`  加一句理由,并有专门的显著性阈值规则:

```
Applyastandalone-pagesignificancethreshold:page-worthysubjectsarecentraltothesource,recurmeaningfully,carrysubstantiveclaims,orarereusableacrossthewiki.Donotmarkpassingmentions,ordinarystoryprops...aspage-worthy.
```

**第二步·生成**( `buildGenerationPrompt` , `ingest.ts:2391` )。system = 结构约束 + schema/purpose/index/overview,user = **第一步的分析全文 + 源文档全文**,输出  `---FILE:`  块,每块一个 wiki 文件。

这里有个名字与实现的反差,值得单独说:**它叫"思维链摄入",但两个 prompt 都明令禁止输出思维链**—— `Do not output chain-of-thought, hidden reasoning, or a thinking transcript. Reason internally and write only the concise final analysis.`  它要的不是把思考吐出来,而是**"先想清楚、再动笔"的两段式结构**:分析是一份可被检查的中间产物,而不是泄露的内心戏。

prompt 工程里有四处手艺,全是被真实失败磨出来的:

**1. 输出格式段必须放在 system prompt 最末尾。** 代码注释直接承认原因( `ingest.ts:2522` ):

```
// ── OUTPUT FORMAT MUST BE THE LAST SECTION — models weight recent instructions highest ──
```

**2. 语言指令在头、中、尾重复三次**,结尾那次的注释更坦诚( `ingest.ts:2556-2558` ):_Small-to-medium models otherwise drift back to their training-data language for individual pages._ ——中小模型会漂回训练语系,靠"最近指令权重最高"这个 tie-breaker 兜底。

**3. 解析失败是硬失败,不留余地。** 首字符不是  `-` (即  `---FILE:` )就整体丢弃;响应里出现 FILE/REVIEW 之外的散文也算违规( `ingest.ts:2544-2554`  七条 STRICT 要求)。前端还备了一个  `---FILE:`  起手的强校验。

**4. 两步的失败是不对称的。** 第一步输出被截断 → 抛  `NonRetryableIngestError` ,**队列不重试**( `ingest.ts:1103`  +  `ingest-queue.ts:1043` ):分析残缺,后面全错,重试同样会截断。第二步截断 → 记入  `truncatedPaths` ,走**第三轮修复调用**只补缺失文件,并支持  `## Resume checkpoint`  断点续写—— **页面残缺可救,分析残缺不可救**。两步 temperature 都压到  `0.1` 。

生成之后还有可选的第三步·审核建议( `buildReviewSuggestionPrompt` , `ingest.ts:2565` ),专门产出 REVIEW 块,并明确 _"Prefer 1-5 high-signal reviews. If there is nothing worth reviewing, output nothing."_

顺带一条保真规则,对做 RAG 的人很有参考价值( `ingest.ts:2482-2487` ):

```
Preserve subject boundaries: when a source discusses multiple entities/models/..., keep claims, evaluations, limitations, benchmark results ... attached to the exact subject they describe. Preserve structured source data verbatim: copy SQL DDL / CREATE TABLE statements ... A prose-only summary that drops them loses the structure the user imported the source to keep.
```

—— **DDL、表结构、API 签名必须原样保留**;把 A 的结论合并进 B 的页面,是被明令禁止的。

## 五、摄入的工程化:队列、缓存与一条被三处复用的流水线

提示词决定质量,流水线决定它能不能一直跑下去。

![摄入流水线与增量缓存](附件资源/【开源】一款知识库“越读越厚”的开源项目/img_5.png)

**SHA256 增量缓存**( `src/lib/ingest-cache.ts:20,76` )。摄入前先对源文件内容取哈希,命中就跳过。但"跳过"的边界被划得很精确( `ingest.ts:825-917` ):**跳过的是两次 LLM 调用、页面写盘和重嵌入;不跳过的是抽图、图片字幕、注入和该源摘要页的重嵌入**——而且整段包在提交临界区里,开头先  `throwIfIngestAborted` 。注释还诚实记了局限:老文档里的  `## Embedded Images`  段不会被主动清除。

**持久化队列**( `src/lib/ingest-queue.ts` )。队列落到磁盘  `.llm-wiki/ingest-queue.json` ,应用重启自动恢复;默认  `workerLimit = 1`  串行(防并发 LLM 调用),可被  `clampUserConcurrency`  提到 1~64; `MAX_RETRIES = 3` ( `ingest-queue.ts:938` );失败任务在活动面板可取消、可重试。**串行不是性能妥协**:摄入要读 index/overview 并写回,并发摄入会让"读到的现状"互相覆盖。

**一条队列,三个入口。** 手工导入、Chrome 剪藏( `clip-watcher.ts`  每 3000ms 轮询 19827 端口)、以及 Source 文件夹自动监听( `file_sync.rs`  用 notify 监听外部变更, `APP_WRITE_IGNORE_MS = 4000`  屏蔽 App 自己的写入,32MB 以上文件只比 size/mtime、否则 md5 判变更),**全部汇入同一条  `enqueueSourceIngest` **。默认规则( `source-watch-defaults.json` )覆盖 29 个扩展名、排除  `.git/.obsidian/node_modules`  等目录。

**图片摄入是一条独立的小流水线**:Rust 侧纯确定性抽图并算 sha256( `extract_images.rs` )→ VLM 生成事实性描述 → 缓存键是  `图片字节的 sha256` (+ 语言后缀, `image-caption-pipeline.ts:116` )→ 注入资料摘要页。**同一张图换个编码方式不会 miss,因为 hash 的是字节不是 base64 字符串**;多模态总开关关闭时,已有描述仍会被保留。

**删除是级联的**( `fs.rs:1840 collect_related_pages` ):删一个源文件,按三重匹配找相关页——frontmatter  `sources[]`  字段、资料摘要页名、frontmatter 章节引用;**共享实体不删整页**,只从它的  `sources[]`  里摘掉这一条,再清理 index 和失效 wikilink。

## 六、查询管线:Rust 里的混合检索

Karpathy 原文说小规模靠 index.md 就够。这个项目把"规模上去之后"的那条路也铺了:检索主干在  `src-tauri/src/commands/search.rs` (2453 行),四段管线:

![混合检索管线](附件资源/【开源】一款知识库“越读越厚”的开源项目/img_6.png)

**① 分词:中文 CJK bigram。** `tokenize_query` ( `search.rs:995` )对含 CJK 的词做二元组 + 单字 + 整词三路切分( `每个`  →  `每个/个…` ),标点分隔符显式包含全角  `，。！？、；:`  等;停用词过滤在前。

**② 打分:标题加成是一串写死的常量**( `search.rs:15-26` ):

|  |  |  |
| --- | --- | --- |
| 常量 | 值 | 含义 |
|  `FILENAME_EXACT_BONUS`  | 200 | 文件名精确命中 |
|  `PHRASE_IN_TITLE_BONUS`  | 50 | 短语出现在标题 |
|  `PHRASE_IN_CONTENT_PER_OCC`  | 20 | 正文短语每处(最多计 10 处) |
|  `TITLE_TOKEN_WEIGHT`  /  `CONTENT_TOKEN_WEIGHT`  | 5 / 1 | 分词命中:标题权重是正文 5 倍 |
|  `RRF_K`  | 60 | 融合用的 Reciprocal Rank Fusion |
|  `SEARCH_EMBEDDING_TIMEOUT_SECS`  | 8 | 向量请求超时 |

五项全为 0 直接不进候选—— **未命中就不进池,不做兜底打分**。

**③ 向量:可选,且失败要静默降级。** LanceDB( `wiki_chunks_v2`  表)按  `1/(1+distance)`  给相似度;embedding 请求超时/失败只  `eprintln!`  后返回  `Ok(None)` (**退化成纯关键词,绝不让检索失败**);页级分数 = 最高 chunk 分 + 0.3 × 剩余 chunk 分(封顶),**防止长页靠 chunk 数量刷分**。

**④ 融合与图谱扩展:两个反直觉的设计。**
其一,RRF 只在  `vector_hits > 0`  时套用,否则保留关键词原始分( `search.rs:464` )——向量分只做融合,不做绝对判断。
其二,**图谱扩展只有一跳**,注释写在  `search.rs:541` :

```
/// Reserve 15-30% of the final window for one-hop graph expansion.
```

配额是动态的: `graph_result_quota`  里向量命中覆盖率越高,图谱配额越低(30% → 15%),缺额自动还给关键词/向量结果;一跳邻居按种子排名做**秩衰减**累加  `1/(rank+1)` 。README 写的"2 跳遍历带衰减"在代码里查无实据(第十节)。

**上下文预算**是另一处 README 与代码不同的地方。 `src/lib/context-budget.ts:16-21`  的 ASCII 图就是权威:

```
│ idx  │   pages       │  history + sys   │  resp     │ │  5%  │    50%        │    ~30%          │   15%     │
```

常量在  `context-budget.ts:55-60` ( `INDEX_BUDGET_FRAC=0.05`  /  `PAGE_BUDGET_FRAC=0.5`  /  `RESPONSE_RESERVE_FRAC=0.15` ,单页下限 5000 字符)。Rust 侧还有一道兜底  `fit_context_to_model` ( `runtime.rs:3845` ):上下文按字符 clamp 到 8K~400K,**system 优先砍、user 至少保 4000 字符**。回答侧用**编号引用**,前端三级回退解析( `chat-message.tsx:1241` ):隐藏注释  `<!-- cited: 1, 3 -->`  → 正文  `[1]`  →  `[[wikilink]]` 。

## 七、知识图谱:四信号、Louvain,以及两类洞察

原始设计只有  `[[wikilink]]`  交叉引用,没有图分析。本项目建了完整的关联度引擎 + 可视化 + 自动洞察。

**四信号关联度模型**的权重是四个写死的常量( `src/lib/graph-relevance.ts:33-38` ),计算在  `calculateRelevance()` ( `:308-348` ):

|  |  |  |
| --- | --- | --- |
| 信号 | 权重 | 计算 |
| 直接链接 | ** ×3.0 ** | 双向 wikilink 数 × 3 |
| 来源重叠 | ** ×4.0 ** | 共享同一原始资料的页数 × 4(最高) |
| Adamic-Adar | ** ×1.5 ** |  `Σ 1/ln(max(邻居度,2))`  ——共享的"大众邻居"不如共享的"冷门邻居"值钱 |
| 类型亲和 | ** ×1.0 ** | 5×5 非对称矩阵:entity↔concept ** 1.2 ** 、source↔source ** 0.5 ** |

**来源重叠权重最高(4.0)**,这是和"代码知识图谱"类项目最大的分歧:在这个场景里,**两页讲的是同一份资料**比"两页互相链接过"更能说明它们相关——链接可以是 LLM 顺手加的,来源是硬事实。

![四信号关联度与图谱洞察](附件资源/【开源】一款知识库“越读越厚”的开源项目/img_7.png)

**Louvain 社区检测**: `graphology-communities-louvain` , `resolution: 1` ;节点数 ≥  `COMMUNITY_WORKER_THRESHOLD = 500`  时切到 Web Worker 跑,否则主线程。内聚度  `cohesion = 内部边数 / n(n-1)/2` ,但**判定"稀疏社区"用的不是它**—— `graph-insights.ts:163`  的条件是:

```
if(comm.meanIntraDegree<2&&comm.nodeCount>=3){
```

即"社区内每页平均不到 2 条内部链接"。这不是笔误,而是 commit  `37210ca` (2026-09-16, _"make sparse cluster insights scale independent"_)的有意修改:**cohesion 是密度,大社区天然稀疏,会误报;平均内部度与规模无关**。README 里的  `cohesion < 0.15`  已是旧文(第十节)。

**两类洞察**( `src/lib/graph-insights.ts` ):

- 惊奇连接 (  `:52-123`  ):跨社区 +3 、跨类型 +2 (远对如 source↔concept 再 +1)、边缘↔枢纽(度 ≤2 且对方 ≥ 最高度一半) +2 、弱边  `0 < weight < 2`  +1 ; score ≥ 3 才入选 ,上限 5 条。
- 知识空白 (  `:135-215`  ):孤立页(入链 ≤1,最多 5 个)、稀疏社区(  `meanIntraDegree < 2`  )、桥接节点(邻居横跨 ≥3 个社区)。

点击洞察卡片上的 **Deep Research** 按钮,会带  `overview.md`  +  `purpose.md`  调  `optimizeResearchTopic`  生成领域化研究主题(**不是泛泛关键词**),在可编辑确认框里让用户改完才入队。

渲染侧的工程细节同样讲究:ForceAtlas2 在 **220 节点**以上切 worker( `WORKER_LAYOUT_NODE_THRESHOLD` ),迭代次数随规模从 140 降到 28;**位置缓存**用 FNV-1a 哈希(节点+边+间距)做 key,数据不变就不重排,避免每次刷新图都"跳一下";节点大小  `8 + √(link/max)×20` ,再乘一个规模密度系数(>150 节点开始收缩)。

一个不起眼但真实的细节:洞察的"标记已读"是  `useState<Set>` ( `graph-view.tsx:655` ),**纯组件内存态,不落盘**——刷新页面,惊奇连接会重新出现。

## 八、Rust Chat Agent:8 次迭代、两次止损、三段式审批

聊天不是"前端拼个 prompt 调接口",而是一个跑在 Rust 里的工具型 Agent:

|  |  |  |
| --- | --- | --- |
| 模块 | 行数 | 职责 |
|  `agent/runtime.rs`  | 5816 | 主循环、权限、审批、上下文裁剪、取消 |
|  `agent/tools.rs`  | 3888 |  `ToolRegistry`  + 内置工具实现 |
|  `agent/provider.rs`  | 1607 | 三协议分支(OpenAI 系 / Anthropic 系 / Google) |
|  `agent/skills.rs`  | 699 | SKILL.md 扫描与加载 |
|  `agent/context.rs`  | 645 | 上下文拼装、编号引用 |

![Rust Agent 循环](附件资源/【开源】一款知识库“越读越厚”的开源项目/img_8.png)

**止损机制是这个 Agent 最像"人"的地方:**

- 迭代上限  `MAX_AGENT_TOOL_ITERATIONS = 8`  (  `runtime.rs:38`  )。但撞上限不等于失败——  `agent_iteration_limit_answer`  (  `runtime.rs:3476`  )会检查: 如果本轮已经产出了 workspace 文件,就把"达到迭代上限"的话术改写成文件交付清单 。做实事撞到上限,展示成果;空转撞到上限,才说实话。
- 连续 2 次检索无新证据就强制收尾 (  `runtime.rs:1800-1816`  ,  `consecutive_no_gain_retrievals >= 2`  ):每次工具调用后对比 evidence 数,没有增量就计数,计满就  `force_final_next`  。 防止"smart 模式"无限重试烧钱。

**Shell 审批是三段式,而且"不等待"**(这点最反直觉):

- 免审批判定 (  `is_shell_command_allowed_without_prompt`  ,  `runtime.rs:3653`  )= 命令字符串与已批准项 逐字符全等 ∨ 作用域被限制在  `agent-workspace/`  内。作用域检查是词法级的:命令里出现  `http://`  、  `curl`  、  `wget`  、  `ssh`  、  `$(`  、反引号,或任何 token 提到  `~`  、  `$HOME`  、  `..`  、workspace 外的绝对路径 → 一律要求审批 。没有命令解析器,只有黑名单 + 路径白名单——简单,但可审计。
- 审批边界不挂起等待 。命中审批时 Agent 返回一个观察  `shell.exec.approval_required`  ,主循环 把提示作为最终回答、本轮直接结束 (  `runtime.rs:1761-1798`  );前端收到后重建历史,带上  `approvedShellCommands: [command]`  重发(  `chat-panel.tsx:1330-1381`  ),Agent 从边界续跑。 一个 turn 的生命周期因此是干净的:要么完成,要么停在一个可明确恢复的边界上。
- 首道闸:  `shell.exec`  只在本回合有 active skill 时才可用(  `runtime.rs:1900`  ),skill 的偏好探测命令会被静默跳过。

**Skills 走"懒加载"**: `skill_roots`  四个根( `skills.rs:79-99` )—— `<项目>/.llm-wiki/skills` 、 `~/.claude/skills` 、 `~/.codex/skills` 、 `~/.agents/skills` ,项目级覆盖用户级。关键设计是  `load_skill_directory` **只把 SKILL.md 注入 prompt,附属文档留给 Agent 用  `skill.read_file`  按需读**( `skills.rs:281-284` )——skill 再大也不会挤爆上下文。这也意味着:**你在 Claude Code 里装的同一批 skill,这个 App 的 Agent 也能用**(两个系统共享目录约定)。

**传输层还有个"借壳"设计**: `claude_cli.rs`  会 spawn 真实的  `claude`  CLI 当纯文本补全引擎。两个坑被显式处理:① Claude Code 没有可移植的  `--system-prompt` ,所以**把 system 折进第一条 user 消息**(注释说明这是为了绕开 prompt-injection 守卫);② content **必须是 block 数组**,传字符串会让 CLI 直接崩在  `W is not an Object` ( `claude_cli.rs:332-337` )。桌面 App 不继承登录 shell 的 PATH,检测和执行都要手动补( `child_path_env` )。

取消则是全链路的: `cancel.rs`  用  `Arc<AtomicBool>`  + 50ms 轮询,所有等待点包在  `tokio::select! { biased; _ = token.cancelled() => ... }`  里——注释也承认边界:_只能停止等待,无法杀掉 blocking pool 里已经在跑的 OS 工作_。

## 九、一个本地端口的三种用法:API、MCP、扩展

这个项目的对外能力全靠**两台 tiny_http + 一个 stdio 进程**,安全边界写得很清楚:

![本地 API 与三种接入方式](附件资源/【开源】一款知识库“越读越厚”的开源项目/img_9.png)

**19828:本地 HTTP API**( `api_server.rs` , `PORT: u16 = 19828` )。13 条业务路由(README 只列了 8 条),方法白名单 GET/POST/PATCH,默认绑定  `127.0.0.1` 。鉴权有三个层次,最后一层最容易被忽略:

- Token 三种携带方式(query  `?token=`  / header  `x-llm-wiki-token`  /  `Bearer`  ),比较用  `constant_time_eq`  常数时间;
-  `allowUnauthenticated`  开关可让 只读 接口免 token;
- 但写接口和 Agent 聊天永远要 token ——  `is_token_required_request`  (  `api_server.rs:427`  )对  `chat`  /  `pages/embed`  /  `pages/write`  无条件要求,测试名就叫  `paid_or_mutating_agent_routes_always_require_a_token`  (  `:3732`  )。

**"只读可以开放,写入永远鉴权"是这个 API 唯一需要记住的规则。** 外加限流(1s 窗口 120 请求)、在途并发闸(64 / 8 个 chat 流 / 4 个 embed)、请求体上限(普通 1MB、chat 40MB),以及  `list_public_roots`  只暴露  `purpose.md / schema.md / wiki / raw/sources`  四个根、跳过隐藏文件与符号链接。

**19827:Chrome 剪藏**( `clip_server.rs` )。扩展用 Readability + Turndown 把网页转 Markdown(截断 100 万字符)POST 过来,App 每 3 秒轮询拉走,**汇入与手工导入完全相同的摄入队列**;App 未运行也能离线预览提取结果。这台服务器做了 API 服务器没做的事:**显式 loopback 校验**( `request_is_loopback` ),非本机请求必须带同一枚 token,注释写明原因:_否则会泄露项目路径并允许网络上任意设备写入。_

**MCP Server:12 个工具,零本地逻辑。** `mcp-server/src/index.ts`  的每个工具都经  `api-client.ts`  打到  `http://127.0.0.1:19828/api/v1` ——README 说得很直白:_so MCP clients use the same project registry, file permissions, search backend, graph backend, and Source Watch rules as the app._ 检索、图谱、权限**只有一份实现**,MCP 只是转发。另外还有配套 agent skill 仓库( `npx skills add …/llm_wiki_skill.git` ),且刻意不响应"搜我的笔记"这类泛指—— **只有你明说 LLM Wiki / 我的知识库才触发**。

## 十、文档与代码的五处不一致

一个项目诚实不诚实,不看它写了什么,看它的文档**哪里过时了还没人粉饰**。这五处都是我逐行核对过的(都是小问题,但值得写出来):

|  |  |
| --- | --- |
| README 里的说法 | 代码里的事实 |
| 上下文"60% Wiki / 20% 聊天历史 / 5% 索引 / 15% 系统提示" | 实际是  `5% / 50% / ~30% / 15%`  (  `context-budget.ts:55-60`  ),"60%"只出现在设置页 UI 文案里 |
| 图谱扩展" ** 2 跳 ** 遍历带衰减" | 实际是 ** 一跳 ** + 秩衰减  `1/(rank+1)`  + 15~30% 动态配额(  `search.rs:541`  ) |
| 低内聚社区警告  `cohesion < 0.15`  | 实际是  `meanIntraDegree < 2`  (  `graph-insights.ts:163`  ),2026-09-16 改为与规模无关 |
| 深度研究"研究结果 ** 自动摄入 ** Wiki" | 实际 ** 刻意绕开 ** 摄入:  `deep-research.ts:689-712`  直接写页 + 建向量,注释写明原因—— _ 回流摄入会造出第二张摘要页,并从自己的缺口里递归产生低价值 review _ |
| "  `overview.md`  每次摄入后重新生成" | 生成 prompt 明令  `Do not generate wiki/overview.md`  ,全仓只有项目创建时写一次占位(  `project.rs:182-194`  );index 才有确定性重建 |

另外两处小的:README 的 API 端点只列了 8 条(实为 13 条),MCP README 只列了 10 个工具(实为 12 个)。

**这些不是缺陷,恰恰是可信度的来源**——深度研究那条尤其漂亮:它主动放弃了"自动摄入"这个听起来很美的卖点,并在代码注释里写清了递归风险。一个愿意把自己的功能写"少"的项目,其他数字更值得信。

## 十一、写在最后:几个反直觉的结论

读完 13 万行,有七个结论和文档的第一印象不同:

- "思维链摄入"禁思维链。 两个 prompt 三处  `Do not output chain-of-thought`  。它要的是 可见的两段式结构 (分析 → 生成),不是内心戏。
- 大 Wiki 的 index 不让 LLM 写。 Karpathy 原设计里 LLM 每次更新 index;这里改成应用确定性重建,理由是 "so large wikis are never rewritten through model output" 。
- 缓存命中不等于什么都不做。 SHA256 命中跳过的是 LLM 调用与写盘,抽图、打字幕、注入、重嵌入照跑,且整段仍在提交临界区内。
- 检索图谱扩展只有一跳 ,配额随向量覆盖率 反向 滑动(30%→15%)——向量越有用,图谱越让位。
- API 只读可以无鉴权,写入和聊天永远要 token。 一条规则管住整个本地 API。
- 深度研究刻意不回流摄入。 防止"用自己产出的页面喂自己,再从缺口里递归生成 review"。
- Shell 审批不挂起等待 ,而是结束整个 turn,由前端带着已批准命令重发续跑——turn 的生命周期永远干净。

这七点背后是同一种气质:**把边界守严,把理由写下来。** 队列注释解释为什么默认串行,Agent 注释解释为什么限额放后端,深度研究注释解释为什么不回流,prompt 注释解释为什么格式段要放最后—— **这个仓库的注释密度,是我读过的开源项目里靠前的。**
