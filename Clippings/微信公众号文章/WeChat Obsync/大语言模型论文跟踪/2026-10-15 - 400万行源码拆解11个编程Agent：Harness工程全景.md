# 400万行源码拆解11个编程Agent：Harness工程全景

PAPER · 论文信息

标题Harness Engineering: Anatomy, Architecture, and Evolution of Coding Agents — A Source-Code Study of Eleven Systems

作者Paul Barbaste¹˒²†、Tristan Darrigol²、Germain Vu²、Tom Wiltberger²

机构¹Inclusive Brains；²Wavestone AI Lab

原文https://arxiv.org/abs/2609.00006

### INSIGHT · 核心洞察 大模型要变成能读写代码库的编程 Agent，靠的是模型之外的那一层运行时：循环、工具、上下文、权限、编排和扩展接口。这篇论文把这一层称为 Harness，并给出一个判断标准：读源码看它在七个子系统上分别做了什么选择，而不是只看基准分数。这决定了我们该先搭哪些部件、哪些部件可以晚点做，以及怎样理解各家产品之间的差异。 一个只有 bash 工具、约 100 行代码的循环，在 SWE-bench Verified 上自报的成绩与百万行级的产品处在同一区间。可一旦要放进企业代码库，它缺的不是解题能力，而是沙箱、审批、上下文压缩和插件生态。大量工程投入究竟花在哪里、为什么，正是这篇论文追问的问题。 作者阅读了 11 个生产级编程 Harness 的源码，合计约 400 万行 Python、TypeScript 和 Rust，归纳出 13 条横向观察、29 种复用设计模式和 18 条设计建议。它是 arXiv 预印本，方法是源码阅读而非运行测评：论文不跑分、不排名，其中 Claude Code 部分基于 2026 年 3 月流出的源码快照。文中的结论描述系统怎样构建，不直接说明哪个更好用。

📌 **一句话总结**　本文提出 Harness Engineering（Harness 工程）的参考解剖图，围绕七个子系统和一个季度的源码演化，区分各系统的结构选择、横向趋同模式与平台化信号三类发现。

01

BACKGROUND

## 研究背景：Agent = 模型 + Harness

论文先固定研究对象：Agent 由模型和 Harness 组成，Harness 是除模型以外的全部运行时。这个说法在 2026 年初才进入工程圈，几个月内就出现了实践指南、形式化定义和自动演化 Harness 的研究。作者想补上缺少的一环：以生产源码为依据，说清 Harness 到底由什么组成。

为避免概念混用，论文划出四条边界。Harness 不等于 LangChain、AutoGen 这类框架，框架是开发者导入的库，Harness 是开发者在其中工作的运行时；它也不是 SWE-bench 的评测 harness，后者包裹 Agent 去跑任务，方向正好相反；它更不是编排器，编排器从上方协调多个 Harness，本身不实现编辑循环。区分这些角色，是为了让后文的比较始终针对同一类对象。

![图 1](附件资源/400万行源码拆解11个编程Agent：Harness工程全景/img_1.png)

图 1｜Harness 的七个子系统围绕 Agent 循环展开，界面层负责人和程序的接入；方框只表示功能划分，不表示每个系统都有独立模块。

图 1 把 Harness 拆成七块：Agent 循环、LLM 集成、工具与动作、记忆与上下文、安全与权限、多 Agent 编排、扩展机制。作者的论点是，从 100 行的研究基线到百万行的产品，每个系统都必须在这七件事上表态，哪怕表态是“不做”。表 1 给出每个子系统在语料中最小和最大的实现。

![表 1](附件资源/400万行源码拆解11个编程Agent：Harness工程全景/img_2.png)

表 1｜七个子系统的作用及最小、最大实现；“最大”指工程投入，不代表效果最好。

例如 Agent 循环，最小形态是 Mini-SWE-Agent 的一个 while 循环加一个 bash 工具，最大形态是 OpenHands 基于持久事件日志的会话引擎，支持并行动作批次。两端相差几个数量级，读这张表时，要把它当作设计空间的地图，而不是成熟度的阶梯。

### 1.1 十一个系统，三个数量级

研究语料覆盖四家模型厂商的旗舰 Harness（Claude Code、Codex CLI、Gemini CLI、Mistral Vibe），再加七个开源项目：OpenHands、Aider、Mini-SWE-Agent、Hermes、Pi、OpenCode 和 OpenClaw。其中 OpenClaw 本质上是多渠道个人助手网关，编码任务转交给其他 Agent，作为非编程的对照点；Databricks 的 Omnigent 是编排多个 Harness 的“元 Harness”，单独作为第二个对照。

![表 4](附件资源/400万行源码拆解11个编程Agent：Harness工程全景/img_3.png)

表 4｜十一个系统的语言、规模、工具数、沙箱与标志性能力；“规模”为定性的数量级，跨语言与计数口径不可直接比较。

表 4 最右一列是每个系统独有的能力：Aider 有 13 种随模型切换的编辑格式，Codex 有 Agent 自己维护的跨会话记忆，Gemini CLI 把模型路由当作运行时调度，Pi 则把几乎一切都做成扩展。作者在 4 月版里列过各系统自报的 SWE-bench 分数，这一版删掉了，理由是这些数字来自不同模型代际和配置，放在一张表里容易被误读为排名。

### 1.2 这项研究补了什么视角

已有文献大致分三类：基准综述只报分数，不碰架构；概念分类描述模式，不看实现；同期唯一的源码级分类研究只覆盖开源系统，没有纳入厂商自研 Harness。本文的切入点是同时纳入四家厂商系统，并把分析延伸到权限、编排、扩展接口和提示词内容。

另一个额外视角来自时间。原有八个系统在 4 月版之后没有被替换，而是重新锁定到 7 月的版本，因此论文带有一份对照的纵向样本：同一批 Harness，相隔一个季度做源码 diff。这让“行业在趋同”这类说法可以落到具体代码变化上检验，而不只是印象。

02

ANATOMY

## 结构解析：七个子系统怎样做取舍

### 2.1 循环：复杂度不预测成绩

所有系统都实现了 ReAct 式的“推理—行动”循环，差别在复杂度、并发和状态管理。图 2 把它们归为三种范式：九个系统采用迭代式“行动—观察”；Aider 是唯一以反思为主体的循环，编辑后跑语法检查、编译和 flake8，再把错误送回模型，默认最多反思 3 次；协调者—工作者则是叠加在迭代循环上的一层分派。

![图 2](附件资源/400万行源码拆解11个编程Agent：Harness工程全景/img_4.png)

图 2｜三种循环范式：(a) 迭代式，(b) 反思增强，(c) 协调者—工作者叠加层；一个系统可以组合多种原语。

同属迭代式，实现也可以差很远。Claude Code 把工具调用按“是否并发安全”分批，读类工具可以并行，写类工具默认串行；OpenHands 按工具声明的资源加锁，只有争用同一资源的调用才串行。论文的观察 1 由此给出：代码规模跨三个数量级，循环的复杂程度却不能预测基准成绩，生产系统的大部分代码花在安全、体验、扩展和客户端上。这一判断依赖各系统自报的分数，不能当作受控实验的结论。

### 2.2 工具与编辑：从一个 bash 到上百个工具

![图 3](附件资源/400万行源码拆解11个编程Agent：Harness工程全景/img_5.png)

图 3｜各系统内置工具或编辑格式的数量（2026 年 7 月）；OpenHands 与 Codex 为默认工具面，数量多少不代表能力强弱。

图 3 从 Mini-SWE-Agent 的 1 个 bash 工具，排到 OpenClaw 的 109 个以上。工具一多，提示词就会膨胀，于是“延迟加载”开始扩散：Claude Code 先只暴露工具名，用到时再检索完整定义，论文称这让初始提示缩小约 40%；Codex 独立实现了类似机制。作者据此建议，工具超过约 15 个再考虑延迟加载，少于这个数，额外的间接层不划算。

文件编辑被作者视为影响改码准确率的关键环节（观察 4）。前沿模型阵营收敛到“精确唯一子串替换”，Mistral Vibe 在一个季度内删掉了模糊匹配工具，改用 Claude Code 式的精确匹配；面向更广模型范围的系统则保留容错链，例如 OpenCode 九级匹配，相似度阈值 0.65。第三条路是 Gemini CLI 用一次 LLM 调用修复匹配失败。这些都是设计选择的描述，论文没有在统一任务上比较它们的准确率。

### 2.3 记忆与上下文：分歧点转向“谁来写记忆”

![图 4](附件资源/400万行源码拆解11个编程Agent：Harness工程全景/img_6.png)

图 4｜四种上下文管理策略，按复杂度排列；从左到右是实现复杂度递增，不是效果递增。

上下文压缩已经趋同：11 个系统中有 7 个在达到阈值时调用 LLM 做摘要。具体参数各不相同，Claude Code 在距窗口上限约 13K token 处触发，Gemini CLI 在 50% 时压缩并保留最近 30%。观察 5 指出，真正的差异转移到记忆的写入路径，出现了四种治理方式：Codex 由沙箱内的子 Agent 整理记忆；Gemini CLI 把提取结果放进收件箱，由用户审核；Hermes 允许模型直接写，但限制字数并在会话内冻结；OpenClaw 在每次回复前先让一个子 Agent 检索记忆。

这里有一个值得注意的共同点：没有任何系统把向量检索作为主要记忆底座，Hermes 用的是 SQLite 全文检索。它与第 3 章的“代码检索不用 RAG”是同一现象在记忆层的延伸，但样本只有 11 个系统，不宜外推到所有 Agent 产品。

### 2.4 安全与编排：两笔最贵的投入

![图 5](附件资源/400万行源码拆解11个编程Agent：Harness工程全景/img_7.png)

图 5｜Claude Code 的三层权限：静态 Hook 规则、LLM 权限分类器、用户确认对话；上层更快，下层更可靠。

安全是语料中分歧最大的维度。Claude Code 依次经过规则、分类器和人工确认三层；Codex 在 7 月快照里扩展为四层，包括 Starlark 编写的执行策略和跨三种操作系统的原生沙箱。4 月版曾认为“体量越大越会做 OS 沙箱”，扩充语料后这条相关被推翻：Hermes 与 OpenCode 体量相当，却没有任何 OS 级隔离，前者把预算花在提示注入扫描和技能供应链上，后者花在按语法解析的命令权限上（观察 6）。仍然成立的是成本一侧：原生沙箱一旦要做，就是数千行级别的投入。

![图 6](附件资源/400万行源码拆解11个编程Agent：Harness工程全景/img_8.png)

图 6｜六种多 Agent 编排模式及代表系统；红色节点负责派生，蓝色节点被派生，模式之间不存在高低之分。

多 Agent 方面，11 个系统中有 9 个支持，协调者—工作者结构在多个独立开发的代码库里分别出现（观察 7）。各家优化的目标不同：Claude Code 让子 Agent 共享提示缓存，省成本；Codex 维护带深度追踪的线程树，重隔离与规模；Mistral Vibe 在进程内顺序执行，求简单。作者也提醒，这种趋同只适用于把多 Agent 做进核心的系统，Pi 就刻意保持单 Agent，并且实际使用多集中在并行探索代码库阶段，而不是并行写代码。

03

FINDINGS

## 发现解析：缺席、趋同与平台化

### 3.1 两个“缺席”比“出现”更有信息量

作者检查了全部依赖清单，并在三种语言的源码中搜索十余种 Agent 框架的导入。结论是：约 400 万行代码里，没有一条 Agent 运行时路径导入 LangChain、LangGraph、AutoGen、CrewAI 等通用框架，Gemini CLI 甚至没用 Google 自家的 Genkit 和 ADK。所有循环都用宿主语言的异步原语手写。

![表 13](附件资源/400万行源码拆解11个编程Agent：Harness工程全景/img_9.png)

表 13｜各系统代替向量 RAG 的代码检索方式；OpenClaw 的嵌入检索只用于对话记忆，不用于源码。

第二个缺席是代码检索不用向量嵌入。表 13 显示，所有系统都依赖 ripgrep、glob、tree-sitter 和自动发现的 Markdown 上下文文件。作者给出的解释是：代码自带路径、语法树、类型等确定性结构，又随时在变，预先建好的嵌入几乎注定过期。这两个缺席经历了语料扩大三倍和三个月后的复查。但检查方法有边界：只查了依赖清单和静态导入，没有追踪动态加载和内部分支，作者自己说“会意外，但不会震惊”。

### 3.2 Skills 超过 MCP，ACP 多了一个角色

![表 10](附件资源/400万行源码拆解11个编程Agent：Harness工程全景/img_10.png)

表 10｜各系统对 Skills 的支持方式；“符合规范”指遵循 agentskills.io 的 SKILL.md 格式，不代表实现质量。

扩展标准在这个季度分出了先后。11 个系统中 9 个实现了 SKILL.md 技能包，8 个支持 MCP；4 月两者打平，打破平局的是 Pi，它支持技能、明确拒绝 MCP。若去掉非编程的 OpenClaw，MCP 是 10 个中的 7 个。技能层还出现三个成熟信号：9 个采用者中 8 个只预先加载元数据，正文按需读取；技能可以按触碰的文件路径或运行环境条件激活；分发出现了注册中心、信任分级和隔离区，Hermes 和 Gemini CLI 甚至开始由 Agent 自己编写技能。

协议层的变化更出乎设计初衷。ACP 原本连接编辑器和 Agent，目前 11 个系统中 6 个已采用，并多出“托管 Harness”的用法：OpenHands 可以把 Claude Code、Codex 或 Gemini CLI 当作可替换的后端来驱动。与此同时，9 个多 Agent 系统中有 8 个，内部子 Agent 仍用进程内原语通信，不走标准协议。作者的建议是对外提供 ACP 服务，对内保持进程内调用；A2A 目前只有 Gemini CLI 在押注，规模化需求尚未得到证明。

### 3.3 九十天的源码 diff：趋同变成了模仿

纵向对比给出四个动向。第一，趋同从“独立重新发现”变成可追溯的借鉴：Codex 原样采用了 Claude Code 的 Hook 事件命名，还提供导入 Claude Code 会话与设置的工具；OpenHands 直接读取 Claude Code 的插件清单格式。第二，模式在语料中快速扩散，延迟加载工具从 1 个系统增加到 3 个，只读规划模式从 2 个扩展到全部 4 个厂商系统。作者据此判断，一项差异化能力的“半衰期”目前以周计。

第三，行为规则从提示词迁到配置。Codex 的新一代模型提示删掉了“不要自动提交”和“不要过度设计”类条款，改由特性开关控制；Mistral Vibe 删除了“永不提交”的硬规则。第四，代码库本身在以平台速度增长：Codex 的 Rust 工作区从约 62.1 万行增至约 112 万行，crate 从 89 个增至 126 个；Mistral Vibe 从 3.56 万行增至 6.3 万行，增长 77%；同期 Aider 只有 18 次提交，进入社区维护。行数是近似计数，只用于说明数量级，不适合跨语言比较。

作者也坦承，4 月版的三条观察在这一版被实质修正。他们由此区分两类结论：工具数量、功能格子、版本号这类“清单型”结论几周就会过时；循环分类、子系统解剖和两个缺席这类“结构型”结论至今保持稳定。读这篇论文的具体数字时，最好带着这个区分。

### 3.4 从工具到平台

![表 15](附件资源/400万行源码拆解11个编程Agent：Harness工程全景/img_11.png)

表 15｜Harness 与框架的双向合流：Harness 变成可导入的 SDK，框架厂商则开始发布 Harness；列出的是已发布的具体制品，不代表市场份额。

论文的中心论点是：2026 年上半年，编程 Harness 完成了从工具到平台的转向。表 15 给出两个方向的证据。Claude Agent SDK、openai-codex SDK 让 Harness 可以作为库导入；反过来，LangChain 基于 LangGraph 推出的 Deep Agents，独立采用了 SKILL.md、AGENTS.md、子 Agent 和待办规划，与本文语料的惯例几乎一致。作者因此给“框架缺席”一个历史解释：Harness 没有采用框架，而是取代了框架，然后自己变成了可导入的框架。

平台化还表现在三类经济信号上：插件和技能有了市场与信任分级；厂商开始为对方的会话数据写导入工具，迁移成本成为竞争手段；Codex 的配置栈出现了企业设备管理层，可以强制限制用户能改什么。Omnigent 则从上方把这一切再包一层：通过统一 API 编排 11 个厂商的 Harness，其中 5 个是本文研究对象。它自己重新实现了沙箱和策略这些昂贵部分，再通过各家的 Hook 机制施加统一策略。作者的判断是，竞争单位已经从 Agent 循环转移到循环周围的生态接口；这是对现状的归纳，并没有预测哪种格局会胜出。

### 3.5 数字要与测试对象一起读

论文刻意不跑分，引用的成绩全部来自各系统自报或其他论文。Mini-SWE-Agent 在 SWE-bench Verified 上自报 74% 以上，Codex 自报 69.1%。两者使用的模型、评测轮次和部署配置都不同，前者无沙箱、后者有沙箱，作者明确表示不据此做正面比较，只把它当作“门槛很低”的定性说明。

更接近受控证据的是作者引用的 AHE 研究：从一个只有 bash 的种子 Harness 出发自动演化，在 SWE-bench Verified 上达到 71.9%。它的组件消融显示，工具贡献 +3.3 个百分点，中间件 +2.2 个百分点，长期记忆 +5.6 个百分点，单独改系统提示反而是 −2.3 个百分点，演化出的 Harness 还能迁移到四个模型家族。这组数字来自另一篇论文的单一基准，本文把它读作“结构性部件比提示词措辞更可迁移”的提示性证据，而非结论。

在此基础上，作者提出“脚手架—能力前沿”的直觉：固定任务和模型时，脚手架复杂度与成功率可能呈凹曲线，先陡升、再进入平台期，此后的投入主要换来安全、体验和扩展。论文明确说这是待检验的假设，并给出验证所需的条件：固定任务分布、固定模型、可量化的复杂度指标和目标成功率。Anthropic 多 Agent 研究系统“比单 Agent 基线高 90.2%、token 消耗约 15 倍”的数字同样被注明：对照的是简单聊天基线，不是经过优化的单 Agent 流水线。

04

TAKEAWAY

## 总结：先搭最小 Harness，再按失败模式加部件

这篇论文把十一个编程 Agent 放到同一张解剖图上：循环、工具、记忆、安全、编排、扩展，再加上一个季度的源码演化和一个元 Harness 对照。它真正研究的不是“哪个 Agent 更强”，而是模型之外那一层运行时怎样被设计、怎样趋同，又怎样长成平台。这让不同产品的差异可以落到具体的工程选择上讨论。

对正在搭建 Agent 的读者，一个可借鉴的出发点是：从一个 while 循环、一个 bash 工具和分层的 Markdown 上下文文件起步，只在观察到具体失败时再增加工具；工具超过约 15 个再做延迟加载；在留出的任务集上证明有效之前，不为代码建向量检索；技能优先于 MCP，对外提供 ACP 服务，子 Agent 留在进程内；安全规则写成数据或策略文件，即使提供“放行一切”模式，也保留一条不可绕过的底线。把 Harness 当作可以拆解、可以对照源码检验的工程对象，就能更清楚地判断每一行代码在为什么付费。
