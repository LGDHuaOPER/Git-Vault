# 项目管理完整学习手册：从基础认知到组织级实践（思维导图版）

#

# 第一部分 基础认知

## 1.1 项目与运营的区别

```
所有工作
├── 日常运营
│   ├── 目的：长期维持
│   ├── 特征：持续重复
│   └── 举例：生产线运行、系统维护
│
└── 任务（项目）
    ├── 目的：尽快结束
    ├── 特征：临时、独特、目标明确
    └── 举例：新产品开发、工厂建设
```

**判断原则**：接到任务后首先判断——是为了把这件事做长期，还是为了尽快结束。出发点不同，后续管理方式完全不同。

## 1.2 任务的进一步分类

```
任务
├── 常规任务
│   ├── 经验可完全复用
│   ├── 按SOP执行即可
│   └── 核心策略：标准化
│
└── 创新任务
    ├── 经验需批判性看待
    ├── 需要探索和突破
    ├── 核心策略：不破不立
    │
    └── 实现方式
        ├── 靠个人实现 → 专家思维
        └── 靠他人实现 → 管理思维
            ├── 向下管理：依靠不如自己的人（职能管理/家长制）
            └── 向上管理：依靠比自己更厉害的人（项目管理）
```

**关键洞察**：项目管理本质上是向上管理——依靠比我们更厉害的人（领导、客户、专家），把他们整合在一起，共同实现目标。

## 1.3 项目的核心特征

```
项目
├── 临时性：有明确的开始和结束
├── 独特性：每个项目都不同
├── 一次性：只发生一次
├── 不确定性：需要大量协调
└── 目标性：目标明确，以合同/协议确认
```

## 1.4 项目管理的“五规”

```
通过规定的人员
+ 在规定的预算内
+ 在规定的时间内
+ 实现规定的目标
+ 满足规定的质量
= 项目管理的五规
```

## 1.5 五大过程组

```
启动 → 规划 → 执行 → 监控 → 收尾
│        │        │        │        │
批准项目  制定方案  按计划做  监督纠偏  正式结束
```

**日常工作理解**：

- 启动：想清楚为什么做、做什么、谁参与
- 规划：制定行动方案
- 执行：按计划推进
- 监控：随时检查偏差，及时调整
- 收尾：验收确认，总结经验

## 1.6 项目管理铁三角

```
        ┌─────────┐
        │  范围   │
        └────┬────┘
             │
    ┌────────┼────────┐
    │        │        │
    ▼        ▼        ▼
┌───────┐┌───────┐┌───────┐
│  时间  ││  成本  ││  质量  │
└───────┘└───────┘└───────┘
```

**核心规则**：任何一个发生变化，其他都会受影响。范围扩大→需要更多时间或成本；时间压缩→需要缩小范围或增加成本。

## 1.7 项目启动阶段三要素

```
启动阶段：Why + What + Who
├── Why：为什么要立项？
│   └── 识别真实需求：want（想要）→ need（需要）
├── What：目标是什么？
│   └── 原则：SMART
│       ├── S：具体的
│       ├── M：可衡量的
│       ├── A：可实现的
│       ├── R：相关的
│       └── T：有时限的
└── Who：谁参与？
    └── 干系人：能影响项目或被项目影响的人
```

**干系人管理四象限**：

```
                    权力高
                     ↑
      第二象限      │      第一象限
   （保持满意）      │    （重点管理）
   定期汇报          │    密切沟通
                     │
  ──────────────────┼──────────────────→ 利益高
                     │
      第三象限      │      第四象限
   （监督）         │    （随时告知）
   最小投入          │    保持透明
```

## 1.8 启动阶段关键文档

```
启动阶段输出文档
├── 可行性分析报告（商业计划书）：是否盈利？如何盈利？
├── 项目任务书：开发什么？功能指标？目标？风险？
├── 市场需求说明书：客户为什么用？为什么选我们？
├── 需求映射表：将客户语言转化为产品需求语言
├── 多方案选择：选择快速满足客户需求的方案
├── 专利产权分析：专利检索，新专利可申请性
├── 产品风险分析：识别产品相关风险
├── 产品包需求：完整的产品需求定义
└── 项目计划：初步时间安排和里程碑
```

## 1.9 规划阶段的核心子计划

```
项目管理计划
├── 范围管理计划：目标是什么？能否实现？
├── 需求管理计划：各相关方需求是什么？
├── 进度管理计划：时间安排
├── 成本管理计划：预算及监控
├── 质量管理计划：质量标准与控制
├── 资源管理计划：人员与物资配置
├── 沟通管理计划：信息传递机制
├── 风险管理计划：风险识别与应对
├── 采购管理计划：外部资源获取
├── 干系人参与计划：干系人管理策略
├── 变更管理计划：变更审批流程
└── 配置管理计划：版本与配置控制
```

## 1.10 项目监控要点

```
监控什么？
├── 项目进度：实际与计划的偏差
├── 项目成本：当前成本与计划成本
├── 范围变更：是否有范围蔓延
└── 风险与质量：风险是否可控，质量是否达标
```

**监控的价值**：

- 避免合理的计划在实施中落空
- 避免执迷不悟地按不合理计划行事
- 将监控数据保存，为持续改进提供依据

## 1.11 项目收尾阶段

```
收尾任务
├── 产品验收：确认可交付成果符合标准
├── 文档归档：整理所有项目文档
├── 经验教训总结：记录成功经验和失败教训
├── 资源释放：释放人员、设备等资源
├── 最终报告：向相关方提交项目最终报告
└── 庆功与复盘：团队认可 + 组织过程资产更新
```

# 第二部分 计划与知识管理

## 2.1 PDC3A计划框架

```
从PM介入项目到客户启动会议前的准备工作

Prepare（准备）
├── 项目需求收集
├── 背景文档/合同/SOW
└── 识别关键干系人
        ↓
Discovery（发现）
├── 用户需求确认研讨会
├── 调查问卷、检查清单
└── 区分want和need
        ↓
Check（检查）
├── 目标愿景
├── 计划草案、资源列表
├── 问题清单、差距分析
└── 内部团队达成共识
        ↓
Clarify（澄清）
├── 阶段划分
├── 可交付成果定义
└── 建立里程碑节点
        ↓
Confirm（确认）
├── 需求/产品功能确认
└── 获得正式认可
        ↓
Action（行动）
├── 内部启动会：计划初稿、PBI/SBI
└── 客户启动会：基线计划、验收标准、资源列表
```

**核心认知**：计划（verb）比计划（noun）更重要——花时间讨论计划的过程，比最终输出的文档更有价值。

> "Plans are worthless but Planning is everything." —— Dwight David Eisenhower

## 2.2 知识管理

### 知识管理的三大困境

```
三大典型问题
├── 人走知识丢
│   ├── 文档存在个人电脑而非公司系统
│   ├── 版本未经审批
│   └── 仅少数文档上传至知识库
│
├── 数字坟场
│   ├── 知识入库即沉睡
│   ├── 检索困难，匹配不到真实需求
│   └── 知识过期仍被调用
│
└── 流程与执行两张皮
    ├── 标准流程与实际操作脱节
    ├── 新人依赖“师傅带徒弟”
    └── 组织对人的依赖大于对系统的依赖
```

### DIKW模型

```
DIKW金字塔
智慧（Wisdom）    ← 预测与判断能力
    ↑
知识（Knowledge） ← 可执行、可复用的认知单元
    ↑
信息（Information）← 结构化、有关联的数据
    ↑
数据（Data）      ← 原始事实与数字
```

### SECI模型（知识转化螺旋）

        隐性知识        显性知识

            │              │
    ┌───────┴───────┐ ┌───┴───────┐
    │  社会化（S）   │ │ 外部化（E） │
    │  隐性→隐性    │→│ 隐性→显性  │
    │  师徒传承     │ │ 撰写报告   │
    └───────┬───────┘ └───┬───────┘
            │              │
            ▼              ▼
    ┌───────┴───────┐ ┌───┴───────┐
    │  内部化（I）   │←│  组合（C）  │
    │  显性→隐性    │ │  显性→显性 │

    └───────┬───────┘ └───┬───────┘
            │              │
        显性知识        隐性知识
            ▼              ▼
```

### 乔哈里视窗

```
                自己知道      自己不知道
别人知道      开放区          盲区
别人不知道    隐藏区          未知区
```

| 区域 | 管理策略 |
| --- | --- |
| 开放区 | 加强共享机制 |

知识管理落地三机制

# 第三部分 PMO与项目集管理

## 3.1 PMO三层能力模型

```
PMO能力三层模型
│
├── 第三层：扩展能力（进阶加分项）
│   ├── 组织资源管理
│   ├── 整体风险控制
│   ├── 经营分析
│   ├── 产品管理
│   └── 技术运营
│
├── 第二层：必备能力（落地支撑力）
│   ├── 流程建设
│   ├── 人才培养
│   ├── 工具搭建
│   ├── 知识沉淀
│   └── 适应变化
│
└── 第一层：基本能力（保底基本功）
    ├── 进度跟踪
    ├── 项目组合管理
    ├── 偏差检查
    └── 支持决策
```

**核心逻辑**：先靠基本能力做项目、攒经验 → 再用必备能力把数据和资源转化为价值 → 最终靠扩展能力持续创新、建立体系。

## 3.2 天赋能力 vs 可培训能力

| 类型 | 特征 | 包含能力 |
| --- | --- | --- |
| 天赋能力 | 天生具备，难以培训 | 大局观、领导力、内驱力、忠诚度、共情能力 |
| 可培训能力 | 通过学习可以掌握 | 项目管理技能、行业知识、沟通技巧、文档写作 |

**核心观点**：天赋能力决定能走多高，可培训能力决定能否胜任。招聘时关注天赋，培养时关注技能。

## 3.3 PMO四重身份进化

```
PMO进化路径
│
第一重：执行监督者
├── 职责：盯进度、查文档
└── 核心价值：确保内容及过程合规
        ↓
第二重：流程优化者
├── 职责：改进项目管理体系
└── 核心价值：提升组织效率
        ↓
第三重：数据分析师
├── 职责：输出项目洞察报告
└── 核心价值：以数据支持决策
        ↓
第四重：战略资产运营商
├── 职责：管理知识资本，驱动创新
└── 核心价值：从管理过程到创造直接收益
```

## 3.4 项目经理 → 项目集经理：能力跃迁

```
项目经理                          项目集经理
├── 聚焦单一领域              ├── 跨多个业务领域（研产供销服全链条）
├── 精通本领域业务            ├── 理解公司整体经营价值链
├── 与职能管理者沟通          ├── 与高管/战略决策层沟通
├── 保交付、控成本、守质量    ├── 战略对齐 + 整体价值最大化
└── 按既定流程执行            └── 建流程带人，推动变革
```

### 项目集经理四大核心能力

```
项目集经理四大核心能力
├── 1. 战略链接与业务拆解能力
│   └── 将战略目标拆解为可执行的项目集
│
├── 2. 跨业务价值链理解能力
│   └── 从公司经营全价值链视角看问题
│
├── 3. 复杂相关方领导与沟通能力
│   ├── 向上：高管（战略价值）
│   ├── 横向：各事业部（跨部门协调）
│   └── 向下：各子项目经理（双矩阵挑战）
│
└── 4. 变革管理能力
    ├── 认知层面：让大家认同新打法
    ├── 组织层面：汇报线从职能线变为项目线
    └── 流程层面：建立项目集流程指导书
```

### 项目集的核心价值：增量收益（1+1>2）

| 协同领域 | 单项目做法 | 项目集协同做法 | 增量效果 |
| --- | --- | --- | --- |
| 沟通机制 | 各子项目各自开会 | 统一沟通体系 | 减少重复会议 |
| 资源配置 | 各项目独立申请 | 整体评估共享 | 降低总成本 |
| 风险管理 | 各项目独立应对 | 统一识别跨项目风险 | 避免重复踩坑 |
| 知识管理 | 各项目各自积累 | 跨项目复用 | 加速学习曲线 |

# 第四部分 组织级项目管理

## 4.1 项目管理三层次模型

```
高层：项目组合管理
├── 核心逻辑：选择大于努力
├── 核心问题：哪些项目该做？
├── 核心动作：优先级排序 → 末位淘汰
└── 考核指标：投资回报率
        ↑
中层：项目集群管理
├── 核心逻辑：资源集约化
├── 核心问题：如何在项目间共享资源？
├── 核心动作：提炼共性 → 标准化 → 复用
└── 考核指标：成本降低
        ↑
基层：单项目管理
├── 核心逻辑：基于目标的执行
├── 核心问题：如何用更少资源实现目标？
├── 核心动作：找关键路径 → 砍掉无效工作
└── 考核指标：进度、质量
```

**组织设计原则**：每一层关心自己该关心的事，不要越级思考。基层想得少，执行力才好；中层想共性，但没选择权；高层看长远，做投资决策。

## 4.2 项目 vs 运营的本质区别

```
项目 = 尽快结束（临时性任务）
运营 = 长期维持（持续性工作）

判断标准：接到任务后，问自己——是为了长期做下去，还是为了尽快完成？
```

## 4.3 三种交付模式

```
三种交付模式
├── 线性交付
│   ├── 逻辑：一次做对，一次做好
│   ├── 适用：目标稳定、环境可预测
│   └── 典型：工程建设
│
├── 敏捷交付
│   ├── 逻辑：客户需求变化，快速响应
│   ├── 适用：目标频繁变化
│   └── 典型：软件开发
│
└── 自适应交付
    ├── 逻辑：预判变化，主动引导
    ├── 适用：能预判未来趋势
    └── 典型：头部企业引领市场
```

**混合模式**（当前主流）：同一项目中不同组成部分采用不同交付方式：

- 结构/造型：线性交付（不能轻易改）
- 软件/电气：敏捷交付（随便迭代）
- 关键零部件：固定（供应商决定）

## 4.4 组织级项目管理的四层架构

```
四层架构
│
第1层：顶层设计
├── 虚实结合的组织结构（科层制 + 项目制）
├── 稳定性靠科层，灵活性靠项目
└── 解决“架构”问题
        ↓
第2层：组织治理
├── 决策机制、授权体系
├── 生产关系界定（谁决策、谁执行、谁协调）
└── 解决“责权”问题
        ↓
第3层：项目管理方法论
├── 不同类型项目的方法论
├── 流程/标准/工具
└── 目标是“让新手也能把项目做好”
        ↓
第4层：项目执行
├── 与具体业务场景结合
├── 基于方法论开展实际工作
└── 执行层按体系执行
```

## 4.5 实体组织 vs 虚拟组织

| 对比维度 | 科层制实体组织 | 项目虚拟组织 |
| --- | --- | --- |
| 作用 | 提供稳定性和凝聚力 | 提供灵活性和创造价值 |
| 管理方式 | 家长制、职能管理 | 民主集中制 |
| 用人逻辑 | 螺丝钉（按岗位培养） | 用人所长（发挥特长） |
| 激励逻辑 | 按岗位职责 | 按贡献大小 |

**虚实结合，如同太极**：科层制是底盘，项目制是方向盘，两者缺一不可。

## 4.6 PMO的定位

```
PMO（项目管理办公室）
├── 本质：支撑项目虚拟组织体系运转的实体部门
├── 主要工作：出政策/制度草案，说服决策层发布
├── 关键能力：制定制度、推行民主集中制
└── 国家标准：正在制定《项目管理办公室建设和运营》国家标准
```

## 4.7 民主集中制

```
民主集中制三步骤
├── 民主：把不同组织的人凑在一起，充分讨论
├── 集中：最终共同决定
└── 效果：项目的事是大家共同决定的，谁不落实就说不过去
```

**核心认知**：项目管理（尤其是项目集/组合层面）本质上是在用民主集中制做决策。

## 4.8 项目管理 vs 职能管理：用人逻辑

| 对比维度 | 职能管理 | 项目管理 |
| --- | --- | --- |
| 用人逻辑 | 螺丝钉（按岗位培养） | 用人所长（发挥特长） |
| 约束方式 | 岗位限定 | 不拘泥于岗位职责 |
| 优势 | 培养专业性 | 激活个体、激发创新 |
| 适合人群 | 听话、执行力强 | 有主见、能突破常规 |

**关键洞察**：项目中用的人，往往是科层制实体组织中经常被压制的那部分人——他们有创新能力，但在传统组织中可能被视为“危险分子”。在项目这种进攻型组织中，他们反而能发挥巨大作用。

# 第五部分 敏捷实践

## 5.1 VUCA——敏捷的适用场景

```
VUCA环境特征
├── V（易变性）：环境、行业、技术频繁变化
├── U（不确定性）：未来走势难以预测
├── C（复杂性）：项目涉及的模块和元素越来越多
└── A（模糊性）：缺乏相应经验，进入陌生领域
```

## 5.2 Stacey矩阵

```
                    需求不确定性
                    高
                     ↑
   ┌─────────────────┼─────────────────┐
   │    复杂项目      │    混乱项目      │
   │  （适应性方法）   │  （无法可解）    │
   └─────────────────┼─────────────────┘
                     │
   ┌─────────────────┼─────────────────┐
   │    简单项目      │    超复杂项目    │
   │  （预测性方法）   │  （适应性方法）  │
   └─────────────────┼─────────────────┘
                     │
                     └──────────────→ 技术不确定性
                    高
```

| 项目类型 | 推荐方法 |
| --- | --- |
| 简单项目（技术+需求都确定） | 预测型方法 |
| 复杂/超复杂项目 | 适应性方法（敏捷） |
| 混乱项目 | 任何方法都无法解决 |

## 5.3 敏捷宣言

```
敏捷价值观（左侧 > 右侧）
├── 个体和互动 > 流程和工具
├── 工作的软件 > 详尽的文档
├── 客户合作 > 合同谈判
└── 响应变化 > 遵循计划
```

**日常工作理解**：

- 与其死守流程，不如多和人沟通
- 与其写冗长文档，不如先拿出可用的东西
- 与其签死合同，不如和客户保持合作
- 与其坚持原计划，不如灵活调整

## 5.4 敏捷12原则（工作实用版）

```
敏捷12原则
├── 产品相关
│   ├── 及早且持续交付有价值的成果
│   ├── 欢迎需求变更
│   ├── 频繁交付，周期越短越好
│   └── 简单——做必要的，不做多余的
│
├── 团队相关
│   ├── 客户代表与开发人员每日互动
│   ├── 激励团队，相信他们能完成任务
│   ├── 面对面沟通最有效
│   ├── 可持续发展，保持稳定节奏
│   ├── 自组织团队自己认领任务
│   └── 定期反省如何提高效率
│
└── 实施相关
    ├── 可正常运作的成果是衡量进度的主要指标
    └── 持续注重技术专精和良好设计
```

## 5.5 Scrum框架

### 三大角色

```
Scrum三大角色
├── 产品负责人（PO）
│   ├── 管需求（产品待办列表）
│   ├── 代表客户声音
│   └── 价值最大化
│
├── 敏捷教练（SM）
│   ├── 管流程
│   ├── 服务型领导
│   └── 消除障碍、促进团队
│
└── 开发团队（Team）
    ├── 创造价值
    ├── 自组织、自管理
    └── T型人才（通用型专家）
```

### 四大会议（PDCA闭环）

```
四大会议
├── 迭代规划会议（Plan）
│   ├── 迭代第1天召开
│   └── 选择本次迭代要完成的用户故事
│
├── 每日站会（Do）
│   ├── 每天早晨，不超过15分钟
│   └── 三件事：昨天干了什么、今天要干什么、有什么阻碍
│
├── 迭代评审会议（Check）
│   ├── 迭代结束时召开
│   └── 演示增量成果，获取PO反馈
│
└── 迭代回顾会议（Act）
    ├── 迭代结束时召开（评审会之后）
    └── 经验教训总结：做得好/做得不好/下次怎么改
```

### 回顾会议五步法

```
回顾会议五步法
1. 准备/开场：活跃气氛，破冰
2. 收集数据：收集客观数据
3. 产生洞见：分析数据，发现根因
4. 决策：挑出改进项，下个迭代尝试
5. 结束会议：感谢每位成员的贡献
```

## 5.6 敏捷需求管理

### 用户故事三段论

```
用户故事格式：
作为 [角色]，我想要 [功能]，以便 [价值]

示例：
作为 老师，我想要 笔记本电脑有手写功能，以便 用更丰富的形式传递知识
```

### 3C原则

```
3C原则
├── 卡片（Card）：简短的描述
├── 对话（Conversation）：围绕卡片讨论
└── 确认（Confirmation）：验收标准
```

### 需求颗粒度层级

```
需求颗粒度（从粗到细）
史诗 → 特性 → 用户故事 → 任务
```

### 验收标准 vs 完成定义

```
验收标准（AC）
├── 针对：单个用户故事/功能
├── 问题：这个功能要达到什么要求才算满足？
└── 谁定：客户/PO

完成定义（DoD）
├── 针对：整个团队/项目
├── 问题：什么叫“完成了”？内部达到什么标准？
└── 谁定：团队内部
```

### MVP vs MMF

```
MVP（最小可行产品）
├── 目的：获得客户反馈
└── 交付时机：每个迭代

MMF（最小可售特性）
├── 目的：上市销售
└── 交付时机：每个发布版本

关系：多个MVP迭代 → 组合成MMF → 上市
```

## 5.7 敏捷规划五层结构

```
敏捷规划五层
第1层：愿景（Vision）
└── 一句话描述产品目标
        ↓
第2层：产品路线图（Roadmap）
└── 版本发布时间线
        ↓
第3层：发布计划（Release Plan）
└── 本次发布包含几个迭代
        ↓
第4层：迭代计划（Sprint Plan）
└── 本次迭代完成哪些用户故事
        ↓
第5层：每日计划（Daily Plan）
└── 每日站会确定当天任务
```

## 5.8 需求优先级排序方法

```
优先级排序方法
├── MoSCoW法则
│   ├── M：必须有（最高）
│   ├── S：应该有
│   ├── C：可以有
│   └── W：这次没有
│
├── 100点投票法
│   └── 每人分得方案数×20%的票数进行投票
│
└── Kano模型
    ├── 基本型需求（最高优先级）
    ├── 期望型需求
    ├── 兴奋型需求
    └── 无差异性需求（最低优先级）
```

## 5.9 时间盒概念

```
时间盒（固定容量，不能随意扩大）
├── 每日站会：15分钟
├── 迭代规划会议：4小时（原则上限）
├── 迭代周期：1~4周
└── 回顾会议：必须开

核心规则：容量固定，超了就拆，不加班
```

## 5.10 敏捷核心实践

```
核心实践
├── 渗透式沟通
│   └── 集中办公，问题刚提出就可能被解决
│
├── 任务板/看板
│   ├── 任务板：看迭代任务状态（To Do/In Progress/Done）
│   └── 看板：看整个工作流程，限制WIP数量
│
├── 燃尽图/燃起图
│   ├── 燃尽图：剩余工作量下降（范围固定）
│   └── 燃起图：已完成工作量上升（范围变化）
│
└── 累计流量图
    └── 对应看板，展示队列、WIP、周期时间、交付周期
```

# 第六部分 PMBOK第七版标准框架

## 6.1 十二大原则

```
项目管理十二大原则
├── 1. 管家式管理：负责任地使用资源
├── 2. 营造协作团队环境：把不同的人拧成一股绳
├── 3. 有效干系人参与：让该支持的人支持你
├── 4. 聚焦价值：项目最终看创造了什么价值
├── 5. 系统思维：不能只看局部
├── 6. 展现领导力：让人自愿追随
├── 7. 裁剪：活学活用，不死板
├── 8. 将质量融入过程：质量不是最后查出来的
├── 9. 驾驭复杂性：面对越来越复杂的项目
├── 10. 优化风险应对：管理好风险
├── 11. 拥抱适应性和韧性：能应对变化，能快速恢复
└── 12. 驱动变革：推动改变
```

## 6.2 八大绩效域

```
八大绩效域
├── 干系人绩效域：谁会影响/被影响？
├── 团队绩效域：团队协作得好吗？
├── 规划绩效域：计划有条理吗？
├── 项目工作绩效域：执行推进得好吗？
├── 交付绩效域：成果有价值吗？
├── 测量绩效域：项目状态清楚吗？
├── 不确定性绩效域：风险可控吗？
└── 开发方法与生命周期绩效域：用对方法了吗？
```

## 6.3 模型速查

```
常用模型
├── 情境领导力模型
│   ├── 能干且愿意干 → 授权型
│   ├── 能干但不愿意干 → 参与型
│   ├── 不能干但想干 → 教练型
│   └── 不能干也不想干 → 告知型
│
├── 沟通模型：发送者→编码→媒介→解码→接收者→反馈
│
├── 激励模型
│   ├── 双因素理论：保健因素不能激励，激励因素才能激励
│   ├── 三种内驱力：自主、专精、目的
│   └── 麦克米兰三需求：成就、权力、归属
│
├── 变革模型
│   ├── ADKAR：认知→渴望→知识→能力→巩固
│   └── 科特8步：紧迫感→联盟→愿景→沟通→清除障碍→短期成果→深入变革→巩固文化
│
├── Stacey矩阵：判断用预测型还是敏捷
│
├── 团队发展模型：形成→震荡→规范→成熟→解散
│
└── 冲突模型
    ├── 合作/解决问题（双赢）
    ├── 妥协（双方让步）
    ├── 缓和/包容（单方让步）
    ├── 强迫（输赢）
    └── 撤回/回避（双输）
```

## 6.4 方法速查

```
常用方法
├── 估算方法
│   ├── 类比估算（参照类似项目）
│   ├── 参数估算（用参数模型）
│   ├── 三点估算（乐观+悲观+最可能）
│   ├── 自下而上估算（WBS拆细了算）
│   └── 亲和估算（T恤尺码：S/M/L/XL）
│
├── 数据分析方法
│   ├── 备选方案分析
│   ├── 标杆对照
│   ├── 根本原因分析（鱼骨图、5Why）
│   ├── 挣值管理（EVM）
│   └── 价值流图（识别增值/非增值活动）
│
└── 常用会议
    ├── 开工会：项目开始时对齐目标
    ├── 每日站会：15分钟同步进度
    ├── 迭代规划会：决定本迭代做什么
    ├── 评审会：演示成果，获取反馈
    └── 回顾会：总结经验教训
```

## 6.5 工件速查

```
常用工件
├── 战略类：商业论证、项目章程、愿景声明、路线图
│
├── 日志与登记册：假设日志、变更日志、问题日志、风险登记册、干系人登记册、待办事项列表
│
├── 计划类：迭代计划、发布计划、项目管理计划
│
├── 分解结构：WBS（工作）、OBS（组织）、RBS（风险）
│
├── 基准：范围基准、进度基准、成本基准
│
└── 可视化工具：燃尽图、燃起图、鱼骨图、仪表盘、累计流量图
```

## 6.6 裁剪

```
裁剪四步
1. 选择开发方法（预测/混合/敏捷）
2. 对组织进行裁剪（角色、职责、决策机制）
3. 对项目进行裁剪（过程、工具、工件）
4. 持续改进

核心原则：项目管理知识体系是框架，不是每样都要用。用不上的就裁掉。
```

## 6.7 XP（极限编程）补充

```
XP核心实践（13个）
├── 整个团队：所有人都推动价值
├── 规划游戏：用轻松方式做规划
├── 小版本发布：尽早交付
├── 客户测试：客户写用户故事+验收
├── 集体代码所有权：团队对代码共同负责
├── 编码标准：统一规范
├── 可持续步调：不压榨精力
├── 系统隐喻：用通俗比喻解释技术术语
├── 持续集成：频繁集成，快速发现Bug
├── 测试驱动开发（TDD）：先写测试→写代码→通过→重构
├── 简单设计：只做当前需要的
├── 结对编程：两人一机，轮流写代码+监督
└── YAGNI原则：“你不会需要它”——只做必要的
```

**刺探（Spike）** ：在零次迭代中做研究和实验，不产生价值，只为后续开发做准备。

## 6.8 Lean（精益）补充

```
精益七大浪费
├── 额外特性：客户根本没想要的功能
├── 未完成的工作：干到90%没交付
├── 工作切换：切换任务本身不产生价值
├── 移动：不必要的移动
├── 等待时间：等待不产生价值
├── 缺陷：修复缺陷是浪费
└── 同步学习：踩过的坑又踩一遍

核心工具：价值流图——识别增值活动和非增值活动
```

# 第七部分 应用指南

## 7.1 不同场景下的知识使用

```
场景一：接到新项目
→ 使用：启动阶段框架（Why+What+Who）、SMART目标、干系人矩阵

场景二：制定项目计划
→ 使用：WBS分解、五大过程组规划阶段、PDC3A框架

场景三：项目执行中遇到变更
→ 使用：变更管理、铁三角（评估范围/时间/成本影响）

场景四：项目延期或超支
→ 使用：挣值管理（EVM）、偏差分析、根本原因分析

场景五：需要团队高效协作
→ 使用：敏捷四大会议、自组织团队、仆人式领导

场景六：组织要推广项目管理
→ 使用：PMO三层能力、裁剪方法、民主集中制

场景七：面对不确定的项目
→ 使用：Stacey矩阵判断方法、敏捷宣言、Scrum框架

场景八：建立知识管理体系
→ 使用：DIKW模型、SECI模型、乔哈里视窗、知识熔断机制

场景九：从单项目管理者成长为多项目管理者
→ 使用：项目集经理四大能力、增量收益思维、争取资源三层策略
