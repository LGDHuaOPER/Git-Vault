# AI 评测开源框架全景

> 导读： 大模型能力突飞猛进，但" 模型强 ≠ 产品好 "。怎么知道一个模型、一套 RAG/Agent 应用到底能不能用？答案是 评测 。本文分四个模块，帮你建立完整的 AI 评测认知：①综述——为什么评、评测范式怎么演进；②Benchmark 盘点——模型能力怎么量化；③应用级 + Agent/RAG 评测——模型之外的硬仗；④开源框架横评——6 款高星框架逐一拆解，附安装、使用与选型。数据截至 2026-07-28。

## 一、综述：为什么评，以及评什么

过去两年，几乎每个团队都踩过同一个坑：**榜单分数很高的模型，接进业务后表现翻车**。原因在于，榜单（Benchmark）测的是"模型在固定试卷上的能力"，而真实业务是开放、多步、带工具、有用户的长链路。所以 AI 评测的本质，是把"模糊的好用"变成"可度量、可对比、可追踪"的信号。

### 1.1 评测范式的演进

评测方法本身，也经历了一轮快速进化：

| 阶段 | 代表方法 | 特点与局限 |
| --- | --- | --- |
| ** 人工评测 ** | 专家打分、众包标注 | 质量高但慢、贵、难规模化 |
| ** 自动指标 ** | BLEU / ROUGE / 准确率 | 快但只匹配表面，难评语义 |
| ** 基准 Benchmark ** | MMLU / GSM8K / HumanEval | 可复现排名，但易被刷榜/污染 |
| ** LLM-as-Judge ** | 用强模型当裁判 | 便宜可规模化，但裁判也有偏见 |
| ** 在线评测 ** | A/B、生产埋点、监控 | 最贴近真实，但需工程基建 |

### 1.2 评测的四大分类

按"评什么、为谁评"，AI 评测可划为四类，本文后续模块正好对应：

> ① 模型能力（Benchmark） ——考模型本身：通用知识、推理、代码、多模态、安全对齐。 ② 应用生产级（Online Eval） ——考产品：端到端质量、在线 A/B、LLM-as-Judge、安全红队。 ③ Agent 与 RAG 评测 ——考多步协作：RAG 忠实度、Agent 工具调用、Web/代码任务。 ④ 评测工程（Framework） ——考评测工具链本身：本文模块四要横评的 6 个开源框架。

一句话区分：**①考模型、②考产品、③考多步骤协作、④考评测的工具**。下面先盘②以外的"评什么"，模块四再讲"用什么评"。

## 二、Benchmark 盘点：模型能力怎么量化

模型能力评测是最成熟的领域，围绕能力维度拆成五类榜单。看榜时记住：分数高不代表什么都强，要看它考的是哪一类能力。

| 能力维度 | 代表 Benchmark | 评的是什么 |
| --- | --- | --- |
| ** 通用知识 ** | MMLU、C-Eval、CMMLU | 多学科选择题，覆盖文理医法 |
| ** 数学推理 ** | GSM8K、MATH、GPQA | 链式推理、研究生级科学问答 |
| ** 代码 ** | HumanEval、MBPP、SWE-bench | 函数生成 → 真实仓库级修复 |
| ** 多模态 ** | MMMU、MMBench、DocVQA | 图文理解、图表、文档问答 |
| ** 安全对齐 ** | TruthfulQA、HarmBench | 真实性、拒答有害请求能力 |

> 读榜的三个陷阱： ① 数据污染 ——训练集可能"见过"考题，分数虚高；② 刷榜 ——针对公开榜过拟合，换榜即崩；③ 语种/文化偏差 ——英文榜高分 ≠ 中文场景好用。结论：榜单只能做初筛，真实选型要靠模块三的应用级评测。

## 三、应用级 + Agent/RAG 评测：模型之外的硬仗

当模型被接进 RAG、Agent、生产系统，评测对象从"模型"变成"整套链路"。这是最贴近工程、也最容易被忽视的部分。

### 3.1 RAG 评测：检索质量决定上限

RAG 的回答质量，取决于"有没有检对、有没有答准"。业界事实标准 **RAGAS** 给出四个核心指标：

| 指标 | 含义 | 差了会怎样 |
| --- | --- | --- |
| ** Faithfulness 忠实度 ** | 答案是否忠于上下文 | 出现幻觉、编造 |
| ** Answer Relevancy 答案相关性 ** | 是否回答了问题 | 答非所问 |
| ** Context Relevancy 上下文相关性 ** | 检索内容是否相关 | 检回垃圾、噪声大 |
| ** Context Recall 上下文召回 ** | 该检的是否都检到了 | 漏检关键信息 |

### 3.2 如何做 Agent 评测（方法论）

Agent 评的是"规划—调用—反思"的闭环能力。它比 RAG 评测更难，有三个本质差异：**①非确定性**——同一输入两次跑出的轨迹可能完全不同；**②长链路**——多步工具调用中任一步出错都会雪崩；**③目标模糊**——"任务完成"难以用单一准确率衡量。所以 Agent 评测不能只看最终结果，更要看**过程**。

#### 3.2.1 Agent 评测的 6 个维度

| 维度 | 评什么 | 常用算法 |
| --- | --- | --- |
| ** 任务成功率 ** | 最终是否达成目标 | 端到端 0/1 或 LLM 判定 |
| ** 工具调用准确率 ** | 调对工具、参数正确 | 与 gold action 比对 / 执行校验 |
| ** 规划合理性 ** | 步骤顺序是否最优 | LLM-as-Judge 评轨迹 |
| ** 反思与纠错 ** | 出错后能否自我修正 | 错误步骤是否被纠正 |
| ** 轨迹效率 ** | 步数 / Token / 耗时 | 步数、成本、延迟统计 |
| ** 安全合规 ** | 有无越狱/泄露/违规 | 红队扫描 + 规则拦截 |

#### 3.2.2 可落地的 5 步评测流程

- 定义任务集 ——准备 50~200 条真实业务任务（带环境/工具/Mock），而非玩具题；最好含"易/中/难"梯度。
- 搭建评测环境 ——沙箱 / Mock 工具 / 影子库，保证可复现、可一键重置。
- 跑 Agent 采轨迹 ——记录完整 trajectory（思考 Thought、动作 Action、观察 Observation、结果），这是后续所有指标的数据基础。
- 多维打分 ——结果判分 + 过程指标 + LLM-as-Judge 评轨迹质量，形成每任务的评分卡。
- 归因与迭代 ——按维度下钻，定位"是规划弱还是工具错"，反哺 Prompt / 工具 / 模型，形成闭环。

#### 3.2.3 最小示例：用轨迹做 LLM-as-Judge

把 Agent 的完整轨迹交给强模型打分，是成本最低、最易上手的 Agent 评测方式：

| trajectory = agent.run(task="订一张明天北京→上海的机票") score = llm_judge( trajectory=trajectory, rubric=["任务成功率","规划合理性","工具调用准确性","安全合规"] ) print(score) # {'success':0.9,'planning':0.8,'tool_use':0.85,'safety':1.0} |
| --- |

#### 3.2.4 主流 Agent 基准（快速索引）

> AgentBench ——8 类真实环境（OS、数据库、Web 等）统一评测多智能体； τ-bench（tau-bench） ——客服/工具调用场景，测 Agent 与用户+API 的协作； WebArena / BrowseComp ——网页操作与开放信息检索任务； SWE-bench ——真实 GitHub Issue 修复，代码 Agent 的硬标杆。

### 3.3 生产级评测：上线后才是开始

真正进入生产，要靠持续评测：**在线 A/B 实验**对比版本效果、**LLM-as-Judge** 用强模型批量打分（便宜可规模化，但需注意裁判偏见）、**安全红队 / 越狱测试**主动攻击暴露风险。这一层没有"标准答案"，靠的是把评测嵌进 CI/CD 与监控。

## 4.1 Agent 评测专项工具

通用框架之外，还有一类更"贴着 Agent"的工具：它们不做模型榜单，而是专注 Agent 的**轨迹追踪、可观测与自动化评测**。下面是 3 款高活跃度、体验好的开源选择（数据截至 2026-07-28）：

| ** 🪢 7. Langfuse · 开源 LLM 工程平台（观测+评测） **** ⭐ 32.0k ** |
| --- |

## 4.3 选型决策树：按场景对号入座

下面是 8 条最常见的评测诉求。先判断你属于哪一类，再看对应的典型业务场景——能直接对号入座，基本就不会选错。

> 🇨🇳 国产 / 中文模型横向对比？ → OpenCompass 💡 例：团队要选基座模型，想用 C-Eval、CMMLU 等中文榜一次性跑完 Qwen / DeepSeek / GLM 的对比报告，且要求数据本地私有化、不外传。

> 📐 发论文 / 跑标准学术榜？ → lm-evaluation-harness 💡 例：做学术研究的同学需要复现 MMLU、GSM8K、HellaSwag 等结果，或在论文里引用一份可复现、社区公认的基准分数。

> 📚 做 RAG，只看检索 / 生成质量？ → RAGAS 💡 例：企业知识库问答上线了，想量化"检索到的上下文相关性"和"答案忠实度"，定位到底是召回不准，还是生成阶段产生了幻觉。

> 🔬 LLM 应用做生产级回归测试（pytest 风）？ → DeepEval 💡 例：客服机器人每次改 prompt 都担心回归，希望像写 pytest 一样写断言——"答案不能含价格误导""与参考答案相似度 > 0.8"——并在 CI 里自动跑。

> 🛡️ 提示词 / Agent 迭代 + 红队 + 进 CI/CD？ → Promptfoo 💡 例：运营一个多轮 Agent，需批量对比 3 套 prompt 在 50 个测试用例上的成功率，同时跑越狱 / 注入红队扫描，结果自动进 GitHub Actions。

> 🐢 Agent 安全 / 偏见 / 合规扫描？ → Giskard 💡 例：金融 / 医疗场景上线前，要扫描模型是否会泄露 PII、被提示注入绕过、或对特定群体产生偏见，满足合规审计要求。

> 🪢 Agent 轨迹观测 / 调试 / 评测平台？ → Langfuse / Opik 💡 例：生产环境里 Agent 偶发调用错工具，需要回放完整 trace——看到每一步 LLM 输入输出、token 成本，并用 LLM 自动给整条轨迹打分。

> 🔬 标准化 Agent 基准研究 / 沙箱评测？ → Inspect AI 💡 例：研究型团队要在可复现的沙箱里评测 Agent 在 Web、Shell、代码等任务上的多轮完成率，结果能被同行精确复现。

> 协议提示： MIT 与 Apache-2.0 均商用友好：Giskard、DeepEval、RAGAS、OpenCompass、Opik 为 Apache-2.0，Promptfoo、lm-eval-harness、Inspect AI 为 MIT；Langfuse 为 自定义协议（基于 MIT 但含部分功能限制，商用前需确认 LICENSE） 。生产选型前仍建议逐条阅读官方 LICENSE。

## 五、写在最后

AI 评测不是"跑个分"就结束，而是一条从**模型能力 → 应用质量 → 生产监控**的完整链路。本文的四个模块，恰好对应这条链路的四个视角：综述建立认知、Benchmark 量化模型、应用/Agent/RAG 评测逼近真实、开源框架把这一切工程化落地。

对于技术决策者，最实用的建议是：先用 1 个框架把评测跑起来——RAG 场景从 RAGAS 起步，生产应用用 DeepEval 写回归，提示词红队用 Promptfoo——比纠结"哪个最权威"重要得多。评测本身也会进化，今天的 LLM-as-Judge，明天可能就是持续在线的评测智能体。

毕竟，能度量，才能改进。
