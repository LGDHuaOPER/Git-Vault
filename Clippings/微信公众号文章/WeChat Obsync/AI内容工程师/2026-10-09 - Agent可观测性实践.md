# Agent可观测性实践

## 学习目标

- 理解 Agent 可观测性的三大支柱：追踪、指标、日志
- 掌握 OpenTelemetry 的使用
- 学会设计分布式追踪系统

## 引言

可观测性是确保Agent系统稳定运行的关键能力。通过收集和分析系统运行数据，可观测性帮助我们理解系统行为、诊断问题、优化性能。本章将深入探讨Agent可观测性的实践方法，包括日志、监控、追踪和告警。

## 核心概念

### 概念1：可观测性三大支柱

可观测性通常基于三大支柱：

- 日志（Logs）： 记录系统运行过程中的事件和状态变化。日志提供详细的上下文信息，便于问题诊断。
- 指标（Metrics）： 量化系统运行状态，如请求量、响应时间、错误率等。指标提供系统运行的整体视图。
- 追踪（Traces）： 记录请求在系统中的完整路径，便于分析分布式系统中的性能瓶颈和错误。

这三大支柱相互补充，共同构成完整的可观测性体系。

### 概念2：日志管理

日志管理是可观测性的基础。关键实践包括：

- 结构化日志： 使用JSON等结构化格式记录日志，便于解析和分析。
- 日志级别： 合理使用日志级别，区分不同重要程度的信息。
- 日志收集： 集中收集所有节点的日志，便于统一分析。
- 日志存储： 选择合适的存储方案，支持日志的长期保存和快速查询。
- 日志分析： 使用工具分析日志，发现异常和趋势。

良好的日志管理能够大大提高问题诊断效率。

### 概念3：指标监控

指标监控提供系统运行的实时视图。关键实践包括：

- 关键指标定义： 定义系统的关键性能指标（KPI），如延迟、吞吐量、错误率等。
- 指标收集： 定期收集指标数据，如使用Prometheus等工具。
- 指标存储： 存储指标数据，支持历史查询和分析。
- 可视化： 使用Grafana等工具将指标可视化，便于理解。
- 告警： 设置告警规则，当指标异常时及时通知。

指标监控帮助我们及时发现和解决问题。

### 概念4：分布式追踪

分布式追踪用于分析请求在分布式系统中的完整路径。关键实践包括：

- 追踪上下文传播： 在服务调用链中传递追踪上下文。
- Span创建： 为每个操作创建Span，记录操作的详细信息。
- 追踪收集： 收集所有追踪数据，如使用Jaeger、Zipkin等工具。
- 追踪分析： 分析追踪数据，发现性能瓶颈和错误。
- 服务依赖分析： 通过追踪数据构建服务依赖图。

分布式追踪对于理解复杂系统的行为至关重要。

### 核心代码示例

```
class AgentTracer:
    """Agent 追踪器 - 分布式追踪"""

    def __init__(self, service_name: str):
        self.service_name = service_name
        self.spans: list = []
        self.current_trace_id: Optional[str] = None

    def start_trace(self, name: str) -> Span:
        import uuid
        trace_id = str(uuid.uuid4())
        span_id = str(uuid.uuid4())

        span = Span(
            span_id=span_id, trace_id=trace_id, name=name,
            start_time=time.time(), attributes={"service": self.service_name}
        )
        self.spans.append(span)
        self.current_trace_id = trace_id
        return span

    def end_trace(self, span: Span):
        span.end_time = time.time()
        span.duration = span.end_time - span.start_time

    def get_trace(self, trace_id: str) -> list:
        return [s for s in self.spans if s.trace_id == trace_id]
```

## 基础追踪：OpenTelemetry 集成

OpenTelemetry 是分布式追踪的标准方案，课程用 AgentTracer 把它封装成 Agent 侧的追踪能力：

- 初始化： 创建 TracerProvider，挂载 BatchSpanProcessor 与 OTLPSpanExporter（endpoint 为 localhost:4317），把 Span 批量导出到追踪后端。
- 打点： 每次执行用 start_as_current_span 创建 agent_execution Span，写入 agent.id 与 task 属性。
- 结果记录： 成功写入 result.success=true；异常写入 result.success=false 与 error.message 后重新抛出，保证异常不被追踪逻辑吞掉。

```
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter

class AgentTracer:
    """Agent 追踪器: 基于 OpenTelemetry 的基础追踪"""

    def _setup_tracer(self):
        provider = TracerProvider()
        exporter = OTLPSpanExporter(endpoint="localhost:4317")
        provider.add_span_processor(BatchSpanProcessor(exporter))
        trace.set_tracer_provider(provider)
        return trace.get_tracer(self.service_name)

    def trace_agent_execution(self, agent_id: str, task: str):
        with self.tracer.start_as_current_span("agent_execution") as span:
            span.set_attribute("agent.id", agent_id)
            span.set_attribute("task", task)
            try:
                result = self._execute_task(agent_id, task)
                span.set_attribute("result.success", True)
                return result
            except Exception as e:
                span.set_attribute("result.success", False)
                span.set_attribute("error.message", str(e))
                raise
```

## 指标收集：指标定义

三大支柱中的"指标"，课程用 Prometheus 客户端落地为四类采集器，每个指标都带标签（label），便于按 Agent、状态、模型任意切分：

- Counter： agent_tasks_total 任务总数，按 agent_id、status 累加；agent_token_usage_total Token 使用总量，按 agent_id、model 切分，是成本归因的数据源。
- Histogram： agent_task_duration_seconds 任务耗时分布，桶为 0.1/0.5/1/2/5/10 秒——P95、P99 延迟由此计算。
- Gauge： agent_active_count 当前活跃 Agent 数量，可增可减的瞬时值。

配套的 record_task、record_tokens、set_active_agents 三个方法把任务状态、耗时与 Token 消耗写入指标，构成后续告警规则与监控看板的数据底座。

## 跨 Agent 追踪

一个请求穿过多个 Agent 时，需要用统一的 Span 结构把整条调用链串起来。课程定义的 TraceSpan 包含：

- span_id / trace_id / parent_span_id： 分别标识当前 Span、整条链路与父级 Span。
- agent_id / operation： 标明是哪个 Agent 执行了什么操作。
- start_time / end_time / attributes / status： 记录耗时、附加属性与运行状态。

追踪树按 parent_span_id 关系构建：先用 span_id 建立索引，再把每个 Span 挂到其父 Span 的 children 下，没有父级的 Span 成为根节点，从而还原出"端到端任务 → 子 Agent → 工具调用"的完整树形结构。start_span、end_span 负责记录每个环节的起止时间与状态，get_trace 可按 trace_id 取出该次请求的全部 Span。

## 分布式追踪器实现

课程的 DistributedTracer 维护一组 TraceSpan，按 parent_span_id 关系重建树形结构，支持端到端的链路可视化：

```
@dataclass
class TraceSpan:
    """追踪 Span"""
    span_id: str
    trace_id: str
    parent_span_id: str
    agent_id: str
    operation: str
    start_time: float
    end_time: float
    attributes: Dict[str, Any]
    status: str

class DistributedTracer:
    """分布式追踪器"""

    def __init__(self):
        self.spans: List[TraceSpan] = []

    def start_span(self, trace_id: str, parent_span_id: str, agent_id: str, operation: str) -> str:
        """开始 Span"""
        span_id = str(uuid.uuid4())

        span = TraceSpan(
            span_id=span_id,
            trace_id=trace_id,
            parent_span_id: parent_span_id,
            agent_id: agent_id,
            operation: operation,
            start_time=time.time(),
            end_time=0,
            attributes={},
            status="running"
        )

        self.spans.append(span)
        return span_id

    def end_span(self, span_id: str, status: str = "ok"):
        """结束 Span"""
        for span in self.spans:
            if span.span_id == span_id:
                span.end_time = time.time()
                span.status = status
                break

    def get_trace(self, trace_id: str) -> List[TraceSpan]:
        """获取追踪"""
        return [s for s in self.spans if s.trace_id == trace_id]

    def get_trace_tree(self, trace_id: str) -> Dict:
        """获取追踪树"""
        spans = self.get_trace(trace_id)

        # 构建树结构
        root = None
        span_map = {}

        for span in spans:
            span_map[span.span_id] = {
                "span": span,
                "children": []
            }

        for span in spans:
            if span.parent_span_id and span.parent_span_id in span_map:
                span_map[span.parent_span_id]["children"].append(span_map[span.span_id])
            else:
                root = span_map[span.span_id]

        return root
```

成本监控：成本追踪

成本追踪是 Agent 运营的必要能力。课程用 CostTracker 为每一笔模型调用记账：

- 记账粒度： 每条 CostEntry 包含 agent_id、model、输入/输出 Token、成本、时间戳与 task_id。
- 成本计算： 按模型单价表计算，输入成本 = 输入 Token × 输入单价 ÷ 1000，输出成本同理，两者相加。
- 汇总统计： get_summary 支持按 agent_id 与起始时间过滤，输出总成本、输入/输出 Token 总量与任务数。

```
@dataclass
class CostEntry:
    """成本条目"""
    agent_id: str
    model: str
    input_tokens: int
    output_tokens: int
    cost: float
    timestamp: datetime
    task_id: str
```

```
class CostTracker:
    """成本追踪器: pricing = {"model": {"input": 0.01, "output": 0.02}}"""

    def record(self, agent_id, model, input_tokens, output_tokens, task_id):
        cost = self._calculate_cost(model, input_tokens, output_tokens)
        self.entries.append(CostEntry(
            agent_id=agent_id, model=model,
            input_tokens=input_tokens, output_tokens=output_tokens,
            cost=cost, timestamp=datetime.now(), task_id=task_id))
        return cost

    def _calculate_cost(self, model, input_tokens, output_tokens) -> float:
        if model not in self.pricing:
            return 0
        pricing = self.pricing[model]
        input_cost = input_tokens * pricing.get("input", 0) / 1000
        output_cost = output_tokens * pricing.get("output", 0) / 1000
        return input_cost + output_cost
```

成本数据可以接入告警规则形成成本监控闭环，例如"每任务成本超过 1 美元"触发警告，与错误率超过 10%、P95 延迟超过 5 秒等质量与性能告警一起构成完整的告警覆盖。

## 告警配置：告警规则

告警把指标变成行动。课程的 AlertManager 维护一组 AlertRule——每条规则包含名称、条件函数、严重级别和提示消息，严重级别分 INFO、WARNING、CRITICAL 三级；每次检查逐条评估条件，命中即生成告警并发送（实际实现对接 Slack、邮件等渠道）。

课程内置三条默认规则，正好呼应质量、性能、成本三类指标：

- high_error_rate： 错误率超过 10% → CRITICAL（严重告警）。
- high_latency： P95 延迟超过 5 秒 → WARNING（警告）。
- high_cost： 每任务成本超过 1 美元 → WARNING（警告）。

## 告警规则实现

课程的 AlertManager 维护一组 AlertRule——每条规则包含名称、条件函数、严重级别和提示消息，严重级别分 INFO、WARNING、CRITICAL 三级；每次检查逐条评估条件，命中即生成告警并发送（实际实现对接 Slack、邮件等渠道）。

```
class AlertSeverity(Enum):
    """告警严重性"""
    INFO = "info"
    WARNING = "warning"
    CRITICAL = "critical"

@dataclass
class AlertRule:
    """告警规则"""
    name: str
    condition: Callable[[Dict], bool]
    severity: AlertSeverity
    message: str

class AlertManager:
    """告警管理器"""

    def __init__(self):
        self.rules: list = []
        self.alerts: list = []

    def add_rule(self, rule: AlertRule):
        """添加规则"""
        self.rules.append(rule)

    def check(self, metrics: Dict):
        """检查告警"""
        for rule in self.rules:
            if rule.condition(metrics):
                alert = {
                    "rule": rule.name,
                    "severity": rule.severity.value,
                    "message": rule.message,
                    "metrics": metrics
                }
                self.alerts.append(alert)
                self._send_alert(alert)

    def _send_alert(self, alert: Dict):
        """发送告警"""
        # 实际实现发送到 Slack、邮件等
        print(f"ALERT [{alert['severity']}]: {alert['message']}")

def create_default_alerts() -> AlertManager:
    """创建默认告警"""
    manager = AlertManager()

    # 高错误率告警
    manager.add_rule(AlertRule(
        name="high_error_rate",
        condition=lambda m: m.get("error_rate", 0) > 0.1,
        severity=AlertSeverity.CRITICAL,
        message="错误率超过 10%"
    ))

    # 高延迟告警
    manager.add_rule(AlertRule(
        name="high_latency",
        condition=lambda m: m.get("latency_p95", 0) > 5.0,
        severity=AlertSeverity.WARNING,
        message="P95 延迟超过 5 秒"
    ))

    # 高成本告警
    manager.add_rule(AlertRule(
        name="high_cost",
        condition=lambda m: m.get("cost_per_task", 0) > 1.0,
        severity=AlertSeverity.WARNING,
        message="每任务成本超过 $1"
    ))

    return manager
```

## 实践指导

## 实践指导

### 如何应用

- 需求分析： 明确系统的可观测性需求，如日志保留时间、监控指标等。
- 工具选型： 选择合适的日志、监控和追踪工具。
- 数据收集： 实现日志、指标和追踪数据的收集。
- 数据存储： 配置数据存储，确保数据的安全和高效访问。
- 可视化与告警： 配置可视化仪表板和告警规则。
- 持续优化： 根据使用情况持续优化可观测性方案。

### 注意事项

- 性能影响： 可观测性不应过度影响系统性能。
- 数据量控制： 控制收集的数据量，避免存储成本过高。
- 隐私保护： 确保可观测性数据不泄露敏感信息。
- 团队培训： 对团队进行可观测性工具和方法的培训。

## 总结

- 可观测性基于日志、指标和追踪三大支柱，帮助我们理解系统行为、诊断问题。
- 日志管理提供详细的上下文信息，便于问题诊断。
- 指标监控提供系统运行的实时视图，帮助我们及时发现问题。
- 分布式追踪用于分析请求在分布式系统中的完整路径，发现性能瓶颈。
- 可观测性实践需要考虑性能影响、数据量控制、隐私保护等问题。
