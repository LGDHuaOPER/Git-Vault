# 生成式 AI 可观测性 2.0：成本、安全、质量三大支柱

![头图](附件资源/生成式%20AI%20可观测性%202.0：成本、安全、质量三大支柱/img_1.jpg)

![](附件资源/生成式%20AI%20可观测性%202.0：成本、安全、质量三大支柱/img_2.jpg)

微服务时代，架构师的安稳觉靠四个指标守着：延迟、错误率、流量、饱和度。Prometheus 上的 Grafana 看板一片绿，全是 HTTP 200 OK，系统稳得很。

但引入 LLM 和 AI Agent 之后，这片绿色变成了陷阱。

**1**

**监控为什么失效了**

某跨境电商上线了 AI 客服 Agent。大量用户投诉 AI 答非所问，甚至辱骂客户。运维紧急打开监控，APM 告警安安静静，网关吞吐正常，微服务延迟极低，错误率是完美的 0%。问题出在哪？

传统基础设施监控只能告诉你系统是否在运行，无法告诉你运行得是否正确。LLM 哪怕正在一本正经胡说八道，或者陷入死循环疯狂消耗 Token，它返回给网关的依然是一个结构完美的 JSON 和标准的 HTTP 200。

响应成功不再等同于业务正确。传统 APM 需要升级为面向生成式 AI 的可观测性 2.0，架构师需要构建三根新支柱：成本、安全与质量。

**2**

**Token 计费带来的风险**

传统云原生架构里，突发流量顶多导致算力扩容、账单上浮。但 LLM 的成本按 Token 线性计算，这衍生出了两类在旧体系里不存在的风险。

第一种叫钱包拒绝服务攻击（Denial of Wallet）。恶意用户构造循环 Prompt，比如请重复哈哈一万次并分析每次的区别，或者滥用 Agent 工具链诱导高频无限调用。服务器不会宕机，但企业级 API 额度会在几小时内被掏空。

第二种风险来自模型漂移。OpenAI 或 Anthropic 更新底层模型版本时，即使对外声称能力提升，内部 Token 吞吐和 Prompt 消耗规律可能发生质变。某些微小的提示词不兼容可能引发 Agent 多轮重试，导致账单隔夜暴涨 8 到 10 倍。

应对方式有两个。一是 Token 配额与断路器：在网关层实现基于用户或租户维度的窗口期 Token 计数，某个会话 1 分钟内消耗超过阈值直接熔断。二是工具调用预算：为单次请求的 Agent 思考链设置最大深度，比如 Agent 调用底层 API 不超过 N 次。

**3**

**构建安全双向护栏**

传统系统的攻击是确定性的，SQL 注入、XSS，有明确的漏洞模式可以匹配。大模型面对的是基于自然语言的模糊攻击，越狱和提示词注入，以及模型发散性导致的数据泄露。

静态防火墙解析不了 Prompt 的语义。现在需要在 Agent 输入和输出端各架一道语义护栏：

-
-
-
-

```
用户请求 ──> [ 输入拦截器: 语义扫描/越狱检测 ] ──> Agent 思考/大模型                         │ 用户感知 输入端实时扫描用户 Prompt，用轻量级安全模型（如 Llama-Guard）或者向量匹配检测越狱尝试和提示词注入。输出端则对模型生成的文本做正则与 NER 混合扫描，身份证号、信用卡、内部代码片段、敏感密钥一旦出现立即脱敏或拦截。

**4**

**质量评判：让大模型审大模型**

怎么量化一个 Agent 回答得好不好？人工刷日志成本极高，面对海量流式数据也没有实时性。

可观测性 2.0 引入 LLM-as-a-Judge 机制，重点观测两个硬核指标（参考 RAGAS 框架）：

上下文相关性（Context Relevance）：评估系统检索出来的知识是否真能回答用户的问题。防止给模型喂一堆垃圾信息然后得到垃圾输出。

忠实度（Faithfulness）：评估模型的回答是否有严谨的依据来源于检索上下文。如果回答包含上下文中根本没有的字段或数字，判定为幻觉。

落地时通常采用异步流，将用户请求、检索到的上下文和模型回答拷贝一份推到 Kafka，由后置评估服务打分：

-
-
-
-
-
-
-
-
-
-

```
JUDGE_PROMPT = """你是一个严谨的架构审计员。请根据提供的【上下文】，评估【AI回答】是否完全基于事实。如果有任何一句回答是上下文中未提及的，或者矛盾的，请将其判定为"有幻觉"。
【上下文】: {context}【AI回答】: {answer}
请输出 JSON 格式：{"faithfulness_score": 0.0到1.0, "reason": "原因"}"""
```

通过这种近线打分机制，可以在 Grafana 上绘制系统幻觉率趋势图和回答质量水位线。一旦平均得分低于 0.8，触发工程告警，提示需要优化 Prompt 或清洗向量库数据。
