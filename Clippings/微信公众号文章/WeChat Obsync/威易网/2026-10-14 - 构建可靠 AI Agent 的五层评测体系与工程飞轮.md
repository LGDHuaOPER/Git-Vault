# 构建可靠 AI Agent 的五层评测体系与工程飞轮

_这篇文章非常硬核且具有实战价值，讨论了当前大模型落地最痛的一个坎——如何构建可靠的 Agent 评测体系。文章为你做了全文深度翻译，专业术语均对照业界常用规范进行了本土化润色，如要查看英文原版，请点击文章底部的“查看原文”：_

我们很清楚该如何让 Agent 变得更强大，但真正困难的问题在于：我们究竟能不能真正信任它们？

现如今，搭建一个 AI Agent 已经变得异乎寻常的简单。

给模型设定一个目标，给它挂载几个工具，加上检索增强与记忆模块，再用一个编排调度循环（orchestration loop）把它包裹起来——转眼之间，你就拥有了一个只需极少人类介入就能搜索网页、查询数据库、调用 API、更新记录、生成文档并执行多步骤工作流的系统。

只需几个小时，你就能攒出一个令人惊叹的 Demo 原型。

但紧接着，就会有人抛出那个真正致命的问题：

我们怎么知道这个 Agent 是真的管用？

不是问它在演示 Demo 时表现得好不好；

不是问它在工程团队手动测试的那区区 5 个样本上有没有成功；

更不是问它最终吐出的答案看起来是不是“挺合情理”。

真正的问题是：当面对成百上千种截然不同的真实场景时，这个系统还能稳定工作吗？

当用户的输入含糊不清时会怎样？当外部工具调用超时时会怎样？当 API 返回了意料之外的数据时会怎样？当检索带回了完全错误的上下文时会怎样？当对话轮次变得很长时会怎样？当 Prompt 发生微调时会怎样？当你升级了底层的基座大模型时会怎样？

甚至更关键的是——当 Agent 采取了一条工程团队从没预料到、但逻辑上完全合法的执行路径时，又会怎样？

这正是智能体系统的棘手之处。现在的挑战早已不是“如何让 Agent 拥有更多能力”，而是能否衡量它们的行为模式、理解它们的失败原因、敏锐捕获性能倒退（regressions），并最终决断它们是否可靠到足以推向生产环境。

如今阻碍落地的瓶颈，日益从**“Agent 的能力边界”转变为“Agent 的评测能力”**。

### 传统软件靠断言（Assertions），Agent 靠分布（Distributions）

传统软件为我们提供了一个非常清晰简单的测试范式：

给一个函数输入 Input X，预期得到 Output Y。

如果函数返回了别的东西，测试就宣告挂掉。

我们可以写单元测试断言，写确定性的集成测试。我们可以把同一个测试跑上一千遍，并理所当然地预期一模一样的行为。

但 Agent 彻底打破了这种范式。

一个 Agent 面对完全相同的任务两次，它可能会：

- 选择截然不同的工具；
- 以不同的次序调用工具；
- 检索到不同的上下文信息；
- 采取不同的推理策略；
- 第一次执行花了 3 步，第二次却用了 8 步；
- 遇到错误时的自愈与恢复方式完全不同；
- 或者输出形式略有差异的最终结果。

而上述所有差异，并不必然代表 Agent “做错了”。

这就是根本性的范式转移。

在评估 Agent 时，我们不再是在评估单次、确定性的执行过程。

我们评估的是一种“可能行为的概率分布”（Distribution of possible behaviors）。

因此，我们的工程目标绝不该是：

> 强行让每一次执行都严丝合缝、完全相同。

更合理的目标应当是：

> 确保不同的执行路径，都能稳定可靠地落在可接受的结果边界（Outcome Boundary）之内。

这是一个难度高出几个维度的工程命题。

### 评估绝不仅仅是看准确率（Accuracy）

许多团队在做 Agent 时犯的最大错误，就是依然把它当作传统的对话机器人（Chatbot）来对待。

他们只评测最终的回复：

- 答案正确吗？
- 内容切题吗？
- 文笔顺畅吗？

这些问题依然重要，但远远不够。

设想一个负责核保审批的 Agent，最终确实给出了正确的核保建议。

听起来很棒，对吧？

但在整个执行过程中，它却：

- 调用了一个毫无必要的外部供应商接口；
- 向另一个服务传递了错误的参数；
- 检索了一堆根本用不上的垃圾数据；
- 跳过了一项强制性的合规校验；
- 对着同一个工具疯狂重试了 4 次；
- 消耗了预期 10 倍的 Token 用量；
- 然后，以某种诡异的方式“蒙对”了最终答案。

如果你只评估最终输出，这次执行就算作通过（PASS）。

但在实际生产运维中，它理应被直接判挂（FAIL）。

一旦大模型升级为 Agent，评测的最小单元就彻底变了。

你不再只是评测简单的：输入 → 输出

你必须全盘评估：输入 → 规划 → 推理 → 工具选择 → 工具参数 → 工具响应 → 状态转移 → 进一步推理 → 最终动作 → 真实物理世界/系统状态的改变

这整条执行轨迹（Trajectory），全都需要纳入考量。

### Agent 评估的五个层级

在实践中，将 Agent 评估拆解为五个层级会非常清晰：

![](附件资源/构建可靠%20AI%20Agent%20的五层评测体系与工程飞轮/img_1.jpg)

- 结果评估（Outcome Eval） ：Agent 真的搞定任务了吗？
- 轨迹评估（Trajectory Eval） ：Agent 走了一条合理的路径吗？
- 质量评估（Quality Eval） ：交付的结果质量到底好不好？
- 可靠性评估（Reliability Eval） ：反复运行还能稳定管用吗？
- 生产评估（Production Eval） ：它在真实业务中创造价值了吗？

每一层回答的问题都截然不同。

这是最基础、也最关键的一层。

假设一个客服 Agent 对用户说：“您的退款已成功处理。”

这句话本身不能证明任何事。

真正的问题是：支付系统里到底有没有生成那笔退款记录？

对于执行真实动作的 Agent 来说，宿主环境往往才是唯一的真理来源（Source of Truth）。

不要问：_Agent “嘴上说”完成任务了吗？_而是要问：_系统状态真的发生了预期的变更吗？_

比如：

- 退款真实发起并落库了吗？
- 工单真的创建了吗？
- 数据库字段确实更新了吗？
- 保单配置真的被修改了吗？
- 目标文件确实生成了吗？
- 代码部署成功了吗？
- 酒店预订确认了吗？

由此引出了衡量 Agent 最为核心的指标：

任务成功率（Task Success Rate） = 成功完成的任务数 / 总尝试次数

哪怕你的推理架构再优雅、上下文记忆再精妙、日志链路再漂亮——如果这个 Agent 面对任务时成功率只有 70%，上面那些全都是空中楼阁。

设想两个 Agent 面对同一个任务，最终都完成了目标。

但一个走了最优路径，另一个在死循环和冗余调用里绕了一大圈才碰巧成功。两者显然不能划等号。

这就是为什么**执行轨迹评估（Trajectory Eval）**至关重要。

常用的核心指标包括：

- 工具选择准确率（Tool Selection Accuracy） ：选对工具了吗？
- 参数正确率（Argument Correctness） ：传递的参数与 Payload 是否精准无误？
- 必经步骤覆盖率（Required-Step Coverage） ：业务规定的强制节点都走到了吗？
- 冗余工具调用率（Unnecessary Tool Calls） ：是否存在浪费动作或无意义的调用？
- 执行步数（Step Count） ：完成任务总共耗费了多少步？
- 死循环率（Loop Rate） ：是否陷入重复动作或逻辑死循环？
- 非法动作率（Invalid Action Rate） ：是否尝试了不合规、不可行或非法的操作？
- 容错恢复率（Recovery Rate） ：工具报错或下游超时后，能否成功自愈并继续推进？

但这里存在一个微妙之处：某些工作流只有唯一正确的路径；但在另一些场景下，可能存在多种条条大路通罗马的可能（例如 A→B→D 与 A→C→D 同样合理）。

因此，评测不能一味死板地追问：_Agent 是否严格遵循了“预设的标准路径”？_有时我们更应该问：_Agent 走的是否是一条*合法、安全且足够高效的有效路径_？*

随着 Agent 自主权（Autonomy）的提升，这一区分会变得越来越关键。

并非所有的 Agent 任务都会产生能用代码直接断言的状态变更。

比如：

- 调研这家公司的竞品情况；
- 分析这份研报；
- 解释为什么这笔理赔申请会被驳回；
- 输出一套系统架构建议；
- 总结最新财报数据；
- 对比不同商业策略。

这些任务通常没有唯一的标准答案，此时就需要引入语义层面的评估（Semantic Evaluation）。

常见的考察维度包括：正确性（Correctness）、完整性（Completeness）、事实依据（Groundedness）、相关性（Relevance）、指令遵循度（Instruction Adherence）、真实性（Factuality）、引文质量（Citation Quality）、推理一致性（Reasoning Consistency）、格式合规度（Format Compliance）以及专业领域指标。

这就是LLM-as-a-judge（大模型作为裁判）大显身手的场景。

裁判模型接收：原始任务 + Agent 最终回复 + 检索/执行上下文 + 评分细则（Rubric） + 参考答案（如有）

然后给出结构化评分：正确性: 0.92 | 完整性: 0.86 | 依据真实性: 0.97 | 指令遵循: 1.00

大模型裁判固然好用，但它也带来了另一个令人头疼的事实：

你的裁判本身也是概率性的。

裁判大模型可能会出现前后打分不一致、存在偏见、偏爱冗长回复（Verbosity Bias）、无法识别专业领域的细微硬伤，甚至在给同一段回答评分两次时给出自相矛盾的结果。

因此，裁判模型本身也需要被评测。

成熟的团队通常采用这样的闭环：人类专家精标样例 → LLM 裁判打分 → 比对人类与 LLM 打分差异 → 衡量分歧度 → 持续迭代裁判 Prompt 与评分细则

评测系统本身就是核心产品的一部分，必须拿出对待生产级代码一样的严谨度去打磨它。

这大概是当前 Agent 评测中最容易被忽视的盲区。

假设你的 Agent 跑通了一个测试用例，看起来很完美。

现在，把完全相同的场景连续跑 10 次。

你可能会看到这样的结果：通过、通过、通过、失败、通过、通过、失败、通过、通过、通过

这揭示了一个单次测试永远测不出来的真相：这个 Agent 拿的不是 8/10 分的答卷，而是面临着“稳定性仅有 80%”的严重可靠性危机。

对于具有随机性的系统，反复压测是刚需。核心指标包括：

- Pass@1 ：单次常规执行成功的概率。
- 重复运行成功率（Repeated-Run Success） ：相同场景在多轮反复测试下的成功率。
- 行为方差（Behavioral Variance） ：多次运行之间波动的剧烈程度（步数、耗时、Token 消耗、工具选择是否忽高忽低）。
- 长尾失败率（Tail Failure Rate） ：表现最差的 1%、5% 或 10% 的长尾极端情况下会发生什么？

在金融、医疗、核心系统操作等高风险领域，这一点尤为致命——一个 95% 场景下优雅丝滑、却在 5% 的极端情况下捅出大篓子的 Agent，在商业上就是完全不可用的。

这里存在一个残酷的数学事实：

假设系统中的每一次关键决策准确率高达 98%。98% 听起来是个极高的数字，对吧？

但如果这个复杂工作流由 20 个互为依赖的决策步骤组成：$$ 工作流端到端可靠性 \approx 0.98 \times 0.98 \times \dots \times 0.98 \approx 0.98^{20} \approx 66.7% $$

每增加一步，系统就多了一处可能失败的薄弱环节。

这意味着一个略微反直觉的结论：Agent 的自主性越强、决策链路越长，保证可靠性的难度就呈指数级飙升。

工作流越长，意味着更多的决策点、更多的工具调用、更多的状态转移、更多可能被污染的上下文、更多外部系统的不可控因素，以及微小误差被层层放大的机会。

这就是为什么盲目让 Agent 具备“从调 5 个工具升级到能连续调 50 个动作”的能力，并不能直接让它变强——能力（Capability）与可靠性（Reliability），根本就是两个不同的维度。

到最后，光有技术层面的正确性是不够的。

终极问题终究是：这个 Agent 真的有用吗？

这正是技术评测与商业价值挂钩的交汇点。生产环境中最重要的指标包括：

- 任务达成率（Task Completion Rate） ：用户最终解决核心诉求了吗？
- 人工介入接管率（Human Takeover Rate） ：自动化中途崩塌、必须由人工接管的频次有多高？
- 升级率（Escalation Rate） ：Agent 主动向人类呼救求援的频率。
- 用户人工修正率（User Correction Rate） ：用户不得不手动修改 Agent 输出内容的比例。
- 端到端耗时（Time to Completion） ：这个工作流用 Agent 代替人工，到底有没有提速？
- 重试率（User Retry Rate） ：用户是否因为初次结果不够理想而反复重问？
- 中途弃用率（Abandonment Rate） ：用户在任务彻底跑完前掀桌子放弃的比例。
- 合规越界率（Policy Violation Rate） ：Agent 自主操作过程中是否触碰了安全与合规红线？
- 业务核心 KPI 贡献度 ：到底有没有拉动实际业务收益？
- 单次成功任务成本（Cost per Successful Task） ：经济账到底算不算得过来？

最后这个成本指标尤为关键。

许多 AI 基建团队天天紧盯“每次请求成本”（Cost per Request），但这完全找错了衡量单位。

用户根本不在乎你发了多少次 API 请求，用户在乎的是任务有没有办妥。

花 $0.40 彻底搞定了一项原本需要人工操作 15 分钟的复杂工作流，其商业价值远高于一个只花 $0.05 却频频出错、反倒需要人工花时间擦屁股的便宜方案。

单次成功任务成本 = Agent 总消耗成本 / 成功交付的任务总数

Agent 的真正价值计量单位从来不是 Token，而是交付的成果（Completed Work）。

### 生产级 Agent 评测计分卡（Scorecard）

如果我今天要在生产环境构建一个 Agent，我的核心评估看板会由以下关键项构成：

- 结果 ：任务成功率（是否真的办妥了？）、最终系统状态正确性（数据与状态变更对不对？）；
- 可靠性 ：多轮运行一致性（多次执行的表现是否稳如泰山？）；
- 安全 ：策略违规率（是否突破安全边界与业务红线？）；
- 工具调用 ：工具选择准确率、工具参数传参正确率；
- 轨迹控制 ：核心必要步骤覆盖率；
- 韧性与容错 ：异常自愈恢复率（面对外部超时与垃圾数据时能否自救？）；
- 输出质量 ：事实性与真实性（是否基于可靠上下文推断？）；
- 运营协同 ：人工修正率、人工接管率；
- 系统效率 ：单次成功任务成本、P50 / P95 延迟；
- 防倒退（Regression） ：与历史版本的 Delta 差异（升级后有没有在修复 A 的同时把旧功能 B 搞炸？）。

说一个 Agent 的综合表现有“92 分”，对工程排查毫无意义。

真相往往是：它在简单任务上成功率 99%，中等任务上 91%，而在你最核心的命脉业务流程中，成功率只有 47%。

平均数是最大的掩护与谎言。

评估指标必须分门别类切片下钻分析：按任务类型、业务流分类、难度等级、工具类型、模型版本、Prompt 版本、用户客群、执行步数分布、以及具体失败类型分别统计。

分布本身，远比那个光鲜的平均值重要得多。

### 实战 Agent 评测架构设计原则

在设计生产级评测架构时，有一条至关重要的设计原则：

![](附件资源/构建可靠%20AI%20Agent%20的五层评测体系与工程飞轮/img_2.png)

> 能用确定性代码验证的地方，绝不要让大模型去猜。

- 能写  `assert payment.status == "refunded"`  的，绝不要去问大模型“这段话看起来像是退款成功了吗？”；
- 能用 JSON Schema 强校验字段的，绝不要问大模型“这个 JSON 格式看起来对不对？”；
- 能用  `assert tool == "refund_customer"`  断言的，绝不要靠裁判模型去评判“选这个工具听起来合不合理”。

只把非确定性的判别留给概率性的大模型裁判，确定性的逻辑全部交给代码。

### 评测数据集比评测模型更重要

再聪明的大模型裁判也救不了烂透了的数据集。生产级评测集必须包含多维来源：

- 黄金案例（Golden Cases） ：业务专家精细定义的核心业务场景及标准预期；
- 生产实网流量（Production Traffic） ：真实用户输入的千奇百怪的边界场景，往往超出工程师的想象力；
- 历史翻车案例库（Historical Failures） ：每一次有价值的生产事故，都必须抽象为一条永久的自动化回归测试用例。这构成了 AI 工程中最核心的飞轮： 生产事故 → 提炼为评测用例 → 修复 Agent 缺陷 → 跑回归测试 → 安全上线 同样的重大事故，原则上只允许发生一次。
- 边缘案例（Edge Cases） ：主动注入缺失字段、冲突数据、超时重试、工具崩溃、意图模糊、超长对话中断等；
- 对抗与安全用例（Adversarial Cases） ：Prompt 注入攻击、敏感数据泄露防护、越权调用与非法提权防护；
- 合成扩充用例（Synthetic Cases） ：当你明确了失败模式的分类后，可以用大模型低成本批量扩充该类别的测试集，但合成数据只能作为辅助，切忌本末倒置脱离真实业务。

### 离线评测是“单元测试”，在线评测是“传感器”

两者缺一不可。

- 离线评测（Offline Evals） ：发布前的防线。每当你改动了底座模型、Prompt、工具 Schema、检索策略、Memory 或是图编排逻辑，必须跑一遍离线评测套件，把它无缝嵌入到 CI/CD 流程中：  `提交代码 PR → 自动化跑 Eval → 与基线对比 → 出现指标倒退（Regression）则阻止合并，无异常方可发布。`
- 在线评测（Online Evals） ：生产运行时的探针。线下无论怎么模拟，也涵盖不了复杂现实世界的全部变数。持续对线上真实链路进行抽样，挂载结果校验、安全监控、异动告警以及失败归因分析，将线上挖掘到的异常数据持续反哺给离线测试集。

这构成了完整的Agent 评测飞轮（Eval Flywheel）：研发构建 → 离线评测 → 上线部署 → 链路观测 → 在线监控 → 捕获长尾故障 → 沉淀入数据集 → 迭代修复 → 循环往复

这一飞轮的运转效率，将成为未来 Agent 工程团队之间最核心的竞争壁垒。

### 失败归因分类与打分同样重要

假设你的任务成功率从 92% 暴跌到了 84%。这只能说明系统出事了，但无法指导你该去修哪里。

一套成熟的评测体系必须具备失败分类法（Failure Taxonomy）：

- 规划决策失误
- 选错工具
- 参数拼装错误
- 检索召回失败
- 关键上下文丢失
- 工具本身执行异常
- 模型推理逻辑硬伤
- 违背业务策略
- 超时中断
- 陷入逻辑死循环
- 最终输出格式错乱
- 虽答对但引发了错误的系统副作用

唯有做到这一步，评测系统才能真正转型为可落地的 Debug 调试工具。工程师听到的不再是一句笼统的“新版模型变差了”，而是精准的洞察：“新模型让逻辑推理错误减少了 15%，但工具参数格式错乱的概率却上升了 8%”。

这就是可以立即着手修复的明确工单。

### 评测体系自身必须严格进行版本控制

看到评测大盘上打分从 81% 跃升到 89% 先别急着开香槟。

在这两次实验之间，如果你同时微调了底座模型、Prompt、工具描述、测试集范围，甚至连裁判模型的 Prompt 和打分细则都变了——那么这 8 个点的提升到底是谁带来的？

你根本无从得知。

必须对实验中的每一次变量严格做版本快照锁定：模型版本、Prompt 版本、工具定义版本、评测集版本、裁判模型及打分细则版本、以及每次调用的详尽 Trace 报文。缺乏版本严谨性的评估看板，看起来再高大上，也只是一堆无法复现的伪科学数字。

### 我们的终极目标并不是消灭一切随机性

当工程师第一次直面 Agent 的多变与不确定性时，本能反应往往是：“我怎么才能把它改写成完全确定性的？”

在资金划转、高危删除、合规审计等红线环节，绝对的确定性确实必不可少。

但如果强行将所有的自主决策工作流都锁死在唯一一条死板的代码路径上，我们又何必多此一举使用 Agent？

更合理的工程愿景是：

> 允许内部存在多种合法的发散路径，但最终能稳稳收敛在可预测的结果边界之内。

内部非确定性，外部结果高度可预期——这才是 Agent 工程化的真正艺术。

### 我最为看重的北极星指标

如果要为生产级 Agent 挑选唯一一个终极北极星指标，我会定为：

可靠任务交付率（Reliable Successful Task Completion）

即：Agent 在合规策略与安全约束之内，以合理可控的成本与耗时，在不需人工介入的情况下，稳健达成了物理世界或业务系统的最终目标。

这才是我们真正追求的东西。因为一个 Agent 完全可能做到：

- 结果正确，但存在严重安全漏洞；
- 结果正确，但稳定性极差（掷骰子）；
- 结果正确，但烧光了巨额 Token 成本；
- 结果正确，但耗费了无法忍受的超时时间；
- 绕了一大堆无效操作后碰巧成功；
- 结果正确，但成功率只有 70%。

以上任何一种情况，都算不上真正达到了生产可用标准。

### 可观测性（Observability）与评测（Evaluation）正在走向合流

传统软件工程中，系统监控追踪（Observability）和软件测试（Testing）通常泾渭分明：

- 监控解答：“系统刚才发生了什么？”
- 测试解答：“系统表现得对不对？”

但在 Agent 体系下，这两者的边界正在彻底瓦解。

链路追踪（Trace）告诉你：模型看到了什么？做出了什么决策？调用了什么工具？返回了什么？状态如何迁移？而评测器（Evaluator）则紧随其后给出评判：这个决策过程是优秀的吗？

没有评测的链路追踪，只是一堆枯燥死板的日志流水；而没有全链路 Trace 的评测，即便告诉你任务失败了，也根本无法回答它究竟挂在了哪一步。两者深度绑定的闭环，才是支撑下一代可信 Agent 的坚实基座。

### 总结：从能力竞速到信任构建

生成式 AI 的上半场，整个行业都在狂热追逐：如何生成更惊艳的文本与答案？

而 Agent 时代的到来，将我们推向了一个更艰难的战场：我们如何构建一个行为可度量、可理解、且真正值得信赖的自主系统？

最终在这场竞逐中胜出的团队，未必是拥有最炫酷的图编排架构、最巧妙的 Prompt 技巧、或是天天尝鲜最新开源框架的团队。

胜出的，必将是拥有最高效“评测飞轮”的团队。

当别的团队还在靠看几条 Bad Case 和生产告警凭玄学 Debug 时，能够清晰洞察“挂在哪、为什么挂、发生概率有多高、影响哪些客群、改动有无引发性能倒退、能否安全上线发布”的团队，其工程迭代的进化速度将形成降维打击。

让 Agent 走向可靠，从来不是靠消灭所有的随机性，而是靠精准度量它、合理约束它，并在失败中构建持续进化的飞轮机制。

AI 智能体的未来，绝不仅仅关于“能力”（Capability），它最终关乎于“信任”（Trust）。
