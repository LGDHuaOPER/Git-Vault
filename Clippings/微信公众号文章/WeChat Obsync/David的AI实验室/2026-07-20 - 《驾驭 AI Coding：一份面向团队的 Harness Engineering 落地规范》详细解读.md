# 《驾驭 AI Coding：一份面向团队的 Harness Engineering 落地规范》详细解读

**原文标题：**《驾驭AI Coding：一份面向团队的Harness Engineering落地规范》

**原文作者：** atreusliu

**解读说明：** 本文按原文章节完整梳理并进一步分析。涉及案例数据、产品能力和内部工具名称时，均表示“原文所述”，不等同于本文进行了独立事实核验。

01

PART

### 一、先说结论：这篇文章真正讨论的不是“如何让 AI 多写代码”

文章开篇提出了一个非常准确的判断：

交付代码的成本已经接近免费，但交付好代码的成本依然很高。

这句话划出了普通 AI Coding 与 Harness Engineering 的分界线。

普通 AI Coding 关注的是“这一次能不能生成代码”；Harness Engineering 关注的是“团队能不能持续、稳定、低风险地生成符合工程标准的代码”。前者优化单次对话，后者改造整个研发系统。

因此，文章的核心并不是介绍 MCP、Skills、Rules、知识库、Plan 模式等概念，而是回答两个更重要的问题：

**·** 这些工具在一套完整的 AI 研发体系中各自承担什么职责？

**·** 怎样把它们组合成可执行、可验证、可追溯、可持续改进的团队工作流？

可以把全文压缩为一句话：

**Harness Engineering，就是把团队对“好代码”的判断，从个人经验和聊天提示词中抽离出来，固化为 AI 能读取、工具能执行、流程能验证、Git 能追溯的工程系统。**

这也是本文最有价值的地方：它没有把 AI 当作更快的代码补全工具，而是把 AI 当作一个需要上下文、工具、流程、边界、评估和恢复机制的新型执行者。

### 三、核心概念：Agent 为什么不等于模型

3.1 原文的核心公式

原文给出了全文最重要的公式：

...text

Agent = Model + Harness

其中：

**·** **Model** 提供语言理解、推理和生成能力；

**·** **Harness** 提供工具、上下文、权限、状态、执行编排、评估、恢复和记忆；

**·** **Agent** 才是能够在真实研发环境中持续完成任务的执行主体。

大模型本身没有可靠的长期状态，不天然知道项目架构，也不能自动获得数据库 Schema、业务文档、CI 日志或团队规范。如果只给模型一个需求，然后期待它自行做对所有技术决策，实际上是在把工程质量交给概率。

Harness 的意义，就是把这些缺失的工程条件补齐。

3.2 三层结构

原文把整体系统分为三层：

...text

┌──────────────────────────────────────────────┐

│ 应用层：IDE 插件 / CLI / Web UI / 用户交互   │

├──────────────────────────────────────────────┤

│ Harness 层：                                 │

│ 工具调用 / 上下文管理 / 权限校验 / 状态持久化│

│ 执行编排 / 评估验证 / 约束恢复 / 记忆系统    │

├──────────────────────────────────────────────┤

│ 模型层：Claude / GPT / DeepSeek / 其他 LLM   │

└──────────────────────────────────────────────┘

这里最容易被低估的是中间层。模型可以替换，IDE 也可以替换，但团队积累的规范、知识、工具接入方式和验证流程不应随着工具更换而消失。

3.3 “Harness”这个比喻的含义

Harness 原意是马具。马很有力量，但只有缰绳、马鞍和控制机制齐备，力量才能被稳定地用于运输、耕作或作战。AI 也一样：能力强不代表可直接用于生产。

这个比喻至少包含三层意思：

**·** **Harness 不是限制能力，而是把能力转化为生产力。**

**·** **Harness 既包括“允许做什么”，也包括“不能做什么”。**

**·** **AI 越强，Harness 越重要。**能力放大后，错误的影响范围也会同步放大。

### 四、为什么单纯的 Vibe Coding 难以进入团队生产环境

原文总结了三类致命问题。

4.1 架构混乱

AI 倾向于选择当前上下文中最短、最容易实现的路径，而不是主动维护整个项目的长期一致性。例如，功能 A 使用一套组件，功能 B 又引入另一套功能重叠的组件；Controller、Service、Repository 的职责逐渐混在一起。

这类代码可能“现在能跑”，但会抬高后续修改成本。AI 提高了局部实现速度，却可能制造更大的系统性负债。

4.2 上下文雪崩

随着项目扩大，模型不可能在每次任务中无成本地读完所有文件和历史对话。命名、边界条件、已做决策和业务约束会逐渐漂移。例如同一个字段先叫 user_id，后续又被生成为 uid。

问题不只是上下文窗口大小，而是缺少上下文架构：

**·** 哪些信息必须始终加载？

**·** 哪些信息按任务加载？

**·** 哪些信息只在需要时深入查看？

**·** 哪些决策必须固化到仓库而不是留在聊天记录里？

4.3 可维护性丧失

如果代码生成过程完全存在于一次性对话中，人类只看到了最终文件，就很难知道：

**·** 方案为什么这样设计；

**·** 哪些备选方案被放弃；

**·** 哪些边界条件已考虑；

**·** 哪些地方是为了兼容现有系统；

**·** 后续变更应该遵循什么原则。

最终结果是“只有生成它的 Agent 知道它为什么这样写”，而会话一旦结束，这部分知识就丢失了。

4.4 Harness 要补足的四类工程能力

原文对应提出四类能力：

**·** **安全边界：**权限控制、审计记录、拒绝追踪；

**·** **可观测性：**Token、成本、决策过程和执行结果可查看；

**·** **可靠性：**重试、降级、确定性验证和兜底机制；

**·** **扩展性：**工具生态、Skills 和多 Agent 协作。

我的理解是：Vibe Coding 的问题并不是“AI 写得不够聪明”，而是“团队没有为 AI 建立生产系统”。继续更换模型只能改善局部效果，不能替代 Harness。

### 五、Harness Engineering 的六大支柱

六大支柱是全文的核心框架。它们分别回答六个问题：

| 支柱 | 核心问题 |
| --- | --- |
| 上下文管理 | AI 应该看到什么？ |
| 工具系统 | AI 能触达和操作什么？ |
| 执行编排 | AI 应按什么顺序完成任务？ |
| 状态与记忆 | AI 应该记住什么？ |
| 评估与观测 | 怎样判断 AI 做得对不对？ |
| 约束与恢复 | AI 不能做什么，失败后怎样恢复？ |

5.1 支柱一：上下文管理（Context Architecture）

上下文管理的目标不是把所有资料一次性塞给 AI，而是构造“渐进式披露”的信息结构。

原文给出的主要手段包括：

| 实践 | 载体 | 作用 |
| --- | --- | --- |
| 渐进式披露 | `AGENTS.md` | 用约 100 行索引告诉 AI 去哪里找详细资料 |
| 结构化规范 | `requirements.md`、`task.md` | 把需求、决策和任务写入 Git |
| 变更隔离 | `changes/` 或独立 Plan 目录 | 把当前变更与存量知识分开 |
| 知识分层 | Skills 按需加载 | 从描述到指令，再到详细步骤逐层加载 |
| 知识挂载 | Wiki、代码库、自定义文件 | 注入业务和技术背景 |
| 代码知识化 | AI Wiki | 根据代码生成项目结构化说明 |

原文强调，不应建立一个几千行的巨型 AGENTS.md。正确方式是让 AGENTS.md 充当目录和导航，把架构、规范、需求、命令和注意事项拆到专门文档中。

#### 解读

这实际上是把软件的信息架构应用到了 AI 上下文。人类开发者也不会每天从头读完整个 Wiki，而是先看目录，再定位相关文档。AI 同样需要这种导航结构。

“仓库是系统记录（System of Record）”是这一支柱的底层原则：重要信息必须可版本化、可检索、可评审，而不能只依赖聊天历史或个人记忆。

5.2 支柱二：工具系统（Tool System）

原文把工具系统概括为三件套：MCP、Skills 和知识库。

#### MCP：连接实时世界

MCP 负责让 AI 读取或操作模型上下文之外的系统：

**·** 数据库 MCP：读取实时 Schema，避免编造表和字段；

**·** 知识库 MCP：访问内部业务文档；

**·** API MCP：查询服务接口；

**·** 运维 MCP：连接 CI/CD、监控、日志和告警。

#### Skills：封装做事方法

Skills 不只是提供信息，而是封装完成某类任务的步骤、模板、前置条件和注意事项。例如：

**·** 内部配置中心接入；

**·** CRUD 代码生成；

**·** 公共中间件集成；

**·** skill-creator 这类生成其他 Skill 的元技能；

**·** 技能搜索和发现。

#### 知识库：提供业务说明

知识库负责告诉 AI 当前系统“是什么”，例如：

**·** 团队 Wiki；

**·** 公共 SDK 代码库；

**·** 项目 AI Wiki；

**·** PRD、设计稿、会议纪要等文件。

原文用了一个很形象的比喻：

MCP 是开门的钥匙，Skills 是开门后做的事，知识库是进门前读的说明书。

#### 解读

三者不能互相替代：

**·** 知识库可能告诉 AI 数据表的业务含义，但不保证 Schema 是最新的；

**·** MCP 可以读取最新 Schema，却不会自动告诉 AI 如何遵循公司接入规范；

**·** Skill 能给出标准步骤，却仍需要 MCP 提供实时数据、知识库提供业务背景。

真正有效的是组合，而不是单项工具数量。

5.3 支柱三：执行编排与多 Agent 协作

原文设计了“3+1 Phase”工作流：

| 阶段 | 核心动作 | 主要产物 | 角色 |
| --- | --- | --- | --- |
| Phase 1：计划 | 澄清需求、生成并审核 Spec | `requirements.md`、`task.md` | Planner + 人工 Review |
| Phase 2：编码 | 加载 Rules、Skills、MCP 实现任务 | 源码、单元测试 | Generator |
| Phase 3：交付 | 合规、逻辑和架构审查 | 可合入 PR | Evaluator |
| Phase 4：沉淀 | 归档 Spec、更新知识 | 历史资产和知识库 | Archiver |

对应四类 Agent：

**·** **Planner：**需求分析、方案设计和任务拆解；

**·** **Generator：**编码和测试；

**·** **Evaluator：**检查规范、逻辑和风险；

**·** **Archiver：**归档变更、更新知识资产。

#### 解读

多 Agent 的价值不在于“同时开很多机器人”，而在于职责分离。生成者不应该独占评价权；计划、实现、评估、归档应采用不同目标和上下文。

每个任务必须有 Acceptance Criteria（验收标准），否则 Evaluator 没有稳定的判断依据。没有验收标准的多 Agent，只是把一段模糊任务在多个模型调用之间传递。

5.4 支柱四：状态与记忆

原文把记忆分为四层：

| 类型 | 实现方式 | 生命周期 |
| --- | --- | --- |
| 短期记忆 | 当前对话上下文 | 单次会话 |
| 中期记忆 | Memories | 跨会话 |
| 长期记忆 | Git 中的 Spec | 项目全生命周期 |
| 变更记忆 | Spec Deltas / Plan 目录 | 单次变更周期 |

#### 解读

这一区分非常重要。个人偏好可以放在 Memories 中，但架构决策、接口约束和业务规则不能只存在于个人 Memories，因为它们需要团队共享、代码评审和版本追踪。

更稳妥的原则是：

**·** **个人习惯**进入 User Rules 或 Memories；

**·** **团队标准**进入 Team Rules；

**·** **项目事实**进入项目仓库；

**·** **当前需求**进入 Spec；

**·** **实时状态**通过 MCP 获取。

5.5 支柱五：评估与观测

原文提出四层验证：

| 层次 | 验证内容 | 典型方式 |
| --- | --- | --- |
| L1 语法 | 编译、格式、Lint | `go build`、`golangci-lint` 等 |
| L2 逻辑 | 功能和边界是否正确 | 单元测试、集成测试 |
| L3 规范 | 是否遵循 Rules | AI 合规审查、静态检查 |
| L4 架构 | 是否破坏既有设计 | 人工与 AI 联合审查 |

#### 解读

“能编译”只是最低层，不代表逻辑正确；“测试通过”也不代表符合架构约束。四层验证需要分开看，避免把一个绿色构建结果误认为全部质量保障。

其中适合机器确定性执行的检查，应尽量落到编译器、Lint、测试和脚本；涉及业务权衡与架构方向的判断，仍需人工参与。

5.6 支柱六：约束与恢复

原文给出了三级约束：

**·** **硬性红线（Rules）：**不可违反，例如 Controller 不写业务逻辑、接口必须有文档注解、查询必须经过 Repository；

**·** **软性约束（Skills）：**推荐流程，例如优先复用既有工具类、使用统一日志模板；

**·** **安全策略（Safety）：**高风险操作兜底，例如数据库变更先生成 SQL、重要操作先备份、自动检测影响范围。

恢复机制包括 Git 全量管理、变更记录可追溯、编译失败后的回滚等。

#### 解读

约束必须分级。把所有建议都写成“必须”会让规范失去可执行性；把所有规则都写成“建议”又无法形成质量底线。

同时，真正成熟的 Harness 不只会阻止错误，还应支持恢复。AI 会犯错是系统假设，而不是意外事件。因此必须提前设计：怎样发现、怎样停止、怎样回滚、怎样记录原因。

### 六、AI Coding 一体化架构：它是一条闭环，不是一条流水线

原文在第二章进一步给出分层架构。综合文章描述，可以表示为：

...mermaid

flowchart TB

A[输入层Spec / 自然语言 / 代码上下文]

B[配置中心Rules / Skills / Docs / Commands / Memories]

C[模式引擎Plan 模式 / Agent 模式]

D[Agent 核心生成 / 审查 / 测试 / 重构]

E[MCP 层DB / API / Wiki / CI-CD / Monitor]

F[输出层代码 / 测试 / 文档 / 日志]

G[度量层AI 代码占比 / 交付量 / Bug 率]

A --> B --> C --> D

D <--> E

D --> F --> G

G -.反馈和改进.-> B

最关键的一条箭头是从度量层回到配置中心。Rules 和 Skills 不应一次写完后永久不变，而要根据实际结果持续调整。

例如：

**·** AI 多次生成 N+1 查询，就在 Rules 和 Review Checklist 中增加对应检查；

**·** 某类接入反复出错，就沉淀为业务 Skill；

**·** AI 经常误解某个业务概念，就补充知识库或调整 AGENTS.md 索引；

**·** 某个 MCP 使用率低但消耗大量 Token，就降低优先级或移除。

这意味着 Harness 不是一组静态配置，而是研发治理系统。

### 七、三阶段落地路线：先建立底线，再接工具，最后形成飞轮

原文建议渐进式实施：

| 阶段 | 周期 | 目标 | 核心产出 |
| --- | --- | --- | --- |
| 第一阶段：基础建设 | 1～2 周 | 全员能使用 AI Coding，并有基本约束 | 工具安装、团队 Harness 仓库、基础 Rules、知识库 |
| 第二阶段：工具接入 | 2～4 周 | 接入 MCP、沉淀 Skills、跑通 Spec 驱动开发 | MCP、Skills、Plan/Agent 工作流 |
| 第三阶段：持续优化 | 持续 | 用度量推动规范和知识演进 | 审计、看板、规范迭代、知识飞轮 |

解读

这个顺序非常合理：先有规则和记录，再增加 AI 的权限和工具。如果一开始就接入大量 MCP，而团队尚未建立安全边界、评审流程和变更记录，AI 只会更快地制造不可控变更。

更适合企业的做法，是先选择 1～2 个风险可控、反馈周期短的试点项目，而不是一次全员铺开。

### 八、第一阶段：基础建设的具体内容

8.1 工具安装与模型选择

原文以 CodeBuddy IDE 插件和 CLI 为例，说明 VS Code、JetBrains 与内部 CLI 的安装方式，并强调 CLI 需要 Node.js 20+。

模型选择策略可以概括为：

**·** 复杂编码可以考虑能力更强的外部模型；

**·** 敏感业务优先使用内部部署模型；

**·** 无法判断时使用自动模型选择。

原文明确提醒：外部模型可能发送代码上下文到外部服务。对企业来说，这不是简单的“模型偏好”，而是数据分级和合规决策。

建议补充的治理动作：

**·** 建立代码和数据敏感等级；

**·** 明确每个等级允许使用的模型；

**·** 记录模型调用、上下文范围和操作日志；

**·** 对密钥、个人信息和生产数据做自动脱敏；

**·** 对外部模型设置仓库和目录级访问边界。

8.2 Memories 与 Commands

原文建议用 Memories 记录稳定的个人或项目偏好，例如技术栈、注释语言、命名方式、统一响应封装等；同时配置 /init、/pre-mr-checklist、/spec-create、/spec-plan 等常用 Command。

需要注意：重要的项目约束不应只放在 Memories。Memories 适合辅助，不适合充当团队唯一事实源。

8.3 建立 `team-harness` 仓库

原文给出的目录思路如下：

...text

team-harness/

├── rules/

│   ├── global/

│   ├── golang/

│   ├── python/

│   └── frontend/

├── skills/

│   ├── common/

│   └── business/

├── templates/

│   ├── AGENTS.md

│   └── project.md

├── docs/

│   └── onboarding.md

└── README.md

并通过同步脚本或 CI，把团队规范同步到业务仓库的 .codebuddy/ 目录。

#### 解读

这一设计的价值在于把 AI 配置从个人电脑中移到团队 Git：

**·** 有版本；

**·** 有 Review；

**·** 可回滚；

**·** 可分支；

**·** 可比较不同版本效果；

**·** 新成员可以快速获得同一套起点。

为了避免同步脚本覆盖项目特定规则，实际落地时建议区分：

**·** team-managed/：团队统一管理，不允许项目直接修改；

**·** project-owned/：项目自定义；

**·** 冲突时明确优先级；

**·** 同步时输出变更清单并保留版本号。

8.4 三层 Rules

原文把 Rules 分为：

| 层级 | 作用域 | 典型内容 |
| --- | --- | --- |
| User Rules | 个人所有项目 | 个人偏好、交互方式 |
| Team Rules | 团队项目 | 统一编码、安全和协作底线 |
| Project Rules | 单个项目 | 项目架构、目录、业务约束 |

文章提供的规则示例覆盖：

**·** 分层架构；

**·** Controller 不写业务逻辑；

**·** 数据查询经过 Repository；

**·** API 文档注解；

**·** 函数和命名规范；

**·** error 必须显式处理；

**·** 单函数长度限制；

**·** SQL 变更使用脚本；

**·** 敏感配置进入配置中心；

**·** 最小变更原则；

**·** 优先复用现有模块；

**·** 新功能需要单元测试。

#### 解读

规则应该尽可能满足三个条件：

**·** **具体：**“代码要优雅”无法执行，“Controller 不包含业务判断”可以检查；

**·** **可验证：**最好能映射到静态检查、测试或审查项；

**·** **有层级：**区分不可违反、默认建议和例外流程。

规则还应有负责人和更新周期，否则很容易出现文章第八章所说的“写完半年不维护”。

8.5 `AGENTS.md` 的正确定位

原文建议将 AGENTS.md 控制在约 100 行，主要包含：

**·** 项目概述；

**·** 架构和目录；

**·** 常用命令；

**·** 当前需求或文档索引；

**·** 关键注意事项；

**·** 详细规则的链接。

它应该是目录，不是百科全书。

一个有效的 AGENTS.md 不追求“信息最多”，而追求“让 AI 最快找到正确资料”。

8.6 知识库

原文推荐挂载四类知识：

| 类型 | 内容 | 优先级示例 |
| --- | --- | --- |
| 团队 Wiki | 架构、接口、业务、技术方案 | P0 |
| 核心代码库 | 公共 SDK、中间件、框架源码 | P0 |
| 业务资料 | PRD、设计稿、会议纪要 | P1 |
| AI Wiki / 运维手册 | 项目结构、部署、监控、故障处理 | P1～P2 |

验收标准不是“知识库已创建”，而是“团队成员提出具体业务问题时，AI 能引用正确资料回答”。这体现了文章一贯的结果导向。

### 九、第二阶段：工具接入和 Spec 驱动开发

9.1 MCP：只在实时性或外部能力确有价值时接入

原文没有鼓励“接得越多越好”，反而提出明确判断：

**·** 纯逻辑推理、普通代码生成不一定需要 MCP；

**·** 如果直接 API 调用更简单，就不必引入 MCP；

**·** MCP 带来的复杂度大于收益时，不要使用。

文章介绍了 stdio、streamable-http 和逐步淘汰的 sse 等配置方式，并提醒：

**·** 超时单位是毫秒；

**·** 参数数组需要正确拆分；

**·** MCP 通常只在 Agent 模式生效；

**·** 密钥不能硬编码；

**·** 连接后必须用真实任务验证，而不是只看配置文件存在。

推荐接入顺序是：

**·** P0：数据库 MCP、代码协作平台 MCP；

**·** P1：Wiki、需求管理 MCP；

**·** P2：CI/CD、监控和运维 MCP。

#### 解读

MCP 是能力和风险的共同放大器。接入前应明确：

**·** 只读还是可写；

**·** 可访问哪些环境；

**·** 是否允许操作生产；

**·** 调用是否留痕；

**·** 凭证生命周期；

**·** 失败时是否有幂等和回滚机制。

默认只读、最小权限、环境隔离和人工确认，应成为企业 MCP 的基础策略。

9.2 Knot 平台与团队共享

原文以 Knot 为例，介绍智能体、知识库、MCP 市场、Rules 市场和 Skills 等模块，并说明可以通过网页、机器人、API、CLI、流水线和定时任务使用。

这里的关键不是某个平台本身，而是“团队统一发布和共享”的能力。只有当 Rules、Skills、知识库和 Agent 配置能够统一治理，Harness 才能从个人效率工具升级为组织能力。

9.3 SubAgent：把职责和上下文打包

文章建议构建需求分析、架构设计、数据库、Code Review、运维排障等专用子智能体。每个智能体绑定不同知识库、MCP、Rules 和 Skills。

原文特别强调，SubAgent 的描述同时承担路由规则，因此描述中应写明触发场景。

#### 解读

仅靠自然语言描述进行路由可能出现误调用。企业环境可以进一步增加：

**·** 明确的输入输出 Schema；

**·** 触发条件和排除条件；

**·** 允许调用的工具白名单；

**·** 最大执行范围；

**·** 失败和升级策略；

**·** 关键任务的人工确认点。

9.4 Skills：把重复经验变成可复用能力

原文建议 Skill 至少包含：

**·** name 和 description；

**·** 前置条件；

**·** 操作步骤；

**·** 代码模板；

**·** 注意事项；

**·** 验证方法。

创建流程是：分析现有成功实现，生成 Skill，人工审查，在真实触发语句中验证，再提交到团队仓库。

这比“从零编写最佳实践”更可靠，因为 Skill 应从已经验证过的项目模式中提炼，而不是凭空设计。

9.5 Spec 与 Plan 模式

原文提供了四阶段流程：

**·** 在 Plan 模式描述需求，生成 requirements.md；

**·** 人工检查范围、边界、接口、数据结构、异常和验收标准；

**·** 生成 task.md，切换 Agent 模式逐项实现；

**·** 人工 Review，随后归档 Spec 和变更记录。

文章用“用户操作日志模块”演示了需求、查询、接口和 90 天清理机制等内容如何先进入 Spec，再进入实现。

#### 解读

Spec 驱动不是要求所有需求都写长文档。它的核心是按风险选择合适粒度：

**·** 小于半天、影响局部、无架构变化：可用简短任务说明；

**·** 跨模块、涉及数据结构或接口：需要完整 requirements.md 和 task.md；

**·** 高风险变更：还应增加迁移、回滚、监控和兼容计划。

Spec 的质量决定了 Agent 的上限。需求含糊时，让 AI 立即编码只会把模糊性隐藏进实现。

### 十、日常开发 SOP：把规范带入真实场景

10.1 新需求开发

文章区分简单需求和复杂需求：简单需求可以直接在 Agent 模式处理，但仍必须遵循 Rules；复杂需求应先进入 Plan 和 Spec 流程。

一个可执行的新需求 SOP 可以概括为：

**·** 判断任务规模和风险；

**·** 读取相关 AGENTS.md、Rules 和知识库；

**·** 明确验收标准；

**·** 复杂任务先生成 Spec；

**·** 按任务清单实施；

**·** 编译、测试和规范检查；

**·** AI 辅助 Review；

**·** 人工确认并归档。

10.2 Bug 修复

原文给出三条红线：

**·** 一个 PR 只修一个 Bug；

**·** 必须写出能复现问题的测试；

**·** Commit 使用清晰格式，例如：

...text

fix: [模块名] 修复xxx问题 (#issue编号)

其中“先写复现测试”尤其重要。它把“我觉得修好了”变成“原问题可重复出现，修复后测试通过”，并为后续回归提供保护。

10.3 AI 辅助 Code Review

原文的检查清单覆盖：

| 类别 | 重点 |
| --- | --- |
| 架构 | 分层是否正确，是否复用已有模块 |
| 质量 | error 是否处理，核心逻辑是否有测试 |
| 安全 | SQL 注入、敏感信息硬编码 |
| 性能 | N+1、全表扫描、无界查询 |
| 规范 | Commit 是否清晰，变更是否聚焦 |

AI 可以快速扫描模式性问题，但不应替代人工对业务正确性、架构方向和风险取舍的判断。

### 十一、五条团队协作红线

原文提出五条红线：

**·** **先 Spec 后 Code：**复杂需求不得无方案直接编码；

**·** **Rules 共享：**项目 Rules 必须进入 Git，不能只存在本地；

**·** **Skill 沉淀：**重复、通用的做法应抽象为 Skill；

**·** **MCP 优先：**关键实时元数据优先通过 MCP 获取，避免手工副本过期；

**·** **变更可追溯：**所有变更必须有清晰 Commit 和历史记录。

这五条红线共同指向一个原则：不要让团队关键知识只存在于个人电脑、聊天记录或人的脑中。

### 十二、八类反模式及其根因

| 反模式 | 表面现象 | 深层问题 | 改进方式 |
| --- | --- | --- | --- |
| 巨型 Prompt | 一次输入几千字 | 缺少上下文分层 | Plan + Spec + 按需加载 |
| 跳过审核直接编码 | AI 立刻改文件 | 模糊需求直接进入实现 | 复杂需求先审核 `requirements.md` |
| Rules 长期不维护 | 规范与项目脱节 | 没有规范运营机制 | 月度 Review、负责人制度 |
| MCP 过度接入 | Server 多、Token 高 | 把工具数量当成熟度 | 只保留 P0/P1 和高价值接入 |
| Skill 不原子化 | 一个 Skill 包办所有事 | 难触发、难维护、难组合 | 一个 Skill 解决一类问题 |
| 盲目信任 AI | 不 Review 直接合入 | 把生成能力误当判断能力 | 测试 + AI CR + 人工 CR |
| Chat 历史当文档 | 决策只留在会话 | 信息不可共享、不可追溯 | 持久化到 Git 中的 Spec |
| 一个 PR 改所有 | 多个不相关变更混合 | 难审查、难回滚 | 一 PR 一问题、最小变更 |

这些反模式看似不同，根因其实只有三个：

**·** 没有结构化上下文；

**·** 没有职责和风险边界；

**·** 没有验证与反馈闭环。

### 十三、`harness-audit`：文章最值得借鉴的设计

原文第九章提出用 harness-audit Skill 对项目进行合规性体检。它做三件事：

**·** **打分：**量化当前成熟度；

**·** **诊断：**定位缺项和风险；

**·** **开方：**按优先级给出改进建议。

13.1 七个审计维度

| 维度 | 权重 | 主要检查内容 |
| --- | --- | --- |
| `AGENTS.md` | 15% | 是否存在、是否精炼、是否含必要索引 |
| Rules | 20% | 目录、Frontmatter、架构/风格/安全规则 |
| Skills | 15% | 数量、结构、业务相关性、规范性 |
| MCP | 10% | 配置质量、敏感信息、连接能力 |
| Plan 模式 | 15% | `requirements.md`、`task.md` 和归档 |
| 工程规范 | 15% | 目录分层、README、依赖、`.gitignore` |
| Commit 与协作 | 10% | Commit 格式和变更粒度 |

总分 100，按 S/A/B/C/D 分级。

13.2 示例结果传达了什么

原文示例项目得到 75 分、A 级。其优势是 AGENTS.md 精炼、Rules 较完整、已有业务 Skill、项目目录规范；主要问题是没有 MCP、部分 Commit 过于模糊、Plan 缺少 archive。

文章给出的 Quick Wins 包括：

**·** 约 30 分钟接入数据库 MCP；

**·** 约 5 分钟建立 Plan 归档目录；

**·** 约 20 分钟加入 commit-msg Hook。

这种输出方式比只给总分更有意义，因为它同时给出了投入、收益和优先级。

13.3 最重要的边界：体检不是 KPI

原文明确强调：审计结果是体检，不是绩效指标。

这是非常关键的提醒。一旦把 Harness 得分直接变成绩效指标，团队很可能开始为了分数创建空目录、形式化文档和无价值配置，最终使审计失去真实性。

更合理的指标是：

**·** 高优先级问题关闭率；

**·** AI 引入缺陷率是否下降；

**·** Review 返工次数是否减少；

**·** 从需求到合入的周期是否缩短；

**·** 新成员达到有效产出的时间是否缩短。

13.4 “AI 审计 AI”的可信度问题

harness-audit 很有创新性，但仍存在递归风险：由 AI 判断 AI 工作体系是否合规，可能出现主观或不稳定评分。

建议将审计拆成两类：

**·** **确定性检查：**用脚本或 CI 完成，如 JSON Schema、Frontmatter、目录、敏感信息、Commit 格式、测试状态；

**·** **语义性检查：**由 AI 辅助，如 Rules 是否清晰、Spec 是否覆盖边界、架构描述是否一致；

**·** **最终结论：**由人工 Review 关键风险和例外情况。

### 十四、文章最有价值的五个观点

14.1 规范必须成为工程资产

如果规范只存在于 Wiki 或口头约定中，AI 不一定能稳定读取，更无法自动执行。将其放入 Git、Rules、Skills、CI 和审计流程，规范才真正进入系统。

14.2 仓库应成为长期记忆

聊天记录不是可靠知识库。需求、任务、决策、验收标准和变更结果必须进入仓库，才能支持团队协作和长期维护。

14.3 工具必须组合使用

MCP、Skills、知识库、Rules 各有边界。单独接入某个工具通常只能解决局部问题，组合后才能形成真实工作流。

14.4 生成与评估必须分离

不能因为 AI 能写代码，就默认它也能无偏差地评价自己的结果。Planner、Generator、Evaluator、Archiver 的职责分离，是多 Agent 体系中比“Agent 数量”更重要的设计。

14.5 Harness 必须可观测、可演进

没有审计和反馈，Rules 会过期、Skills 会失效、MCP 会膨胀。Harness 不是一次性建设，而是持续运营的研发基础设施。

### 十五、文章落地时需要补充考虑的难点和边界

15.1 隐私、成本与模型能力的平衡

原文提醒外部模型可能传输代码上下文，但实际落地还需要进一步明确：

**·** 哪些代码可以外发；

**·** 哪些仓库必须使用内部模型；

**·** 上下文是否含生产数据或个人信息；

**·** 模型调用成本如何预算；

**·** 内外部模型能力差异怎样评估。

建议建立按任务类型和数据等级选择模型的策略，而不是由开发者自行判断。

15.2 Rules 冲突和版本治理

当 User、Team、Project 三层 Rules 同时存在时，可能出现冲突。文章没有详细展开优先级、灰度和回滚机制。

建议补充：

**·** 明确优先级和禁止覆盖项；

**·** Rules 使用语义化版本；

**·** 重大变更先在试点仓库验证；

**·** 保留变更日志和效果对比；

**·** 对例外情况建立审批和到期机制。

15.3 多 Agent 交接损耗

从 Planner 到 Generator，再到 Evaluator，每次交接都可能丢失上下文。解决方法不是无限增加 Prompt，而是使用结构化交接物：

**·** 输入范围；

**·** 已确认决策；

**·** 未决问题；

**·** 验收标准；

**·** 修改文件清单；

**·** 测试结果；

**·** 已知风险。

15.4 指标定义仍需细化

原文提出 AI 代码占比、交付量和 Bug 率等度量，但没有给出统一口径。企业真正采用前应定义：

**·** AI 代码占比如何识别，重写后的代码是否计入；

**·** Bug 的观察窗口；

**·** 交付量按 PR、需求还是功能点计算；

**·** 如何避免通过拆 PR 或扩大代码行数“优化”指标。

推荐优先关注结果指标，而不是代码产量：交付周期、缺陷逃逸率、回滚率、Review 返工、测试覆盖和新人上手时间。

15.5 行业合规要求

金融、医疗、政企等场景还需补充：

**·** 模型调用留痕；

**·** 数据跨境和数据驻留；

**·** 代码来源和许可证审查；

**·** 生产操作双人确认；

**·** 高风险变更审批；

**·** 生成内容的责任归属。

### 十六、适合企业研发团队的落地行动清单

16.1 第 0～2 周：建立最小可用 Harness

**·** 选择 1～2 个试点项目；

**·** 明确允许使用的模型和数据边界；

**·** 创建 team-harness 仓库；

**·** 为试点项目编写精炼的 AGENTS.md；

**·** 建立 Global、Security、项目架构三类基础 Rules；

**·** 建立 requirements.md、task.md 和 archive 模板；

**·** 固化编译、Lint、测试命令；

**·** 对项目做第一次 Harness 基线审计；

**·** 记录当前交付周期、Bug 率和 Review 返工基线。

16.2 第 2～6 周：接入高价值工具

**·** 只读方式接入数据库 MCP；

**·** 接入代码平台、需求平台或 Wiki 中最有价值的一项；

**·** 从真实成功案例沉淀 2～3 个原子化 Skills；

**·** 跑通需求分析、编码、Review、归档的 3+1 Phase；

**·** 为 Commit、Frontmatter、敏感信息增加确定性 CI 检查；

**·** 定义 Planner、Generator、Evaluator 的交接格式；

**·** 对照基线复盘效率和质量变化。

16.3 第 6 周以后：形成持续改进机制

**·** 每月 Review Rules 和 Skills；

**·** 清理低使用率、低收益 MCP；

**·** 每季度做项目 Harness 体检，但不作为 KPI；

**·** 建立 Rules 和 Skills 负责人制度；

**·** 把高频 Review 问题转化为自动检查；

**·** 将事故和返工原因反馈到 Rules、Skills、测试或知识库；

**·** 评估新人上手时间是否下降；

**·** 形成跨项目共享的标杆实践。

### 十七、一个可直接采用的最小闭环

如果团队暂时无法一次搭建完整体系，可以先实现下面这个最小闭环：

...mermaid

flowchart LR

A[需求描述] --> B[requirements.md]

B --> C{人工审核}

C -->|不通过| B

C -->|通过| D[task.md]

D --> E[AI 按 Rules/Skills 实现]

E --> F[编译 + Lint + 测试]

F -->|失败| E

F -->|通过| G[AI Review]

G --> H[人工 Review]

H -->|退回| E

H -->|通过| I[合入并归档 Spec]

I --> J[复盘并更新 Rules/Skills]

这个闭环只要求五类基础资产：

**·** 一个精炼的 AGENTS.md；

**·** 一套基础 Rules；

**·** 一个需求与任务模板；

**·** 一组可重复执行的验证命令；

**·** 一个归档与复盘机制。

即使暂时没有复杂 MCP、多 Agent 平台或知识库，这五项也能显著提高 AI Coding 的稳定性。

### 十八、总体评价

这篇文章的最大贡献，不是介绍了多少 AI 工具，而是给出了一个统一的工程解释框架：

**·** 用上下文管理解决“AI 看什么”；

**·** 用工具系统解决“AI 能做什么”；

**·** 用执行编排解决“AI 先做什么、后做什么”；

**·** 用状态与记忆解决“经验怎样留下”；

**·** 用评估与观测解决“结果怎样判断”；

**·** 用约束与恢复解决“出错怎样控制”。

同时，文章没有把 AI 描述成可以取代工程判断的万能工具。它在结尾明确指出：最终质量仍需人来把关。开发者需要知道什么是好代码，能够判断 AI 产出是否足够好，并在关键位置做出正确取舍。

这使全文最终落在一个非常稳健的结论上：

AI 降低了代码执行成本，但没有降低工程质量标准；模型越强，团队越需要把判断、规范和验证写进系统。

文章提出的“让工具适配规范，而不是让个人不断适配工具”，是从个人 AI 辅助走向团队 AI 工程化的关键转折。模型、IDE、Agent 平台都可能快速变化，团队真正需要长期积累的是可迁移的规范、知识、流程和验证能力。

用原文最后的表达概括：

**流水的工具，铁打的规范。**
