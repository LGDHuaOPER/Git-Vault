# 在线评估、护栏与用户反馈信号：实时拦截 bad case

**// **你好，这里是公众号：【ArchSynapse AI】。

第 16、17 讲那套评估，有个共同的前提：**离线**——在数据集上、发布前跑。它回答的是"这一版好不好"。

但离线评估有个躲不掉的**时间差**：等你在数据集上发现问题，那条坏答案早就送到用户手里了。线上此刻正在生成的这一条，离线评估管不着。

这一讲，我们把评估从"事后"搬到"事中"—— **在用户看到之前，就把坏输出拦下来**。靠三样东西：护栏（实时拦）、在线采样评估（抓漂移）、用户反馈（把用户变成免费评委）。

这也是**最小必读路径的第七站、最后一站**。走完它，你的 Agent 就集齐了那三个字：**看得见（观测）、测得准（评估）、拦得住（在线）。**

- ●   ●

| ** 01 ** | ** 离线 vs 在线：一个考试，一个值班 ** |
| --- | --- |

先把两者的分工掰清楚，别重复造轮子：

|  | ** 离线评估（第 16、17 讲） ** ：在固定数据集上、 ** 发布前 ** 跑。像一场 ** 考试 ** ——回答"这一版该不该上线"。批量、可复现，但是事后的。 |
| --- | --- |
|  | ** 在线评估（这一讲） ** ：在 ** 真实流量 ** 上、实时或近实时跑。像 ** 值班 ** ——回答"这一条该不该放出去"、"线上正在悄悄变差吗"。 |

两个都要，因为它们防的是不同的事故：**离线防"发布即翻车"，在线防两件离线够不着的事**——① 单条坏答案实时伤到用户，② 发布之后质量慢慢地烂掉（drift）。

考试再重要，也替代不了值班。我们从最实时的那道防线——护栏——开始。

- ●   ●

| ** 02 ** | ** 护栏（Guardrail）：最廉价的在线评估，能"拦"不只是"报" ** |
| --- | --- |

护栏是在线评估里**最便宜**的一层：对每一条响应，在返回用户**之前**，跑一遍**代码级的检查**（是规则，不是模型），毫秒级、可全量。

检查什么？都是些"一票否决"的硬规则：

|  | 输出 ** 格式/schema ** 合法吗（该返回 JSON 却吐了一段散文）？ |
| --- | --- |
|  | 该带的 ** 引用/来源 ** 带了吗（RAG 场景要求有据）？ |
|  | 有没有泄露 ** 内部信息 ** （系统 prompt、内部字段）？ |
|  | ** 金额、数量 ** 这些关键字段，在合理范围内吗？ |

护栏和离线评估最本质的区别，就一个字：**它能"拦"。** 离线评估只能事后告诉你"这条错了"；护栏因为跑在返回之前，能**直接不让坏答案出门**——拦截、降级、或改写。

- ●  ●  python

```
def guardrail(answer: str) -> tuple[bool, str, str]:
"""返回 (是否放行, 发给用户的内容, 触发的规则名)。
    规则名很重要——否则你只知道"拦了多少",不知道"拦了什么"。"""
ifnot answer.strip():
returnFalse, "抱歉，我没太理解，正在为您转接人工。", "empty_answer"
if mentions_amount(answer) andnot amount_in_valid_range(answer):
returnFalse, "这个问题我需要请人工帮您核实一下。", "amount_out_of_range"# 退款场景要命
# …更多规则:schema、是否含引用、是否泄露内部字段…
returnTrue, answer, ""

def respond(user_msg: str) -> str:
with tracer.start_as_current_span("handle_turn") as span:
        answer = agent(user_msg)
try:
            passed, final, rule = guardrail(answer)
except Exception as e:
# ★ 护栏自己也会坏,而它就站在用户和响应之间——必须明确"坏了怎么办"
#   这里选 fail-open:护栏故障不该拖垮产品,先放行,但留痕告警
            span.set_attribute("guardrail.error", type(e).__name__)
            span.record_exception(e)
return answer            # 高代价场景请改成 fail-closed,见下文
        span.set_attribute("guardrail.passed", passed)              # 护栏结果进 Trace(第10讲)
ifnot passed:
            span.set_attribute("guardrail.action", "blocked")       # 拦了就留痕,好复盘
            span.set_attribute("guardrail.rule", rule)              # 拦在哪条规则上
return final
```

注意三点：

**一是护栏结果要进 Trace**，而且要记**触发了哪条规则**（ `guardrail.rule` ）——只记  `passed`  你就只有一个总数，没法下钻"到底哪条规则在疯狂误伤"。

**二是成本**：规则护栏极便宜（毫秒级），可以全量上；但如果你想用**小模型/LLM 当护栏**（判语义类违规），它就慢了、贵了，**同步跑会拖垮延迟**，得掂量——这笔账也要进第 25 讲的成本核算。

**三是最容易被忽略的一点：护栏自己也会失败，而它此刻正站在关键路径上。** 规则函数可能因为意外格式抛异常，模型护栏更是会超时、会限流。如果不管，结果很讽刺—— **你为了拦住坏答案，把一个本来没问题的回答变成了用户看到的 500**。所以必须明确表态：

|  | ** fail-open（护栏坏了就放行） ** ：保住可用性，代价是那一刻处于"无保护"状态； |
| --- | --- |
|  | ** fail-closed（护栏坏了就拦/转人工） ** ：保住安全，代价是护栏一抽风就大面积伤体验。 |

怎么选？**就用第六节那套"按错误代价定"的框架，只不过这次判的对象是护栏自己**：质量类护栏（格式、语气）选 fail-open，别让一个护栏 bug 拖垮整个产品；高代价护栏（退款金额、隐私泄露）选 fail-closed，宁可多转几次人工，也不能在无保护状态下把钱放出去。**无论选哪个，都要留痕告警**——护栏静默失效，是最危险的一种"看似有防线"。

护栏很强，但它只拦得住"明规则能描述"的违规。那些**说不清、但在慢慢变坏**的呢？

- ●   ●

| ** 03 ** | ** 在线采样评估：专抓"缓慢漂移" ** |
| --- | --- |

有一类问题护栏永远抓不到：**质量的缓慢漂移（drift）。** 比如你换了个知识库版本、或模型供应商悄悄更新了，幻觉率从 3% 温水煮青蛙式地爬到 8%——每一条都没违反硬规则，护栏全放行，可整体质量在烂。

抓它的办法，是**在线采样评估**：对线上流量**抽样**（比如 1%），**异步**跑第 17 讲那个**校准过的 LLM-as-Judge**，产出一条持续的质量信号——每天的幻觉率、任务完成率曲线。

两个关键词：

|  | ** 抽样 ** ：全量跑 Judge 太贵（它自己烧 token），1% 足够看出趋势； |
| --- | --- |
|  | ** 异步 ** ：它不挡在用户和响应之间，不加一毫秒延迟——它的任务不是"拦这一条"，而是"盯整体趋势"。 |

它产出的，正是第 8 讲那些**趋势类指标**的数据来源。价值在于：**让你在用户大规模投诉之前，先从曲线上看到"这周幻觉率比上周高了 2 个点"**，把温水里的青蛙提前捞出来。护栏管"这一条"，采样评估管"这一片"。

- ●   ●

| ** 04 ** | ** 用户反馈：最便宜、最真实的一群评委 ** |
| --- | --- |

前面两道都是你自己在评。但别忘了，你还有一群**免费、且最真实**的评委—— **用户自己**。他们无时无刻不在给你信号：

|  | 显式的：👍 / 👎、评分； |
| --- | --- |
|  | 隐式的、其实更值钱的： ** 追问 ** （"我不是这个意思"）、 ** 转人工 ** 、 ** 重复提问 ** 、立刻离开。 |

**这一讲最该你动手做的一件事，就是把这些反馈信号，和对应的 Trace / Session 关联起来**——让"这通对话被点踩了"和"这通对话的完整链路"能对上。

**但这里有个时序上的硬约束，必须先讲清楚**，否则你会走进死胡同：用户点踩发生在响应之后**几十秒甚至几分钟**，那时候那条 Span 早就  `end()`  并且**已经导出走了**。而**已导出的 Span 是改不了的**——你没有任何 API 能回头给它补一个属性。（这正是第 15 讲讨论"点踩为什么没法参与采样决策"时提到的同一个时序问题。）

所以正确的做法不是"改 Span"，而是**按**  `trace_id`  **做关联**，两条路：

- ●  ●  python

```
# 前提:响应时必须把 trace_id 透出给前端,让反馈能带着它回来
def on_user_feedback(trace_id: str, session_id: str, signal: str):
# 路径一(推荐):调观测平台的"反馈/评分"接口,由服务端把它挂到已存在的 Trace 上
#   Langfuse / Phoenix / LangSmith 这类平台都提供按 trace_id 附加 score/feedback 的 API
    obs_platform.add_score(trace_id=trace_id, name="user_feedback", value=signal)

# 路径二:存进你自己的库,以 trace_id / session_id 为键,查询分析时再和 Trace 数据 join
    feedback_store.save(trace_id=trace_id, session_id=session_id, signal=signal)
```

一旦关联上，好处是连锁的：被点踩的 case 能**一键拉出 Trace 做归因**（第 13 讲）、能**自动沉淀进回归集**（第 16 讲）、能**喂给评估驱动开发的飞轮**（第 19 讲）。用户的每一次不满，都不再白白流失，而是变成让系统变好的燃料。

但记住第 8 讲那句"单个信号会骗人"：用户反馈**有噪声**（误点、纯情绪、手滑），它是**信号，不是真相**。别拿单个点踩就去改 prompt，要结合量级和其他信号一起看。

- ●   ●

| ** 05 ** | ** 三道防线怎么摆在一起 ** |
| --- | --- |

把这一讲的三样东西，拼成一套完整的在线防御部署，各司其职、互不干扰：

用户请求 → Agent 产出回答

### 护栏检查 同步 毫秒级 全量 挡在用户之前

通过放行

|  | 不通过 拦截 / 降级 / 转人工 |
| --- | --- |

### 返回用户

在线采样评估异步抽样 1%

跑校准过的 LLM-as-Judge → 质量曲线 / 漂移告警

|  | 用户反馈 事件驱动 用户 👎 / 转人工 → 按 trace_id 关联 → 进回归集 / 喂 EDD 飞轮 |
| --- | --- |

三道防线的分工，一句话记牢：**护栏管"这一条"（实时硬拦），采样评估管"这一片"（趋势预警），用户反馈管"喂飞轮"（真实信号）。** 它们分别对应第 2 讲失败家族里不同的应对姿态——有的错要当场拦死，有的错要盯趋势，有的错要收集起来慢慢改。

- ●   ●

| ** 06 ** | ** 护栏该"拦"还是"标"？——一道必须业务一起拍的题 ** |
| --- | --- |

还有一个问题绕不过去：护栏发现一条可疑输出，该**拦截**（block），还是只**标记**（flag）放行？

两条路各有代价：

|  | ** 拦截 ** ：坏答案出不去了，但代价是 ** 可能误伤 ** ——把本来没问题的答案也拦了，或降级成"转人工"伤了体验。 |
| --- | --- |
|  | ** 标记 ** ：体验不受影响，但代价是 ** 坏答案还是送到了用户面前 ** ，你只是"知道了"。 |

**怎么选，取决于这个错的代价**：

|  | ** 高代价错 ** （退款金额算错、泄露隐私、合规违规）→ ** 宁可误伤也要拦 ** 。用户被多转一次人工，远比真退错一笔钱轻。 |
| --- | --- |
|  | ** 低代价错 ** （语气略生硬、格式小瑕疵）→ ** 标记就好 ** ，别为了小错牺牲全体验。 |

看出来了吗？这又是第 8 讲"体验 vs 健康"、第 17 讲"假阴 vs 假阳"那个权衡的第三次现身—— **同一套取舍逻辑，换个场景又来了。**

而"谁来决定"，答案很明确：**不该是工程师一个人拍脑袋。** 每一类错的容忍度（该拦还是该标、误伤率能接受多少），得**业务、风控一起定**——因为拦错了伤体验、放错了担风险，这两头的账，都不是工程师一个人背得动的。

最后划一道边界：这一讲护栏管的是**质量类**违规（格式、编造、越界）。而"有没有人在**攻击**你的 Agent"（提示注入、越狱）属于**安全类**——它同样在返回前拦，但机理和目标完全不同，是第 26 讲的正题。**别把质量护栏和安全护栏混成一锅**，它们该分开设计、分开值守。

- ●   ●

| ** ✓ ** | ** 小结 ** |
| --- | --- |

这一讲，我们把评估从"事后"搬到了"事中"：

| ** 1 ** | ** 离线 vs 在线 ** ：离线是考试（发布前防翻车），在线是值班（实时拦坏答案 + 抓漂移）——都要。 |
| --- | --- |
| ** 2 ** | ** 护栏 ** ：最廉价的在线评估，代码级检查、返回前跑，能"拦"不只是"报"；结果（含触发的规则名）进 Trace；模型护栏慎用同步； ** 还要给"护栏自己坏了"表态——fail-open 还是 fail-closed ** 。 |
| ** 3 ** | ** 在线采样评估 ** ：抽样 + 异步跑校准过的 Judge，专抓护栏够不着的"缓慢漂移"，喂第 8 讲的趋势曲线。 |
| ** 4 ** | ** 用户反馈 ** ：最真实的免费评委，关键是 ** 按 **  `trace_id`  ** 把反馈关联到 Trace ** （Span 已导出、改不了，得走平台反馈接口或自建库 join），让它喂归因、喂回归集、喂 EDD 飞轮——但它是信号不是真相。 |
| ** 5 ** | ** 拦还是标 ** ：按错误代价定，高代价拦、低代价标；而且是业务/风控一起拍，不是工程独断。 |

到这里，**最小必读路径的七站全部走完了**（1、2、3、4、10、11、18）——你的 Agent 已经看得见、测得准、拦得住。恭喜！剩下的都是"锦上添花、把体系做扎实"：下一讲（第 19 讲）我们讲**评估驱动开发（EDD）**，把这一讲收集到的用户反馈、badcase，真正变成"系统越用越准"的自动飞轮——评估篇的所有线头，将在那一讲收成一个闭环。
