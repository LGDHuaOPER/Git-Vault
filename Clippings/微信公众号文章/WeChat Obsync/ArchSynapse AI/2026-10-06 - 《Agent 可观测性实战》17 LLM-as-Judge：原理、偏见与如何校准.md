# LLM-as-Judge：原理、偏见与如何校准

**// **你好，这里是公众号：【ArchSynapse AI】。

第 16 讲那个评估脚本里，我留了个占位：

- ●  ●  python

```
# ok &= judge(answer, case)   # 占位,下一讲填上
```

"关键词在不在"用  `in`  就能判，可"这答案**有没有编造**"、"语气**得不得体**"、"**答得好不好**"——这些需要**理解语义**的维度，规则判不了。这一讲，我们就把  `judge()`  填上：请一个大模型来当裁判，也就是 **LLM-as-Judge**。

但先把丑话说在前面，这也是第 9 讲就埋下的警告：**这个裁判，它自己也是个会看走眼的非确定系统。** 一个没校准过的裁判给你的分数，你根本不敢信——那等于第 2 讲说的"用一个非确定系统去调试另一个非确定系统"，不确定性只会叠加。所以这一讲的重头，不在"怎么用"，而在最后那个大多数团队都跳过的动作：**怎么校准出一个你敢信的裁判。**

- ●   ●

| ** 01 ** | ** LLM-as-Judge：把"人才能判的题"变得可规模化 ** |
| --- | --- |

规则判分（第 16 讲的  `in` ）只能回答"格式对不对、关键词在不在"。可你真正关心的质量维度——有据性、语气、任务是否达成——全是**需要理解语义**的判断题，规则束手无策。人工能判，但慢、贵、扛不住线上一天上万条。

LLM-as-Judge 就是那个中间解：**让另一个大模型，读"输入 + 输出（+ 参考资料）"，按你给的标准打分或判对错。** 它把"只有人能判的语义题"变得**可自动化、可规模化**。

最典型的用法，正是第 13 讲那个"忠实性幻觉"的批量版：让 Judge **逐句抽取回答里的事实主张，再逐条去召回文档里找依据，找不到的就判为幻觉**。第 13 讲你靠人眼一条条断案，现在 Judge 帮你把它跑到全量——这就是第 13 讲结尾说的"Trace 出物证、评估做批量审判"落了地。

那这个"裁判"具体怎么写？

- ●   ●

| ** 02 ** | ** 一个可复用的 Judge 模板 ** |
| --- | --- |

先给你一个能直接改用的模板。别急着看代码，**它的每一处设计都是为了对抗 Judge 的不靠谱**：

- ●  ●  python

```
import json, re

JUDGE_PROMPT = """你是严格的质检员。判断【回答】是否**完全基于【参考资料】**,有没有编造。

【用户问题】{question}
【参考资料】{context}
【回答】{answer}

评判规则:
1. 回答里每一条事实性陈述,都必须能在参考资料中找到依据;
2. 只要有一处内容超出资料、或凭空编造,即判 unfaithful;
3. 语气、格式、详略,都不在本次评判范围内(只看"有没有编")。

请先逐条列出回答中的事实陈述,并各自标注"有依据 / 无依据",最后再下结论。
只输出 JSON:{{"reason": "逐条分析...", "verdict": "faithful 或 unfaithful"}}"""

def parse_judge_output(text: str) -> dict:
"""裁判的输出不一定是干净 JSON：可能裹着 ```json 围栏、带一句客套话。
    所以先剥壳再解析,解析不了就返回显式失败态——绝不让它抛出去炸掉整轮评估。"""
    t = re.sub(r"^```(?:json)?|```$", "", text.strip(), flags=re.M).strip()
    m = re.search(r"\{.*\}", t, re.S)               # 兜底:从文本里抠出最外层 JSON
try:
return json.loads(m.group() if m else t)
except (json.JSONDecodeError, AttributeError):
return {"verdict": "judge_failed", "reason": f"裁判输出无法解析: {text[:200]}"}

def judge_groundedness(question: str, context: str, answer: str) -> dict:
with tracer.start_as_current_span("llm_judge groundedness") as span:   # 裁判也要埋点!见第五节
        resp = judge_client.chat.completions.create(
            model="<和被评模型不同家族的模型>",     # 对抗"自我偏好",见第三节
            temperature=0,                          # 判分要可复现,别让裁判自己也飘
            response_format={"type": "json_object"},# 从源头约束成 JSON(兼容接口普遍支持)
            messages=[{"role": "user",
"content": JUDGE_PROMPT.format(question=question, context=context, answer=answer)}],
        )
        result = parse_judge_output(resp.choices[0].message.content)
        span.set_attribute("judge.verdict", result["verdict"])
return result
```

四个关键设计，逐一说：

|  | ** 给明确的评判规则（rubric），别只说"好不好" ** ：模糊的标准 = 飘忽的分数。你把"什么算编造、什么不算"写死到什么程度，裁判就稳到什么程度。 |
| --- | --- |
|  | ** 先讲理由，再下结论 ** ：让它先逐条分析、最后才给 verdict（这就是给裁判上"思维链"）。直接让它蹦一个结论，它会草率；逼它先摆证据，判得明显更准，还顺带给了你可核查的依据。 ### ⚠️ 这里藏着一个 改坏了还不报错 的细节：这个好处 完全依赖  `reason`  排在  `verdict`  前面 。模型是顺序生成 token 的——先写  `reason`  ，推理才真正发生在下结论之前。一旦有人图顺眼把它调成  `{"verdict": ..., "reason": ...}`  ，模型就变成 先蹦结论、再为结论编理由 （事后合理化），准确率悄悄下滑，而 JSON 照样合法、代码照样跑。 字段顺序就是思维链的顺序，别随手调换。 |
|  | ** 结构化输出（JSON），但一定要容错 ** ：  `verdict`  +  `reason`  ，程序好解析，  `reason`  还能留证据。不过别指望裁判永远吐干净 JSON——它可能裹一层 ```  `json`  围栏、加句客套话，甚至输出截断。所以①用  `response_format`  从源头约束，②再加一层剥壳解析兜底。 ** 关键是解析失败时返回 **  `judge_failed`  ** 这个显式失败态，而不是把异常抛出去 ** ——否则你批量评估几千条，一条格式跑偏就中断整轮，跑了半小时全白费。（这个失败率本身也是第五节要观测的指标。） |
|  | ** 用离散结论，别用 1–10 打分 ** ：LLM 打细粒度分数极不稳定（同一条今天 7 分明天 8 分）。二元（faithful / unfaithful）或三档（好/中/差）的一致性，远高于十分制。 |

还有两个藏在代码里的要点，第三、五节展开：**裁判用不同家族的模型**（ `model=` ）、**裁判本身也要埋点**（那个  `start_as_current_span` ）。

- ●   ●

| ** 03 ** | ** 裁判有偏见：它会系统性地骗你 ** |
| --- | --- |

LLM-as-Judge 不是个中立的法官，它带着**系统性偏见**。你不知道它往哪偏，就会被它系统性地误导。三个最有名的，务必记住：

|  | ** 位置偏见（Position Bias） ** ：让它比较"A 和 B 哪个好"时，它会莫名偏爱排在前面（或后面）的那个，跟内容无关。 ** 对策 ** ：两个顺序各评一次，只取两次一致的结果；或随机化顺序再统计。 |
| --- | --- |
|  | ** 长度偏见（Verbosity Bias） ** ：它倾向于认为 ** 更长、更啰嗦 ** 的回答更好，哪怕啰嗦的那个其实在灌水。 ** 对策 ** ：在 rubric 里明确"简洁不扣分、啰嗦不加分"，把这条偏见摁住。 |
|  | ** 自我偏好（Self-preference） ** ：模型会 ** 偏爱自己（或同家族模型） ** 生成的输出。 ** 对策 ** ：这就是第二节让你"裁判用不同家族模型"的原因——别用 GPT 评 GPT、用 DeepSeek 评 DeepSeek，容易护短。 |

一句话：**裁判是有立场的证人。** 你得知道它的立场，才能在设计时把这些偏见一条条摁下去。但就算你全摁了，你怎么知道摁干净了没有？——这就逼出了本讲最关键的一步。

- ●   ●

| ** 04 ** | ** 校准：你到底凭什么，敢信这个裁判？ ** |
| --- | --- |

这是全讲的灵魂，也是**绝大多数团队直接跳过、然后栽跟头**的一步。

第 9 讲我提出过"裁判评得准吗"这个问题，当时没给答案。现在我把答案总结成一句话，请你记在心上：**未经人工验证的裁判分，等于上线未测试的代码。** 你不能默认 Judge 是对的——它跟你的 Agent 一样，是个会犯错的非确定系统。**你花大力气给 Agent 建评估，结果却闭着眼睛相信那个评估 Agent 的裁判——这不荒谬吗？**

所以，裁判上岗前，必须**先考核它**。这个考核，就叫校准，五步：

| ** 1 ** | ** 建一个"人工金标"集 ** ：挑 100~200 条真实样本，让人（最好是懂业务的人）严格标好正确答案（faithful / unfaithful）。这是你的 ** 标准答案（ground truth） ** 。 |  |
| --- | --- | --- |
| ** 2 ** | ** 让 Judge 也评这一批 ** ：拿它的判定，和人工标签逐条比。 |  |
| ** 3 ** | ** 算一致性，而且别只看一个准确率数字 ** ：要看 ** 混淆矩阵 ** ——尤其分清两类错： | ** 假阴性 ** （人工说是幻觉，Judge 却放过了）：漏网之鱼，在安全/合规场景 ** 最致命 ** ； |
|  | ** 假阳性 ** （人工说没事，Judge 却误判有问题）：误伤，会让你白忙活去查好案例。 哪类错更不能忍，取决于你的业务——但你 ** 必须知道它们各是多少 ** （一致性指标可以用 Cohen's kappa 这类，比"准确率"更抗类别不均衡）。 |  |

**4**

**不达标就迭代裁判**：改 rubric、补几个 few-shot 示例（把它判错的那些喂回去当例子），重新跑校准，直到一致性到你能接受的水平。

**5**

**达标才敢上岗，且要定期复校**：模型会更新、线上数据会漂移，今天校准好的裁判，三个月后可能就飘了。所以**定期抽样重校**，别一劳永逸。

这里有个**极易混淆、我必须挑明**的点：**校准用的"人工金标集"，和第 16 讲那个"评估集"是两码事。**

|  | 第 16 讲的评估集，是拿来 ** 评你的系统 ** 的（系统输出 vs 期望）； |
| --- | --- |
|  | 这一讲的人工金标集，是拿来 ** 考你的裁判 ** 的（裁判判定 vs 人工判定）。 |

一个考学生，一个考监考老师。**别拿同一批数据、同一个动作把两件事混着做**——你会既没考准学生、也没验对老师。

- ●   ●

| ** 05 ** | ** 把校准做成循环，并观测你的裁判 ** |
| --- | --- |

把上面五步收成一个**可复用的校准循环**，贴在你的评估流程里：

- ●  ●

```
造人工金标集 → Judge 评同一批 → 比对(看混淆矩阵/kappa)
     ↑                                      │
     └──── 改 rubric / 补 few-shot ←── 不达标 ┘
                                       └ 达标 → 裁判上岗 → 定期抽样复校
```

最后留一个有意思的回旋，也是第二节代码里那个  `start_as_current_span("llm_judge ...")`  的用意：**你的裁判，本身也是一次 LLM 调用——它也要被观测。**

它有成本（评估一天上万条，裁判自己也在烧 token，这笔账要进第 25 讲的成本核算）、有延迟、也会调用失败、还可能输出不合法的 JSON。所以请把裁判也当成一等的被观测对象，给它埋点、进 Trace。**这是个漂亮的闭环：你用可观测性去观测 Agent，也要用它，去观测那个替你评判 Agent 的裁判。** 谁来监督监督者？——可观测性。

- ●   ●

| ** ✓ ** | ** 小结 ** |
| --- | --- |

这一讲，我们把那个占位的  `judge()`  填成了一个**你敢信**的裁判：

| ** 1 ** | ** LLM-as-Judge 是什么 ** ：让大模型按 rubric 判语义题，把"只有人能判"变得可规模化——第 13 讲的人眼断案，就此跑到全量。 |
| --- | --- |
| ** 2 ** | ** 模板四要点 ** ：明确 rubric、先理由后结论（  `reason`  必须排在  `verdict`  前）、结构化输出 ** 并容错 ** （解析失败返回  `judge_failed`  ，别炸掉整轮）、用离散结论别用十分制。 |
| ** 3 ** | ** 三大偏见 ** ：位置、长度、自我偏好——裁判是有立场的证人，设计时逐条摁下去（尤其"裁判用不同家族模型"）。 |
| ** 4 ** | ** 校准是灵魂 ** ：未经人工验证的裁判分 = 未测试的代码；用人工金标集考核裁判，看混淆矩阵、分清假阴/假阳，不达标就迭代，达标也要定期复校。 |
| ** 5 ** | ** 金标集 ≠ 评估集 ** ：一个考学生（系统），一个考老师（裁判），别混。 |
| ** 6 ** | ** 裁判也要被观测 ** ：它自己是一次有成本、会失败的 LLM 调用——用可观测性监督监督者。 |

有了校准过的裁判，你就有了一个能规模化、可信赖的"质量传感器"。下一讲，我们把它从"事后离线评估"搬到"事中在线拦截"—— **在线评估、护栏与用户反馈信号**：怎么在用户看到坏输出**之前**就把它拦下来。这是最小必读路径的最后一站。

| ** ? ** | ** 思考题 ** |
| --- | --- |

| ** 1 ** | 本讲最想问你的那句： ** 你的 Judge 和人工判断的一致性，到底有多高？你测过吗？ ** 我打赌很多团队的答案是"没测过、直接信了"。如果你正好是——今天就挑 50 条线上样本，人工标一遍、Judge 评一遍，算算一致性。这个数字，很可能会让你重新看待你之前所有的"评估结论"。 |
| --- | --- |
| ** 2 ** | 顺着第四节想一个权衡：对你的 ** 退款场景 ** ，是"假阴性"（放过了一个不该退的幻觉判断）更可怕，还是"假阳性"（误拦了一个本该正常的回答）更可怕？你会把裁判的 rubric 往哪个方向调松/调严？（提示：这跟你的业务是"怕错放"还是"怕误伤"直接相关。） |
