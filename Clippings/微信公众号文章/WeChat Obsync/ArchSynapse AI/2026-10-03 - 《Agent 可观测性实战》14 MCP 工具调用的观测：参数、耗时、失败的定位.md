# MCP / 工具调用的观测：参数、耗时、失败的定位

**// **你好，这里是公众号：【ArchSynapse AI】。

第 13 讲我们把 RAG 那条"检索 vs 生成"的锅分清了。但 Agent 跟外部世界打交道，检索只是其中一种；更常见、也更容易出事的，是**工具调用**——查订单、查物流、发起退款。

工具是 Agent 的"手脚"，是它伸向真实世界的接口。可也正因为伸到了外面，它成了整条链路上**最容易"背刺"你的一环**：接口会超时、会限流、会返回脏数据、会悄悄改字段。这一讲，我们就把工具调用彻底盯死，尤其是那个能动真金白银的退款写操作。

- ●   ●

| ** 01 ** | ** 工具为什么最容易"背刺" ** |
| --- | --- |

回到第 2 讲的四大不确定性，工具调用是其中独立的一条。原因就俩字：**外部**。工具连着的是你控制不了的世界——第三方 API、数据库、别的团队的服务，它们什么时候超时、什么时候返回个空、什么时候偷偷改了返回格式，都不由你。

但真正致命的，是第 2 讲那个"工具失败未兜底"：**Agent 常常不把工具的失败当回事。** 工具返回了个空结果、一个错误码，它不会停下来，而是**煞有介事地基于这坨"空气"继续编答案**。于是一个上游的小毛病，被 Agent 放大成一个理直气壮的错误回复。

所以工具观测的目标很明确：**让每一次工具调用的入参、出参、耗时、成败，都无所遁形**——尤其是那些"没抛异常、但其实已经失败"的调用。

- ●   ●

| ** 02 ** | ** 工具 Span 到底该记什么 ** |
| --- | --- |

第 11 讲我们写过一个最简版的  `call_tool` 。这一讲把它加厚，补上真正救命的几样：

- ●  ●  python

```
import requests, httpx

# 错误分类用一小组"自己定义的固定值"，面板才聚合得起来（见第六节）
TIMEOUT_ERRORS = (TimeoutError, requests.exceptions.Timeout, httpx.TimeoutException)

def call_tool(name: str, args: dict, is_write: bool = False):
with tracer.start_as_current_span(f"execute_tool {name}") as span:
        span.set_attribute("gen_ai.tool.name", name)                       # 第 6 讲标准命名
# 注意：入参/出参很可能含手机号、地址、金额等 PII，
#      生产环境务必先按第 15 讲的办法脱敏，再往观测后端写
        span.set_attribute("app.tool.arguments", json.dumps(args, ensure_ascii=False))
        span.set_attribute("app.tool.is_write", is_write)                  # 读/写标记，见第三节
try:
            result = TOOLS[name](**args)
            span.set_attribute("app.tool.result",
                               json.dumps(result, ensure_ascii=False)[:1000])
# ★ 最关键的一步：工具"返回了" ≠ "成功了"
#   空结果、业务错误码这类"语义失败"不会抛异常，必须主动标出来
if is_semantic_failure(result):
                span.set_attribute("app.tool.semantic_error", True)
                span.set_status(Status(StatusCode.ERROR, "工具返回空/错误码，但未抛异常"))
return result
except TIMEOUT_ERRORS as e:
            span.set_attribute("app.tool.error_type", "timeout")           # 归一化成固定值
            span.set_status(Status(StatusCode.ERROR, str(e)))
            span.record_exception(e)
raise
except Exception as e:
            span.set_attribute("app.tool.error_type", classify(e))         # 限流/参数/上游/其他
            span.set_status(Status(StatusCode.ERROR, str(e)))
            span.record_exception(e)
raise
```

四个要点，逐一说：

|  | ** 入参 + 出参 ** ：排查"参数拼错"（订单号填成了用户 ID）和"结果误用"，全靠这两样原文。 |
| --- | --- |
|  | ** 耗时 ** ：Span 自带（起止时间一减），不用你操心——但它是第五节排障的主角。 |
|  | ** 错误分类（ ** `error_type` ** ） ** ：别只标一个笼统的  `ERROR`  。是超时、限流，还是参数错、业务错误码？分好类，你才能在面板上看出"这个工具到底怎么个不靠谱法"。这里有个 ** 很容易踩的坑 ** ：Python 内置的  `TimeoutError`  抓不到  `requests`  /  `httpx`  抛出的超时（它们抛的是各自库的异常类），所以要像上面那样把它们一起纳进来。更要紧的是——  `error_type` ** 请用你自己定义的一小组固定值 ** （  `timeout`  /  `rate_limit`  /  `bad_request`  /  `upstream_error`  …），别图省事直接塞  `type(e).__name__`  ：否则同一种超时会散成  `Timeout`  、  `ConnectTimeout`  、  `ReadTimeout`  好几个名字，第六节那张面板就永远聚不成一行。 |
|  | ** 语义失败（ ** `semantic_error` ** ） ** ：这是 ** 最容易漏、也最该记 ** 的一条。工具没抛异常、HTTP 也是 200，但返回的是空数组或  `{"code": -1}`  ——这在业务上就是失败。你不主动把它标成  `ERROR`  ，它就是第 2 讲那个"静默失败"，会一路骗过你的告警。 |

- ●   ●

| ** 03 ** | ** 读 vs 写：两类工具，观测重点截然不同 ** |
| --- | --- |

第 5 讲切 Span 时我们就区分过"读工具"和"写工具"。到了观测落地，这个区分**必须**贯彻，因为它俩的风险根本不是一个量级。

**读工具（如**  `query_order` **、** `query_logistics` **）**：无副作用。观测重点是**延迟、成功率、结果质量**。它错了顶多"查不到 / 查错了"，可以重试、可以降级，天塌不下来。

**写工具（如**  `issue_refund` **）**：有副作用，动的是真金白银。它错一次就是**事故**，而且**不能简单重试**——重试一次可能就是重复退款。所以写工具的观测重点，从"性能"转向了**留痕、幂等、审计**。它的 Span 要额外记这些：

- ●  ●  python

```
def issue_refund(order_id, amount, *, reason, idempotency_key, decided_by):
with tracer.start_as_current_span("execute_tool issue_refund") as span:
        span.set_attribute("gen_ai.tool.name", "issue_refund")
        span.set_attribute("app.tool.is_write", True)
        span.set_attribute("app.refund.order_id", order_id)
        span.set_attribute("app.refund.amount", amount)
        span.set_attribute("app.refund.reason", reason)             # 决策依据：为什么退这笔
        span.set_attribute("app.refund.idempotency_key", idempotency_key)  # 幂等键：防重复退
        span.set_attribute("app.refund.decided_by", decided_by)     # 谁授权/哪个 Agent 发起
# …执行退款…
```

看到  `reason` 、 `idempotency_key` 、 `decided_by`  这几个字段了吗？它们回答的是审计三问：**为什么退、会不会重复退、谁让退的。** 这不只是排障用，更是**合规和事后追溯**的硬要求——一旦出现纠纷或误退，这条 Span 就是你的"操作记录"。

这里我先埋个明确的钩子：写工具是整个系统**安全风险最高**的面。针对它的提示注入、越权调用怎么观测、怎么告警，是第 26 讲安全那一讲的正题。而你今天记下的这些审计字段，正是那一讲要用的原料—— **又一次，观测在前，能力在后。**

- ●   ●

| ** 04 ** | ** MCP 工作流：别让它变成链路上的黑盒 ** |
| --- | --- |

现在越来越多团队用 **MCP（Model Context Protocol）** 来接工具——它把"Agent 怎么调外部工具/服务"标准化了。好处是解耦、通用，但它给你的链路**多插了一跳**：

- ●  ●

```
Agent → MCP Client → MCP Server → 真正的工具/API
```

这一跳很容易变成观测盲区。因为 **MCP Server 常常是个独立进程**（甚至独立服务），你的 Agent 进程里那套 Span 上下文，默认传不过去——结果就是：Agent 侧看到"调了个 MCP 工具"，然后线索就断了，工具那头到底发生了什么，一片漆黑。

解法你其实已经会了，就是第 12 讲那套**跨进程传播**：在 MCP Client 发起调用时  `inject`  把 traceparent 塞进去，在 MCP Server 侧  `extract`  出来接上。把这一跳纳入 Trace 后，你才能看清：是哪个 MCP Server、哪个 tool、在协议层还是在底层 API 出的错。

**一句话：MCP 让工具调用标准化了，但你得主动把它这一跳"焊"进链路，别让标准协议变成链路上的黑盒断点。**

- ●   ●

| ** 05 ** | ** 一个真实味道的排障案例：慢在"算"，还是慢在"等"？ ** |
| --- | --- |

讲个把前面几讲的观测能力串起来用的案例——它的原型在国内团队里很常见。

**告警响了**：某功能 P95 延迟从 0.9s 飙到 8s。第一反应，很多人会甩锅给模型："大模型今天又抽风了。"

但你打开这条慢 Trace 的瀑布图，故事完全不同：

invoke_agent ……总耗时 8.1s

### chat 调用自建 DeepSeek 模型 …… 耗时 7.9s ← 慢在这

等待（排队 + 网络）7.1s ⚠️

|  | 实际推理 0.8s |
| --- | --- |

关键在于：如果你**把"等待"和"实际推理"拆开记了**，你会一眼看到——慢的不是"算"（推理只花了 0.8s，和平时一样），而是"等"（排队等了 7.1s）。根因根本不在模型、也不在 Agent 逻辑，而是**自建推理服务的并发被打满，请求在排队**。修法也就清楚了：扩容、限流、或优化排队调度，跟模型和 prompt 一点关系没有。

**但这个拆分怎么来？这里必须说清楚，否则你会无从下手。** 站在 Agent 这一侧，你能测到的只有"发出请求→收到响应"这一整段 7.9s—— **客户端根本无法知道其中多少在排队、多少在推理**。要拿到这个拆分，只有两条路：

| ** 1 ** | ** 让推理服务也进链路 ** （推荐）：用第 12 讲那套  `inject`  /  `extract`  ，把 traceparent 一路传到自建推理服务里，由 ** 服务端自己开 Span ** 分别记"排队"和"推理"两段。这样瀑布图上那个缩进层级才真实存在—— ** 这一跳不焊进链路，你连"慢在算还是慢在等"都分不出来。 ** |
| --- | --- |
| ** 2 ** | ** 让服务端把耗时回传 ** ：推理服务在响应头或响应体里带上  `queue_time`  、  `inference_time`  （vLLM 这类推理框架本身就暴露这类指标），客户端取到后写成 Span 属性，比如  `app.llm.queue_ms`  /  `app.llm.infer_ms`  。改造量小，适合你没法给推理服务加埋点的场景。 |

这个案例的价值，不在于结论，而在于那个**动作**：**因为 Span 把耗时拆解开了，你才能区分"慢在算"还是"慢在等"。** 没有这层拆解，你只会对着模型一通瞎调，白白浪费一晚上。（阿里云就公开分享过一个几乎一模一样的真实案例——AI 网关发现自建 DeepSeek 耗时异常，最终追踪定位到是推理请求排队所致。）

| ** 06 ** | ** 落点：工具健康面板怎么设计 ** |
| --- | --- |

把这一讲的观测数据聚起来，就是一张**按工具聚合**的健康面板。它是第 8 讲那套"分层大盘"往工具这一层的下钻：

| 工具 | 读/写 | 调用量 | 成功率 | P95 耗时 | 主要失败 |
| --- | --- | --- | --- | --- | --- |
|  `query_order`  | 读 | 12,400 | 99.2% | 95ms | 超时 0.5% |
|  `query_logistics`  | 读 | 8,100 | 97.0% | 180ms | 脏数据 2% ← 可疑 |
|  `issue_refund`  | 写 ⚠️ | 320 | 98.7% | 240ms | 余额不足 |

### 写操作审计 ：  `issue_refund`  每笔留痕（依据 / 幂等键 / 授权），可追溯。

这张面板一摆，几件事立刻浮现：

|  |  `query_logistics`  的成功率只有 97%、且 2% 是"脏数据"——这就是第 2 讲说的 ** 不可靠工具 ** ，该去找上游算账，或给它加一层校验/降级。 |
| --- | --- |
|  |  `issue_refund`  单独挂了一个 ** 写操作审计视图 ** ——每一笔退款都能追溯到"依据、幂等键、授权者"，这是读工具不需要、写工具必须有的。 |
|  | 每个数字都能继续下钻到具体的 Trace（第 4 讲的链路）——面板拉警报，Trace 去破案，老搭档了。 |

| ** ✓ ** | ** 小结 ** |
| --- | --- |

这一讲，我们把工具这个"最容易背刺"的环节盯死了：

| ** 1 ** | ** 工具为什么危险 ** ：它连着不可控的外部世界，而 Agent 常常"不把工具失败当回事"，把上游小毛病放大成理直气壮的错误。 |
| --- | --- |
| ** 2 ** | ** 工具 Span 记四样 ** ：入参、出参、耗时、（分类的）成败；最容易漏的是 ** 语义失败 ** ——返回了但其实失败了，必须主动标  `ERROR`  。 |
| ** 3 ** | ** 读 vs 写重点不同 ** ：读工具盯性能与质量；写工具盯留痕、幂等、审计（  `reason`  /  `idempotency_key`  /  `decided_by`  ），也为第 26 讲安全埋了点。 |
| ** 4 ** | ** MCP 别成黑盒 ** ：多出的"MCP Server"那一跳，用第 12 讲的跨进程传播焊进链路。 |
| ** 5 ** | ** 排障靠拆解 ** ：把"等待 vs 实际推理"拆开记，才能分清"慢在算还是慢在等"，不再盲目怪模型。 |

实战篇只剩最后一块拼图了。前面几讲我们一路在"记原文、记入参、记召回文档"——可这些原文里，塞满了手机号、订单地址、支付信息。**把它们原样送进观测后端，在国内就是合规红线。** 下一讲，我们就正面解决这个从第 3 讲一路绷到现在的弦：**合规地记录上下文——脱敏、采样与数据保留。**
