# Span 怎么切：LLM 调用 / Agent 推理 / 工具 / 检索的建模

**// **你好，这里是公众号：【ArchSynapse AI】。

第 4 讲我们把 Span 定义成"观测的最小积木"，还轻描淡写地说"一次 LLM 调用是一个 Span，一次工具调用是一个 Span"。

但真到你手上，事情没那么简单。**"哪些操作该独立成一个 Span、每个 Span 该记什么、粒度切到多细"——这不是照抄定义就能会的，它是一门直接决定你观测质量的手艺活。** 切得太粗，瀑布图上一坨黑箱，你还是不知道"在哪一步歪的"；切得太细，Span 数量爆炸，存储成本和性能一起崩。

这一讲，就把这门手艺讲透。我们先给 Span 分"工种"。

- ●   ●

| ** 01 ** | ** 先给 Span 分工种：常见的 Span 类型 ** |
| --- | --- |

为什么要先分类型？因为**不同工种的 Span，要记的东西天差地别**——一个 LLM 调用要记 token 和 prompt，一个检索要记命中文档和相似度，你不可能用一套字段套所有。而且成熟的观测平台，正是**靠 Span 的"类型"来做 AI 感知的可视化**：它一看这是个 Retriever Span，就知道该把召回文档排出来给你看。

行业里这套"工种"划分，主要来自 **OpenInference** 的  `span.kind` （这是一套建立在 OpenTelemetry 之上、专为 AI 应用设计的语义约定，正式的属性命名我们放到第 7 讲介绍，这里先建立建模直觉）。常见的有这么几类，我用电商客服系统给你对上号：

|  | ** LLM ** ：一次大模型调用。如"判断用户意图"、"生成最终回复"。 |
| --- | --- |
|  | ** Tool ** ：一次工具/函数调用。如"查订单状态"、"发起退款"。 |
|  | ** Retriever ** ：一次检索。如"从知识库检索退款政策"。 |
|  | ** Reranker ** ：对检索候选做重排。 |
|  | ** Embedding ** ：把文本转成向量。 |
|  | ** Agent ** ：一个能自主决策的智能体单元。如"主 Agent 编排"、"退款子 Agent 决策"。 |
|  | ** Chain ** ：一段 ** 固定编排 ** 的流程打包（区别于 Agent 的"自主决策"）。 |

记住这套工种，因为下一节的"记什么"，是严格按工种来的。

- ●   ●

| ** 02 ** | ** 每类 Span 该记什么：一张对照表 ** |
| --- | --- |

这是本讲的第一个核心交付。把它当成你设计埋点时的"字段清单"：

| Span 类型 | 电商客服里的例子 | 该记的关键属性 | 语义 |
| --- | --- | --- | --- |
| ** LLM ** | 意图判断、生成回复 | 模型名、输入 messages、输出 completion、输入/输出 token、温度等参数、结束原因 | 推理 |
| ** Tool ** | 查订单、发起退款 | 工具名、入参、返回值、状态（OK/ERROR/超时）、耗时 | 执行 |
| ** Retriever ** | 检索退款政策 | query、命中文档（ID + 片段）、每篇相似度分、召回条数 | 执行 |
| ** Reranker ** | 对候选文档重排 | 输入候选、重排后顺序、重排分 | 执行 |
| ** Embedding ** | 把 query 向量化 | 输入文本、模型、向量维度 | 执行 |
| ** Agent ** | 主 Agent 编排、退款子 Agent 决策 | Agent 标识、输入目标、输出决策、下挂的子步骤 | 推理（决策/编排） |
| ** Chain ** | 一段固定流程的打包 | 这段的整体输入 / 输出 | 视内容而定 |

两个提醒：

**第一，"该记什么"里最值钱的，往往是输入输出的原文。** LLM Span 里的 prompt/completion、Retriever Span 里命中的文档片段——这些才是你日后归因"幻觉是检索错还是生成错"（第 13 讲）的关键证据。**但正因为值钱，它们也最敏感**：里面常混着手机号、地址、支付信息。所以"记原文"和"脱敏"必须成对出现，这根弦第 15 讲会专门收紧。

**第二，别忘了记"状态"。** 尤其是 Tool Span——工具超时、返回空、报错，都要如实标成  `ERROR`  并挂上原因。第 2 讲那个高发的"工具失败未兜底"（Agent 拿着空结果硬编），你能不能抓到，全看这个状态字段有没有记对。

- ●   ●

| ** 03 ** | ** 粒度的艺术：切太粗 vs 切太细 ** |
| --- | --- |

知道了工种和字段，真正考验手艺的问题来了：**到底切多细？**

我们看两个极端。

**切太粗的团队**，喜欢把一整次 Agent 循环塞进一个 Span，把中间发生的一切拼成一大坨 JSON 塞进属性里。结果？瀑布图上就孤零零一根横条，你想知道"是检索慢还是生成慢"、"在哪一步开始跑偏"，对不起，全糊在那坨 JSON 里—— **这等于把 Trace 退化回了第 3 讲说的 Logs，第一公民的价值荡然无存。**

**切太细的团队**，走向另一个极端：每一次字符串拼接、每一个  `if`  判断、每一次变量赋值都建一个 Span。结果 Span 数量爆炸，一次简单对话上千个 Span，瀑布图淹没在噪音里根本没法看，存储成本飙升，埋点本身还拖慢了 Agent 性能。

那黄金准则是什么？我给你一句话，贴工位上：

一个 Span = 一个你将来会想"单独提问"的操作单元。

怎么判断"会不会单独提问"？就问三件事：这一步，你将来会不会想**单独看它的耗时**？会不会想**单独判断它成没成功**？会不会想**单独看它的输入输出**？—— **三个只要有一个"会"，就该给它独立建 Span；一个都不会，就别建。**

按这条准则，经验法则很清晰：

|  | ** 一定要独立成 Span ** ：LLM 调用、工具调用、检索、重排。因为它们正是耗时、成本、失败的高发点，也是归因的关键节点。 |
| --- | --- |
|  | ** 不必单独建 Span ** ：纯内存的字符串处理、格式化、简单的数据搬运。它们不耗时、不会失败、你也不会单独去看——顶多作为父 Span 的一个属性或事件记一笔。 |

这条准则也顺手回答了本讲思考题的一半：一次工具调用失败、连着重试了好几次，你会怎么切？——因为你**将来一定会想分别看"每一次分别为什么失败、各花了多久"**，所以它们值得各自成 Span。具体切法（几个 Span、什么父子关系）我留到思考题，你先用这条准则推推看。

- ●   ●

| ** 04 ** | ** 一个被忽略的关键标注：这一步，是"想"还是"做"？ ** |
| --- | --- |

上面那张表最右列，我埋了一个字段：**语义——推理，还是执行？** 现在专门讲它，因为它是排障时最省时间的一刀。

Agent 的每个 Span，本质上不是"在想"就是"在做"：

|  | ** 推理 / 规划（想） ** ：模型在思考、在决策。对应 LLM Span、Agent 的编排与决策 Span。 |
| --- | --- |
|  | ** 执行 / 行动（做） ** ：调工具、检索、写操作。对应 Tool、Retriever Span。 |

为什么非要标它？因为它直接决定你**往哪个方向查**。回到第 2 讲的失败家族：

|  | "意图误解"、"规划绕路"是 ** 想错了 ** ——根因在 prompt、在模型、在上下文，改工具没用； |
| --- | --- |
|  | "工具用错"、"失败未兜底"是 ** 做错了 ** ——根因在工具接口、在参数、在外部服务，改 prompt 没用。 |

线上出问题时，如果你的 Span 上清清楚楚标着"想/做"，你第一眼就能**把问题分流**到正确的战场，而不是对着 prompt 和接口两头瞎猜。这个小小的标注，能帮你省下大量的"猜错方向"的时间。

（实现上，"想/做"既可以直接体现在 span.kind 上——LLM/Agent 天然偏"想"、Tool/Retriever 天然偏"做"，也可以额外打一个自定义属性显式标注，看你团队习惯。）

- ●   ●

| ** 05 ** | ** 落到实处：退款那一轮的 Span 切分方案 ** |
| --- | --- |

把这一讲的四节，全部落到我们的贯穿案例上。还是"用户要退款"这一轮，一个**切得恰到好处**的 Span 树长这样（小标签里是工种和语义，灰字是该记的关键属性）：

主AgentAgent想(编排)

goal="处理用户退款请求"

### 意图识别 LLM 想 in=用户消息 · out=intent:退款 · tokens=48/12

### 查订单 Tool 做 in=order_id · out=状态:已签收 · 95ms · OK

### 退款子Agent Agent 想(决策) goal="判断并执行退款"

检索退款政策Retriever做

query="签收后能退吗" · 命中[政策v2 0.82]

|  | 判断是否符合规则 LLM 想 out=可退 · 依据=政策v2第3条 · tokens=520/30 |
| --- | --- |

|  | 发起退款(写!) Tool 做 ⚠️高风险 in=order_id, amount · out=success · 220ms |
| --- | --- |

### 汇总生成回复 LLM 想 tokens=610/180

对着这棵树，你能立刻体会到前四节的价值：

| ** 1 ** | ** 工种分明 ** ：一眼看清哪些是模型在想（LLM/Agent）、哪些是在跟外部世界打交道（Tool/Retriever）。 |
| --- | --- |
| ** 2 ** | ** 粒度恰当 ** ：整轮共 8 个 Span（2 层 Agent、3 次 LLM、2 次工具、1 次检索）各自成 Span，中间的字符串拼接没有污染视图。 |
| ** 3 ** | ** 想/做清晰 ** ：万一这次退款批错了，你顺着"做"的 Span（查订单→发起退款）查执行，顺着"想"的 Span（判断规则那次 LLM）查决策依据，五分钟分流完毕。 |
| ** 4 ** | ** 高风险可见 ** ：那个标了 ⚠️ 的"发起退款(写!)" Span，就是我们从开篇就盯着的安全靶区——它的入参、依据、结果都留了痕，等到第 26 讲做安全审计时，直接就能用上。 |

**这棵树，就是你在实战篇（第 10 讲起）真正要用代码"长"出来的东西。** 今天先把设计想清楚，动手时就不会乱。

- ●   ●

| ** ✓ ** | ** 小结 ** |
| --- | --- |

这一讲讲的是 Span 建模这门手艺：

| ** 1 ** | ** 先分工种 ** ：LLM / Tool / Retriever / Reranker / Embedding / Agent / Chain——类型不同，记的属性不同，平台的可视化也依赖它（工种来自 OpenInference，正式标准见第 7 讲）。 |
| --- | --- |
| ** 2 ** | ** 按工种记属性 ** ：那张对照表是你的字段清单；最值钱的是输入输出原文（也最需脱敏），最易漏的是"状态"字段。 |
| ** 3 ** | ** 粒度黄金准则 ** ：一个 Span = 一个你将来会"单独提问"的操作单元；LLM/工具/检索必独立，纯内存处理不必。 |
| ** 4 ** | ** 标注"想 / 做" ** ：让排障时能一眼把问题分流到"改 prompt"还是"查接口"两个战场。 |

原理篇讲到这，我们已经能把一次 Agent 执行，建模成一棵结构清晰、属性得当的 Span 树了。但你可能已经注意到：我一直在说"该记模型名"、"该记 token"、"该记工具名"—— **这些字段到底该叫什么名字？** 是  `model`  还是  `llm.model_name`  还是  `gen_ai.request.model` ？

字段命名看似琐碎，却直接决定你的数据能不能被各家平台认得、换工具时要不要推倒重来。下一讲（第 6 讲），我们就来啃这块硬骨头：**OpenTelemetry GenAI 语义约定**—— `gen_ai.*`  到底约定了什么。
