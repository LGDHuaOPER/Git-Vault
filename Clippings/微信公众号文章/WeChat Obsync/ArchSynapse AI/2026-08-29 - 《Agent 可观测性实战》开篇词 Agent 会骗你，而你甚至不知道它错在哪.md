# Agent 会骗你，而你甚至不知道它错在哪

**// **你好，这里是公众号：【ArchSynapse AI】。

先给你讲一个真事的"变体"——细节我做了脱敏，但每一个做过 Agent 上线的人，大概率都遇到过它的某个版本。

一个电商客服 Agent，上线三周，运行平稳。某天下午，一位用户问："我这个订单还能退吗？"Agent 回答得体、语气专业，还贴心地补了一句：

### "您的订单符合我们的『7 天无理由退款延长至 30 天』活动，现在申请仍在有效期内。"

用户很高兴，截图，申请退款。问题是—— **这个"30 天活动"根本不存在。** 是 Agent 自己"脑补"出来的。更糟的是，这还不是偶然抽风：**同样的问法，它几乎每次都这么答，只是一直没人发现**——等到运营察觉，已经有几十个用户拿着同样的截图来要说法了。

现在请你打开那一刻的监控大盘，猜猜你会看到什么？

延迟正常，错误率 0，没有任何异常堆栈，接口全是干干净净的 200。你的 APM、你的日志、你的告警系统，**从头到尾都觉得一切安好**。

这就是 Agent 时代最让人脊背发凉的地方：**它出错的时候，不会报错。**

- ●   ●

| ** 01 ** | ** 你的监控没瞎，它只是在看错的东西 ** |
| --- | --- |

这里先澄清一个误会，免得我们一开始就跑偏：**可观测性不是 Agent 时代才发明的东西。**

恰恰相反，它是一门在传统分布式系统里已经非常成熟的学问。Metrics、Logs、Traces "三大支柱"，Jaeger、Zipkin 这样的分布式追踪，乃至我们后面会大量用到的 OpenTelemetry 本身—— **都诞生在微服务、云原生的世界里，而不是 AI 的世界里。** 一个像样的后端团队，早就有一整套可观测性体系了。

所以问题不是"传统后端没有可观测性、Agent 才需要它"。问题是—— **当你把这套现成的体系对准 Agent，它突然看不见你最想看的东西了。**

为什么？两件事同时变了。

**第一，故障的『长相』变了。**

传统系统出故障是"显式"的、会举手的：抛异常、返回 500、超时、进程挂掉。我们这代后端工程师被训练出的条件反射就是——报错即失败，不报错即正常，大盘绿着就能安心下班。

可 Agent 的失败往往不是崩溃，而是**一本正经地给出一个错误答案**。这种失败有个专门的说法，叫 **静默失败（quiet failure）**：系统在线、接口 200、指标全绿，但输出是错的。它之所以"静默"，是因为 Agent 本就是**概率式**的（同一句话问两遍可能走两条路）、**多步**的（一步歪了后面全歪）、**状态依赖**的（第 5 轮的翻车，根子可能埋在第 2 轮）——错误在链路内部悄悄发生，却不会在任何一个环节触发"报错"。开头那句"30 天活动"就是典型：从基础设施的角度看，**什么都没坏。**

**第二，你盯着看的『信号』错了。**

你现有的可观测性体系，盯的是基础设施和服务层：CPU、内存、QPS、延迟、错误率。这些对 Agent 依然有用，但 Agent 的"对不对"根本不住在这些指标里——它住在 **prompt、模型输出、工具调用的参数与返回、检索到的文档、每一步的推理决策**里。而这些，恰恰是那套为基础设施设计的观测体系**默认不采集**的。

所以，你的监控没瞎。它只是在**看错的层**——盯着机房的仪表盘，却指望它告诉你楼上那位住户说了什么谎。

| ** 02 ** | ** Agent 需要的，是被"重新设计"过的可观测性 ** |
| --- | --- |

既然可观测性本身不是新东西，那这门专栏到底讲什么新东西？

讲的是：**怎么把这套成熟的方法，重新设计、扩展到 Agent 的语境里去。**

顺带厘清一组常被混淆的概念—— **监控（Monitoring）和可观测性（Observability）**。它俩在传统后端里就并存，并不是"传统只有监控、Agent 才有可观测性"：

|  | ** 监控 ** 回答" ** 有没有 ** 出问题"：错误率超没超阈值、延迟高不高，面向你预先设定好要盯的指标； |
| --- | --- |
|  | ** 可观测性 ** 回答" ** 为什么 ** 出问题、 ** 在哪一步 ** "：让你能对系统提出 ** 事先没预设过 ** 的问题，靠的是足够丰富的过程数据，尤其是链路 Trace。 |

这组区分在微服务时代就成立。Agent 时代真正的变化，是可观测性要采集的**内容**被大大扩展了——除了传统三大支柱，还要覆盖：每一次 LLM 调用的 prompt / completion / token 用量；每一次工具调用的入参、返回、耗时；多步推理的完整链路与多智能体调用关系；以及三个 Agent 时代才凸显的新维度—— **质量（答案好不好）、成本（这次花了多少钱）、安全（有没有被攻击）**。

回到开头那个退款乌龙。**做过这层扩展**的团队，能把那次对话完整"回放"出来：看到 Agent 检索知识库命中了哪几篇文档、把哪段上下文喂给了模型、模型在哪一步开始"发挥"。问题从"玄学"变成"案发现场"，五分钟定位。

**没做的团队**呢？就算配齐全套 APM，也只能眼睁睁看着大盘一片绿，靠用户投诉倒推，在"用非确定系统调试非确定系统"的泥潭里越陷越深。

这，正是这门专栏要一步步带你补上的东西。

- ●   ●

| ** 03 ** | ** 这门专栏，我想和你约定三件事 ** |
| --- | --- |

市面上讲 AI Agent 可观测性的材料不少，但要么停在"三大支柱是 Metrics、Logs、Traces"的名词科普，要么是某个工具的软文。我想做的不一样。开篇，我先和你约定三件事：

**第一，不灌名词，只走工程路径。**

我们会拿一个贯穿全程的真实项目——一套**电商客服多智能体系统**——从"裸奔"状态开始，一讲一讲地给它装上眼睛：先是第一条能看的 Trace，然后是多步 Agent 的全链路追踪、多轮会话的 Session 归因、RAG 的幻觉溯源、工具调用的定位，再到评估、成本、安全、告警。**每一讲都有可复制、能跑通的代码，而不是漂亮的示意图。**

这套示例系统长这样，请你先记住它，后面每一讲都会用到：

|  | ** 客服主 Agent（Supervisor） ** ：理解用户意图，编排下面的子 Agent，汇总最终回复； |
| --- | --- |
|  | ** 订单查询子 Agent ** ：调订单/物流 API，属于"读"操作，相对安全； |
|  | ** 退款子 Agent ** ：要判断金额和规则，属于"写"操作，是 ** 高风险环节 ** （也是后面安全那一讲的重点靶区——开头那个乌龙就出在这里）； |
|  | ** RAG 知识库 ** ：回答政策、商品问题，是 ** 幻觉高发区 ** 。 |

多轮会话、多智能体协作、读/写工具、RAG、甚至对抗性输入——一套系统全占齐了。它踩过的每一个坑，大概率也是你会踩的。

**第二，进阶为主，但地基我会补。**

这门专栏面向有一定后端或算法背景、已经在做 LLM 应用的工程师，也照顾架构师和技术负责人关心的体系设计与选型。原理与标准（比如 OpenTelemetry 的 GenAI 语义约定）我会讲透，但不会假设你是可观测性专家——Trace、Span、Session 这些地基，我会用最省力的方式帮你补上。

**第三，标准中立，不绑架你的技术栈。**

心智模型、数据模型和标准跨语言、跨框架通用；动手代码以 Python + OpenTelemetry SDK 为主，但走的是 OTel 标准 API，迁到 Java、Go 并不难，关键处我会给对照。用 Dify、Coze、百炼这类低代码/云平台的读者，手动埋点章节需结合平台自带能力来看，其余照样适用。

| ** 04 ** | ** 怎么读这门专栏 ** |
| --- | --- |

全专栏 6 个模块、29 讲，从"为什么"一路讲到"怎么落地、怎么经营"。你不一定要从头啃到尾。

**如果你正在救火，只想尽快把可观测性跑起来**，先走这条**最小必读路径**（7 讲）：

### 第 1 讲（为什么）→ 第 2 讲（失败模式）→ 第 3 讲（三支柱 + 全景）→ 第 4 讲（Trace/Span/Session）→ 第 10 讲（第一条 Trace）→ 第 11 讲（多步 Agent 追踪）→ 第 18 讲（在线护栏）。

跟完这 7 讲，你手里的 Agent 会具备：一条从用户请求到最终响应、可回放的**全链路 Trace**；按对话（**Session**）归因、能定位"第几轮、哪个子 Agent、哪个工具"出问题的能力；以及一道在用户看到之前就能**实时拦截坏输出的线上护栏**。从"裸奔"到"看得见、拦得住"，最快一周。

**如果你想系统建设**，就跟着模块顺序走：认知篇解决"想明白"，原理篇解决"懂标准"，实战篇解决"埋得上"，评估篇解决"测得准"，平台篇解决"选得对"，进阶篇解决"经营好"。

需要提醒的是：同一个主题（比如幻觉、成本、安全）会在不同深度反复出现——这不是重复，而是**螺旋式递进**。幻觉在第 8/9 讲先给量化口径，在第 13 讲做溯源，在评估篇用 Judge 打分；安全从第 3 讲立为支柱，到第 26 讲成体系。原理篇建立概念，实战与进阶篇层层落地，正文会用"详见第 X 讲"把它们串起来。

| ** 05 ** | ** 结语：从"能观测"到"会经营" ** |
| --- | --- |

我常说一句话：**可观测性不是给 Agent 装监控，它是 Agent 工程化的基础设施。**

一个看不见内部的 Agent，你没法评估它、没法优化它、没法信任它，更没法把它交给业务去扛真金白银。而当你能看清它的每一步、量化它的好坏、守住安全和成本的底线，你的 AI 应用才算真正从"能跑的 Demo"，走向"可经营的产品"。

开头那个退款乌龙，会是我们贯穿全程的反面教材。到专栏结束时，我希望你不仅能一眼看穿它错在哪，还能在它发生之前就把它拦下来。

那么，我们从最根本的一个问题开始——

**为什么偏偏是 Agent，把"可观测性"从锦上添花，逼成了不做不行的刚需？**
