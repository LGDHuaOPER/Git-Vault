# 从"能跑"到"可信"：Agent 为什么把可观测性推上刚需

**// **你好，这里是公众号：【ArchSynapse AI】。

开篇词结尾，我抛给你一个问题：**为什么偏偏是 Agent，把"可观测性"从锦上添花，逼成了不做不行的刚需？** 这一讲就来正面回答它。

答案，藏在一个几乎所有团队都经历过的落差里—— **你的 Agent"能跑"，离它"能被信任"，中间隔着一条又深又宽的鸿沟。而可观测性，就是填平这条鸿沟的第一铲土。**

我们先把这条鸿沟看清楚。

- ●   ●

| ** 01 ** | ** Demo 五次全过，上线为什么就翻车 ** |
| --- | --- |

你一定有过这样的经历。

做 Agent 的时候，你在本地反复调试，跑了五次、十次，效果拔群，于是信心满满地上线。结果没几天，用户的奇葩反馈就来了：答非所问的、一本正经胡说的、该调工具不调的、调了工具又没用对结果的……

问题出在哪？不是你的 Agent 变笨了，而是**样本量变了**。

Demo 阶段你跑 10 次，就算有 2% 的出错率，你大概率一次都碰不上。可上线之后，它一天要跑 5 万次——那 2% 就是**每天 1000 次翻车**。更麻烦的是，这 1000 次里的大多数，不会给你报错，只会安安静静地给用户一个错误答案，然后被淹没在"一切正常"的绿色大盘里。

Demo 看的是"能不能跑通一次"，生产要的是"跑一万次里有几次会坑我、坑在哪"。**前者叫『能跑』，后者叫『能信任』。** 这门专栏，本质上就是在教你怎么把 Agent 从前者推到后者。

要理解为什么这件事在 Agent 身上格外难，我们得做两个对比。

- ●   ●

| ** 02 ** | ** 对比一：Agent 和传统微服务，根本不是一个物种 ** |
| --- | --- |

我们太习惯用调试微服务的经验来对付 Agent 了，可它俩的"故障基因"完全不同。

**传统微服务是确定性的。** 同样的输入，永远给同样的输出；它出故障的方式是"显式"的——抛异常、返回非 200、超时、OOM。这些故障有一个共同点：**它们会主动举手告诉你"我坏了"。** 于是你的告警能抓到、日志能记下、trace 能标红——这类显式故障，正是传统告警与 APM 最擅长捕捉的。

**而 Agent 恰恰相反。** 开篇词里我用"概率式、多步、状态依赖"这三个词描述过它的失败——这一讲，我们把它们放进"和微服务对比"的框架里，你会看得更透：微服务是输入与输出一一对应的确定关系，Agent 却是**同一个输入可能走出不同路径、一次回答背后串着一长串动作、后一步还依赖前一步的结果**。以我们的电商客服系统为例，用户一句"我要退款"，主 Agent 要先理解意图、调订单子 Agent 确认状态、交退款子 Agent 判断规则、再检索知识库确认政策，最后汇成一句话—— **这条链路上任何一环歪了，最终答案都可能错，但没有任何一环会"报错"。**

一句话对比就清楚了：**微服务的故障会"举手"，Agent 的故障会"伪装"。** 它把一个错误答案包装得和正确答案一模一样，语气专业、格式工整，然后骗过你的用户，也骗过你的监控。

这就是为什么，你那套为微服务打造的监控体系，在 Agent 面前会"失明"。它不是不努力，是**它要抓的『显式故障』，在这里根本没发生。**

- ●   ●

| ** 03 ** | ** 对比二：Agent 也不是"单轮 LLM 调用"的放大版 ** |
| --- | --- |

有人会说：LLM 应用我做过啊，不就是调个大模型 API 吗，加点监控不就行了？

如果你的应用只是"单轮问答"——用户问一句，模型答一句——那确实还好办。你甚至可以人肉抽查：把 prompt 和 completion 打出来，扫一眼就知道对不对。

但 Agent 不是这个量级的复杂度。Agent 的核心是一个**循环**：规划（Plan）→ 行动（调用工具）→ 观察（看工具返回）→ 再规划……直到它认为任务完成。在这之上，还叠加了多智能体协作、记忆读写、RAG 检索。

复杂度的差别，不是线性的，是**组合爆炸**的。单轮调用只有一个"出错点"（模型答得对不对）；而一个多步、多 Agent 的循环，出错点是每一步、每一次工具调用、每一次上下文传递的**乘积**。

随手举几个只有 Agent 才会遇到、单轮调用根本不存在的"新型故障"：

|  | ** 工具调用错了 ** ：该调订单查询，结果调了退款；或者参数拼错了，把订单号传成了用户 ID。 |
| --- | --- |
|  | ** 规划绕远路 ** ：本该一步查到的信息，Agent 兜了五步，token 烧了一大把还未必对——用户没感觉，你的账单有感觉。 |
|  | ** 多 Agent 互相甩锅 ** ：最终答案错了，是主 Agent 编排错了、退款子 Agent 判断错了，还是订单子 Agent 返回了脏数据？没有链路，你根本分不清。 |

这还只是冰山一角—— **完整的失败模式，下一讲我会用一张专门的"分类表"来盘**。这里你只需记住它们的一个共性：**靠"打印 prompt 和 completion"全都看不出来。** 你需要的是把整个循环的每一步都记录下来、串成一条可回放的链路——而这，正是可观测性要给你的东西。

- ●   ●

| ** 04 ** | ** "能跑"和"能信任"，到底差在哪五件事 ** |
| --- | --- |

绕了一圈，我们可以给"鸿沟"一个精确的定义了。

**"能跑"只有一个标准：不崩溃。** 进程活着，接口通着，不抛异常。

**"能信任"至少有五个标准**，缺一个你都不敢把它交给业务：

| ** 1 ** | ** 对不对（正确性） ** ：答案在事实上是对的吗？ |
| --- | --- |
| ** 2 ** | ** 有没有根据（Groundedness） ** ：答案是基于真实的知识库/工具结果，还是模型自己编的？——开头那个"30 天活动"，就栽在这一条。 |
| ** 3 ** | ** 贵不贵（成本） ** ：这次回答烧了多少 token、多少钱？是不是绕了远路？ |
| ** 4 ** | ** 安不安全 ** ：有没有人在用提示注入攻击它？它会不会被诱导做出越权的危险操作（比如乱批退款）？ |
| ** 5 ** | ** 能不能查（可归因） ** ：出了问题，你能不能快速定位到是哪一步、哪个 Agent、哪个工具的锅？ |

你会发现，**第 1 到 4 条是"结果"，第 5 条是前 4 条的前提。** 你没法评估一个看不见过程的系统的正确性，没法优化一个看不见成本构成的系统，没法防住一个看不见攻击路径的系统。**可观测性（第 5 条），是其余一切的地基。**

这也是为什么我说：可观测性不是"锦上添花的运维工具"，而是"Agent 能不能被信任"的**准入门槛**。

- ●   ●

| ** 05 ** | ** 它在 LLMOps 全景里，站在什么位置 ** |
| --- | --- |

把视野再拉高一点。整个 LLM 应用的生命周期，通常被叫做 LLMOps，大致是这么一个闭环：

### 开发 → 上线 → 观测 → 评估 → 优化 → 再上线……

注意"观测"在中间的位置。它是这个闭环的**数据底座**：

|  | 你想做 ** 评估 ** （这答案好不好）？评估的原始素材，是观测记录下来的线上真实对话。 |
| --- | --- |
|  | 你想做 ** 优化 ** （换个模型、改个 prompt、加个缓存）？判断优化有没有效，靠的是观测提供的前后对比数据。 |
|  | 你想做 ** 成本治理、安全防护、告警自愈 ** ？全都建立在"你能看见发生了什么"之上。 |

一句话：**LLMOps 这个飞轮能不能转起来，取决于观测这根轴稳不稳。** 观测缺位，后面评估、优化、治理全是空中楼阁——你连"现在到底怎么样"都不知道，谈何"变得更好"。

后面的专栏，基本就是沿着这个闭环展开的：先把观测（实战篇）建起来，再讲评估篇、平台篇、进阶篇。这一讲你只需要记住一件事：**观测是起点，也是地基。**

- ●   ●

| ** 06 ** | ** 落地清单：不装可观测性，你会踩哪些坑 ** |
| --- | --- |

理论讲完，我们落到最实在的地方。用我们的电商客服系统举例，如果你不做可观测性，下面这些坑，你几乎一个都躲不掉——我按"你多久会踩到"排了个序：

| 你会踩的坑 | 没有可观测性时的惨状 | 有了之后 |
| --- | --- | --- |
| ** 幻觉答案 ** （如"30 天活动"） | 靠用户投诉才发现，无法复现，不知道是检索错还是生成错 | 回放对话，一眼看出是知识库命中了过期文档，还是模型硬编 |
| ** 成本悄悄暴涨 ** | 月底账单翻倍，不知道钱花在哪个功能、哪个用户、哪次绕路上 | 按 Agent/功能/用户拆解 token 成本，精准定位"烧钱大户" |
| ** 多 Agent 甩锅 ** | 答案错了，主/订单/退款三个 Agent 互相"看不出谁的锅" | 全链路 Trace 里，哪个 Agent 哪一步出错，一目了然 |
| ** 多轮越聊越偏 ** | 用户说"越聊越离谱"，你无法定位是第几轮开始跑偏 | 按 Session 回放，精确定位污染起点 |
| ** 退款被注入攻击 ** | 有人用话术诱导 Agent 乱批退款，事后毫无审计痕迹 | 高风险写操作留痕：决策依据、触发链路、可追溯可审计 |
| ** 换模型不敢换 ** | 想把贵模型换成便宜的，但不知道质量会不会掉，只能凭感觉 | 用观测+评估数据做 A/B，用数据决策 |

这张表，你可以直接拿去做团队内部的"为什么我们需要投入可观测性"的说服材料。**每一行，都是真金白银或用户信任的流失。**

- ●   ●

| ** ✓ ** | ** 小结 ** |
| --- | --- |

这一讲，我们其实只讲透了一件事：**为什么可观测性对 Agent 是刚需，而不是选配。**

三个要点带走：

| ** 1 ** | ** Agent 的故障会伪装。 ** 它概率式、多步、状态依赖，出错时往往不报错，而是给一个"看起来对"的错误答案——传统监控为"显式故障"而生，天然抓不住这种"静默失败"。 |
| --- | --- |
| ** 2 ** | ** "能跑"≠"能信任"。 ** 能跑只要不崩，能信任要同时满足对、有据、不贵、安全、可归因五条，而"可归因"（也就是可观测性）是其余一切的地基。 |
| ** 3 ** | ** 观测是 LLMOps 飞轮的轴。 ** 评估、优化、治理全都建立在"看得见"之上，观测缺位，后面全是空谈。 |
