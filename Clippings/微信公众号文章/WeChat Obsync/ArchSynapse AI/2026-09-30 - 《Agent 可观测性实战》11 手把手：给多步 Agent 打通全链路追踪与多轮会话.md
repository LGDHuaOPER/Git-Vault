# 手把手：给多步 Agent 打通全链路追踪与多轮会话

**// **你好，这里是公众号：【ArchSynapse AI】。

第 10 讲，我们让示例项目产出了第一条 Trace——但它只有孤零零一根横条，因为我们只埋了一次 LLM 调用。

这一讲，把这根横条**养成一棵枝繁叶茂的树**，而且是能跨轮次串起来的树。具体是三件事，也正好对应本讲的三节：

| ** 1 ** | ** 循环追踪 ** ：给"规划—工具—观察—再规划"的多步循环建起父子 Span，长成第 5 讲设计的那棵树； |
| --- | --- |
| ** 2 ** | ** Session 组织 ** ：把一通对话的多轮，正确收敛进一个 Session； |
| ** 3 ** | ** 记忆/上下文观测 ** ：把"每一步到底喂了什么进模型"记下来，让上下文的膨胀与污染看得见。 |

代码继续，都可复制即跑（沿用第 10 讲初始化好的  `tracer`  和  `client` ）。

- ●   ●

| ** 01 ** | ** 循环追踪：嵌套 Span，自动成树 ** |
| --- | --- |

先说一个能让你少写一半代码的好消息：**父子关系是自动的。**

OpenTelemetry 用一个"当前 Span"的上下文变量在背后记账。你只要用**嵌套**的  `with tracer.start_as_current_span(...)` ，里层的 Span 就会自动认外层那个当"爹"。你不用手动去传 Span ID。

于是，第 5 讲那棵退款 Span 树，落成代码就是这样：

- ●  ●  python

```
import json
from opentelemetry.trace import Status, StatusCode

def run_turn(session_id: str, user_msg: str, history: list) -> str:
# 一次 Agent 循环 = 一条 Trace 的根 Span
with tracer.start_as_current_span("invoke_agent customer_supervisor") as root:
        root.set_attribute("session.id", session_id)            # 会话钥匙，见第三节
        root.set_attribute("gen_ai.agent.name", "customer_supervisor")

        intent = plan(user_msg, history)          # ① 规划：内部开一个 LLM 子 Span
        order  = call_tool("query_order",         # ② 行动：调工具，子 Span 自动挂到 root 下
                           {"order_id": intent["order_id"]})
        answer = generate(user_msg, history, order)  # ③ 观察+生成：又一个 LLM 子 Span
return answer

def call_tool(name: str, args: dict):
# Span 名同样用"{操作} {对象}"的低基数写法
with tracer.start_as_current_span(f"execute_tool {name}") as span:
        span.set_attribute("gen_ai.tool.name", name)
        span.set_attribute("app.tool.arguments", json.dumps(args, ensure_ascii=False))
try:
            result = TOOLS[name](**args)
            span.set_attribute("app.tool.result", json.dumps(result, ensure_ascii=False))
return result
except Exception as e:
            span.set_status(Status(StatusCode.ERROR, str(e)))
            span.record_exception(e)
raise
```

 `plan`  和  `generate`  内部各自也用  `start_as_current_span("chat")`  开自己的 LLM Span，因为它们是在  `root`  的  `with`  块里被调用的，就自动成了  `root`  的孩子。

跑一遍，去 Phoenix 里看—— **你会看到一棵和第 5 讲那张设计图几乎一模一样的树**： `invoke_agent`  在最上面， `chat` 、 `execute_tool`  缩进挂在下面。你在第 5 讲纸上画的东西，现在真的从代码里长出来了。

记住这个结论：**Agent 的循环，在 Trace 上就长成一棵嵌套的父子 Span 树**——每一步"想"和"做"，都是树上的一个节点。

- ●   ●

| ** 02 ** | ** 一个必须知道的陷阱：换到线程池，树就断 ** |
| --- | --- |

上面"自动成树"有个前提，我必须现在就给你敲响警钟：**它依赖那个记账用的"当前 Span"能被子任务看见**。而在 Python 里，这个 context 存在  `contextvars`  中—— **它在"线程"和"协程"两种并发下的行为，恰好是相反的。**

**线程池：会断。** 新起的（或复用的）worker 线程**不会继承**提交方的 context。子任务里  `start_as_current_span`  一看"当前没有父亲"，就会开出一条**全新的 Trace**：

- ●  ●  python

```
# ❌ 反例：丢进线程池并发跑工具，父子关系丢失
with ThreadPoolExecutor() as pool:
    results = pool.map(lambda n: call_tool(n, {...}), ["query_order", "query_logistics"])
# call_tool 里开的 Span 拿不到 root 的 context —— 会另起一条 Trace
```

这里有个细节值得你记牢，它直接决定你**怎么排查**：这些 Span 并不是"游离在你那条 Trace 里的孤儿节点"，而是**带着全新的 trace_id、变成了另一条独立的 Trace**。所以当你发现主 Trace 里少了两个工具调用时，别在那棵树里找——去 Trace 列表里翻，你会看到几条莫名其妙、看不出关联的孤立 Trace，那就是它们。（ `loop.run_in_executor`  本质也是丢进线程池，同理。）

补救的核心思路是**手动把 context"接力"过去**：在主线程抓住当前 context，在子线程里先  `attach`  它，再开 Span。完整写法、以及多智能体并发协作下怎么系统地保住这条因果链，是第 12 讲的正题。

**asyncio：一般不会断，别白忙活。** 这里要特意澄清一个很多人搞反的点—— `asyncio.Task`  在创建时会**拷贝一份当前 context**，所以  `asyncio.gather(...)`  里的协程**看得见外层的当前 Span，子 Span 会正确挂上去**，你不需要手动接力。

但 asyncio 有另一个更隐蔽的坑：如果你在某个 Span 的  `with`  块里  `create_task`  了一个"发射后不管"的任务，等它真正跑起来时，父 Span 可能**早就结束了**——子 Span 会挂到一个已经关闭的父亲上，时间轴看着会非常诡异（子任务的时间跑到了父 Span 之外）。所以 asyncio 下要盯的不是"context 传没传过去"，而是"**父 Span 的生命周期，有没有覆盖住子任务**"。

- ●   ●

| ** 03 ** | ** Session 组织：给每一轮盖同一个"章" ** |
| --- | --- |

第 4 讲讲过：一条 Trace 只覆盖一轮，一通多轮对话要靠 **Session** 串起来。而第 4 讲也提醒过——Session 不是 OTel 的原生对象，它是**靠给每轮的 Trace 盖上同一个**  `session.id`  **印章**实现的。

你注意到了吗？第一节的  `run_turn`  里， `root.set_attribute("session.id", session_id)`  已经把这个印章盖上了。所以多轮对话的主循环，就是不断用同一个  `session_id`  调  `run_turn` ：

- ●  ●  python

```
history, session_id = [], "S-1024"

for user_msg in ["我的订单还能退款吗？", "那多久到账？", "用的哪张卡退？"]:
    answer = run_turn(session_id, user_msg, history)          # 每轮 = 一条新 Trace
    history += [{"role": "user", "content": user_msg},
                {"role": "assistant", "content": answer}]     # 历史滚进下一轮
```

这三轮会产生**三条独立的 Trace**，但它们都盖着  `session.id = "S-1024"` 。到了 Phoenix（或任何支持 Session 的平台），你就能按这个 id 把它们**分组、按顺序回放**——第 4 讲说的"这通对话在第几轮跑偏"，现在你有抓手了。

对应地，另一个结论也成立了：**多轮对话，在 Trace 上就是一组共享同一个**  `session.id`  **的 Trace。**

- ●   ●

| ** 04 ** | ** 记忆/上下文观测：把"喂进去的到底是什么"记下来 ** |
| --- | --- |

现在做第三件、也是最容易被所有人忽略的事。

回看上面的  `history += ...` ——它在**默默变长**。第 1 轮 history 是空的，第 3 轮它已经塞了两轮问答。而每次调 LLM，这坨越来越长的 history 都会被喂进上下文窗口。第 4 讲说过：上下文会**膨胀**、会**被污染**、会**被悄悄截断**。可如果你不把它记下来，这一切都是黑箱。

所以我们在生成回复前，**把即将进入上下文窗口的东西、连同它的 token 构成，一起记进 Span**：

- ●  ●  python

```
def generate(user_msg: str, history: list, order: dict) -> str:
with tracer.start_as_current_span("chat") as span:
        system_prompt = "你是电商客服助手，只依据给定资料回答……"
        retrieved = retrieve_policy(user_msg)     # 本轮若检索了知识库就有值
        messages = ([{"role": "system", "content": system_prompt}]
                    + history

                    + ([{"role": "system", "content": "参考资料：" + retrieved}] if retrieved else [])

                    + [{"role": "user", "content": user_msg}])

# ★ 记忆/上下文观测：把上下文的"构成"和"体量"记成属性
        total_tokens = count_tokens(messages)
        span.set_attribute("app.context.turn_index", len(history) // 2 + 1)
        span.set_attribute("app.context.tokens.total",   total_tokens)
        span.set_attribute("app.context.tokens.history", count_tokens(history))
# 本轮没检索时 retrieved 为空，别直接丢给 count_tokens
        span.set_attribute("app.context.tokens.retrieved",
                           count_tokens(retrieved) if retrieved else0)
# 注意：CONTEXT_LIMIT 是"你自己设的上下文预算"，不是模型窗口上限（见第五节）
        span.set_attribute("app.context.truncated", total_tokens > CONTEXT_LIMIT)

        resp = client.chat.completions.create(model="deepseek-flash", messages=messages)
# …（token/结束原因等按第 10 讲记录）
return resp.choices[0].message.content
```

（ `count_tokens`  用  `tiktoken`  之类估算即可，精度要求不高——你要的是**趋势**，不是精确到个位。）

就这么几行  `set_attribute` ，你就把"上下文"从黑箱变成了可观测对象。现在，每一条  `chat`  Span 上都记着：这是第几轮、总共喂了多少 token、其中历史占多少、检索占多少、有没有被截断。

| ** 05 ** | ** 落点：一张图看穿"上下文在滚雪球" ** |
| --- | --- |

把上面三轮对话的上下文观测数据拉出来排一排，就是第 4 讲承诺过的那张**"上下文构成随轮次变化"图**：

- ●  ●

```
轮次        system   历史    检索    本轮    合计tokens   截断?
第1轮        120      0      340     18       478        否
第2轮        120     210      0      12       342        否   ← 追问，本轮没检索
第3轮        120     460      0      15       595        否   ← 历史在滚雪球…
第4轮        120     980      0      20      1120        否
 …
第8轮        120    3400      0      16      3536        是 ⚠️ ← 历史撑爆预算，最早的被悄悄丢了
```

### 这里的"截断"撞的是什么？ 不是模型的窗口上限——如今动辄几万、十几万 token 的窗口，3536 根本撑不爆。真实生产里先撞上的，几乎都是 你自己设的那道预算线 ：为了控成本和延迟，团队通常会主动把历史截在几千 token（也就是代码里那个  `CONTEXT_LIMIT`  ）。所以这张表真正在说的是： 你的预算什么时候被吃满、以及被谁吃满的 。

这张表一摆出来，两件"黑箱里的事"立刻现形：

|  | ** 膨胀（bloat）看得见 ** ：历史那一列一路上涨，到第 8 轮撑到截断——这解释了"为什么越聊越慢、越聊越贵"。 |
| --- | --- |
|  | ** 污染定位得到 ** ：假设第 2 轮 Agent 把订单号记错了，这个错会一直待在"历史"里，第 3 轮之后的每一轮都背着它。你顺着 Session 一轮轮看上下文构成，就能 ** 精确定位到错误是第几轮混进历史的 ** ——这也是修复"多轮漂移"唯一的下手点。 |

**改造小结**：相比第 10 讲的单次调用，这一讲的 diff 其实就三处——① 用嵌套 Span 把循环建成树；② 每轮根 Span 盖上  `session.id` ；③ 生成前把上下文构成记进 Span。三处加起来不到 20 行，但你的 Agent 从"能看一次调用"升级成了"能回放整通对话、还能看穿上下文"。

这一讲，我们把一次孤立的埋点，扩成了全链路 + 多轮 + 上下文可观测：

| ** 1 ** | ** 循环追踪 ** ：嵌套  `start_as_current_span`  自动成父子树——Agent 的循环，在 Trace 上就是一棵嵌套 Span 树。 |
| --- | --- |
| ** 2 ** | ** 异步陷阱 ** ：自动成树只在同步同线程成立，一并发就出"孤儿 Span"，需手动接力上下文。 |
| ** 3 ** | ** Session 组织 ** ：给每轮 Trace 盖同一个  `session.id`  ——多轮对话 = 一组共享 session.id 的 Trace，可分组回放。 |
| ** 4 ** | ** 记忆/上下文观测 ** ：生成前把上下文的构成与 token 体量记进 Span，让膨胀、截断、污染从黑箱变成一张能看穿的表。 |
