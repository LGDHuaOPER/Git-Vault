# 可观测性 ≠ 监控：三大支柱的重构与一张全景地图

**// **你好，这里是公众号：【ArchSynapse AI】。

上一讲，我们拿到了一张《Agent 失败模式分类表》——9 个失败家族，知道了 Agent 会怎么坏。

这一讲要回答的是它的下半句：**用什么去抓这些坏？**

答案听起来有点反高潮：还是那三样你熟得不能再熟的老工具——Metrics、Logs、Traces。但别急着划走，因为 Agent 给它们**换上了新的镜头，还额外加了三个你以前不用管的维度**。这一讲的最后，我会把这一切收进一张贯穿全专栏的**能力全景地图**，让你清楚地看到：第 2 讲那 9 个失败家族，分别要靠地图上的哪一块去抓。

我们先从一个必须澄清的误会开始。

- ●   ●

| ** 01 ** | ** 先破一个误会：可观测性，不是 Agent 发明的 ** |
| --- | --- |

开篇词里我讲透过一点，这里只用一句话收束：**可观测性是分布式系统里一门成熟的老学问**——三大支柱、OpenTelemetry 全都成长于微服务世界，一个像样的后端团队早就在用了。Agent 没有"发明"它，只是给它出了新考题。

不过本讲标题写着"可观测性 ≠ 监控"，那就得把这条最容易混的边界钉死：**监控（Monitoring）和可观测性（Observability）不是一回事，在传统后端里本就并存。** 监控回答"**有没有**出问题"——盯的是你预设好的指标（错误率、延迟超没超阈值），本质是"已知问题的预警"；可观测性回答"**为什么**、**在哪一步**"——让你能对系统提出事先没预设过的问题，本质是"未知问题的排查"。打个比方：监控是体检报告上那几个亮红灯的指标，可观测性是能让你顺着血管一路查下去、搞清楚"到底哪儿堵了"的造影。

所以，Agent 时代真正变的，**从来不是"要不要可观测性"，而是"可观测性要观测什么"**。故障形态变了（静默失败），要盯的信号也变了（从基础设施层，深入到语义层）。你现成的那套体系没瞎，只是镜头对错了地方。这一讲，就是帮你把镜头调准。

- ●   ●

| ** 02 ** | ** 三支柱的"重构"：老瓶，装新酒 ** |
| --- | --- |

我们一根一根来看，Agent 往每根支柱里，倒了什么新酒。

**Metrics（指标）：从"机器健康"到"业务与质量健康"。**

传统指标你很熟：QPS、延迟、错误率、CPU/内存。这些对 Agent 依然有用（它终究跑在机器上）。但 Agent 让指标长出了两类全新的家族：

|  | ** 成本类 ** ：每次调用的 token 用量、每个任务的花费、TTFT（首 token 延迟）、TPM。这些以前你根本不用管，现在它直接决定你的账单——第 8、25 讲细讲。 |
| --- | --- |
|  | ** 质量类 ** ：工具调用成功率、任务完成率、平均工具调用次数、幻觉率。注意，这些是 ** 业务/质量 ** 指标，不是机器指标。它们回答的是"Agent 干得好不好"，而不是"机器累不累"。 |

**Logs（日志）：从"程序在想什么"到"模型看到和说了什么"。**

传统日志记的是程序的执行轨迹。Agent 的日志里，多了一类分量极重的内容：**完整的 prompt 和 completion**——模型到底看到了什么上下文、又原原本本吐出了什么。排查一个幻觉，你十有八九要回到这段原文去看。

但这里有个**坑，必须现在就提醒你**：完整 prompt/completion 里往往塞满了用户手机号、订单地址、支付信息这类敏感数据。**把它们原样灌进日志后端，在国内是踩合规红线的。** 所以"记什么、怎么脱敏、存多久、谁能看"，是一门必须认真对待的功课——我们专门留了第 15 讲讲它。你先记住这根弦。

**Traces（链路）：重构最深的一根，也是 Agent 观测的"第一公民"。**

如果说前两根是"加内容"，Trace 则是被**彻底重新定义**了。

在 Agent 语境里，**一次完整的 Agent 循环 = 一条 Trace**：从用户发问，到主 Agent 规划、调订单子 Agent、调退款子 Agent、检索知识库、再到最终回复，整条链路上的每一个动作，都是这条 Trace 上的一个 **Span**（我们下一讲会把 Trace/Span/Session 讲透，这里先建立直觉）。

为什么我说 Trace 是"第一公民"？因为三根支柱回答的问题层次完全不同：

|  | ** Metrics ** 告诉你："幻觉率从 3% 涨到了 8%。"——知道 ** 变差了 ** 。 |
| --- | --- |
|  | ** Logs ** 告诉你："这一条回答的原文长这样。"——知道 ** 某一条什么样 ** 。 |
|  | ** 只有 Traces ** 能告诉你："这一次，Agent 先检索到了一篇过期文档，然后把它当真喂给了模型，模型在第三步开始发挥……"——知道 ** 这一次完整地发生了什么、到底在哪一步歪的 ** 。 |

而第 2 讲我们反复强调：**Agent 的问题，几乎都是"在哪一步"的问题。** 所以在 Agent 可观测性里，Trace 不再是三选一里的一个选项，而是**绝对的主角**。这也是后面实战篇几乎所有章节都围着 Trace 转的原因。

- ●   ●

| ** 03 ** | ** 三支柱之外，Agent 还长出了三个新维度 ** |
| --- | --- |

光把老三样装满还不够。Agent 还逼着我们在三大支柱之外，额外盯三件传统后端根本不操心的事——其实它们在第 1 讲的"能信任五件事"里就已经露过面，这一节我把它们正式立成可观测性的**三个新维度**：

|  | ** 质量（Evaluation） ** ：这答案到底对不对、好不好？传统系统不需要"评估输出质量"——返回 200 就是对的。但 Agent 的输出是有灰度的，你必须有一套办法量化"好坏"。这是评估篇（第 16~20 讲）的主题。 |
| --- | --- |
|  | ** 成本（Cost） ** ：这次回答烧了多少钱？值不值？Agent 的成本极易失控，而且和质量深度纠缠（ ** 便宜模型多绕几步，未必更省 ** ）。第 25 讲会把它做成北极星指标。 |
|  | ** 安全（Safety） ** ：有没有人在攻击它？它会不会被诱导做危险操作？尤其是我们那个能动真金白银的 ** 退款子 Agent ** 。第 26 讲专门收拾它。 |

这三个维度不是凭空长出来的，它们**依附在 Trace 之上**——一次对话的质量分、成本、安全判定，最终都挂回到那条 Trace/Session 上。所以你会看到一个反复出现的模式：**Trace 是骨架，质量/成本/安全是挂在骨架上的血肉。**

- ●   ●

| ** 04 ** | ** 映射表：Agent 的每一样东西，该记到哪里 ** |
| --- | --- |

概念讲完，落到最实操的问题：**你手里 Agent 产生的这一堆数据，到底哪样该进哪根支柱、哪个维度？** 这张表帮你一次对齐：

| Agent 产生的东西 | 归到哪里 | 为什么 | 相关讲 |
| --- | --- | --- | --- |
| 延迟 / QPS / 错误率 / TTFT | Metrics（系统） | 传统机器指标，照旧 | 第 8 讲 |
| token 用量、单次/单任务成本 | Metrics（成本维度） | 要按趋势聚合看 | 第 8、25 讲 |
| 工具成功率、任务完成率、幻觉率 | Metrics（质量维度） | 需按时间聚合监控 | 第 8、9 讲 |
| 完整 prompt / completion | Logs 或 Trace 属性（ ** 须脱敏 ** ） | 排障要看原文 | 第 10、15 讲 |
| 工具入参 / 出参 / 耗时 | Trace（工具 Span 属性） | 属于链路某一步 | 第 14 讲 |
| 检索命中的文档、相似度 | Trace（Retriever Span） | 归因幻觉的关键证据 | 第 13 讲 |
| 推理步骤、多 Agent 编排关系 | Trace（Span 父子结构） | 只有链路能还原因果 | 第 11、12 讲 |
| 用户反馈（👍/👎、转人工） | Trace 附加信号 + Metrics | 既挂到具体对话，也要聚合 | 第 18 讲 |
| LLM-as-a-Judge 打分、评估结果 | 质量维度（挂到 Trace/Session） | Agent 时代新增 | 第 16、17 讲 |
| 安全分、注入检测、越权标记 | 安全维度（挂到 Trace） | Agent 时代新增 | 第 26 讲 |

你只要扫一眼"归到哪里"这一列就会发现：**大量关键信息，最后都往 Trace 上挂。** 这不是巧合——再次印证了 Trace 的"第一公民"地位。

- ●   ●

| ** 05 ** | ** 四层参考架构：数据从进来到用起来，要走几层 ** |
| --- | --- |

知道了"记什么"，接下来是"这套系统长什么样"。任何一套可观测性方案，无论开源还是商业，无论国内还是国外，剥开看都是这四层：

### 4

应用层人在这一层做决策

告警 · 根因定位 · 会话回放 · Dashboard

### 3

分析层

Trace 分析 · 评估(Eval) · 成本分析 · 质量/安全看板

### 2

存储层

指标库(时序) · 日志库 · 链路库（常用 ClickHouse 等列存）

### 1

采集层数据从这里进来

OpenTelemetry SDK / 探针（埋点：LLM · 工具 · 检索 · 推理）

▲

你的电商客服 Agent（主 Agent · 订单 · 退款 · RAG 知识库）

从下往上理解它：

|  | ** ① 采集层 ** ：给 Agent"埋点"，把 LLM 调用、工具调用、检索、推理等都变成 Span 和指标送出去。这是实战篇（第 10~15 讲）手把手要教的。标准化的关键就在这一层——用 OpenTelemetry，你上面三层就能自由更换。 |
| --- | --- |
|  | ** ② 存储层 ** ：三类数据（指标/日志/链路）通常分库存，因为它们的读写模式完全不同。链路数据量大、要做复杂分析，常落在 ClickHouse 这类列存上。 |
|  | ** ③ 分析层 ** ：把原始数据变成"人能看懂的东西"——Trace 瀑布图、评估看板、成本报表。这是平台的价值高地。 |
|  | ** ④ 应用层 ** ：你真正每天打交道的地方——告警把你从睡梦里叫醒、根因定位帮你五分钟破案、会话回放让你复现那个"时有时无"的 bug。 |

这四层里，具体该选哪些开源或商业组件来填（Langfuse？Phoenix？观测云？自建？），是平台篇（第 21~24 讲）的重头戏，这里先不展开。你现在只要**记住这个骨架**——后面每讲一个工具、每做一次选型，我们都会把它放回这张四层图里定位。

- ●   ●

| ** 06 ** | ** 全景地图：9 个失败家族，分别在哪一层被抓住 ** |
| --- | --- |

现在，我们把第 2 讲的《失败模式分类表》和这一讲的观测能力**接起来**——这就是我答应过你的"全景地图"。它回答的是：**每一类失败，主要靠哪根支柱/哪层能力去抓？**

| 失败家族（第 2 讲） | 主要靠什么抓住它 | 落在支柱/维度 | 主攻讲 |
| --- | --- | --- | --- |
| 意图误解 | Session 回放 + 质量评估 | Trace / 质量 | 11、9 |
| 规划绕路 / 死循环 | 全链路 Trace + 轨迹评估 | Trace / 质量 | 12、20 |
| 工具用错 | 工具 Span（入参/出参） | Trace | 14 |
| 工具失败未兜底 | 工具 Span + 错误标记 | Trace / Metrics | 14 |
| 幻觉 / 无据生成 | Retriever Span + Judge 打分 | Trace / 质量 | 13、17 |
| 上下文污染 / 多轮漂移 | Session + 上下文观测 | Trace | 4、11 |
| 多 Agent 甩锅 | 跨 Agent 父子 Span | Trace | 12 |
| 成本失控 | 成本指标归因 | Metrics / 成本 | 8、25 |
| 安全 / 越权 | 安全分 + 高风险操作审计留痕 | 安全 | 15、26 |

这张表值得你盯着多看十秒，因为它暴露了一个特别重要的事实：**九分之七的失败家族，主战场都在 Trace（及挂在其上的质量/安全维度）。** Metrics 负责"拉响警报、看趋势"，但真正让你"破案"的，几乎永远是那条能回放的链路。

这也是为什么我在这门专栏里，会把最多的篇幅压在 Trace 相关的实战上。**先把 Trace 这根脊梁骨立起来，其余的血肉才有地方挂。**

- ●   ●

| ** ✓ ** | ** 小结 ** |
| --- | --- |

认知篇到这里就收尾了。我们花三讲，建立了一套完整的心智模型：

| ** 1 ** | ** 可观测性不是 Agent 发明的 ** ——它成熟于分布式系统；Agent 变的是故障形态和要观测的信号，不是"从零建立"。 |
| --- | --- |
| ** 2 ** | ** Agent 会怎么坏 ** ——9 个失败家族，一张病历模板。 |
| ** 3 ** | ** 用什么抓这些坏 ** ——三大支柱各自"重构"（Metrics 加成本/质量、Logs 加 prompt/completion、Trace 成为第一公民），外加质量/成本/安全三个新维度；整套东西落在"采集→存储→分析→应用"四层架构里；而九成失败的主战场，是 Trace。 |

想清楚"为什么"和"看什么"，我们就可以放心地进入原理篇，去搞懂"怎么建模"了。

下一讲（第 4 讲），我们正式掀开 Trace 的盖子，把 **Trace / Span / Session** 这三层地基一次性打牢——特别是 **Session**，它是多轮客服场景里那个"越聊越偏"问题的唯一观测入口。这也是最小必读路径的第四站。
