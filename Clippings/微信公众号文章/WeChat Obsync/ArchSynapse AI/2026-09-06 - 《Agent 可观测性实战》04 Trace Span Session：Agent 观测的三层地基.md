# Trace / Span / Session：Agent 观测的三层地基

**// **你好，这里是公众号：【ArchSynapse AI】。

第 3 讲我抛了一个结论：**Trace 是 Agent 观测的"第一公民"**，九成失败的主战场都在它身上。也随口用了"一次 Agent 循环 = 一条 Trace"这样的说法。

这一讲，我们就把盖子正式掀开，把这套语言彻底吃透。因为从下一个模块（实战篇）开始，你写的每一行埋点代码、看的每一张 Trace 图，都建立在三个词之上：**Span、Trace、Session**。

它们是一组"俄罗斯套娃"，从小到大：**Span 是最小积木，Trace 把积木串成一次任务，Session 把多次任务串成一通对话。** 尤其是最外层的 Session——它是我们那个"越聊越偏"的多轮客服难题，唯一的观测入口。这也是很多团队会漏掉的一层。

我们从最小的积木讲起。

- ●   ●

| ** 01 ** | ** Span：观测的最小积木 ** |
| --- | --- |

**一个 Span，就是一次"有始有终、你想单独看一眼"的操作。**

它记录四样东西，你可以用"给一个操作装了个秒表 + 便签"来理解：

|  | ** 名字 ** ：这一步在干嘛，比如  `llm.chat`  、  `tool.query_order`  、  `rag.retrieve`  ； |
| --- | --- |
|  | ** 起止时间 ** ：什么时候开始、什么时候结束——两者一减，就是 ** 耗时 ** ； |
|  | ** 属性（Attributes） ** ：这一步的上下文键值对，比如模型名、token 数、工具入参、检索到的文档； |
|  | ** 状态 ** ：成功还是失败（  `OK`  /  `ERROR`  ），出错还能挂上异常信息。 |

在传统后端里，一个 Span 通常是"一次函数调用"或"一次 RPC"。到了 Agent 这儿，Span 的含义被我们**按语义重新划分**了——一次 LLM 调用是一个 Span，一次工具调用是一个 Span，一次检索是一个 Span，一步推理决策也可以是一个 Span。

拿我们电商客服系统里"用户要退款"这一轮举例，它会产生这么一串 Span：

一轮「我要退款」产生的 Span 序列

### Span 主Agent.规划意图 15ms

### Span 工具.查订单状态 120ms attributes: order_id=..., status=已签收

### Span RAG.检索退款政策 80ms attributes: 命中文档=[退款政策v2], 相似度=0.82

### Span 退款子Agent.判断是否可退 10ms attributes: 结论=可退

### Span LLM.生成最终回复 900ms attributes: model=..., tokens=350

看，一串 Span 就是一次操作的"分解动作"。但光有一堆散落的 Span 还不够——你怎么知道它们属于**同一次任务**？这就要靠 Trace 了。

- ●   ●

| ** 02 ** | ** Trace：把散落的 Span 串成"一次完整任务" ** |
| --- | --- |

**一条 Trace，就是一组有因果关系的 Span 的集合，代表一次完整的任务执行。**

它靠两个 ID 把 Span 们缝在一起：

|  | ** Trace ID ** ：一次任务全局唯一。上面那 5 个 Span，共享同一个 Trace ID——这就是它们"是一家人"的凭证。 |
| --- | --- |
|  | ** Span ID + 父 Span ID ** ：记录 Span 之间的 ** 父子关系 ** 。主 Agent 的规划 Span 是"父"，它调起的"查订单""检索""退款判断"就是它的"子"；而"生成回复"又在这些子步骤之后。 |

这套"谁是谁的爸爸"的关系，靠的就是每个 Span 都记着自己的  `parent span ID` 。它拼出来的，就是一次任务的**因果链与时序**。在可观测平台里，这条链会被画成一张**瀑布图**（waterfall，像甘特图）——横轴是时间，每个 Span 一根横条，缩进表示父子层级。

**这张瀑布图，就是你破案时盯着看的东西。** 回到第 3 讲那个论断：Metrics 告诉你"幻觉率涨了"，而这张瀑布图能告诉你"这一次，是 RAG 在 80ms 里命中了一篇过期文档、然后 LLM 基于它发挥了"——它把"在哪一步歪的"直接摊在你面前。

所以我们反复说的那句话，现在可以精确地重述了：**一次 Agent 循环（从用户单次请求，到规划、调工具、观察、再规划，直到给出最终回复）= 一条 Trace。**

这里插两个你迟早会碰到的概念，先建立印象，细节留到后面：

|  | ** 上下文传播（Context Propagation） ** ：Trace ID 怎么在一次任务的各个环节间"传下去"，是全链路追踪的技术核心。在单进程里它靠调用栈自动传；可一旦跨到 ** 异步任务、并发步骤、甚至跨子 Agent 进程 ** ，就得手动接力——接力棒掉了，链路就断了，你会看到一堆"没爹的孤儿 Span"。这正是多智能体追踪最容易翻车的地方，第 12 讲我们专门攻它。 |
| --- | --- |
|  | ** 采样（Sampling） ** ：流量大了，你不可能存下每一条 Trace。传统系统常用"头部采样"（一开始就按比例扔掉一部分）。但 Agent 场景我更推荐 ** 倾向全量、或用"尾部采样" ** ——因为出错的、被用户点踩的、成本异常的那几条，恰恰是最该留下的证据，不能让它们被随机丢掉。这个权衡，平台篇会再谈。 |

到这里，"一轮问答"我们看清楚了。可客服从来不是一问一答就结束的——真正的麻烦，藏在多轮里。

- ●   ●

| ** 03 ** | ** Session：一通完整对话，多轮问题的唯一观测入口 ** |
| --- | --- |

请注意一个容易被忽略的事实（也是当前主流约定）：**一条 Trace，只覆盖"一轮"问答（一个 user turn）。**

用户说"我要退款"，是第一条 Trace；他接着追问"那多久到账？"，是**第二条全新的 Trace**；再问"用的哪张卡？"，第三条……它们各自独立，各有各的 Trace ID。

问题来了：第 2 讲那个高发的失败家族—— **上下文污染、多轮漂移**（用户抱怨"越聊越离谱"）——你要在哪儿看？

如果你只有一条条孤立的 Trace，你是看不出来的。因为"越聊越偏"是一个**跨轮次**的现象：第 2 轮埋下的错（比如记错了订单号），要到第 4、5 轮才爆发。你盯着第 5 轮那条 Trace 看到天亮，也找不到病根—— **病根在第 2 轮那条 Trace 里。**

这就是为什么我们需要套娃的最外层：**Session（会话）。**

**一个 Session，就是把同一通对话里的多条 Trace，用一个 Session ID 串起来。**

这里要提醒一句，免得你实战时扑空：和 Span、Trace 这种 OpenTelemetry **原生原语**不同，Session 在实现上通常**不是一个内置对象**——你在 SDK 里找不到"Session API"。它是靠给同一通对话的多条 Trace 打上同一个  `session.id`  属性、再在观测平台里分组出来的。具体怎么打这个 id，第 10、11 讲动手时会做。

有了它，三件"只在会话层才成立"的事才能做：

| ** 1 ** | ** 定位"第几轮开始跑偏" ** ：把一通对话的所有 Trace 按顺序排开回放，你能一眼看到污染是从哪一轮引入的。这是修复多轮漂移的 ** 唯一 ** 下手点。 |
| --- | --- |
| ** 2 ** | ** 会话级的指标与质量 ** ：这通对话一共几轮才解决问题？总共花了多少钱？最后用户满意吗、有没有转人工？这些都不是单轮指标，必须在 Session 上聚合。 |
| ** 3 ** | ** 跨轮上下文的健康度 ** ：历史越滚越长，有没有把早期的错误信息一直背在身上？ |

一句话：**Trace 让你看清"这一轮怎么了"，Session 让你看清"这通对话怎么了"。** 对多轮客服这种场景，缺了 Session 层，你的观测就是瞎了一只眼——而这恰恰是很多只跟着"单轮 LLM 教程"搭起来的团队，最容易漏掉的地基。

- ●   ●

| ** 04 ** | ** 别忘了：进入模型的"上下文"，本身就是观测对象 ** |
| --- | --- |

讲完三层套娃，我要特别拎出一个东西，请你从现在起就当成**最容易被漏掉、却必须盯住的观测对象**——那就是**上下文（Context）**。

我们太容易只盯着"Agent 说了什么"（输出），却忘了问一句更关键的：**这一步，模型到底"看到"了什么？**

一次 LLM 调用，真正喂进模型的上下文窗口里，通常塞着一大堆东西：系统 prompt、前几轮的对话历史（或其摘要）、这一轮 RAG 检索到的片段、工具返回的结果……它会**膨胀**（context bloat，越聊越长、越来越贵）、会**被污染**（早期的错误信息赖着不走）、会**被悄悄截断**（超了窗口长度，最早的历史被丢弃，而你毫不知情）。

第 2 讲那些"多轮漂移"、"成本失控"的失败，根子往往就在这团上下文里。所以，**把每一步注入的上下文如实记录下来，是排查这类问题的前提。**

这一讲你先建立这个意识就够了：**上下文不是"背景"，它是必须被如实记录的关键证据。** 具体怎么埋点、怎么画出"上下文构成随轮次变化"的图、怎么揪出膨胀和污染，我们放到第 11 讲手把手做。

| --- | --- |

|  | Span 退款子Agent.判断 结论=可退 |

…

从下往上，就是我们这一讲的三层地基：

|  | ** Span ** （最里层）：一次操作的秒表 + 便签； |
| --- | --- |
|  | ** Trace ** （中间层）：一轮问答的完整因果链，破案主战场； |
|  | ** Session ** （最外层）：一通对话，多轮问题的唯一观测入口； |
|  | 而 ** 上下文 ** ，像血液一样流经每一条 Trace，是你排查漂移和成本时要盯的一等对象。 |

记住这张图。实战篇从第 10 讲开始，我们做的所有埋点，本质上都是在**亲手把这张图，从你的电商客服 Agent 里"长"出来**。

- ●   ●

| ** ✓ ** | ** 小结 ** |
| --- | --- |

原理篇的第一块地基打好了：

| ** 1 ** | ** Span / Trace / Session 是从小到大的三层套娃 ** ：Span 是最小操作单元，Trace 是一轮问答（一次 Agent 循环）的完整因果链，Session 是一通多轮对话。 |
| --- | --- |
| ** 2 ** | ** Trace 靠 Trace ID + 父子 Span 关系 ** 缝合成因果链，画成瀑布图，就是你"破案"时盯的东西；上下文传播断了会出"孤儿 Span"（第 12 讲细讲），采样在 Agent 场景要偏向"别丢掉出错的那几条"。 |
| ** 3 ** | ** Session 是多轮场景不可省的一层 ** ——"第几轮开始跑偏"、"这通对话花了多少钱、满不满意"，只在会话层才看得见。 |
| ** 4 ** | ** 上下文是第一类观测对象 ** ：进入模型的到底是什么，本身必须被记录，这是排查漂移与成本失控的前提（方法见第 11 讲）。 |

下一讲（第 5 讲），我们把镜头对准 Span 内部：**Span 到底该怎么"切"？** LLM 调用、Agent 推理、工具、检索，各自该建成什么样的 Span、记哪些属性、粒度切到多细才既看得清又不烧钱——这是决定你观测质量的一门手艺活。
