# AI-Native可观测层｜可观测性架构解析：追踪到评估的生产级监控体系

![](附件资源/AI-Native可观测层｜可观测性架构解析：追踪到评估的生产级监控体系/img_1.png)

我前面写过一篇评估层的实战，这篇接着聊聊观测层。它俩是搭档，一个管给结果打分，一个把过程数据捞回来。所以这篇适合与前面评估层的数据飞轮拼起来一起看。

通俗讲，应用可观测性就是靠应用自己发出来的那些遥测数据，去测量、监控、理解它运行时到底在干什么。

这事儿在AI应用上特别难办，因为AI-Native和传统软件最大的区别，是输出不确定，它是个概率模型。以前写个普通接口，参数进去，结果基本是稳的。AI不一样，延迟会波动，token会烧钱，同一个功能，不同人用出来的效果都可能不一样。

于是以前根本不用操心的调试问题就全冒出来了：什么导致了延迟？为什么这个特定请求会失败？为什么同一个功能俩人用起来差异这么大？

这些问题搞不定，项目就不好落地。所以一套完整的应用监控体系是重要的。

架构是流向，那这些层到底在捞哪些信号？

**02****可观测性的核心信号**

下面讲的是一些分项信号的功能归属细节，放到全景图中是这样流转的：①链路信号+③内容信号从SDK经OTLP进入收集层的Collector，按数据面/控制面分落存储层（②度量信号指标与①链路高频span落存储层的ClickHouse，③内容大body落存储层的S3，控制面低频配置落Postgres），④由侧翼worker消费队列写回，⑤语义字段横着串起整条链路。

**①链路信号（Traces）：应用/Agent层SDK采集**

**LLM调用span**（chat / completion / generate三类）：复现问题、定位劣化（模型/参数/供应商归因）。

**Embedding span**（向量化独立成链）：排查向量化异常、检索质量归因、向量成本核算。

**Retrieval span**（RAG检索命中）：验证RAG命中质量、诊断没召回/召回错误。

**Tool / Function调用span**（工具链逐级）：审计工具链、定位Agent失效步骤（参数错/结果错）。

**Agent步骤span**（编排与决策）：理解编排决策、复现多步Agent行为。

G**uardrail span**（安全审查决策）：审查规则、命中结果、拦截/放行。

**Workflow / Router span**（多步流程与路由）：步骤顺序、条件分支、嵌套关系。

**②度量信号（Metrics）：Collector透传 + 侧翼聚合**

**量：**Request Volume（按模型/模板/flow分组）、Token Consumption（含cache命中/未命中、reasoning、多模态拆分）、Embedding请求量。

**延迟：**TTFT、TPOT（每token生成速率）、端到端Duration、检索延迟、工具调用延迟。

**质量：**Eval Score漂移、Tool成功率、无效工具调用率、429 Rate Limit命中率、内容审查命中率、Prompt/Model漂移。

**成本：**Cost per Request / per Model / per Session、Cache Hit Rate、缓存节省额。

**③内容信号（Logs/事件）：挂span的语义负载**

**prompt / completion全文**：大body → S3/MinIO（对象存储按需回读）。

**reasoning / thinking内容**：与主回答分开记录。

**tool参数与结果全文：**挂Tool span附属事件。

**retrieval命中chunk：**挂Retrieval span。

**guardrail决策细节：**挂Guardrail span。

**人工反馈评分：**挂trace关联评分事件。

**④侧翼产出信号（Evals / Cost）：Worker侧翼**

**Score事件：**LLM-as-judge、数据集实验、人工评分的评估结果，worker写回存储。

**成本计算事件：**定价表版本锚 + token用量 × 单价，会话/项目级归因。

**漂移 / 告警事件：**质量退化跟成本突变的阈值告警。

**⑤横贯关联字段（语义标准层）**

Session ID / User ID：**用户级归因与体验诊断**

Trace ID + Run ID：**全链路关联与实验对比**

Prompt模板名+版本：**漂移溯源**

Model Name/ID：**模型升级追踪**

另外还有MCP server/session、采样标记、PII脱敏标记、定价版本。

**03****工具与工程能力对比**

信号盘清楚了，聊聊工具。这行当看着热闹，能打的其实就固定几家。

主流的方案有LangSmith、Langfuse等，以下是截至2026年10月的多维度对比：

![](附件资源/AI-Native可观测层｜可观测性架构解析：追踪到评估的生产级监控体系/img_3.png)

**2026年并购与选型影响**

**ClickHouse于2026年1月收购Langfuse**，收购之后Langfuse的开发节奏没掉，近六个月约3400次提交，GitHub星数35.8k，**依然是开源自部署的事实标准。**

Mintlify于2026年3月收购Helicone后，后者进入维护模式，新特性停摆，不建议新项目再选它。

ServiceNow收购Traceloop后停售其SaaS，OpenLLMetry库保留，但路线图已经归ServiceNow。

**这几个收购信号说明LLM可观测性工具作为一条独立赛道的窗口期在收窄，头部标的基本都被传统巨头消化了。**

商业格局说完，再看协议。

**标准协议现状**

**OpenTelemetry GenAI语义约定是现在的事实标准**，但状态并不稳定。到2026年年中，gen_ai开头的全部属性还都停在Development状态，而不是Stable，并且已经从主仓库搬到了独立仓库open-telemetry/semantic-conventions-genai。

OpenLLMetry的语义约定已经上游进OpenTelemetry，是三个方案里对OTel原生兼容性最好的路径。

**一个可以参考的第三方决策规则是：**如果还没选定后端，默认走OTel GenAI语义；如果已经锁定Phoenix或Arize AX当UI，就直接产出OpenInference语义。

**还有一个近期的数据：Arize Phoenix每月OTel插桩下载量达2200万次**，LangSmith与Langfuse都在2026年3月增加了OTLP端点。**这说明整个行业正在往OTel互操作的方向收拢。**

**数据模型的两条路线**

现在有两条数据模型路线。

Langfuse用的是trace、observation、score三层的自有模型，其中observation涵盖了span、generation、event这些类型。

OpenInference用属性约定来描述LLM、Retriever、Reranker、Tool、Agent、Evaluator这些span类型。

OTel GenAI用gen_ai前缀的标准化属性。

工程上真正要取舍的是：选SDK方案，未来换工具就得重新插桩；选OTel语义，换后端就只需要改collector。因为OTel约定还在Development状态，字段可能会变，得锁定版本再做兼容处理。

**存储与性能架构**

Langfuse的存储架构最值得借鉴，它重度依赖ClickHouse，采用先落对象存储、再进队列、最后批量写ClickHouse的异步链路，把突发流量转化成队列深度，而不是数据库压力。

Phoenix从单机SQLite起步，最轻量，适合小规模与评估阶段。

**04****落地指南**

落地这事没有统一答案，我觉得得**先看自己的环境，再匹配合适的方案。**

自研、SaaS、开源私有化三条路各有各的适用场景，没有绝对的好坏。

**自研**这条路，**适合已经有了成熟分布式追踪基础设施、而且需要深度定制、数据要完全自己掌握的团队**。选它的前提是团队扛得住OTel Collector、存储与查询栈的运维，本质上是把LLM追踪接进已有的追踪管道，而不是从零造轮子。

**SaaS适合起步阶段、团队小、想快速把eval闭环跑起来的场景。**代价就是数据出域、按量或按席计费，外加被单一厂商锁死。

**开源私有化适合数据合规要求高、有自托管运维能力、而且规模大到用SaaS不划算的团队。**Langfuse跟Phoenix是现在最主流的两个选择。

上张选型决策树，可以根据自己的情况对号入座：

![](附件资源/AI-Native可观测层｜可观测性架构解析：追踪到评估的生产级监控体系/img_4.png)

**选型建议**

**如果初创团队快速启动，用Langfuse Cloud最省事儿**：它零运维、功能完整、起步快；接受数据出域跟按量计费；

**如果项目已有OpenTelemetry体系，用OTel GenAI语义插桩 + Langfuse/Phoenix OTLP端点**：插桩层走OTel GenAI语义（OpenLLMetry已停售，其语义已上游进OTel，无需再依赖停售产品）；两个平台都支持OTLP接入，后端随时能换，不会有供应商锁定；

**如果团队是Kubernetes原生部署，用Langfuse自托管（Helm）**：官方Helm部署、SaaS跟自部署同源；云原生、数据不出境；规模化首选；

**如果项目是成本敏感的场景，用Phoenix自托管 / Langfuse自托管：**Phoenix是ELv2自部署全功能免费，内置定价表成本追踪，轻量起步；Langfuse自托管开源免费、功能最全，SaaS月账单超5000美元时接近盈亏平衡。

**接入与插桩**

**优先用OpenTelemetry语义做插桩标准，省得未来换后端时重新插桩。**如果用Langfuse或LangSmith，它们已经提供OTLP摄入端点，SDK说白了就是OTel client的封装。

插桩时，Agent的顶层推理循环用invoke_agent span，LLM调用用chat子span，工具调用用execute_tool子span，父子结构就是因果链。重试必须收进同一个逻辑span，用attempt数属性记录重试次数，别拆span。span命名遵循operation name加model的规范。

必选属性只有gen_ai.operation.name跟gen_ai.provider.name，可补全request和response里的model、finish_reasons、usage的input_tokens跟output_tokens。prompt跟completion文本不进span属性，内容采集是可选的结构化消息。

**采样策略**

**用三层混合采样，这是2026年的共识做法。**

**第一层，错误、拒答、护栏触发、策略干预的trace全量留着。**这些是评估跟调试里最有价值的样本，丢掉它们基本等于把大部分负例扔了。

**第二层，常规成功trace在SDK侧做头部采样，保留1%到10%拿体积基率。**

**第三层，按token成本分位数做尾部采样，保留p95到p99的高成本trace。**高成本低延迟的trace正是规划器循环跟prompt回归藏身的地方。

**一个反例：**有团队全量采集Agent trace，月账单干到了8.1万美元，结果还是错过了关键回归的trace。**全量采集不等于安全。**

**评估联动与告警**

**把评估下沉到observation级，对单个LLM调用、检索、工具执行分别打分，比trace级评估更快更准。**Langfuse从2026年2月起就已经把LLM-as-judge下沉到了observation级，trace级评估被标记成了legacy。

**人工标注用annotation queue来管，配上rubric跟评审权限。**标准闭环是：LLM judge先初评，人工再纠偏，纠偏出来的数据集就当对齐judge的真值。

告警聚焦四类：成本尖峰、延迟尖峰、错误率、幻觉分数。告警阈值应该基于系统自己的基线漂移来定，而不是拍一个绝对数值。

**CI评估门与回流**

在PR门里跑确定性离线评估，用Braintrust的GitHub Action或者promptfoo的before跟after对比，低于阈值就阻塞合并。LLM-as-judge这种异步评估放到生产trace采样上跑，不进同步门。

**错误trace全量留着，负例样本进dataset，再回流到评估迭代、prompt优化跟微调。**

**05****风险与已知问题**

落地做完真跑起来，需要花些时间慢慢调试，但调试的过程本身就是一种积累。

**标准层面的风险**

OTel GenAI语义约定还没稳定下来，字段在v1.37.0从gen_ai.system改成了provider.name，prompt_tokens改成了input_tokens，v1.42.0又整个搬了一次库。缓解手段有三个：通过OTEL_SEMCONV_STABILITY_OPT_IN双发新旧属性，查询侧用COALESCE兜底，CI中用golden-span断言锁定属性键。

**工具层面的已知坑**

Langfuse自托管最高频的坑是ClickHouse系统日志表把磁盘撑爆，官方有reduce-disk-size文档，但社区里还是反复有人抱怨。LangSmith在高流量场景下的tracing延迟开销一直被实测诟病，而且专有数据模型加自托管仅限企业版，带来锁定风险。Helicone代理模式在关键路径上写日志，云写入一慢就会拖住业务响应，而且它已经进了维护模式。Phoenix在月5000万span以上的规模下，UI过滤视图延迟能到8到12秒。Lunary的仓库已经访问不了了，别选它。

**采样与存储的问题**

尾采样在collector崩溃的时候会丢掉窗口内的全部trace；上游退化导致的阈值同时越过，会让单次事故产生成本增加；ClickHouse的子串搜索会触发全表扫描，得在API层直接拒绝contains查询。

最后一个问题，也是最难缠的：数据孤岛和schema碎片化。

Agent trace的schema在不同团队之间碎得很厉害。有研究分析了7.3万个客户Agent schema，证实各团队的遥测形状互不相同，跨工具迁移还是得靠人肉映射。这是选OTel语义而不是专有SDK的最强理由之一。
